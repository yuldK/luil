# 확대·축소하는 보기

지도·도면·노드 그래프·큰 그림을 보여 주는 창이다. [zoom_view_element](../include/luil/ui/zoom_view_element.h)가 내용 하나를 품고, [zoom_controls_element](../include/luil/ui/zoom_view_element.h)가 축소·배율·확대·맞춤 단추를 짓는다. 배율과 위치는 [스크롤](scroll-area-design.md)처럼 앱 상태다. 요소는 받은 발행본을 배치하고 변화 요청만 보낸다.

## 왜 공통 요소인가

휠을 앱 정책에서 요소 id로 가로채면 영역 판별이 화면 밖에 산다. 내용에 단추나 손잡이를 더할 때마다 정책도 고쳐야 한다. 영역 전체를 `pointer_drag_target`으로 세우면 빈 곳 이동은 되지만 그 창이 손잡이가 되어 [터치 몸짓](touch-pen-input-design.md)의 후보에서 빠진다. 기준점 고정 식과 내용 맞춤도 화면마다 두 벌이 된다.

보기는 자기 `zoom_source`를 세운다. 컨트롤러가 흘리는 창과 같은 임자 찾기로 입력을 보내므로 앱은 id 목록을 짓지 않는다. 내용의 손잡이·항목 끌기, 보기의 이동, 두 접촉 확대가 같은 tree 안에서 우선순위를 정한다.

## 상태와 좌표

| 설정 | 뜻 |
| --- | --- |
| `owner` | 같은 표면에서 유일한 보기 키 |
| `zoom`, `origin` | 앱이 소유한 배율과 내용 좌표 0의 위치 |
| `minimum_zoom`, `maximum_zoom` | 유한한 양수 배율 범위 |
| `content_bounds` | 선택적인 내용 전체 경계, 내용 논리 좌표 |
| `zoom_by(factor, anchor)` | 비율과 기준점을 실은 변화 메시지 |
| `pan_by(delta)` | 위치 변화 메시지 |
| `zoom_to(value)` | 보조 기술의 절대 목표 메시지 |
| `wheel` | `zoom`(기본) 또는 `pan` |

원점·기준점·이동량은 **보기 가운데 기준 논리 픽셀**이다. 내용 좌표 `p`의 물리 위치는 `center + scale × (origin + p × zoom)`이다. `scale`은 보기가 부모에게 받은 배율이고, 중첩된 보기에서는 바깥 확대까지 포함한다. 창 크기를 바꿔도 가운데에서 보던 내용 좌표가 그대로 남는다. 왼쪽 위를 기준으로 두면 오른쪽으로 넓어진 만큼 보던 자리가 왼쪽으로 쏠린다.

수치가 유한하지 않거나 배율 범위가 역전되거나 내용 경계가 비어 있으면 생성자는 `invalid_argument`로 거절한다. 범위 밖의 양수 배율·원점은 배치가 다듬는다. `state()`는 배치 뒤의 실제 값을 돌려준다. 앱도 같은 도우미로 자기 상태를 다듬어 다음 frame에 싣는다.

## 계산 도우미

`zoom_about(config, viewport, factor, anchor)`는 배율을 먼저 범위 안으로 다듬고 **실제 비율** `next / current`로 원점을 옮긴다.

```
origin' = anchor − (anchor − origin) × (next / current)
```

상한에서 더 확대해도 실제 비율은 1이라 내용이 미끄러지지 않는다. 기준점 아래의 내용 좌표는 경계 다듬기가 필요하지 않은 한 그대로다.

`pan_by(config, viewport, delta)`도 같은 경계 다듬기를 쓴다. 내용 경계를 받으면 각 축에서 내용과 창의 겹침을 최소 1 논리 픽셀 남긴다. 어느 한쪽이 그보다 작으면 작은 쪽 전부를 남긴다. 가운데 고정이나 빈 공간 제거를 강제하지 않는다 — 큰 도면의 가장자리를 창 가운데로 옮길 수 있어야 한다. 경계가 없으면 이동은 제한하지 않는다.

`zoom_to_fit(config, viewport, margin, maximum_fit_zoom)`는 여백을 뺀 두 축의 비율 중 작은 값으로 내용 전체를 들이고, 내용 가운데를 창 가운데에 맞춘다. 최대 맞춤 배율 기본값은 1이다. 작은 그림을 무작정 키우지 않는 값이며 호출자가 바꿀 수 있다. 최소 배율이 맞춤 비율보다 크면 최소 배율이 이긴다. 여백 때문에 창이 비거나 내용 경계가 없으면 현재 상태를 돌려준다. 도우미는 잘못된 변화량·기준점·창 크기로 NaN을 만들지 않고 현재 상태로 물러선다.

앱은 변화 메시지를 받을 때 **지금 상태**로 식을 적용한다. 발행본의 원점을 factory에 캡처하여 절대 원점 메시지로 바꾸면 한 frame 전에 온 연속 이동이 서로 덮어쓴다. `zoom_to`만 절대 목표다. 그 경로도 지금 배율에서 `value / zoom`을 중앙 기준 `zoom_about`에 적용한다.

## 배치와 그림

자식 하나를 `창 배율 × zoom`의 `arrange_context`로 **한 번만** 배치한다. 내용 경계의 왼쪽 위는 그 내용 좌표에 맞는 물리 위치로 옮기고 폭·높이에도 배율을 곱한다. 경계가 없으면 내용 원점에서 현재 창을 덮는 논리 크기의 slot을 준다. 무한 캔버스의 명시적인 범위·가상화는 내용 컨테이너가 맡는다.

그림에는 같은 배율의 `draw_context`를 준다. 캔버스를 확대 변환하지 않는다. 자식이 받은 bounds 자체가 물리 좌표이므로 글자도 그 배율로 다시 그려지고, 눌리는 자리가 그림과 같다. 보기의 bounds로 그림과 hit test를 함께 자른다. 줌 안의 또 다른 줌도 같은 곱셈 규칙을 쓴다.

이 배율은 luil 자식의 배치·그리기 계약이다. 별도 합성 콘텐츠의 배율과 입력은 그 호스트가 맡는다. WebView2 문서는 기존 `webview_policy::pinch_zoom_enabled`와 원시 포인터 중계를 사용한다.

배율·위치가 바뀔 때마다 앱은 불변 tree를 다시 짓는다. 많은 항목을 품은 노드 그래프에는 이 비용이 크다. 앱은 `(창의 논리 경계 − origin) / zoom`으로 보이는 내용 경계를 얻고, 걸치는 항목만 만들 수 있다. 자식이 배치 시 자리를 만드는 가상화도 한 frame에 한 번만 불린다. 핀치 동안 낡은 그림만 늘리는 모드는 현재 계약에 없다.

## 입력 임자

`zoom_source`는 `scroll_source` 옆에 있다. 휠과 이동의 임자는 역순으로 자식을 먼저 찾고, 보이지 않거나 비활성인 가지는 건너뛰며, clip 밖의 가지를 보지 않는다. 가장 안쪽 흘리는 창이나 보기가 이긴다. `hit_opaque`인 방벽은 뒤의 보기를 막는다. 경계에 닿아도 바깥으로 넘기지 않는다.

컨트롤러는 보기의 휠을 직접 처리한다. 표 없는 `route_wheel(tree, event, scroll_delta)`도 같은 판정과 수정자를 쓴다. 기존 좌표·델타만 받는 짝은 스크롤 호출을 위해 남긴다. `mouse_wheel_event` 뒤에 `control`, `shift`, `horizontal`을 붙여 기존 위치 초기화의 뜻을 지킨다. `WM_MOUSEHWHEEL`은 화면 좌표를 client로 옮긴 뒤 가로 표시를 싣는다.

보기 안쪽의 흘리는 창도 이 공통 경로를 탄다. 텍스트 입력만 구현한 앱 정책의 빈 `on_wheel` 때문에 안쪽 스크롤이 사라지지 않는다. 보기 밖의 기존 앱 휠 정책은 그대로 사용한다.

| 입력 | 결과 |
| --- | --- |
| `zoom` 모드 세로 휠 | 포인터 기준 확대·축소, 한 눈금 1.2배 |
| `pan` 모드 세로 휠 | 내용 이동 |
| Ctrl+휠 | 모드와 무관하게 포인터 기준 확대·축소 |
| `pan` 모드 Shift+휠, 가로 휠 | 가로 이동 |
| 마우스·펜 왼쪽 빈 곳 끌기 | 즉시 이동, 배럴은 기존 우클릭 |
| 터치 빈 곳 이동 | 시간 창·거리 임계 없이 이동 |
| 터치 클릭 대상 이동 | 거리 임계를 넘으면 클릭을 취소하고 이동 |
| 같은 보기의 두 접촉 | 핀치 |
| 초점 있는 보기의 `+`, `=`, `-` | 중앙 기준 확대·축소 |
| 초점 있는 보기의 `0` | 내용 경계가 있으면 맞춤, 없으면 100% |
| 화살표, Page Up/Down | 32 논리 픽셀, 창 높이의 90% 이동 |

`+`, `=`, `-`, `0`은 문자 입력 경로에서 받으므로 키보드 배열과 숫자 패드의 문자 결과를 따른다. 텍스트 입력이 먼저다. 화살표·Page는 텍스트 편집 뒤, [값 step](value-step-design.md)과 묶음 탐색 앞에서 보기 자신이 받는다. Ctrl·Alt를 누른 키는 앱 단축키로 남는다. 정밀 터치패드 핀치가 Ctrl+휠로 오면 같은 휠 경로로 처리한다.

자식의 `pointer_drag_target`과 `drag_source`는 보기 이동보다 앞선다. 터치는 단추를 누른 채 움직여도 도면을 옮길 수 있지만 마우스·펜은 빈 곳에서만 이동한다. 마우스로 단추 위에서 끌다 놓아 실행을 취소하거나, 펜으로 텍스트를 선택하는 기존 동작을 보기 이동으로 바꾸지 않기 위한 결정이다. 보기 배경은 초점과 이동의 자리지만 가짜 클릭 액션·손잡이를 달지 않는다.

## 두 접촉의 수명

첫 접촉이 같은 보기에서 대기·이동 중이고 두 메시지 factory가 모두 있을 때만 둘째 접촉을 받는다. 둘째가 다른 보기·안쪽 흘리는 창·다른 표면이면 버린다. 손잡이·항목 끌기 중인 접촉, 셋째 접촉도 받지 않는다. 둘째가 합류하는 순간 탭·길게 누르기 후보와 눌림 표시를 거둔다.

이동마다 두 점의 이전·현재 가운데와 거리를 잰다. 먼저 가운데 이동을 `pan_by`로 보내고, 그 뒤 현재 가운데를 기준점으로 거리 비율을 `zoom_by`로 보낸다. 두 메시지는 이 순서로 앱 상태에 적용한다. `minimum_pinch_distance` 기본값은 24 논리 픽셀이다. 이전·현재 거리 중 하나라도 이보다 작으면 배율 메시지는 없고 이동만 남는다. 겹친 손가락이 다시 벌어져도 거의 0인 거리로 나누지 않는다.

하나를 떼면 마지막 이동을 반영하고 남은 접촉의 현재 좌표에서 이동을 잇는다. 새 누름·탭 후보로 승격하지 않는다. 무시한 접촉은 계속 무시된다. 두 접촉 중 하나의 취소, 표면 소멸, 입력 큐 유실이면 둘을 함께 거둔다. 마우스·펜 새 누름도 기존 소유권 규칙대로 둘을 취소한다. 임자는 매 이동·뗌마다 최신 tree에서 다시 찾으며 사라지거나 방벽에 가리면 끝낸다.

내용 이동으로 안쪽 흘리는 창·보기가 원래 누른 자리 밑에 와도 이미 잡은 보기의 이동을 빼앗지 않는다.

`touch_gesture_config::pinch_enabled`로 핀치를 끈다. 진행 중 끄면 둘을 취소한다. 켜진 접촉의 거리 기준은 누를 때 값이다. 최소 핀치 거리는 다른 거리와 같이 유한한 양수여야 하고, 설정 전체가 잘못되면 기존 설정을 지킨다. `pan_enabled`는 흘리는 창의 빠른 쓸기 설정이며 보기의 직접 이동은 전용 끌기처럼 따로 산다.

## 단추와 접근성

단추의 기준점은 중앙이다. `zoom_controls_config`에 보기 설정과 **보기의 논리 크기**를 준다. 단추 자체의 폭으로 맞춤을 계산하지 않는다. 범위 끝의 확대·축소 단추는 비활성이고, 맞춤은 내용 경계가 있을 때만 선다. 맞춤은 중앙 기준 확대 뒤 위치 이동 두 변화 메시지를 낸다.

보기의 접근 역할은 `access_role::pane`이다. `access_range { min, max, zoom }`으로 현재 배율을 읽고 `SetValue`는 다듬은 목표를 `zoom_to`로 보낸다. 절대 factory가 없으면 읽기 전용이다. 이동은 Transform 패턴이 없어 내걸지 않는다. 보기 이름은 `set_access_name`으로 담는 쪽이 정한다. 배율은 비율 값이고 단추 곁의 표시는 %다.

## 반드시 유지할 불변식

- 상태는 앱이 소유하고 요소·컨트롤러는 요청만 만든다.
- 원점·기준점·이동량은 가운데 기준 논리 픽셀이고 내용 경계만 내용 좌표다.
- 확대는 다듬어진 실제 비율로 원점을 계산한다.
- 그림 배율과 배치 배율, hit test의 물리 좌표는 같다.
- 내용 배치는 한 frame에 한 번이고 그림·hit test는 같은 창으로 잘린다.
- 휠과 핀치의 임자는 가장 안쪽 하나이며 방벽 뒤의 내용은 움직이지 않는다.
- 손잡이·항목 끌기는 보기 이동보다 앞선다.
- 핀치에는 같은 보기·표면의 접촉 둘만 참여한다.
- 핀치가 끝난 접촉은 탭·길게 누르기로 되돌아가지 않는다.
- 취소·유실은 두 접촉을 함께 끝내고 늦은 뗌은 액션을 만들지 않는다.
- SetValue는 절대값이며 발행본 배율과 비교해 변화량으로 바꾸지 않는다.

| --- | --- |
| 순수 계산 | 기준점 고정, 상한·하한의 실제 비율, 경계 겹침, 맞춤·여백·최대 맞춤 배율 |
| 배치 | 고DPI·확대 배율 곱, 자식 hit test 일치, clip, 한 번의 배치 |

| 핀치 | 같은 보기만 합류, 셋째 무시, 두 뗌 순서, 남은 이동, 겹침, 취소·큐 유실·설정 변경 |
| 키·접근성 | 초점의 표면, 문자·화살표·Page, 범위와 절대 SetValue |

순수 회귀는 [zoom_view_tests.cpp](../tests/zoom_view_tests.cpp), 네이티브 검증은 [pointer_integration_runner.cpp](../tests/pointer_integration_runner.cpp)에 둔다. 합성 입력이 두 접촉을 만들지 못하면 네이티브 핀치 검증은 통과로 세지 않는다. 데모의 확대 보기 페이지에서 휠·빈 곳 끌기·단추·키·터치를 한자리에서 확인한다.

설치 패키지 소비자·그리기 smoke·문서 및 소스 검사를 포함한 CTest 805개도 통과했다.
Debug에서 비활성인 ASan 19개는 실행 결과에 넣지 않는다. 변경한 C++ 소스의 clang-format,
`check_source_style`과 `git diff --check`도 통과했다. 실제 데모에서는 UIA로 절대 배율 설정,
확대 단추, % 표시, 맞춤을 확인하고 배치 결과를 보았다.

같은 RDP 세션의 네이티브 입력은 25개가 통과하고 탐색 6개가 SKIP이었다. 추가한 합성 핀치는
첫 접촉의 UP 뒤 둘째 DOWN이 도착하여 동시 두 접촉 조건을 세우지 못했다. 확대 동작이
실패한 결과나 통과한 결과로 세지 않는다. RDP가 원인이라고 확정하지 않으며 실물 두 손가락
입력은 미검증이다. 접촉 합류·비율·가운데 이동·뗌·취소의 순수 회귀는 별도로 통과했다.

## 남은 열린 질문

- 더블 탭을 확대 계기로 삼을 것인가. 내용의 기존 두 번 탭 동작과 충돌하므로 현재는 추가하지 않는다.
- 핀치 동안 그림만 확대하고 끝에서 tree를 다시 짓는 저비용 모드가 필요한가. hit test·접근성·텍스트가 낡는 기간을 먼저 정해야 한다.
- 범위 끝의 이동을 바깥 보기로 넘길 것인가, 내용 가운데 정렬·빈 공간 금지 정책도 공통으로 둘 것인가.
- Transform 패턴으로 이동을 보조 기술에 공개할 것인가.
