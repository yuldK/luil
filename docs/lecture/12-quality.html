12.1

12.2

창 없이 도는 core가 중심이다

luil_core_tests는 플랫폼을 모르는 층만 링크한다. 그래서 Windows, Android 기기, macOS에서 같은 실행 파일이 선다. 그 아래에 컴파일 없이 도는 정적 검사가, 위에 플랫폼 통합·메모리 검사·실행 파일 smoke·설치본 소비자·합성 화면·대화형 입력이 층으로 쌓인다.

층마다 단위가 다르다. 수는 정적 집계다. macOS에는 이와 나란한 층이 있다: core 2,057(공통 2,002 + AppKit 없는 순수 층 55), luil_net_tests 128, 플랫폼 48, smoke 8, 실제 창 대본 8.

core는 core만 링크한다. 플랫폼 계층이 없으니 core가 링크로 부르는 hook 둘(글꼴 자원, 즉시 종료)은 빈 글꼴 관리자와 abort()를 정의한 stub이 채운다(11강). "그래야 어느 플랫폼에서든 같은 실행 파일이 선다."

창 없는 조립. 세 thread를 조립하는 app_host도 창 없이 core test에서 선다. 데모 페이지 코드까지 소스로 넣어 창 없이 검증한다.

따로 세우는 실행 파일에는 이유가 있다. ICU가 없는 환경은 초기화 캐시를 공유하지 않게 별도 프로세스에서 재현한다. Android의 HTTP 시험은 JNI로 java.net을 부르므로 JVM 안에서만 돈다.

hang은 실패로. 모든 Catch2 test에 timeout 120초를 준다. "hang 유형의 회귀가 무기한 대기 대신 실패로 드러나도록."

테스트 수는 줄면 안 된다. Android 이식의 단계 판정 기준이었다. "줄어든다면 테스트를 다른 실행 파일로 옮긴 것이어야 하고, 합계가 같아야 한다."

  1. 처리 횟수를 세어 frame에 싣는 driver다. 창 없는 조립 test라 tree는 싣지 않는다.
  2. 창 없이 host를 세우고, 직접 게시한 앱 메시지가 logic thread의 driver에 닿는지 본다. 기다림은 3초 상한이라 hang이 무한 대기가 되지 않는다.
  3. raw input은 input thread의 pump가 정책을 거쳐 app inbox로 나른다. F5 키가 앱 메시지가 되어 같은 driver에 닿는다.
  4. 처리 뒤 게시된 frame이 횟수를 반영하는지 보고, 종료 신호가 driver에 닿는지 본다. 3강의 채널과 2강의 종료 순서가 창 없이 검증되는 자리다.

12.3

raster test: 픽셀 넓이로 판정을 잠근다

순수 geometry test는 빠진 draw 호출, 잘못된 clip, 조기 return, 채움과 테의 혼동을 잡지 못한다. raster test는 tree를 비트맵에 그려 픽셀 색과 넓이를 단언한다. 창도 GPU도 필요 없다.

    브라우저 캔버스로 같은 원리를 재현한 것이다. 1 논리 픽셀 테는 경계를 가운데 두고 그어진다. 배율 1이면 획이 물리 픽셀 둘에 반씩 걸쳐 어느 팔레트 색과도 정확히 같지 않다(빨간 점). 배율 2면 같은 획의 가운데에 완전히 덮인 픽셀이 생겨 정확한 색 비교가 된다. 버그 칸을 켜면 "무엇인가 그려졌다"는 단언이 왜 필요한지 보인다.
    1. 기본 버튼은 강조색 채움이고, 같은 색의 테만 그리는 결과는 키보드 초점 표시와 구별되지 않으므로 실패해야 한다. 자리는 모두 물리 픽셀이다.
    2. 한가운데가 강조색이면 테가 아니라 채움이다. fill·border는 가운데 픽셀로 묻는다.
    3. 보통 버튼은 강조색이 아니어야 하지만, 배경색이어도 안 된다. 뒤엣것이 없으면 자식을 아예 그리지 않는 test도 초록으로 지나간다. 반투명 합성값을 적어 두지 않는 까닭도 주석에 있다 — 팔레트를 손볼 때마다 test가 깨진다.
    4. 같은 색이면 덮은 넓이로 묻는다. 상자의 절반을 훨씬 넘게 덮는 것은 테가 결코 할 수 없다.
    5. 초점 테가 있을 때도 넓이로 갈린다. 같은 색이어도 덮는 양이 다르다.

    결정적 픽셀을 만드는 규칙. 색 공간을 주지 않는다 — 주면 그린 색과 읽은 색이 변환을 한 번 지나 팔레트 값과 정확히 같지 않게 된다. 기본 시각은 시계의 처음으로 고정한다(tooltip 지연, caret 깜빡임, 회전 표시가 시각의 함수라서, 9강). 글꼴을 싣지 않고 글을 비운다(OS 글꼴과 rasterizer 판본의 영향을 없앤다).

    거절한 대안: 전체 이미지 golden file. "전체 snapshot은 관련 없는 antialiasing, palette, 글꼴 변경에도 깨진다." 그래서 작은 component 계약에는 집중된 픽셀과 넓이 단언을 쓴다. raster test는 [raster] 태그로 134개다. GPU 경로는 창 없는 Direct3D 12 문맥에서, 합성 화면은 DWM이 합성한 화면 DC를 캡처해서 따로 본다(사람의 데스크톱에 창을 띄우므로 환경 변수로만 켠다).

    12.4

    Release에서만 도는 ASan

    메시징(channel·latest_slot)은 header-only라 이 실행 파일 하나만 AddressSanitizer로 컴파일해도 component 전체가 검사된다. 그런데 Debug에서는 켤 수 없다.

    1. ASan 관문과 메시징 test 둘. 이 두 파일은 core test에도 컴파일된다. Debug의 /RTC1과 ASan이 충돌하므로 Debug가 아닌 구성에서만 켠다.
    2. 보고에 기호가 필요해 Release에서도 debug 정보를 켠다. Catch2는 ASan 없이 빌드되어 STL 주석이 꺼져 있으므로 이 target도 주석을 끈다. 그렇지 않으면 링크가 어긋난다(LNK2038).
    3. Debug에서는 같은 이름의 test가 sanitizer 없이 도는 허위 신호가 되므로 아예 DISABLED로 등록한다. 이름 앞에 asan: 을 붙이고 label asan을 단다.

    두 번째 겹이다. 배선이 어긋나 ASan 없는 바이너리가 asan: 이름으로 돌면, 이 test가 __SANITIZE_ADDRESS__가 없음을 보고 즉시 실패한다. 2026-10-02 기준선의 asan test는 19개였고, 지금 정적 수는 20개다.

    12.5

    고정된 의존성, 네트워크 없는 configure

    "취득을 자동화하지 않으므로 configure는 네트워크를 전혀 쓰지 않는다." 받는 일은 사람이 실행하는 스크립트가, 검사는 configure가 맡는다.

    1. Skia commit만이 아니라 commit + 패키지 판번 + 도구사슬 + 대상 + PNG 코덱이다. 같은 소스 commit을 다시 패키징한 판이 있기 때문이다. commit만 보면 r1이 설치된 기계에서 재설치가 생략되어 낡은 라이브러리가 남는다.
    2. 구성(Release·Debug, 선택으로 기호)마다 파일 이름, 크기, 해시가 함께 적힌다.
    1. 받은 아카이브의 해시가 핀과 다르면 지우고 실패한다. 그래서 같은 핀이면 어느 기계에서든 같은 바이트가 설치된다. 캐시된 아카이브 폴더와 오프라인 모드도 있다.

    configure가 잡는 "링크는 되는데 틀리는" 셋. Skia는 clang-cl로, luil과 소비자는 MSVC로 빌드한다. configure는 패키지가 옆에 적어 둔 args.gn과 toolchain.json을 읽어 세 가지를 확인한다.

    • 컴파일러가 clang-cl인가. MSVC로 세운 Skia는 CPU 래스터를 픽셀 하나씩 처리한다(4000×7000 축소 799.8ms → 13.6ms).
    • is_trivial_abi = false인가. 아니면 sk_sp의 호출 규약이 갈려 실행 중에 깨진다.
    • CRT가 Debug /MTd, 그 밖 /MT인가. 아니면 링커가 원인 없이 실패한다.

    configure는 컴파일러를 찾지도 부르지도 않으므로 소비자에게 clang 설치가 필요 없다.

    기능별 아카이브. SVG, 텍스트 모양 잡기(+fallback), Lottie, AVIF는 모두 기본 끔이다. "끈 기능은 그 아카이브를 링크하지도, 그 고지를 싣지도 않고, 공개 API는 그대로 남아 '지원 안 함'으로 답한다." 테스트·예제 preset은 다섯 기능을 모두 켜서 검증한다.

    upstream CMake를 들이지 않는다. nlohmann/json의 target·install 규칙은 소비자의 솔루션에 끼어든다. 필요한 것은 include 경로 하나다. 공개 헤더는 json_fwd.hpp만 들인다 — "umbrella 헤더 하나가 2만 줄을 끌고 오지 않는 길이다."

    12.7

    소비자 통합 계약을 test로

    소비자는 luil::luil 하나만 링크한다. 그 약속은 문서가 아니라 test가 지킨다. 설치하고, 공백이 든 다른 경로로 옮기고, 별도 프로젝트에서 find_package로 들여 빌드하고 실행한다.

    1. 소비자는 Skia와 같은 정적 CRT를 쓰고 find_package로 들인다. 설치본의 package config는 빌드 트리와 같은 Skia 검사를 다시 한다.
    2. 설치본이 실어 준 함수로 제3자 고지를 만들고 .rc 조각에 넣는다. resource ID 101~104는 라이브러리 몫이라 앱은 비워 둔다.
    3. 링크는 luil::luil 하나다. 설치본의 CMake 함수로 앱 문자열 표도 짓는다. 실행 파일은 resource, 고지 원문, Codicons glyph, 인코더, HTTP client, 문자열 표 서식을 차례로 단언하고 실패마다 다른 종료 코드를 낸다.
    1. 설치한 뒤 공백이 든 다른 경로로 복사한다. 설치본이 빌드 트리의 절대 경로에 매이지 않는지, resource 경로가 공백에서도 풀리는지 본다.
    2. 옮긴 자리를 CMAKE_PREFIX_PATH로 주어 소비자 프로젝트를 configure하고 빌드한다.
    3. 만든 실행 파일을 돌린다. 종료 코드 0이어야 통과다.

    전파하는 것과 하지 않는 것. 공개 헤더 컴파일에 필요한 C++20과 MSVC /utf-8만 전파한다. 경고 수준과 /WX는 PRIVATE다. "라이브러리의 경고 정책이 소비자 앱의 빌드를 깨면 안 된다." 새 toolset이 핀으로 박힌 luil 소스를 경고할 때 소비자가 소스를 고칠 수 없으므로, 경고를 오류로 다루는 옵션은 끌 수 있게 두었다.

    실행 파일 resource가 없는 플랫폼(Android·macOS·iOS)은 Codicons 글꼴을 라이브러리에 바이트 배열로 싣는다. "소비자가 APK assets 같은 자리에 파일을 따로 넣는 단계가 생기지 않는다."

    12.8

    컴파일러가 잡지 못하는 것

    formatter로 줄을 다시 채우지는 않는다. 대신 문자 규칙(인코딩, CRLF, 닫는 중괄호)과 "컴파일러가 잡지 못하는 종류"를 따로 정적 검사로 막는다.

    clang-format을 검사하지 않는 이유. "손으로 고른 줄바꿈(뜻 단위로 묶은 조건, 제 줄에 닫는 중괄호)을 formatter가 다시 채워 버린다." .clang-format은 편집기에서 고른 범위에 쓰는 선택 도구로만 남긴다. 검사기는 UTF-8 무 BOM, CRLF, 탭·줄 끝 공백 같은 문자 규칙과 기계적으로 판정되는 규칙만 본다.

    정적 검사 다섯.

    • 우산 헤더 누락 — 실제로 헤더 둘이 빠져 있었다
    • core의 플랫폼 include (11강)
    • 라이브러리 코드 줄의 한글 — 글은 문자열 표에 산다. 그 검사기 자체의 test도 있다
    • JNI 실패 검사가 ||·&& 체인 맨 앞에 있는가
    • nlohmann/json 중괄호 함정 (아래)

    값 하나를 담은 중괄호는 MSVC에서는 복사다. clang·gcc에서는 initializer_list 생성자가 이겨 원소 하나짜리 배열이 된다. Windows에서 통과한 코드가 macOS·iOS·Android에서 조용히 틀린다. 규칙은 json x = y;, 배열이 뜻이면 json::array({ y })다.
    1. 정규식은 형이 글자로 보이는 자리만 잡는다. 함수가 돌려준 json을 auto로 받는 자리는 못 본다. 객체 json o { { "k", v } }와 빈 json x {}는 걸리지 않는다.
    2. 형이 적힌 선언, auto에 json을 만드는 식, 역참조한 json, ->로 닿는 json. auto로 형이 숨은 나머지 자리는 진단용 json.hpp 사본이 맡는다. 그 사본을 앞세운 clang 빌드로 시험을 돌리면 그런 자리마다 backtrace를 찍고 멈춘다.

    도입 커밋의 기록: Windows 전용 UIA 시험의 53곳을 =로 바꿨다 — "clang이었다면 before["left"]가 배열에 글자 키로 가서 던지고, fixture는 웹 상태를 늘 버렸다." 진단 헤더로 macOS 시험 전체(2,213개)와 예제 smoke를 돌려 걸린 자리는 없었다.

    12.9

    정리

    1. 테스트의 밑변은 플랫폼을 모르는 층만 링크한 luil_core_tests다. 창도 GPU도 없이, 모든 플랫폼에서 같은 실행 파일로 돈다. 그 위에 플랫폼 통합·ASan·smoke·설치본 소비자·합성 화면이 쌓인다.
    2. raster test는 배율 2에서 가운데 픽셀과 덮은 넓이로 판정을 잠근다. "무엇인가 그려졌다"도 함께 묻는다. 전체 이미지 golden file은 거절했다.
    3. 메시징 ASan은 Release에서만 돌고, Debug에서는 DISABLED로 등록하며, 계측 없는 바이너리는 관문 test가 막는다.
    4. 의존성은 핀 JSON(URL·크기·SHA-256)과 submodule로 고정한다. configure는 네트워크를 쓰지 않고, 패키지가 계약(컴파일러·ABI·CRT)에 맞는지만 검사한다.
    5. 소비자 계약은 설치 → 공백 경로로 옮김 → 별도 프로젝트 빌드·실행 test가 지킨다. 경고 정책은 전파하지 않는다.
    6. formatter 대신 문자 규칙과, 컴파일러가 잡지 못하는 종류(우산 헤더, 플랫폼 include, 코드 속 한글, JNI 순서, json 중괄호)를 정적 검사로 막는다.
    12.10

    확인 문제

    cmake --preset vs2026을 처음 실행하면 무슨 일이 일어나나? (Skia를 아직 받지 않았다)

    1. CMake가 핀 JSON의 URL에서 Skia를 내려받는다
    2. Skia 없이 CPU 전용으로 구성한다
    3. fetch_skia.ps1을 쓰라는 오류로 멈춘다
    4. 소스에서 Skia를 빌드한다
    "취득을 자동화하지 않으므로 configure는 네트워크를 전혀 쓰지 않는다." Skia는 스크립트가 핀의 SHA-256으로 받아 둬야 하고, 없으면 configure가 원인과 함께 멈춘다.

    Debug 구성에서 asan:으로 시작하는 test가 보이지만 돌지 않는다. 왜인가?

    1. ASan이 Debug에서 너무 느려서
    2. Debug의 /RTC1이 ASan과 충돌해 Debug에서는 계측이 없고, 계측 없이 도는 허위 신호를 막으려고 DISABLED로 등록해서
    3. Catch2가 Debug에서 ASan을 지원하지 않아서
    4. 설정 실수다
    그래도 배선이 어긋나 계측 없는 바이너리가 돌면, 관문 test가 __SANITIZE_ADDRESS__가 없음을 보고 실패한다.

    raster test가 기본 배율 2.0을 쓰는 까닭은?

    1. 고해상도 화면을 흉내 내려고
    2. 1 논리 픽셀 선의 가운데에 완전히 덮인 물리 픽셀이 생겨 정확한 색 비교가 되므로
    3. 빨리 그리려고
    4. GPU 경로와 같게 하려고
    배율 1에서는 antialias된 1 논리 픽셀 선이 물리 픽셀 둘에 일부씩 섞여 어느 팔레트 색과도 정확히 같지 않을 수 있다. 같은 이유로 색 공간을 주지 않고, 글꼴을 싣지 않고, 시각을 고정한다.

    Skia 패키지가 clang-cl로 컴파일되어 있다. luil을 쓰는 앱도 clang-cl을 설치해야 하나?

    1. 그렇다. ABI를 맞추려면 같은 컴파일러여야 한다
    2. 그렇다. configure가 clang-cl을 찾는다
    3. 아니다. 하지만 Skia를 MSVC로 다시 빌드해야 한다
    4. 아니다. configure는 패키지의 toolchain.json을 읽을 뿐 컴파일러를 찾지도 부르지도 않는다
    luil과 소비자는 MSVC 그대로다. Skia에 clang-cl을 요구하는 이유는 CPU 래스터 성능(799.8ms → 13.6ms)이다. ABI는 is_trivial_abi = false로 맞춘다.

    Windows CI가 초록이어도 macOS·iOS·Android에서 조용히 틀릴 수 있는 코드는?

    1. json x = y;
    2. json x { y };
    3. json o { { "k", v } };
    4. json::array({ v })
    값 하나를 담은 중괄호는 MSVC에서는 복사지만 clang·gcc에서는 initializer_list 생성자가 이겨 원소 하나짜리 배열이 된다. ③은 객체, ④는 의도한 배열이라 괜찮다.

    luil이 CI에서 clang-format 적합성을 검사하지 않는 이유는?

    1. formatter가 손으로 고른 줄바꿈을 다시 채워 버리기 때문에
    2. clang-format이 Windows에서 돌지 않아서
    3. 코드 스타일 규칙이 없어서
    4. 속도가 느려서
    뜻 단위로 묶은 조건, 제 줄에 닫는 중괄호 같은 손 배치를 지킨다. 대신 문자 규칙과 기계적으로 판정되는 규칙만 검사기가 본다.
