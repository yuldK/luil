# 동영상 재생 위젯 설계안

Windows 11 x64용 선택 모듈에서 로컬 MP4·AVI·MPEG-TS를 열고, 디코딩한 영상을 luil 캔버스에 그린다. 영상, 자막, 재생 컨트롤이 첫 버전부터 같은 클립·배율·그리기 순서를 따른다. 앱은 기본 컨트롤을 쓰거나 같은 재생 세션에 자체 luil 요소를 연결한다.

## 라이브러리 API와 동영상 전용 데모

Windows 앱은 `luil::luil`을 링크하고 논리 스레드에 `luil::win32::video_frame_player` 하나를 둔다. 로컬 파일을 `open(path)`한 뒤 `needs_tick()`인 동안 `update()`를 호출한다. `state()`가 `ready`가 되면 `play()`할 수 있고, `stop()`은 처음으로 되감는다. `ended`에서 다시 재생하거나 같은 인스턴스에 다른 파일을 열 수 있다. 오류가 나면 `state()`는 `failed`, `error()`는 실패한 작업과 오류 코드를 준다. 객체를 연 MTA 스레드에서 조작과 소멸까지 수행한다. 현재 불변 프레임은 원본 종횡비를 유지하며 긴 변을 최대 1,920픽셀로 복사한다. [공개 헤더](../include/luil/win32/video_frame_player.h)

트리를 구성할 때는 `video_config::frame`에 `player.image()`를 넣고, `video_element` 생성자의 세 번째 인자로 자막과 버튼을 담은 `layer_element`를 넘긴다. 창 크기와 DPI가 바뀌면 영상과 오버레이 모두 같은 비율로 맞춘 영상 영역에 배치된다. SRT는 파일을 열 때 `luil::read_srt(path)`로 한 번 읽고, `luil::subtitle_at(cues, player.position())`로 현재 한글 자막을 고른다. 종료 시각과 다음 자막의 시작 시각이 같으면 다음 자막만 표시된다. [영상 요소](../include/luil/ui/video_element.h) · [SRT API](../include/luil/text/srt.h)

전용 데모 `luil_video.exe`는 8초 풍경 샘플 **능선의 새벽**으로 열린다. 생성한 풍경 이미지에 느린 카메라 이동, 짧은 연주음과 UTF-8 한글 SRT를 넣었다. 상단에서 **MP4 · AVI · TS**를 직접 고르고, 오른쪽 테마 버튼으로 시스템 → 어두움 → 밝음 순서로 바꾼다. 영상 왼쪽 아래의 **재생** 버튼은 재생 중 **중지**로 바뀐다. 옆 화살표로 다음 샘플을 열 수 있다. Windows의 투명 효과를 끄거나 고대비를 켜면 자막과 버튼 배경을 불투명하게 그린다. 아래 상태 줄에서 재생 상태와 자막 파일을 확인한다. MP4·TS는 H.264/AAC 960×540, AVI는 MJPEG/PCM 640×360이다. [화면 구성](../examples/video/scene.cpp) · [재생 상태와 입력 처리](../examples/video/main.cpp)

데모는 시작할 때 Windows 표시 언어 목록에서 한국어 또는 영어를 골라 버튼, 접근성 이름, 재생 상태와 오류를 표시한다. 일치하는 언어가 없으면 한국어를 쓴다. SRT 자막은 파일에 담긴 원문으로 표시한다.

탐색기에서 MP4·AVI·TS 파일을 데모 창에 놓으면 자동으로 재생한다. 재생 중에 다른 영상을 놓으면 새 영상으로 전환한다. 여러 파일을 함께 놓으면 지원하는 확장자의 첫 파일을 연다. 예를 들어 같은 폴더에 `여행.MP4`와 UTF-8 자막 `여행.srt`가 있으면 영상만 놓아도 자막이 표시된다. 이름이 다른 자막은 실행 인자 `--srt=`로 지정할 수 있다.

개편한 데모에서는 시스템·밝은·어두운 테마, 작은 창의 오버레이 배치, 세 풍경 샘플의 실제 오디오 출력과 한글 SRT를 확인했다. 같은 1080p30 기준 영상의 첫 60초에서 창 섬광과 앱 출력 기준음 30쌍을 비교했다. 영상 시각에서 소리 시각을 뺀 범위는 -3.31~+13.60ms, 중앙값은 -3.12ms였다.

### UI 개편 전 공개 API 데모의 코덱 검증

MSVC Release x64 데모에서 한글 SRT와 재생·중지 버튼을 영상 위에 표시한 상태로 측정했다. 피크는 Windows 출력 장치에서 **데모 프로세스에 해당하는 세션**의 값이다(0~1). 스테레오 PCM 루프백은 같은 프로세스만 캡처했다.

| 컨테이너 | 영상 + 음성 | 샘플 | 출력 세션 피크 |
| --- | --- | --- | ---: |
| MP4 | H.264 + AAC | 번들 motion.mp4 | 0.055604 |
| AVI | MJPEG + PCM | 번들 motion.avi | 0.054931 |
| TS | H.264 + AAC | 번들 motion.ts | 0.055604 |
| AVI | Xvid + MP3 | 2-audio-streams.avi 기본 트랙 | 0.111606 |
| TS | MPEG-2 + AC-3 5.1 | MIB2.0000.ts 앞부분, 1080 | 0.292142 |
| TS | MPEG-2 + AC-3 5.1 | foxksaz.ts 발췌, 720 | 0.189647 |

두 AC-3 샘플은 기본 Media Engine 출력에서 끝까지 재생해도 16비트 PCM의 절댓값이 최대 1이었다. 같은 1080 TS로 Windows 내장 리샘플러를 필수 오디오 효과로 연결한 대조 시험에서 피크가 9,573으로 올라갔다. 선택 효과를 넣은 데모에서는 여전히 무음이어서 최종 구현은 파일을 열기 전에 필수 효과를 연결한다. 두 TS와 Xvid AVI에서 자막·버튼 영역을 제외한 창 중앙의 영상 변화와 중지를 확인했다. 번들 세 개에서는 한 줄·두 줄 한글 자막 전환, 중지 후 첫 자막부터 다시 재생, 마지막 샘플의 종료와 재시작을 확인했다. 결과는 해당 디코더가 설치된 시험 PC 기준이다. [Windows 오디오 효과](https://learn.microsoft.com/en-us/windows/win32/api/mfmediaengine/nf-mfmediaengine-imfmediaengineex-insertaudioeffect)

### UI 개편 전 라이브러리 통합 빌드의 1080p30 시험

동일한 600초 H.264/AAC MP4(18,000프레임)를 RTX 2070 SUPER, 60Hz 로컬 콘솔에서 Direct3D로 재생했다. 1920×1080 영상 위에 자막과 컨트롤을 표시하고, Windows Graphics Capture의 창 시각에서 데모 프로세스 WASAPI 루프백의 기준음 시각을 뺐다. 양수이면 영상이 늦다. 2초 간격의 섬광 300개와 기준음 300개를 모두 짝지었다.

| 10분 실행 | 범위 | 중앙값 | 95백분위 | ±80ms 초과 |
| --- | ---: | ---: | ---: | ---: |
| 첫 라이브러리 통합 빌드 | −18.74~+94.75ms | +11.28ms | +19.42ms | 1/300 |
| 최종 데모 | **−11.73~+55.01ms** | **+5.08ms** | **+21.78ms** | **0/300** |

첫 빌드의 345초 지점에서 소리부터 luil 프레임 전달까지는 +6.76ms, 전달부터 창 캡처까지는 87.99ms였다. 연속 영상이 최신 장을 우선하도록 요청한 경우 GPU 백 버퍼가 사용 중이면 그리기를 건너뛰고, 표시 요청에는 `DXGI_PRESENT_DO_NOT_WAIT`를 사용한다. 큐가 가득 차도 이미 제출한 GPU 작업의 fence는 기록한다. 최종 빌드에서 같은 지점의 영상·음성 차이는 +5.03ms, 전달부터 캡처까지는 11.99ms였다. 두 실행은 전체 경로를 측정했으므로 개별 변경의 효과 크기까지 분리하지는 않았다. [DXGI 표시 플래그](https://learn.microsoft.com/windows/win32/direct3ddxgi/dxgi-present)

전달된 고유 프레임은 17,980개, 누락은 20/18,000개(0.111%)였다. Media Engine 카운터도 렌더 17,980개·누락 20개였다. 창 캡처의 고유 프레임은 17,954개였고 역순 프레임은 0개였다. 창에서 보이지 않은 46개에는 합성과 캡처 단계가 함께 포함된다. 최종 10분 시험의 적용 범위는 60Hz 로컬 콘솔과 디지털 출력이다. 원격 세션 수신 화면·스피커까지의 지연은 별도 측정 대상이다.

최종 실행 파일 SHA-256은 `5EEA19EBBFC3966E9141543EBD79BB5D763092A5D5C597C7AB808FA4B50BC4AC`, 10분 입력 파일은 `1FBFCB973B3B900A7A6FF13AEA0150FD323AD42D6AA3E90BEA1DADC26CAD796E`다.

## 실행 가능한 Windows 프로토타입 · 2026-11-19

`luil_video` 예제를 MSVC Release x64로 빌드하고 Windows 11 26H2(26300.9974)에서 실행했다. 프로토타입은 아래 세 샘플과 UTF-8 한글 SRT를 실행 파일 옆 `video` 폴더에 복사한다. 샘플은 같은 움직이는 도형, 프레임 번호, 짧은 기준음을 담은 자체 제작 256×144·12fps·약 8초 클립이다. MJPEG·PCM AVI를 Windows에서 H.264·AAC MP4로 변환하고 같은 압축 스트림을 MPEG-TS로 재포장했다. 샘플 제작과 재생 모두 FFmpeg를 사용하지 않았다. [예제 소스](../examples/video/main.cpp) · [샘플 파일](../examples/video/assets)

| 실제 재생 파일 | 영상 | 음성 | Windows 출력과 조작 |
| --- | --- | --- | --- |
| `motion.mp4` | H.264/AVC | AAC-LC | 영상 변화, 출력 세션 신호, 한글 자막 전환, 중지·재시작·끝까지 재생 확인 |
| `motion.avi` | Motion JPEG | PCM 16-bit | 같은 항목 확인 |
| `motion.ts` | H.264/AVC | AAC-LC(ADTS) | 같은 항목 확인 |

실제 창에서 UI Automation으로 **재생 → 한 줄 자막 → 두 줄 자막 → 중지 → 재생 → 첫 자막 → 재생 끝**을 확인했다. 두 시점의 창 캡처에서 도형의 위치가 달라지는지 확인하고, Windows Core Audio에서 예제 프로세스에 해당하는 출력 세션의 피크 신호를 측정했다. 이 표는 번들 샘플 세 개의 결과다. 추가 코덱 조합과 1080p30 측정 결과는 아래에 기록했다. 내장 자막은 후속 검증 항목이다.

초기 WIC 비트맵 출력에서 MP4·TS는 재생됐지만 같은 MJPEG AVI는 `MF_E_TRANSFORM_TYPE_NOT_SET`으로 실패했다. 최종 예제는 Media Engine에 D3D11 장치 관리자를 연결하고 BGRA 텍스처로 프레임을 받은 뒤 CPU가 읽을 수 있는 표면을 거쳐 luil 이미지로 옮긴다. 이 경로에서 AVI까지 통과했다. 예제의 코덱 DLL 배포량은 0바이트이며 GPU→CPU 복사 비용이 남는다. [재생기 구현](../src/win32/video_frame_player.cpp)

### 실행 방법

저장소의 Windows 예제 빌드 의존성이 준비된 상태에서 다음 명령으로 실행한다. 인자가 없으면 MP4를 열고 **재생** 버튼을 기다린다. 다른 파일은 `--video=`로 지정하고, SRT는 기본으로 영상과 같은 경로·이름에서 읽는다. 별도 자막은 `--srt=`로 지정한다.

```powershell
cmake --preset vs2026-examples
cmake --build --preset vs2026-examples-release --target luil_video
$player = '.\build\vs2026-examples\examples\Release\luil_video.exe'
& $player
& $player '--video=examples/video/assets/motion.avi'
& $player '--video=examples/video/assets/motion.ts' '--srt=examples/video/assets/motion.srt'
```

계측할 때는 `--frame-log=새파일.csv`를 추가한다. 예제는 유효한 luil 이미지로 복사된 프레임마다 Media Engine의 PTS(100ns)와 복사 완료 시각(QPC)을 기록한다. 첫 줄에 QPC 주파수를 쓰고 정상 종료할 때 엔진이 제공하는 누락·렌더링 카운터를 덧붙인다. 30fps 고정 프레임률 시험에서는 서로 다른 PTS를 원본 프레임 수와 비교할 수 있다. 기존 파일 경로를 주면 생성 오류를 표시한다. [Media Engine 통계](https://learn.microsoft.com/en-us/windows/win32/api/mfmediaengine/nf-mfmediaengine-imfmediaengineex-getstatistics)

### 1080p30 프레임과 음영상 동기 실측

Windows 11 26H2 빌드 26300.9974, Ryzen 9 3900XT, GeForce RTX 2070 SUPER에서 Release x64 예제를 실행했다. Windows Media Foundation으로 만든 10분짜리 H.264 + AAC-LC MP4를 사용했다. 영상은 1920×1080·30fps의 움직이는 도형과 고유 프레임 번호를 담고 있다. 48kHz 스테레오 음성은 1초부터 2초마다 화면 섬광과 동시에 1kHz 기준음을 낸다. 입력 AAC를 PCM으로 풀어 확인한 첫 네 기준음은 각 섬광과 1샘플 이내로 일치했다. 한글 SRT와 luil 재생·중지 버튼을 함께 표시했다.

| 측정 위치 | 관측 범위 | 결과 |
| --- | --- | --- |
| Media Engine → luil 이미지 전달 | 별도 10분 재실행, 원본 18,000프레임 | 서로 다른 PTS 17,986개, 누락 14개(0.0778%). 엔진 자체 카운터도 렌더 17,986개·드롭 14개. 최장 연속 6프레임(200ms) |
| 창에 합성된 영상 | 원본 프레임 0~9,009, 약 5분 | 9,010개 중 8,999개 관측. 누락 11개(0.122%), 연속 누락 최대 1개 |
| 창 영상과 앱의 출력 PCM | 77~299초의 섬광·기준음 112쌍 | 영상 지연 최소 +118.8ms, 중앙값 +181.4ms, 95백분위 +181.4ms, 최대 +212.6ms. 112쌍 모두 ±80ms 기준 초과 |

Windows Graphics Capture에서 앱 창(1920×1134, 영상 1920×1080)의 중앙 행을 읽었다. 12초 교정에서는 360개 번호를 모두 읽었다. 본 측정에서 번호를 직접 읽은 프레임은 8,969개다. 30개는 원본의 흰 도형과 번호 시작 표시가 겹쳤다. 각 구간 안의 서로 다른 중앙 행 해시 3개와 양끝 번호의 차이 4를 대조해 복원했다. 창에서 사라진 11개에는 디코딩·화면 전달·원격 합성·캡처의 영향이 함께 들어 있다.

동기는 섬광이 처음 관측된 창 프레임의 시스템 시각에서 **해당 앱 PID의 WASAPI 루프백 PCM** 기준음 시작 시각을 뺐다. 오디오 패킷 QPC에 첫 유효 샘플의 오프셋을 더했다. 시간 오류가 표시된 패킷은 제외했다. 첫 5분의 오디오 세션 피크 미터로도 독립적으로 150쌍을 관측했고 영상 지연 중앙값은 +208.2ms였다. ±80ms 판정에는 PCM 값을 썼다. 창의 캡처 타임스탬프 대신 프레임을 읽은 순간의 QPC로 계산해도 중앙값 +153.1ms, 최소 +89.9ms였다. 원격 디스플레이는 32Hz로 한 주기가 31.25ms였으며, 모니터와 스피커의 물리 출력 지연은 별도 측정 대상이다. [WASAPI 패킷 시각](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer)

첫 실행 도중 원격 데스크톱 연결이 끊겨 창 캡처와 오디오 관측이 약 5분에 멈췄다. 이후 별도 창 캡처에서 15,390번 프레임(8분 33초)을 확인했고, 앱은 10분에 재생을 마쳤다. 창 누락률의 분모는 연속 관측 구간으로 한정했다. 이후 출력 장치가 없는 같은 세션에서 전달 로그를 켜고 파일을 처음부터 끝까지 다시 재생했다. 프레임 번호 0~17,999에서 전달 PTS 중복·역행은 없었다. 이 재실행의 엔진 누락률은 1% 미만 목표를 충족했다. 첫 실행에서 확인한 음영상 동기는 목표를 넘었다.

### 음영상 지연 원인 분리와 프레임 게시 개선

위 시험과 같은 10분 MP4(18,000프레임), SRT, 1920×1080 영상 영역과 32Hz 원격 디스플레이에서 다시 측정했다. 한 번의 재생 안에서 프레임 PTS를 섬광 번호에 대응시켰다. 같은 PC의 QPC로 ① 해당 앱 출력 PCM 기준음 ② `OnVideoStreamTick` 성공 직후 ③ 불변 luil 이미지 복사 완료 ④ 해당 이미지를 그리는 Skia 호출 직후 ⑤ 창 캡처의 프레임 시각을 짝지었다. ④ 이후에는 GPU 제출, DXGI 표시 대기, DWM과 원격 디스플레이 캡처가 함께 들어간다. 측정 범위는 원격 호스트에서 끝난다. 클라이언트까지의 네트워크 전송과 실제 모니터·스피커 지연은 이 값에 포함할 수 없다.

| 같은 원격 세션에서 바꾼 조건 | 비교한 섬광 수 | PCM → 창 중앙값 | 이미지 복사 | 복사 완료 → Skia 그리기 | 그리기 → 창 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 수정 전 Direct3D, `Present(1)` | 10 | +183.9ms | 7.2ms | 25.8ms | 117.3ms |
| 같은 코드, `Present(0)`만 적용 | 12 | +91.7ms | 7.2ms | 1.4ms | 45.0ms |
| 같은 코드, CPU 렌더러 선택 | 9 | +78.2ms | 7.3ms | 2.3ms | 47.9ms |

각 열은 해당 구간의 중앙값이다. 원래 앱에서도 별도 계측 요소를 넣지 않은 실행에서 16쌍의 PCM → 창 중앙값이 +166.8ms였다. 표시 주기마다 오래된 제출을 소비하는 Direct3D 경로가 이 환경에서 지연을 키웠다는 인과 근거는, 같은 파일·원격 세션에서 표시 정책 하나만 바꿔도 약 92ms가 줄었다는 점이다. 같은 프레임을 다시 제출하는 비용은 첫 그리기 전 대기와 그 뒤의 표시 대기 양쪽에서 관측됐다. [DXGI flip 표시 큐와 동기 간격](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiswapchain-present)

예제는 4ms마다 새 영상을 확인하되 영상·자막·상태가 모두 같으면 프레임을 다시 게시하지 않는다. 입력과 창 크기 변경은 그대로 처리한다. D3D11 읽기 표면의 패딩을 존중해 BGRX 행을 한 번에 불변 이미지로 복사하고, 임시 RGBA 벡터와 후속 변환을 없앴다. `--renderer=auto|direct3d|cpu`로 같은 예제에서 렌더러를 선택할 수 있다. [프레임 게시](../examples/video/main.cpp) · [픽셀 전달](../src/win32/video_frame_player.cpp)

재생 중인 영상의 주 창은 프레임에 `prefer_latest_presentation`을 지정한다. Direct3D는 이 프레임에 `Present(0)`을 써서 대기 중인 오래된 그림을 건너뛸 수 있다. 일반 UI의 기본 동기 간격은 1이다. Windows Media Engine으로 같은 영상을 같은 크기의 창에 직접 표시하는 대조군도 실행했다. 이 대조군에는 luil 오버레이가 없다.

| 실제 실행 | 유효 쌍 | 최소 | 중앙값 | 95백분위 | 최대 | ±80ms 초과 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Windows 엔진 직접 표시 · 30초 | 15 | −6.9ms | −6.9ms | −6.9ms | −6.9ms | 0 |
| 중복 게시 제거·픽셀 경로 변경 · 10분 | 300 | −15.2ms | +44.6ms | +107.1ms | +200.9ms | 37 |
| 새 프레임 우선 표시까지 적용한 계측판 · 30초 | 15 | +29.5ms | +60.7ms | +60.7ms | +60.7ms | 0 |
| 최종 Release · 연결된 약 30초 | 14 | +5.9ms | +64.5ms | +95.7ms | +95.7ms | 1 |

10분간 창과 소리를 모두 기록한 중간 빌드는 300쌍 중 263쌍이 기준 안에 들었다. 엔진에서 luil 이미지로 전달된 고유 PTS는 17,831개, 창에서 직접 관측된 고유 번호는 17,671개였다. 이 실행 중 일부 진단 도구 빌드가 겹쳤다. 같은 원격 환경에서도 Windows 직접 표시 대조군은 15쌍 모두 기준 안이었다. 관찰한 큰 지연을 원격 환경 하나로 돌릴 수 없으며, 원격 클라이언트에서의 실제 출력 차이는 별도 측정 대상이다.

최종 Release 시험은 빌드를 마친 뒤 다른 재생 시험과 겹치지 않게 시작했다. 약 30초 지점에서 원격 세션이 끊기고 활성 오디오 출력 장치가 0개가 됐다. 창 캡처는 902번 프레임에서 끝났다. 이 구간의 원본 903개 중 luil 이미지로 902개가 전달됐고 창에서는 869개 번호를 관측했다. 섬광 15개와 PCM 기준음 15개 중 시간상 대응하는 14쌍을 비교했고 11초 섬광에서 +95.7ms가 측정됐다. 따라서 관측 구간에서 ±80ms 기준을 초과했으며, 최종 빌드의 10분 전체 음영상 동기는 미확인이다.

앱 자체는 10분에 재생 끝에 도달했다. 연결 해제 후를 포함한 전체 전달 로그에는 원본 18,000개 중 7,148개 PTS만 남았고, 엔진의 드롭 카운터는 10,838이었다. 백그라운드 구간의 프레임 전달도 1% 목표에 미달했다. 이 숫자로 연결 중인 창의 누락률을 추정할 수는 없다.

### 60Hz 로컬 콘솔에서 다시 측정한 최종 빌드

2026-11-19에 같은 PC에서 최종 Release와 같은 10분 H.264·AAC 샘플을 다시 실행했다. 실행 파일과 MP4의 SHA256이 직전 시험과 일치했다. Windows가 보고한 세션은 로컬 콘솔이었고, GeForce RTX 2070 SUPER의 3840×2160 디스플레이는 60Hz였다. 창 높이가 1152픽셀로 바뀌어 계측기의 창 높이 검사를 조정했다. 1920×1080 영상, 한글 SRT, luil 컨트롤과 섬광·PCM 매칭 방법은 동일했다.

| 실행 | 유효 쌍 | 최소 | 중앙값 | 95백분위 | 최대 | ±80ms 초과 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 수정 전 Direct3D 계측판 · 30초 대조 | 15 | +25.4ms | +25.5ms | +75.4ms | +75.4ms | 0 |
| 최종 Release · 10분 | 300 | -12.6ms | +7.3ms | +24.0ms | +40.8ms | 0 |

예상한 300개 기준점 중 화면 섬광 300개와 앱의 출력 PCM 기준음 300개를 검출했고, 300쌍을 비교했다. 10분 동안 관측한 모든 기준점이 ±80ms 안에 들었다. 양수는 소리가 먼저 나왔다는 뜻이다. 음성은 해당 프로세스의 루프백 지점에서 측정했다.

엔진에서 불변 luil 이미지로 전달된 서로 다른 PTS는 17,995/18,000개였고, 누락은 5개(0.028%)였다. 합성된 창에서 읽은 서로 다른 프레임은 17,973개였다. 창 단위 미관측 27개에는 렌더링·합성·캡처의 영향이 함께 들어 있다. 32Hz 원격 세션의 최종 빌드 전 구간 결과는 여전히 미측정이다.

각 클립에서 자막과 버튼을 벗어난 중앙 영역의 픽셀 변화를 확인했다. AVI는 샘플 저장소의 3MiB 파일, 첫 TS는 원본의 첫 24,064,000바이트다. 두 번째 TS는 영상·음성 패킷을 유지하고 PAT·PMT를 추가한 별도 표본이다. Source Reader로 AVI의 MP3 두 트랙과 두 TS의 AC-3 트랙이 모두 비무음 PCM으로 풀리는 것도 독립 확인했다. [AVI 표본](https://samples.ffmpeg.org/avi/2-audio-streams.avi) · [1080 TS 표본](https://samples.ffmpeg.org/HDTV/MIB2.0000.ts) · [720 TS 원본](https://samples.ffmpeg.org/MPEG2/foxksaz.ts)

표의 음성 피크는 같은 luil 예제의 진단 빌드에서 실제 재생 버튼을 눌러 측정했다. 영상은 같은 창에 그리며, 같은 Media Engine 인스턴스의 출력을 Windows Web Audio 인터페이스로 받아 PCM 최대 절댓값을 기록했다(1.0이 최대 진폭). 활성 Windows 오디오 출력 장치는 0개였고 대조 MP4도 일반 출력 세션이 사라졌다. 이때 확보한 값은 디코딩 단계의 PCM이었으며, 이후 출력 장치를 연결해 측정한 결과는 위의 공개 API 검증 표에 기록했다. [Media Engine 오디오 출력 연결](https://learn.microsoft.com/en-us/windows/win32/api/mfmediaengine/nf-mfmediaengine-imfmediaenginewebsupport-connectwebaudio)

이 PC에는 MPEG-2·AC-3 디코더가 등록돼 있다. Windows 11 24H2부터 AC-3 기본 제공 여부는 설치 환경에 달려 있다. [Windows 코덱 지원표](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/supported-codecs)

## FFmpeg 없이 출시하는 안

**Windows 11 x64 첫 버전은 Media Foundation의 `IMFMediaEngine` 프레임 서버를 우선 제안한다.** OS가 디코딩·음성 출력·재생 시계를 맡는다. luil은 새 영상 프레임을 받아 Skia에 그리고 그 위에 SRT와 실제 luil 버튼을 올린다. 앱에 동봉하는 미디어 DLL은 0개다. 앱이 체감하는 차이는 영상 위 UI보다 재생할 수 있는 파일의 범위에 있다. [Media Engine 프레임 서버 계약](https://learn.microsoft.com/en-us/windows/win32/api/mfmediaengine/nf-mfmediaengine-imfmediaengineclassfactory-createinstance)

### 구현과 지원 조건

- **프레임 전달.** 프로토타입에서는 `OnVideoStreamTick`이 새 프레임을 알리면 `TransferVideoFrame`으로 D3D11 표면에 받는다. 이를 CPU·Direct3D 렌더러가 공통으로 읽을 수 있는 luil 이미지로 옮기고, 재생 상태 갱신과 화면 다시 그리기는 분리한다. 프레임을 읽는 동안 원본 버퍼를 덮어쓰지 않는다. CPU 읽기와 GPU 재업로드가 기준 성능에 못 미치면 DXGI 표면과 luil의 D3D12 렌더러 사이에 자원을 공유하는 경로를 별도 산정한다. [프레임 전달 API](https://learn.microsoft.com/en-us/windows/win32/api/mfmediaengine/nf-mfmediaengine-imfmediaengine-transfervideoframe) · [luil Direct3D 렌더러](../src/win32/direct3d_skia_renderer.cpp)
- **자막과 조작.** 한글 UTF-8 SRT는 luil이 읽고 엔진의 재생 위치에 맞춰 그린다. MP4 내장 텍스트는 `IMFTimedText`가 노출한 트랙과 큐를 같은 자막 요소에 연결한다. mov_text 트랙 열거, 언어 전환, 탐색 직후 진행 중인 큐 복원까지 실제 파일로 확인한 뒤 지원 조합에 올린다. 트랙을 얻지 못하는 파일도 외부 SRT를 선택할 수 있다. 새 백엔드의 재생·일시정지·중지와 오버레이 동작은 아래 공통 규격을 따른다. [Media Engine 자막 API](https://learn.microsoft.com/en-us/windows/win32/api/mfmediaengine/nn-mfmediaengine-imftimedtext)
- **지원 환경과 오류.** 미디어 기능이 설치된 일반 Windows 11 x64를 기준으로 삼는다. 파일을 여는 시점에 초기화·컨테이너 읽기·트랙 디코딩 실패를 구분할 수 있는 만큼 진단하고 원본 오류를 보존한다. 코덱 목록은 진단 보조 수단이다. 영상과 음성의 실제 출력, 일시정지·탐색·재개가 모두 성공해야 해당 조합을 지원 표에 올린다. [Windows 코덱 조회](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/codec-query)

| --- | --- |

| AVI · MJPEG + PCM / MPEG-4 Part 2 + MP3 | 두 조합을 각각 보장 후보로 둔다. 카메라 AVI와 Xvid 계열의 실제 FourCC·인덱스 변형을 시험해 통과한 조합을 명시한다. |
| TS · H.264 + AAC-LC(ADTS) | 단일 프로그램 로컬 파일을 보장 후보로 둔다. Windows 지원표에 H.264/TS가 있다. AAC 동시 출력, 0이 아닌 시작 PTS·탐색·끝까지 재생을 해당 엔진에서 시험한다. 길이가 불명확하면 순차 재생을 제공한다. |
| TS · MPEG-2 Video + AC-3 | 선택 코덱이 있는 PC에서 조건부 지원. MPEG-2 영상 디코더는 선택 구성이고 Windows 11 24H2부터 AC-3는 기본 포함 대상에서 빠졌다. OEM 설치 여부에 따라 같은 파일의 결과가 달라질 수 있다. |

위 표는 공식 코덱 목록에서 선정한 **인수 시험 목표**다. 현재까지 확보한 실측 결과는 맨 위의 프로토타입 표에 기록했다. 깨끗한 Windows와 선택 코덱을 설치한 Windows로 나누어 결과를 기록한다. [Microsoft Windows 코덱·컨테이너 지원표](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/supported-codecs)

### 견적과 선택 기준

아래는 Windows C++ 개발자 1명, 1080p30 SDR, CPU·Direct3D 양쪽 검증을 전제로 한 추정치다. 본체는 luil 소스·헤더 증가량이고 전체는 예제·시험·빌드·문서를 포함한다.

| 구현안 | 본체 / 전체 추가 줄 수 | 전체 공수 | 앱 배포 증가 |
| --- | ---: | ---: | --- |
| Windows 기본 엔진 | 1,400~2,600 / 2,100~3,800 | 16~28인일 | 미디어 DLL 0개. 연동 코드와 UI로 수십~수백 KiB 예상 |
| Windows 엔진 + 제한된 TS 입력기 | 기본 엔진 안에 본체 900~1,800줄, 전체 1,200~2,400줄 추가 | 10~18인일 추가, 총 26~46인일 | 미디어 DLL 0개. 자체 입력기 코드 추가 |
| FFmpeg 선택 모듈 | 2,700~4,700 / 3,600~6,500 | 26~45인일 | 선택 기능을 쓰는 앱에 약 5~25 MiB |

기본 엔진의 16~28인일은 세션·프레임 전달 5~8일, 자막·컨트롤 5~8일, 포맷별 검증·성능·배포 6~12일이다. 그중 첫 **3~5인일**에 외부 미디어 DLL 없는 소비 앱으로 다섯 시험 조합, SRT·내장 자막, 영상 위 중지 버튼을 확인한다. 1080p30에서 음영상 차이 ±80ms, 프레임 누락 1% 미만을 목표로 잡고 설치 크기도 함께 잰다.

TS 입력기는 **OS에서 H.264와 AAC를 각각 디코딩할 수 있는데 특정 TS에서 트랙 추출이나 탐색만 실패할 때** 고려한다. 단일 프로그램의 PAT·PMT·PES 처리, 타임스탬프 복원, 키프레임 인덱스, Media Foundation 소스 연결과 회귀 시험을 추가하는 견적이다. 누락된 MPEG-2·AC-3 디코더는 이 작업으로 확보되지 않는다. MPEG-2 + AC-3까지 추가 설치 없이 모든 배포 대상에서 보장해야 한다면, 아래 FFmpeg 모듈의 비용과 지원 범위를 기준으로 결정한다.

## 두 백엔드의 공통 재생 시험

아래 각 줄을 별도의 회귀 파일로 유지한다. 8-bit SDR, 프로그레시브 영상, 최대 1920×1080·30fps, 주 창당 활성 세션 하나를 성능 검증 범위로 잡는다. 입력은 로컬 파일이며 확장자와 실제 스트림 정보를 함께 읽어 컨테이너, 영상 코덱, 음성 코덱을 구분해 오류를 보고한다. 다음 다섯 조합은 FFmpeg안을 채택했을 때의 보장 목표다. Windows 기본 엔진안의 목표와 조건은 위 표에 따른다. [FFmpeg 형식·코덱 목록](https://ffmpeg.org/general.html)

| 컨테이너 | 1차 보장 조합 | 검증 포인트 |
| --- | --- | --- |
| MP4 | H.264/AVC + AAC-LC | B 프레임, 가변 프레임 간격, 탐색 뒤 자막과 재생 위치 |
| AVI | MPEG-4 Part 2(Xvid 계열) + MP3 | 오래된 파일의 화면 비율과 인덱스 기반 탐색 |
| AVI | Motion JPEG + PCM 16-bit | 카메라 영상의 색 범위와 음성 속도 |
| MPEG-TS 파일 | H.264/AVC + AAC-LC(ADTS) | 0에서 시작하지 않는 PTS, 길이 추정, 탐색 뒤 시계 재설정 |
| MPEG-TS 파일 | MPEG-2 Video + AC-3 | 단일 프로그램 녹화 파일, 스테레오 출력과 다채널 다운믹스 |

TS는 저장이 끝난 단일 프로그램 파일부터 지원한다. 길이나 탐색 가능 여부를 신뢰할 수 없으면 순차 재생을 제공하고 시간 탐색을 비활성화한다. 방송 녹화 원본 중 1080i는 디인터레이싱 품질 시험이 추가로 필요하다. 다중 프로그램 선택, 방송 자막(DVB·CEA), HLS·실시간 수신은 후속 범위다. 외부 UTF-8 SRT는 공통 출시 요건이다. MP4 내장 텍스트(mov_text)는 FFmpeg안의 출시 목표이고, Windows 기본 엔진안에서는 위 트랙·탐색 검증 결과에 따른다.

## 화면과 조작

- **영상 → 자막 → 컨트롤.** 기존 `layer_element`에 이 순서로 놓으면 위에 있는 실제 버튼이 먼저 입력을 받는다. 자막은 입력을 통과시킨다. 컨트롤은 영상 하단에 반투명하게 띄우고, 표시 중에는 자막의 아래 여백을 막대 높이만큼 올린다. 영상은 원본 표시 비율을 유지하고 자막은 실제 영상 사각형 안에서 줄을 바꾼다. 페이지 스크롤·팝업·모달·DPI 변경 시 전체 위젯이 일반 luil 요소처럼 합성된다. [겹침 배치 계약](../include/luil/ui/layer_element.h)
- **버튼과 키보드.** 재생·일시정지, 중지, 탐색, 볼륨·음소거, 자막 선택·끄기를 제공한다. 일시정지는 현재 프레임과 자막을 유지한다. 중지는 재생을 멈추고 처음 위치의 준비 상태로 돌아가며, 다음 재생은 처음부터 시작한다. 탐색 불가 파일은 중지 후 다음 재생 시 원본을 다시 연다. 창 종료나 파일 닫기는 세션 자원을 해제한다.
- **오버레이 표시.** 포인터를 움직이거나 터치하면 막대를 표시한다. 재생 중 입력이 3초간 없으면 숨긴다. 일시정지·중지, 컨트롤에 키보드 포커스가 있거나 슬라이더를 끄는 동안에는 계속 표시한다. 숨은 상태에서도 Tab으로 진입하면 막대가 다시 나타난다. 버튼 이름·음소거 상태·시간 슬라이더 값은 UI Automation에 노출한다.
- **자막.** 사용자가 외부 SRT를 선택하거나 MP4의 내장 텍스트 트랙 중 하나를 고른다. 한글·여러 줄·시간이 겹치는 큐를 표시하고 고대비 배경을 제공한다. 탐색 직후에는 새 위치에 해당하는 큐를 즉시 다시 찾는다. 내장 자막 탐색은 진행 중인 긴 큐까지 복원하는지 시험한다. 깨진 외부 자막은 자막 오류를 표시하고 영상은 계속 재생한다. ASS 효과·이미지 자막, 레거시 한글 인코딩 자동 감지는 후속 범위다.

## FFmpeg 선택 모듈의 구현 경계

기존 `win32::media_player`는 MFPlay가 자식 HWND에 출력하고 `video_element`가 그 자리를 잡는다. 이번 요구에는 앱의 그리기 단계에서 영상 프레임을 읽을 수 있어야 한다. Windows 미디어 API로 프레임을 받는 방법도 있지만 기본 지원 컨테이너·코덱은 OS 구성의 영향을 받는다. 세 컨테이너의 시험 결과를 배포본마다 재현할 수 있도록 FFmpeg 디코더 구성을 고정한다. 기존 API는 사용 중인 앱을 위해 유지한다. [기존 미디어 연결](selected-nodes.md#windows-미디어-연결) · [Media Foundation 지원 형식](https://learn.microsoft.com/en-us/windows/win32/medfound/supported-media-formats-in-media-foundation)

| 경계 | 구현 제안 |
| --- | --- |
| 앱 API | 세션은 열기·재생·일시정지·중지·탐색·볼륨·자막 선택·닫기와 불변 상태 스냅숏을 제공한다. 상태에는 위치, 길이 또는 미상, 탐색 가능 여부, 자막 목록, 오류가 들어간다. 기본 위젯과 앱의 사용자 정의 오버레이가 같은 명령을 쓴다. 트리를 다시 만들 때는 세션 ID를 유지한다. |
| 미디어 읽기 | 작업 스레드가 libavformat·libavcodec으로 파일을 읽고 타임스탬프가 붙은 프레임을 만든다. 열기·탐색마다 세대를 올리고 이전 패킷·프레임·자막·오디오 버퍼를 폐기한다. 긴 파일도 입력과 큐의 메모리에 상한을 둔다. |
| 음성·시계 | libswresample로 출력 형식을 맞추고 WASAPI 공유 모드로 재생한다. 실제 재생된 오디오 위치를 기준으로 영상과 자막을 고른다. 오디오 트랙이 없는 파일에는 일시정지 가능한 단조 시계를 사용한다. 음소거는 시계를 계속 진행한다. 출력 장치 변경·무효화 시 위치를 보존해 재연결하거나 복구 가능한 오류를 보낸다. [Windows 오디오 시계](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock-getposition) |
| Skia 합성 | 첫 버전은 소프트웨어 디코드 후 libswscale로 SDR 색 범위·행 간격을 고려해 불투명 BGRA로 변환한다. 수명이 보장된 불변 버퍼를 Skia 이미지로 감싸고 렌더 스레드에서 그린다. 프레임 시각에는 기존 트리로 다시 그리기를 요청하고 시간 표시 등 앱 상태는 저빈도로 발행한다. CPU·Direct3D 렌더러를 같은 입력으로 검증한다. GPU 디코딩·제로카피는 실측 뒤 결정한다. |
| 빌드·배포 | 제안 타깃 `luil::media`와 옵션 `LUIL_ENABLE_MEDIA`(기본 OFF)를 둔다. 기능을 쓰는 앱만 FFmpeg 공유 라이브러리를 배포한다. 고정 버전, 필요한 demuxer·parser·decoder·파일 입력만 켠 빌드 설정, 체크섬, 고지와 대응 소스를 패키지에 연결한다. GPL·nonfree 옵션을 끈 LGPL 동적 링크 구성을 기준으로 삼는다. [FFmpeg 배포 안내](https://ffmpeg.org/legal.html) |

## FFmpeg 선택 모듈의 규모와 일정

`main`의 `abeacfa` 기준 `src`·`include`의 추적 C++ 소스·헤더는 511개, 물리적 111,421줄이다. Windows C++·미디어 개발자 1명, 기존 luil 렌더러·컨트롤 재사용, 로컬 파일·소프트웨어 디코드 기준의 계획 추정치다. 외부 FFmpeg 소스 줄 수는 제외했다.

| 작업 | 추가 줄 수 | 인일 |
| --- | ---: | ---: |
| FFmpeg 입력·디코드, 세션·탐색·오류 | 1,000~1,700 | 7~11 |
| WASAPI 출력, 시계·동기화·장치 변경 | 550~950 | 4~7 |
| 프레임 전달, Skia 합성, 렌더러 검증 | 450~850 | 4~7 |
| 자막 트랙·시간 처리, 기본 오버레이·접근성 | 700~1,200 | 5~8 |
| 선택 빌드·배포, 예제, 시험 파일·자동화·실기 검증, 문서 | 900~1,800 | 6~12 |
| **합계** | **3,600~6,500** | **26~45** |

라이브러리 본체는 **2,700~4,700줄(약 2.4~4.2%)**, 전체 일정은 5일 근무 기준 약 **5~9주**다. 선택 모듈을 쓰는 앱의 비압축 Release x64 설치 폴더 증가량은 **약 5~25 MiB**를 초기 예산으로 둔다. 필요한 기능만 넣은 FFmpeg DLL과 연동 코드의 추정이며, 범용 FFmpeg 배포본, PDB, 샘플 영상, 대응 소스 아카이브는 별도다. 현재 산출물 측정치는 없다. 1080p BGRA 한 장은 7.91 MiB이고 세 장은 23.73 MiB다. 디코더 참조 프레임, 오디오 버퍼, GPU 업로드에는 메모리가 더 든다. 1080p30에서 전체 프레임 복사 한 번당 약 237 MiB/s가 이동하므로 공개 이미지 생성 경로의 반복 복사를 먼저 측정한다.

## FFmpeg안의 구현 순서와 공통 출시 시험

1. **첫 3~5인일은 전체 견적에 포함한 성능 검증이다.** 고정한 FFmpeg 빌드로 세 컨테이너를 열고, 1080p30 영상에서 WASAPI 소리와 Skia 영상 위에 SRT 한 줄 및 클릭 가능한 luil 중지 버튼을 함께 띄운다. 기준 PC 사양, CPU·Direct3D 양쪽의 프레임 누락, 복사 횟수와 패키지 크기를 기록한다. 기준 장비에서 목표를 달성하기 어려우면 GPU 경로를 별도 산정한다.
2. **재생과 합성.** 표의 다섯 조합을 열어 일시정지·재개·중지·끝에서 다시 재생을 확인한다. 플래시와 비프가 같은 시각에 기록된 기준 파일로 10분 재생 중 음영상 차이 목표 ±80ms와 누락 프레임 목표 1% 미만을 측정한다. 시간 탐색 뒤 오래된 프레임·음성·자막이 출력되지 않아야 한다. 탐색 불가 TS에는 비활성 슬라이더를 표시한다.
3. **자막과 조작.** 한글 SRT, MP4 내장 텍스트, 자막 끄기, 긴 자막 중간으로 탐색을 시험한다. 막대가 나타나도 자막이 읽히고, 버튼·슬라이더·Tab·UI Automation이 영상 위에서 작동해야 한다. 스크롤·팝업·모달·DPI 전환·창 크기 변경 뒤에도 같은 클립과 순서를 유지한다.
4. **배포와 복구.** A→B 연속 열기, 재생 중 창 닫기, 오디오 장치 변경, 손상된 파일과 미지원 코덱 뒤 정상 파일 열기를 검증한다. 깨끗한 Windows 환경에서 선택 기능 ON/OFF 소비 앱을 각각 실행하고 설치 폴더 크기 차이를 확정한다.
