스레드 모델

UI는 그리기만, input은 판정만, logic은 상태만 맡는다. 세 스레드는 서로를 기다리지 않고, 사건은 channel로, 상태는 latest_slot으로 건넌다.

이 문서를 읽으면

  1. UI·input·logic 세 스레드가 각각 무엇을 소유하는지 말할 수 있다.
  2. app_host가 채널·slot·명령 큐로 세 스레드를 잇는 모양을 그릴 수 있다.
  3. logic loop가 메시지를 묶어 처리하고 frame을 한 번만 게시하는 이유를 설명한다.
  4. 종료 절차의 단계와 시간 예산, 그리고 fail-fast를 고른 이유를 안다.

왜 스레드를 셋으로 나누나

한 스레드가 모든 일을 하면, 가장 느린 일이 화면과 입력을 함께 멈춘다.

전통적인 GUI 프로그램은 창 메시지를 받는 스레드 하나에서 입력 처리, 앱 상태 변경, 그리기를 모두 한다. 그 스레드에서 파일을 읽거나 큰 목록을 다시 정렬하면 그동안 창은 다시 그려지지 않고, 마우스는 눌러도 반응이 없다. luil은 일을 성격에 따라 세 스레드로 나누고, 각 스레드가 소유하는 것을 정해 둔다.

UI thread

OS가 "이 스레드에서만"을 요구하는 것들이다.

  • 창(HWND), 렌더러와 표면
  • WebView2, 클립보드, TSF COM 호출
  • 메시지 루프와 그리기(WM_PAINT)

input thread

입력을 뜻 있는 동작으로 바꾸는 상태 기계다.

  • raw 이벤트의 큐
  • interaction_controller — hover·누름·클릭·끌기·초점
  • interaction_snapshot 게시

logic thread

앱 상태의 유일한 주인이다.

  • 앱 상태와 logic_driver
  • 메시지 처리(handle)와 시간 갱신(tick)
  • 불변 ui_frame·tree 게시

읽기와 쓰기의 규칙UI와 input은 불변 tree를 읽기만 하고, logic은 새 frame과 tree를 만들기만 한다. 앱 상태는 logic에서만 바뀌고, 다른 스레드는 메시지를 보낼 뿐이다. 이 규칙이 지켜지면 tree에는 잠금이 필요 없다.

스레드 사이의 다리

세 스레드는 공유 변수가 아니라 정해진 다리로만 이야기한다. 다리를 눌러 무엇이 건너가는지 보자.

다리는 세 종류다. channel은 사건을 순서대로 나르는 큐(실선), latest_slot은 최신 상태 하나만 두는 칸(점선), 명령 큐는 UI thread에서만 할 수 있는 일을 부탁하는 목록과 깨우기 신호(점점선)다. 두 메시징 장치는 스레드 경계 메시징 문서에서 코드 한 줄까지 읽는다.

조립체 assembly 읽기

세 스레드가 나눠 쓰는 것은 전부 구조체 하나에 들어 있다. 선언 순서까지 설계다.

  1. C++은 멤버를 선언의 역순으로 파괴한다. 스레드(맨 아래)가 가장 먼저, 채널(맨 위)이 가장 나중에 사라진다. 스레드가 아직 쓰는 채널이 먼저 사라지는 일이 구조적으로 막힌다. 스레드 자체는 shutdown()이 먼저 멈춘다.
  2. raw 입력은 4096칸에 drop_oldest다. 포인터 이동이 몰리면 오래된 것을 버린다. 앱 메시지는 1024칸에 reject_newest다. 넘치면 새 것을 거절해 게시한 쪽이 알게 한다. 사건의 성격이 정책을 고른다(스레드 경계 메시징).
  3. frame(UI가 읽음), 주 tree와 표면 tree 목록(input이 읽음), interaction snapshot(UI가 읽음). 발췌 밖 100행에 다섯째인 touch_slot이 있다 — app_host::set_touch_gesture_config가 쓰고 input thread가 읽는 터치 몸짓 설정이다. 새 값이 옛 값을 덮으므로 소비자가 느려도 쌓이지 않는다.
  4. logic이 처리한 메시지의 번호(ticket)를 tree와 함께 게시한다. UI는 "이 tree가 내가 보낸 창 크기 메시지를 반영했는가"를 이 번호로 판단한다. 둘을 따로 게시하면 옛 tree에 새 번호가 붙을 수 있어 한 자물쇠로 묶었다.
  5. 창 최소화·클립보드처럼 UI thread만 할 수 있는 일은 큐에 넣고 깨우기 신호를 보낸다. 신호(창 메시지)는 유실될 수 있어도 내용은 큐에 남아 다음 신호에 실행된다.
  6. 종료 마감시각, 스레드 최상단에서 예외를 잡았다는 faulted, logic이 진입 함수를 벗어났다는 표시. 모두 shutdown()이 무기한 기다리지 않기 위한 장치다(2.8).

조립 순서: 채널 → callback → 스레드

던질 수 있는 준비는 모두 스레드를 시작하기 전에 끝낸다.

  1. std::thread가 join되지 않은 채 파괴되면 std::terminate다. 스레드를 시작한 뒤에 준비가 실패해 예외가 나면 프로세스가 죽는다. 그래서 예외가 날 수 있는 준비(callback 구성)는 전부 앞에 둔다.
  2. frame과 interaction slot에 같은 깨우기 신호를 단다. Win32에서는 PostMessageW지만 이 코드는 그 사실을 모른다. 플랫폼이 준 std::function일 뿐이라 창 없이도 조립된다.
  3. 초기 메시지(창의 첫 크기·배율)를 넘기고 logic thread를 시작한다. logic은 start(), 초기 메시지 처리, 첫 frame 게시 순으로 움직인다.
  4. input thread는 채널과 slot의 참조, 정책, 명령 실행 callback을 받는다. 앱 상태는 넘기지 않는다. input이 상태에 닿을 길 자체가 없다.
  5. input thread를 만들지 못하면(자원 고갈) app inbox를 닫아 logic을 내보내고 join한 뒤 예외를 다시 던진다. 실패는 호출자의 것이고 프로세스는 산다.

logic loop: 묶어서 처리하고, 한 번 게시한다

메시지가 몰려와도 frame은 묶음마다 한 번만 짓는다. 상한 64가 렌더링 기회를 지킨다.

  1. 플랫폼이 확정한 창 크기·배율을 초기 메시지로 먼저 처리한 뒤 첫 frame을 게시한다. 그래서 첫 배치부터 실제 크기를 쓴다.
  2. 예고된 tick이 있으면 그 시각까지, 없으면 250ms만 기다린다. 250ms는 종료 신호를 확인하는 주기다. 메시지도 tick도 없으면 스레드는 잠든다. 바쁜 대기(busy wait)가 없다.
  3. inbox가 닫혔고 비었으면 마지막 frame을 게시하고 돌아온다. 이것이 logic thread의 유일한 정상 출구다.
  4. 한 건을 처리한 뒤 drain(batch, 63)으로 쌓인 것을 한 번의 잠금으로 최대 63개 더 꺼낸다. 한 번 깰 때 최대 64건이다. 상한이 없으면 계속 밀려드는 메시지가 frame 게시를 굶길 수 있다.
  5. UI thread가 만든 파일 대화 상자 결과는 inbox가 가득 차 있으면 따로 보관된다. 이 자리에서 여유가 생긴 만큼 다시 넣는다. 사용자가 고른 파일을 잃지 않기 위한 자리다.
  6. 꺼낸 메시지를 순서대로 handle한다. 처리한 번호(ticket)를 남겨 tree 게시와 짝을 맞춘다.
  7. 예고 시각이 지났으면 메시지가 없어도 tick(now)을 부른다. 무엇이든 바뀌었으면 frame을 한 번 게시하고, 다음 예고를 다시 묻는다.
150
한 번 깰 때 receive_wait로 1건, drain으로 최대 63건을 꺼낸다(진한 칸이 receive_wait). 미리 쌓인 N건은 ⌈N/64⌉번의 묶음이 되고, frame은 묶음마다 한 번 게시된다. 처리하는 동안 새로 들어온 메시지는 다음 묶음으로 간다.

게시 순서: tree 먼저, frame은 마지막

UI를 깨우는 신호는 frame slot에만 달려 있다. 그래서 frame을 맨 나중에 게시한다.

  1. make_frame()은 앱 코드다. luil 개요 문서의 hello처럼 tree를 새로 지어 shared_ptr<const ui_frame>으로 돌려준다.
  2. tree slot에는 깨우기 신호가 없다. input thread는 입력을 처리하기 직전에 이 slot에서 새 tree를 집는다. 처리한 메시지 번호도 같은 자물쇠 안에서 적는다.
  3. 주 창 밖 표면들의 tree를 (id, tree) 목록 하나로 모아 게시한다. input의 controller에게는 표면만 있고 셋의 구분이 없다.
  4. frame 게시가 깨우기 신호를 낸다. 깨어난 UI thread가 무엇을 읽든 이미 새 tree가 게시되어 있다. 순서를 바꾸면 UI가 새 frame에 옛 tree를 짝지을 수 있다.

원자적 transaction은 아니다세 slot은 따로 게시되므로 모든 조회가 한 frame의 transaction은 아니다. input이 새 tree를 받기 전에는 옛 tree로 이벤트를 처리하므로 tree와 interaction이 서로 다른 frame일 수 있다. 그래도 어느 쪽도 수정되지 않으므로 읽는 쪽이 망가진 값을 보는 일은 없다.

시간이 흐르는 두 길

"3초 뒤에 토스트를 지운다"와 "caret을 깜박인다"는 다른 일이다. 하나는 상태가 바뀌고, 하나는 그림만 바뀐다.

예고가 없으면logic은 250ms마다 종료만 확인하고 잔다플랫폼이 timer를 걸지 않는다

둘 다 같은 원칙을 따른다. 시계를 읽는 쪽이 아니라 시각을 예고하는 쪽이다. element와 driver는 "다음에 언제 깨워 달라"만 답하고, 기다림은 루프가 맡는다. 앱은 스레드를 만들지 않고도 "3초 뒤 지운다"를 표현할 수 있다. element는 전환의 소유자가 아니다. 움직임과 시간은 애니메이션 문서에서 다시 다룬다.

종료 절차와 시간 예산

창을 닫을 때 앱은 저장을 끝내야 하고, 프로세스는 영원히 매달리면 안 된다. 두 요구를 시간 예산으로 맞춘다.

0ms

    1. 종료 신호 게시와 처리 대기가 마감시각 하나를 나눠 쓴다. 따로 재면 최악이 3초 + 3초가 된다. 두 상한을 합쳐도 세션 종료 유예(기본 5초) 안에 든다.
    2. 오래 걸리는 handle·tick·make_frame이 cancel()을 보고 일찍 돌아와야 뒤의 단계가 예산 안에 끝난다.
    3. inbox가 가득 차 있으면 reject_newest가 종료 신호를 버린다. 그러면 종료 저장이 통째로 사라진다. 그래서 이 한 건만은 마감까지 1ms 간격으로 다시 넣어 본다.
    4. shutdown_completed()가 참이 될 때까지, 마감까지만 기다린다. 이 시점에는 종료 저장 요청이 worker에 들어가 있다.
    5. 앱이 소유한 worker를 멈춘다. 앱 코드라 던질 수 있으므로 잡고 넘어간다. 채널 close와 join은 반드시 실행되어야 한다.
    6. inbox를 닫으면 건강한 logic은 남은 메시지를 소진하고 수 ms 안에 나온다. 1초를 기다려도 나오지 않으면 platform_fail_fast()로 즉시 끝낸다. 보이지 않는 무기한 hang보다 즉시 실패가 낫다는 선택이다. detach는 assembly 수명을 깨므로 금지다.
    7. input pump는 닫힌 inbox에서 곧바로 돌아오므로 이 join은 짧다. 마지막으로 slot들을 닫는다.

    예외는 오류 전달 수단이 아니다

    스레드 진입 함수를 벗어난 예외는 곧 std::terminate다. luil은 그것을 잡아 "고장"으로 기록한다.

    1. driver의 예외는 계약 밖의 입력이다. 잡지 않으면 프로세스가 끝나므로 여기서 삼킨다.
    2. faulted를 세우고 inbox를 닫는다. 그러면 shutdown()의 게시도 곧바로 포기하고, 쌓여 있던 메시지가 쥔 배경 작업 시간도 돌려준다.
    3. 스레드가 진입 함수를 벗어난다는 표시다. shutdown()은 이 값을 보고 join이 곧 돌아온다는 것을 안다.
    
    오류는 값으로 나른다파일을 열지 못했다, 요청이 실패했다 같은 앱 오류는 메시지나 frame의 상태 값으로 전달한다. 예외로 logic이 멈추면 frame 게시와 메시지 처리가 함께 멎는다. UI는 faulted()를 보고 앱을 끝낼 수 있다.

    창 없이 조립하고 시험하기

    깨우기 신호를 비워 두면 app_host는 창 없이 선다. 종료의 경계 조건을 테스트로 잠글 수 있다.

    아래 테스트는 실제로 있었던 문제를 잠근다. 메시지가 몰린 순간에 세션이 끝나면 포화된 inbox가 종료 신호를 버려 종료 저장이 통째로 날아갔다. 테스트는 inbox 용량의 두 배를 밀어 넣어 종료 신호가 들어갈 자리를 없앤 뒤, 그래도 종료 저장이 돌고 3초 예산을 헛태우지 않는지 확인한다.

    1. 설정이 비어 있으니 깨우기 신호도 창도 없다. logic과 input 스레드, 채널과 slot만 선다.
    2. gate를 닫은 driver는 첫 메시지를 붙잡고 있다. 그 사이 2048건을 넣으면 1024건이 거절된다. 거절은 조용하고, 통계(rejected)로만 보인다.
    3. 종료는 별도 스레드에서 시작하고, 50ms 뒤 gate를 연다. 그동안 종료 신호 게시는 1ms 간격으로 재시도하고 있다.
    4. 종료 저장이 돌았고(closed), 2.5초 안에 끝났다. 종료 신호가 포화에 삼켜졌다면 두 확인이 함께 무너진다.

    요약

    1. UI는 OS 자원과 그리기, input은 상호작용 상태 기계, logic은 앱 상태를 소유한다. 앱 상태를 바꾸는 곳은 logic 하나다.
    2. 스레드 사이에는 정해진 다리만 있다. 사건은 channel, 상태는 latest_slot, UI 전용 작업은 명령 큐와 깨우기 신호로 건넌다.
    3. assembly의 선언 순서가 파괴의 역순이고, 조립은 채널 → callback → 스레드 순서로 고정한다.
    4. logic은 한 번 깰 때 최대 64건을 처리하고 frame을 한 번 게시한다. tree를 먼저, UI를 깨우는 frame을 마지막에 게시한다.
    5. 시간은 예고로 다룬다. 상태가 바뀌면 next_tick/tick, 그림만 바뀌면 next_update다.
    6. 종료는 cancel → 종료 신호(재시도) → 처리 대기 → worker 정지 → close·유한 대기 → join 순서이고, 응답 없는 logic은 fail-fast로 끝낸다.

    자주 묻는 질문

    앱 상태는 어느 스레드에서 바꾸나?

    logic thread다. 앱 상태는 handle과 tick(시작할 때는 start)에서만 바꾼다.

    이 셋과 make_frame·next_tick은 host가 세운 logic thread에서 불린다. UI·input thread와 앱이 만든 worker는 메시지를 보내기만 한다. 그래야 앱 상태에 잠금이 필요 없다 (왜 스레드를 셋으로 나누나).

    driver 함수 중 logic thread가 아닌 곳에서 불리는 것은?

    cancel·make_close_message·shutdown_completed·stop_workers 넷이다. 모두 shutdown() 안에서 UI thread가 부른다.

    이 넷이 읽고 쓰는 값은 스레드 안전해야 한다. hello는 shutdown_completed가 읽는 값을 std::atomic<bool>로 둔다. logic_driver의 헤더 주석은 앞의 셋만 적었지만, 코드에서는 stop_workers도 종료 3단계에서 UI thread가 부른다. 그동안 logic thread는 종료 메시지 뒤에 쌓인 메시지를 아직 처리하고 있을 수 있다 (코드에서 확인한 동작) (종료 절차와 시간 예산).

    오래 걸리는 일(파일 읽기·HTTP·큰 계산)은 어디서 하나?

    handle 안에서 하지 않는다. 앱이 소유한 worker thread나, 자기 thread를 가진 부품(http_client·file_watcher 등)에 맡긴다.

    handle이 도는 동안 logic은 다음 메시지도 frame 게시도 하지 않는다. 라이브러리에 일반 worker pool은 없다. 필요하면 앱이 소유하고 stop_workers에서 멈춘다. 시작할 때 불러올 것도 start()에서 제출만 한다. 망·파일 감시 부품은 자기 thread에서 일하고 결과를 deliver 하나로 낸다 (thread를 가진 부품과 배출구 하나).

    백그라운드 작업의 결과를 앱 상태에 넣으려면?

    worker에서 결과를 메시지(예: load_done_intent)에 담아 post_app_message로 보내고, logic thread의 handle에서 상태에 넣는다.

    post_app_message는 어느 스레드에서 불러도 되고 막히지 않는다. worker가 쓸 app_host 참조는 delegate의 on_started(app_host&)가 준다. 창과 host가 준비된 직후, 이벤트 루프 전에 UI thread에서 한 번 불린다. logic thread는 host가 설 때 이미 돌기 시작하므로 start()가 on_started보다 먼저 불릴 수 있다 (코드에서 확인한 동작). 데모는 host 포인터를 std::atomic에 담고, deliver는 그것이 비어 있으면 아무것도 하지 않는다 (HTTP 요청과 답).

    UI 스레드가 멈추면 입력은?

    입력도 멈춘다. OS 입력은 UI thread의 이벤트 루프가 받아 post_raw_input으로 input thread에 넘기기 때문이다.

    그동안 logic은 기다리지 않고 돌며 frame을 latest_slot에 덮어쓴다. frame이 쌓이지 않고, UI가 풀리면 가장 새 frame 하나를 그린다. delegate의 훅(execute_app_ui_command, make_window_metrics_message 등)은 UI thread에서 불리므로 거기서 오래 걸리는 일을 하지 않는다 (스레드 사이의 다리, latest_slot 읽기).

    handle이 오래 걸리는 동안 창과 입력은?

    창은 마지막 frame을 그리고, hover·눌림 같은 상호작용 표시는 계속 바뀐다. 앱 상태에서 나오는 변화만 늦는다.

    상호작용 상태는 input thread가 게시하고, frame과 같은 깨우기 신호로 UI를 깨운다. 그동안 메시지는 app inbox(1024칸)에 쌓인다. 가득 차면 post_app_message로 넣은 것은 조용히 버려진다. element 액션이 낸 메시지는 input thread가 자리가 날 때까지 1ms 간격으로 다시 넣는데, 그동안은 input thread도 묶여 hover가 멎는다 (코드에서 확인한 동작) (logic loop, 넘칠 때, 무엇을 잃을 것인가).

    make_frame은 언제, 얼마나 자주 불리나?

    시작할 때 한 번, 그 뒤로는 깰 때마다 메시지 묶음(최대 64건)이나 tick을 처리한 뒤 한 번이다. inbox가 닫힐 때 마지막으로 한 번 더 부른다.

    메시지도 예고한 시각도 없으면 부르지 않는다. 묶음 안의 메시지가 몇 건이든 frame은 하나다. make_frame이 nullptr를 돌려주면 그 차례는 게시하지 않고 화면은 직전 frame 그대로다 (코드에서 확인한 동작) (logic loop, 게시 순서).

    logic thread에서 예외가 나면?

    스레드 최상단이 잡아 faulted()를 세우고 inbox를 닫는다. 프로세스는 살지만 그 뒤로 메시지 처리와 frame 게시가 없다.

    start·handle·make_frame·tick 어디서 던져도 같고 test가 이를 잠근다. 정책이 던지면 input thread가 같은 식으로 멈춘다. 그 뒤는 플랫폼마다 다르다. Android는 Activity를 끝내고, macOS는 창을 닫고 앱을 끝낸다. iOS는 기록만 남긴다. Win32는 창을 그대로 두고, 사용자가 닫을 때 닫힘 훅(ui_frame::close)을 거치지 않는다 (플랫폼별 동작은 코드에서 확인한 동작). 그래서 앱 오류는 예외가 아니라 메시지와 상태 값으로 나른다 (예외는 오류 전달 수단이 아니다).

    창을 닫을 때 저장은 어디서 하나?

    make_close_message가 지은 종료 메시지를 handle에서 받을 때 저장을 마치거나 제출하고, 그 뒤 shutdown_completed가 참을 돌려주게 한다.

    host는 종료 메시지를 넣고 그 값이 참이 되기를 기다린다. 게시와 기다림이 합쳐 3초 예산이고, 넘기면 저장을 기다리지 않고 정리로 간다. 모바일 OS는 앱이 뒤로 간 뒤 종료 알림 없이 프로세스를 거둘 수 있다. 그래서 그쪽의 저장은 app_lifecycle::background 메시지에서 한다 (종료 절차와 시간 예산, 닫힘과 수명 주기).

    오래 걸리는 handle이 종료를 늦추지 않게 하려면?

    cancel()을 구현한다. shutdown()이 종료 메시지보다 먼저 UI thread에서 이것을 부른다.

    cancel()에서 앱이 든 취소 표시(std::atomic<bool> 하나면 된다)를 세우고, 오래 걸리는 handle·tick·make_frame이 그것을 보고 일찍 돌아오게 한다. 돌아오지 않으면 종료 메시지가 처리되지 못해 3초 예산을 다 쓰고, inbox를 닫은 뒤 1초를 더 기다렸다가 platform_fail_fast()로 끝난다. cancel로 풀려나는 driver가 2.5초 안에 끝나는 것을 test가 잠근다 (종료 절차와 시간 예산).

    worker는 언제 멈추나? 멈춘 뒤 늦게 온 결과는?

    stop_workers()에서 멈춘다. host는 종료 메시지 처리를 기다린 뒤, inbox를 닫기 전에 이것을 부른다.

    그 전에 worker가 낸 결과는 아직 열린 inbox로 들어가 처리된다. inbox가 닫힌 뒤의 게시는 조용히 버려진다. stop_workers가 던져도 inbox를 닫고 join하는 정리는 그대로 이어진다. cancel()에서 날아가는 일을 먼저 접어 두면 이 단계가 짧아진다 (종료 절차와 시간 예산, thread를 가진 부품과 배출구 하나).

    정책과 delegate는 어느 스레드에서 도나?

    interaction_policy는 input thread, delegate(app_delegate·win32::window_delegate)는 UI thread다. 둘 다 앱 상태를 고치지 않고 메시지만 만든다.

    정책의 글 변환 훅(make_text_edit_action·make_text_composition_action)은 IME·붙여넣기·편집 메뉴 경로에서 UI thread로도 불리므로 순수 변환이어야 한다. delegate 훅이 돌려준 메시지는 app inbox로 가고, 빈 메시지는 게시하지 않는다. 정책이 던지면 input thread가 멈추고 faulted()가 선다 (앱과 라이브러리의 경계).

    창 없이 driver를 시험하려면?

    app_host를 빈 config로 세운다. 깨우기 신호가 비면 창 없이 logic·input thread와 채널만 선다.

    post_app_message로 메시지를 넣고, test thread가 UI thread 노릇을 하며 acquire_frame()으로 게시된 frame을 본다. 소멸자가 shutdown()을 부르므로 종료 절차도 함께 시험된다 (창 없이 조립하고 시험하기, 창 없이 도는 core).

    사례로 확인하기

    입력과 상태를 하나 정해 두고, luil이 그때 무엇을 하는지 코드에서 따라간 결과다. 펼치면 결과와 까닭이 나온다.

    inbox에 메시지 200건이 미리 쌓여 있다. 처리하는 동안 새 메시지가 없다면 logic은 frame을 몇 번 게시하는가?

    4번

    한 번 깰 때 receive_wait로 1건, drain으로 최대 63건, 합쳐 64건을 처리하고 frame을 한 번 게시한다. 200 = 64 + 64 + 64 + 8이므로 4번이다.

    publish_frame()이 frame slot을 tree slot보다 나중에 게시하는 이유는?

    UI를 깨우는 신호가 frame slot에 달려 있어, 깨어난 UI가 새 tree를 보게 하려고

    wake 신호는 frame slot에만 붙어 있다. tree를 먼저 게시해야 신호를 받고 깨어난 UI thread가 이미 게시된 새 tree를 읽는다.

    종료 절차에서 inbox를 닫은 뒤 1초를 기다려도 logic thread가 나오지 않으면?

    platform_fail_fast()로 즉시 끝낸다

    cancel과 close에도 나오지 않는 logic은 회복할 수 없다. 보이지 않는 무기한 hang 대신 즉시 실패를 고른다. detach는 assembly의 수명을 깨므로 금지다.

    "3초 뒤에 토스트를 지운다"를 luil 앱에서 표현하는 올바른 방법은?

    next_tick()이 만료 시각을 답하고, tick(now)에서 토스트를 상태에서 뺀다

    토스트가 사라지는 것은 앱 상태의 변화다. logic의 next_tick이 시각을 예고하면 루프가 그때 tick을 부르고 새 frame을 게시한다. next_update는 그림만 다시 그리는 길이다.
