접근성

luil의 element는 accessibility()로 역할·이름·상태·범위를 답하고, 보조 기술의 명령을 앱 메시지로 옮긴다. 플랫폼 다리는 게시된 tree를 접은 접근 tree를 내주고, 그릴 때마다 발행본을 직전 것과 견줘 바뀐 것을 알린다. 앱이 할 일은 이름을 빠뜨리지 않고, 직접 그린 요소의 정보와 절대 명령을 잇고, 글이 바뀌는 자리를 live region으로 두는 것이다.

이 문서를 읽으면

  1. 아이콘 단추·컨테이너·직접 그린 요소가 보조 기술에 무엇으로 읽히는지 정한다.
  2. 보조 기술의 누르기·고르기·펼치기·값 정하기를 앱 메시지로 받는다.
  3. 상태 글을 live region으로 알린다. 글을 바로 읽히는 API가 없다는 것과 대신 쓰는 길을 안다.
  4. 검사기와 접근 발행본으로 접근 tree를 확인하고 test로 잠근다.

무엇을 하면 되나

라이브러리 요소는 이미 자기 역할과 상태를 답한다. 앱이 할 일은 이름을 빠뜨리지 않는 것, 그리고 직접 그린 요소와 절대 명령을 잇는 것이다.

이름

  • 글리프만 있는 단추는 set_tooltip이 이름(이자 도움말)이다.
  • 목록·탭 막대처럼 글을 세우지 않는 컨테이너는 화면에 뜨지 않는 set_access_name이다.
  • 이름이 비면 누를 수 있어도 접근 tree에서 사라진다.

직접 그린 요소

  • accessibility()를 재정의해 역할·이름·상태·범위를 답한다.
  • 값 정하기·펼치기 같은 절대 명령은 set_access_handler나 access_actions 재정의로 메시지를 낸다.
  • 누르기는 left_click 액션이 그대로 받는다.

상태 글

  • 글이 바뀌면 읽히게 하려면 set_live_region이다.
  • access_role::alert(토스트·정보 막대)는 정하지 않아도 끊고 읽힌다.
  • 입력 칸의 error는 새로 생기면 알림으로 읽힌다.

개념: 접근 tree와 발행본

보조 기술이 보는 것은 게시된 ui tree를 접은 접근 tree다. tree는 frame마다 새로 지어지므로, 무엇이 바뀌었는지는 이전 발행본과 견줘야만 안다.

접기 규칙

  • 보이지 않는 가지는 통째로 빠진다. 자기나 조상이 set_visible(false)면 읽을 자리도 누를 자리도 아니다. 스크롤로 잘려 화면 밖에 있는 것은 그대로 남는다 — 키보드로 닿으면 화면 안으로 들어오기 때문이다.
  • 역할이 none인 요소는 접힌다. stack·panel 같은 배치 요소가 그렇다. 그 자식이 이 자리로 올라와 부모의 형제 줄에 선다.
  • 같은 id가 둘이면 첫 등록만 형제 줄에 선다. 뒤의 것은 구조처럼 접혀 자식만 올라온다. 중복은 ui_tree::duplicate_ids()에 남는 앱 결함이다.
  • 접근 부모는 가장 가까운 접근 조상이다. 없으면 창(fragment root)이다. 이 색인은 tree가 생길 때 한 번 짓는다 — 긴 목록도 형제 걸음이 한 번이다.

역할과 이름의 기본

규칙뜻
기본 accessibility()left_click 액션이 있고 이름이 있으면 button, 아니면 none이다. 이름 없는 단추는 소음이라 승격하지 않는다
이름의 원천 access_name()set_access_name → set_search_label → tooltip 순서다. 자기 글을 그리는 요소(글자 단추·라벨·목록 행·탭)는 그 글이 이름이다
공통 값 access_info_of요소의 답 위에 enabled(enabled()), help(비면 tooltip 글), live(set_live_region, 정하지 않은 alert는 assertive)를 채운다. 발행본과 플랫폼 질의가 모두 이 함수로 읽는다

보조 기술의 명령이 지나가는 길

보조 기술 → UINarrator·VoiceOver가 요소에 명령을 보낸다. UIA 호출은 창의 STA(UI thread)로 모이고, macOS·iOS 다리는 메인 thread에서 돈다.
UI thread다리가 쥔 id로 지금 tree에서 요소를 다시 찾는다. enabled()와 access_reachable을 보고, 비활성·가둠 뒤·숨은 것이면 거절한다.
UI threadplan_access_request가 상태를 보고 요소의 access_actions를 부른다. 앱이 준 factory가 이때 불려 메시지를 만든다.
input thread누르기·켬끔·고르기는 access_click_event로 input thread에 가서 마우스 클릭처럼 interaction_policy::on_click 뒤에 나간다. 그 밖의 명령은 창의 다음 차례에 배분한다.
logic thread앱이 메시지를 받아 상태를 바꾸고 새 frame을 게시한다.
UI thread다음 그리기에서 발행본을 직전 것과 견줘 바뀐 것(property·selected·structure·live region)을 알린다. 앱이 처리하기 전에 상태가 바뀌었다고 말하지 않는 순서다.

id가 정체성이다

  • 다리는 element 포인터가 아니라 (표면, ui_element_id)를 쥐고 물을 때마다 지금 tree에서 다시 찾는다. 그래서 id가 frame을 넘어 같아야 보조 기술의 자리가 이어진다.
  • 자동화 id는 세 플랫폼에서 <kind의 수>:<owner>다 — UIA AutomationId, macOS·iOS의 accessibilityIdentifier. kind 이름이 아니라 열거 값의 수라 키 doc-1인 탭은 17:doc-1이다. popup 안의 요소는 macOS·iOS에서 앞에 popup 표식이 붙는다.
  • id가 사라진 요소에 명령이 오면 UIA는 UIA_E_ELEMENTNOTAVAILABLE로 답한다.

키보드 초점과 보조 기술의 커서

  • 논리 초점은 하나이고 controller가 든다. UIA의 HasKeyboardFocus는 Win32 초점이 아니라 그 표면의 논리 초점이다. 초점이 옮겨 가면 그리는 길에서 알린다 (UIA UIA_AutomationFocusChangedEventId, macOS FocusedUIElementChanged, iOS LayoutChanged).
  • 보조 기술의 커서는 논리 초점을 옮기지 않는다. Narrator·VoiceOver가 요소를 훑어도 키보드 초점은 그대로다. 논리 초점이 옮겨 가면 커서가 따라간다.
  • 보조 기술이 초점을 청하면 UIA SetFocus는 focusable()이고 손이 닿는 요소만 받아 access_focus_event를 input thread에 보낸다. controller가 다시 확인하고 키보드 초점으로 세운다 — 초점 테가 보인다.

알림은 상태의 대조로 난다"이 글을 읽어라"는 API가 없다 (공개 헤더에 speak·announce 같은 이름이 없다). 읽히는 것은 다음 발행본 대조가 찾은 변화다: 이름·값·상태의 property, 새로 골라진 항목, 자식 구성, live region의 글. 상태가 바뀌지 않는 사건인 Invoke만 배분한 순간에 알린다.

만들기: 아이콘 단추와 컨테이너에 이름 붙이기

글이 없는 요소는 이름이 없으면 접근 tree에서 사라진다. 글리프 단추는 tooltip, 컨테이너는 화면에 뜨지 않는 set_access_name이다.

button_element는 accessibility()를 재정의하지 않는다(코드에서 확인한 동작). 그래서 기본 규칙을 탄다 — left_click이 있고 tooltip이 이름이 되어 button "하나 더한다"로 읽힌다. 같은 tooltip이 도움말(UIA HelpText, macOS AXHelp)도 된다. 이름과 설명을 가르려면 set_access_name(u8"더하기")로 이름을, set_tooltip으로 긴 설명을 준다 — 이름은 access name이 먼저다.

기본 규칙 자체를 잠근 test다. 누를 수 있어도 이름이 없으면 none이고, 글자 탐색의 글이 tooltip보다 먼저다.

목록·탭 막대·스크롤 막대처럼 자기 글을 세우지 않는 컨테이너에 tooltip을 달면 빈 자리에 글 상자가 뜬다. 그래서 set_access_name을 쓴다 — 그리기에도 글자 탐색에도 쓰이지 않는다. 컨테이너가 안에 세우는 부품(목록의 스크롤 막대)은 앱이 손댈 수 없어 컨테이너의 이름을 물려받는다.

요소이름은 어디서 오나
자기 글을 그리는 요소 — text_button_element, label_element, 목록 행, 탭그 글
글을 세우지 않는 요소 — list_element, grouped_list_element, menu_element, tab_bar_element, scrollbar_element, slider_element, progress_element, split_handle_element, 라벨 없는 체크access_name() — set_access_name → set_search_label → tooltip
컨테이너가 세우는 부품 — 목록·스크롤 영역·표의 막대, 표의 머리글·본문컨테이너의 이름을 물려받는다
modal 대화 상자, 선택 묶음modal_host_config::name, choice_group_config::name — 비면 이름 없이 선다
사이드바의 폭 손잡이sidebar_config::handle_access_name — 기본 문구가 없다

이름 없는 단추는 소음이라 사라진다누를 수 있는 요소라도 이름이 비면 역할이 none이라 접근 tree에서 빠진다. 오류도 경고도 없다. 탭 막대의 닫기 단추가 바로 그 경우라 보조 기술에 없다 — 탭 문서가 대신 길을 적는다.

만들기: 직접 그린 요소의 역할·값·범위

직접 그린 요소는 accessibility()를 재정의해 역할·이름·상태·범위를 답한다. 값을 정하게 하려면 목표 값을 나르는 메시지를 단다.

범위만 내주는 가장 작은 요소다 (UIA 변환 test의 것). 범위가 있으니 RangeValue 패턴이 서지만 값을 정할 길이 없어 읽기 전용이다 — IsReadOnly가 참이고 SetValue는 E_ACCESSDENIED다.

라이브러리의 별점이 범위·값 글·값 정하기를 모두 잇는 본보기다. 값 글이 비지 않아 UIA Value 패턴도 함께 서고, 값 정하기는 앱의 절대 메시지(change_to)만 탄다.

앱이 그린 요소가 값 정하기를 받는 예는 저장소에 없어 손으로 썼다. 재정의 대신 set_access_handler로 set_value만 앱 메시지로 옮긴다.

  • 계획은 범위가 있는지만 먼저 본다. set_value는 range가 없으면 할 수 없음이고, 있으면 요소의 access_actions에 묻는다. 기본 access_actions는 set_access_handler로 준 처리기를 먼저 부른다. 처리기가 없으면 set_value는 기본 실행이 없다.
  • 값 글을 함께 주면 UIA Value 패턴도 선다. 다만 글로 쓰는 Value.SetValue는 편집 파이프라인에 이어진 edit·combo_box가 아니면 E_ACCESSDENIED다. IsReadOnly는 RangeValue와 Value가 한 함수로 답해서, 값을 받는 이 다이얼은 Value 쪽에서도 "읽기 전용 아님"이라 답한다 — 값을 바꾸는 길은 RangeValue.SetValue다 (코드에서 확인한 동작).
  • step·page는 UIA의 SmallChange·LargeChange로 알려진다. 0이면 알리지 않고, macOS의 오르내림(AXIncrement)은 범위의 1/20을 쓴다. iOS는 걸음이 0보다 크고 값 정하기 계획이 설 때만 Adjustable이다.
  • UIA는 범위 밖 값을 자르지 않고 E_INVALIDARG로 거절한다. macOS는 범위로 자른다.
  • 보조 기술 명령과 키보드는 따로다. 화살표로 값을 바꾸려면 set_key_step_target을 단다.

만들기: 보조 기술의 명령 받기

명령은 "이 요소에서 무슨 메시지인가"로 바뀐다. 계획의 답은 셋이다: 할 수 없음(nullopt), 내 것이지만 할 일 없음(빈 목록), 낼 메시지들.

  1. 누름에는 "이미"가 없다. 할 수 있는지는 요소가 답한다. 빈 계획이 오면 UIA는 거절한다.
  2. 뒤집기라 방향이 없다. checked가 없으면 할 수 없다.
  3. 이미 골라졌으면 할 일이 없다 — 실행은 클릭 하나라 그대로 흘리면 도리어 풀리는 자리가 있다. 다중 선택이면 "이것 하나만"이라 그래도 요소에 간다.
  4. 목표 상태를 나르는 명령이다. 이미 그 상태면 할 일이 없다.
  5. 방향을 본다. UIA Expand는 "펼친 상태로 만들라"이지 "뒤집으라"가 아니다.
  6. 범위·흘림 자리가 없으면 할 수 없다. 흘림 백분율은 같은 자리여도 요소에 간다 (늘어나는 목록의 100은 "끝에 붙어 있으라"다).
  7. 상태가 맞으면 요소의 access_actions가 답한다. 비활성은 여기서 보지 않는다 — 다리가 따로 거절한다.

요소의 기본 access_actions는 처리기 → 절대 명령이면 할 수 없음 → left_click을 요소 한가운데 좌표로 부르기 순서다. 마우스로 누를 수 없는 것은 보조 기술로도 누를 수 없다.

앱이 받겠다고 한 명령만 처리기가 답하고, 나머지는 기본(클릭)으로 물러서는 모양이다 (원문 test):

  • 처리기의 답 규약은 계획과 같다: nullopt면 기본으로 물러서고, 빈 목록이면 "내 것이지만 할 일 없음"이다.
  • 상태를 답하는 요소와 바꾸는 요소가 다르면(그룹의 펼침은 머리행이 쥔다) access_actions를 재정의한다. 라이브러리의 가상 목록 행이 set_access_handler로 더하기·빼기를 옮긴다.
  • 설계 문서는 "여섯 동작"이라 적지만 access_command는 아홉 값이다 — 더하기·빼기·흘림 백분율이 뒤에 더해졌다. 헤더가 맞다.

factory는 순수해야 한다보조 기술 길에서는 factory가 UI thread의 계획 단계에서 불리고 결과가 버려질 수도 있다. UIA가 Invoke 패턴이 있는지 물을 때 invoke 계획을 세워 보고, IsReadOnly도 set_value 계획을 세운다. macOS의 누름 허용 판정과 iOS의 Adjustable 판정도 같다. 그래서 액션·factory는 상태를 바꾸지 말고 메시지만 만들어 돌려준다. 앱 상태를 참조로 잡지 말고 값으로 캡처한다 (코드에서 확인한 동작).

만들기: live region으로 상태 글 알리기

글을 바로 읽히는 API는 없다. 글이 바뀌는 자리를 live region으로 두면 다음 발행본 대조가 그 자리를 읽게 알린다.

비활성 단추에 tooltip으로 까닭을 적으면 그것이 도움말이다. 비활성 단추도 이름과 까닭을 지닌 채 tree에 남고, 활성이나 까닭이 바뀌면 property 변화로 들린다. 판 안의 줄이 바뀌면 판(live region)이 알린다:

  • 역할이 있는 요소만 live region이 된다. test의 판은 이름과 누름 액션을 줘 역할(button)을 세웠다. 역할이 none인 배치 요소에 걸면 접혀서 아무것도 알리지 않는다.
  • 그 요소나 안쪽 요소의 글(이름·값·도움말·오류)이 바뀌거나, 글을 가진 요소가 들고 나면 가장 안쪽 live region이 frame마다 한 번 알린다. 사라진 줄도 글이 바뀐 것이다.
  • 알림의 차례는 property·selected → 다중 선택 → structure → 마지막에 live region이다. 클라이언트가 바뀐 구조를 다시 읽은 뒤 그 글을 읽는다.
  • set_live_region을 부르는 라이브러리 요소·예제는 없다 (test에만 있다). 토스트·정보 막대는 alert 역할이라 정하지 않아도 assertive다.

실행 중에는 검사기 overlay로 요소의 역할과 이름을 보고, test에서는 접근 발행본으로 접힌 tree와 변화를 잠근다.

실행 중: 검사기 overlay

검사기는 frame에 싣는 설정 하나다. 켜는 단축키는 앱이 정한다 — 라이브러리는 키를 예약하지 않는다. 데스크톱 데모의 연결이다 (원문):

  • 정보 상자는 다섯 줄이다. 넷째 줄 handles … access <역할> "<이름>"이 그 요소의 accessibility()다. 값(access_info::value)은 보이지 않는다 — 암호 칸과 긴 글이 새지 않게 한다.
  • overlay는 그리기만 한다. hit test·입력·초점·접근 tree에 닿지 않는다. 정보 상자의 글을 보조 기술로 읽히려면 앱이 dump_tree의 글을 label로 올린다.
  • 모바일 데모는 손가락뿐이라 기본 집기가 inspector_pick::focused다.

test: tree를 글로 잠그기

dump_tree는 ui tree의 모든 요소를 한 줄씩 쓰고, 역할이 있는 요소에만 access …를 붙인다. 접기 전의 tree라 배치 요소도 줄이 있다.

test: 접힌 접근 tree와 변화를 잠그기

보조 기술이 보는 접힌 tree는 make_access_snapshot이고, 두 발행본의 차이는 diff_access_snapshots다. 플랫폼 다리가 쓰는 그 함수들이다.

앱 test에서 "보조 기술이 훑는 차례"를 한 번에 보는 도우미는 저장소에 없어 손으로 썼다. dump_tree와 달리 접힌 발행본을 공통 값(enabled·help·live)까지 쓴다.

플랫폼 차이

어휘·접근 tree·도달 판정·실행 계획·발행본 대조는 세 다리가 같은 함수를 쓴다. 다른 것은 플랫폼 낱말로의 번역과 알림의 모양이다.

오류 없이 조용히 틀리는 자리들이다.

  1. 이름 없는 누를 것은 사라진다. 기본 규칙은 이름이 비면 none이다. 글리프 단추에 tooltip도 access name도 없으면 접근 tree에 없다. 탭의 닫기 단추가 그 경우다.
  2. tooltip은 이름과 도움말을 겸한다. 같은 글이 이름과 HelpText로 두 번 실린다. 실제로 몇 번 읽히는지는 스크린 리더가 정한다. 짧은 이름은 set_access_name에 둔다.
  3. 컨테이너에 tooltip을 달면 화면에 글 상자가 뜬다. 목록·탭 막대의 이름은 set_access_name이다.
  4. 절대 명령은 기본 실행이 없다. 펼치기·접기·값 정하기·더하기·빼기·흘림 백분율은 목표 상태를 나르는 메시지가 없으면 할 수 없는 일이다. 클릭(뒤집기)으로 대신하면 오래된 발행본을 본 두 명령이 두 번 뒤집기 때문이다.
  5. plan_access_request는 비활성을 보지 않는다. 그것만 test하면 비활성 요소도 계획이 선다. 거절은 다리가 enabled()·access_reachable로 한다.
  6. factory는 "묻기만 해도" 불린다. UIA의 패턴 질의, IsReadOnly, macOS·iOS의 허용 판정이 계획을 세운다. 상태를 바꾸는 factory는 보조 기술이 훑기만 해도 앱을 바꾼다 (코드에서 확인한 동작).
  7. 중복 id는 뒤의 요소를 지운다. 형제 줄에는 첫 등록만 선다. 같은 키를 두 목록이나 두 탭 막대에 쓰면 뒤의 것이 접근 tree에서 사라진다.
  8. id가 frame마다 바뀌면 보조 기술이 자리를 잃는다. 다리와 VoiceOver 요소는 id로 frame을 넘는다. 색인이나 주소로 id를 짓지 않는다.
  9. live region은 역할이 있는 요소에만 뜻이 있다. 배치 판에 걸면 접혀서 아무것도 알리지 않는다. 한 frame에 live region 하나는 한 번만 알린다.
  10. 역할이 바뀌면 다른 요소다. property가 아니라 부모의 structure로 알린다.
  11. modal 뒤는 닿지 않는다. 가둠 밖이어도 포인터가 닿는 자리(덮이지 않은 캡션 단추)는 닿는다 — 상자의 아홉 점을 사람이 쓰는 hit_test로 훑는다. 숨긴 가지는 닿지 않고, 스크롤로 잘린 것은 닿는다.
  12. 검사기의 access 줄은 accessibility() 그대로다. enabled·help·live가 없고, dump_tree는 접기 전의 모든 요소를 쓴다. 접힌 접근 tree는 make_access_snapshot으로 본다.
  13. 값 글이 있는 범위 요소의 Value 패턴. IsReadOnly는 RangeValue와 같은 답이라 쓸 수 있는 요소는 "쓸 수 있음"이라 답하지만, 글로 쓰는 Value.SetValue는 E_ACCESSDENIED다. 값은 RangeValue.SetValue로만 바뀐다 (코드에서 확인한 동작).
  14. 다중 선택의 큰 변화는 항목마다 알리지 않는다. 20개를 넘으면 selection_invalidated 하나다.
  15. 그리지 않은 창에는 tree가 없다. 숨긴 채 시작한 창은 자동화로 읽히지 않는다.
  16. 끌기처럼 포인터만의 몸짓에는 보조 기술 명령이 없다. access_command에 "옮겨라"가 없다. 순서 바꾸기·떼어 내기는 메뉴 명령 같은 다른 길을 앱이 준다.
  17. Android에서는 아무것도 읽히지 않는다. access_info를 고쳐도 Android에서는 아무도 읽지 않는다.

자주 묻는 질문

아이콘만 있는 단추를 스크린 리더가 "단추"로도 읽지 않는다.

이름이 비어 역할이 none으로 접혔다. set_tooltip이나 set_access_name으로 이름을 준다.

기본 accessibility()는 누를 수 있고 이름이 있어야 button이다 (이름 붙이기).

이름은 어디서 오나? 우선순위는?

set_access_name → set_search_label → tooltip.

자기 글을 그리는 요소(글자 단추·라벨·목록 행·탭)는 그 글이 이름이다. accessibility()를 재정의한 요소도 보통 access_name()을 쓴다.

목록에 이름을 주려고 tooltip을 달았더니 글 상자가 뜬다.

set_access_name을 쓴다.

그리기에도 글자 탐색에도 쓰이지 않는 이름이다. 목록 안의 스크롤 막대는 목록의 이름을 물려받는다.

직접 그린 요소를 슬라이더로 읽히게 하려면?

accessibility()를 재정의해 role = access_role::slider와 range를 낸다.

값을 정할 수 있게 하려면 set_access_handler로 set_value를 받아 목표 값 메시지를 낸다 (직접 그린 요소).

보조 기술이 "펼쳐라"를 보냈는데 아무 일도 없다.

expand·collapse는 기본 실행이 없다.

목표 상태를 나르는 메시지(목록의 set_expanded 같은 것)를 처리기나 access_actions 재정의로 낸다. expanded를 답하지 않으면 아예 할 수 없는 명령이다.

이미 펼친 그룹에 Expand가 오면?

빈 계획이라 UIA는 S_OK로 답하고 아무것도 하지 않는다.

절대 명령은 "이미 그 상태"면 할 일이 없다. 누르기(invoke)만은 빈 계획이 거절이다.

상태 글이 바뀔 때 읽히게 하려면?

그 글을 담은 역할 있는 요소에 set_live_region(access_live::polite). 끊고 읽어야 하면 assertive.

안쪽 줄의 글이 바뀌어도 그 요소가 한 번 알린다 (live region).

임의의 글을 바로 읽히는 함수가 있나?

없다.

live region, alert 역할(토스트), 입력 칸의 error, 머리글로 초점 옮기기(focus_request)를 쓴다. 모두 다음 발행본의 대조가 알린다.

비활성 단추가 왜 눌리지 않는지 읽히게 하려면?

tooltip에 까닭을 적는다. 그것이 도움말이다.

비활성 단추도 이름과 까닭을 지닌 채 tree에 남는다. 활성이나 까닭이 바뀌면 property로 알린다.

스크린 리더가 요소로 옮겨 가면 키보드 초점도 옮겨 가나?

아니다.

보조 기술의 커서는 논리 초점을 옮기지 않는다. 클라이언트가 SetFocus를 청할 때만 옮기고, 그때는 초점 테가 보인다.

modal 대화 상자 뒤의 단추를 보조 기술로 누를 수 있나?

없다. 다만 가둠 밖이어도 포인터가 닿는 자리는 누를 수 있다.

덮이지 않은 캡션 단추가 그렇다 — 사람이 누를 수 있는 것은 보조 기술도 누를 수 있다.

자동화 script가 요소를 집는 id는?

<kind의 수>:<owner> 꼴의 AutomationId·accessibilityIdentifier다.

kind 이름이 아니라 열거 값의 수다. 그래서 라이브러리는 새 kind를 열거의 끝에 더한다.

접근 tree를 test에서 확인하려면?

make_access_snapshot으로 발행본을 떠서 역할·이름·부모를 본다. 바뀐 것은 diff_access_snapshots다.

그 두 함수가 플랫폼 다리가 쓰는 것이다 (확인하기).

실행 중에 요소의 역할과 이름을 보려면?

ui_frame::inspector에 enabled = true인 inspector_config를 싣는다.

정보 상자의 access 낱말이 역할과 이름이다. 켜는 키는 앱이 정한다.

보조 기술로 누를 때와 마우스로 누를 때 메시지 순서가 다른가?

같다.

누르기·켬끔·고르기는 access_click_event로 input thread에서 on_click 뒤에 나간다. 클릭 대상으로 상태를 잇는 앱도 같은 대상을 본다.

값을 정할 수 있는 별점을 UIA Value 패턴으로 SetValue하면?

거절된다 (E_ACCESSDENIED). 값은 RangeValue로 정한다.

글로 쓰는 Value.SetValue는 편집 칸만 받는다. 그런데 IsReadOnly는 RangeValue와 같은 답이라 거짓으로 읽힌다 (코드에서 확인한 동작).

Android에서 TalkBack이 무엇을 읽나?

luil 화면은 읽히지 않는다.

Android host에는 접근성 계층이 없다. AccessibilityNodeProvider를 쓰려면 Java 클래스가 있어야 해서 들이지 않았다 (플랫폼과 host).
