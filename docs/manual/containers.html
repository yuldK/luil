배치 요소

배치 요소는 자식에게 자리를 나눠 주는 그릇이다. 측정 단계가 없어 길이는 담는 쪽이 정하고, 접힘·폭·흘린 양·도킹 배치·페이지 위치는 모두 앱 상태다. 요소는 그 값을 받아 그리고, 바꾸자는 메시지만 낸다.

  4. 창 폭 등급으로 한 판·두 판을 고른다.

개념: 길이는 담는 쪽이, 상태는 앱이

부모가 slot을 주고 자식이 bounds를 확정한다. 측정 단계는 없고, 맞춤 자리만 자식에게 원하는 크기를 묻는다.

배치 계약과 픽셀 단위는 arrange 계약과 두 가지 픽셀이 설명한다. config의 길이는 논리 픽셀이고 요소가 배율을 곱해 물리 bounds를 만든다. stack과 grid가 남은 자리를 비율로 나누는 걸음은 비율 분배에 있다. 여기서는 쓸 때 알아야 할 세 가지만 추린다.

  • 맞춤 자리만 묻는다. add_fit, grid_track::fit, stretch가 아닌 grid 칸·layer 자식이 자식의 preferred_size를 묻는다. 배치 요소 가운데 이 질문에 답하는 것은 stack·grid·layer뿐이다. 나머지는 답하지 않아 맞춤 자리에서 0이 된다.
  • 상태는 앱이 든다. tree는 frame마다 새로 서고 게시된 뒤에는 바뀌지 않는다. 그래서 접힘·폭·흘린 양은 요소가 기억할 수 없다.
  • 메시지는 대개 변화량이다. 손잡이는 "얼마나 끌었다", 띠는 "얼마나 흘리자", 페이지는 "몇 장 넘기자"를 낸다. tree가 다시 지어져도 끌기가 이어지고, 다음 frame 앞에 여럿이 와도 잃지 않는다.

손잡이를 한 번 끌 때 지나가는 길

사용자판 사이의 손잡이를 누른 채 오른쪽으로 10 물리 픽셀 끈다 (배율 2).
input threadcontroller가 게시된 tree의 손잡이에 pointer_drag_target::on_move를 부른다. 손잡이는 10 ÷ 2 = 5 논리 픽셀로 바꾸고 grows로 부호를 맞춘다.
input thread앱이 준 resize(5)가 make_app_action(intent)로 싼 앱 메시지를 만든다. 메시지는 app inbox로 간다.
logic thread앱의 handle이 판 길이에 5를 더하고 범위로 다듬는다.
logic thread다음 make_frame()이 새 길이로 stack을 처음부터 다시 짓는다. 손잡이도 새 경계에 선다.
input · UI손잡이는 포인터를 따라 옮겨 가도 끌기가 이어진다(follows_pointer). 손을 떼면 finish()가 한 번 온다.

factory는 어디서 불리느냐가 갈린다. 포인터·키·터치·휠이 부르는 factory는 input thread에서 돈다. 보조 기술의 실행(UIA의 Expand·Collapse·Invoke)은 UI thread에서 액션을 짓는다 — Windows는 UIA 호출을 창 thread로 모은다. 그래서 factory는 앱 상태를 참조로 잡지 말고 필요한 값을 복사해 잡는다. 예외가 하나 있다. dock_config::content는 dock_element의 생성자가 부르므로 tree를 짓는 logic thread에서 돈다. 스레드 사이의 다리는 스레드 모델이 설명한다.

넘친 자식은 그려지고 눌린다자르지 않는 요소는 hit test에서도 자식 탐색을 자기 bounds로 막지 않는다. stack에서 넘친 단추는 옆 판 위에 그려지고 거기서 눌린다. 자르는 요소(strip·pager·dock)는 bounds 밖의 자식을 그리지도 누르지도 않고, 끌어 놓을 대상으로도 찾지 않는다. 요소마다의 지도는 컨테이너 지도에 있다.

id

  • stack·wrap·grid·layer·strip·panel·split_handle·pager는 생성자에서 id를 받는다.
  • group·sidebar·root·dock은 config의 owner로 kind와 짝을 지어 스스로 id를 짓는다. 그룹은 { group, owner }와 제목 줄 { group_header, owner }, 사이드바는 판·토글·손잡이 셋이다. 같은 owner를 둘에 주면 id가 겹친다.
  • dock 안의 탭 하나는 { tab, 패널 key }다 — dock의 owner가 붙지 않는다. dock 둘, 또는 dock과 다른 탭 막대가 같은 패널 key를 쓰면 탭 id가 겹친다.
  • 빈 id ui_element_id {}도 중복으로 센다. 겹친 id는 첫 것이 이기고 뒤의 것은 ui_tree::duplicate_ids()에 남는다. duplicate_ids()와 unarranged()가 빈 tree만 게시하는 것이 계약이다.

만들기: 쌓기와 줄바꿈

stack 하나로 대부분의 화면이 선다. 같은 크기 항목이 줄을 넘기면 wrap, 가로로 넘쳐 흘려야 하면 strip이다.

화면 뼈대: stack 안의 stack

  1. 여백 16, 간격 12인 세로 stack이 화면 전체를 받는다.
  2. 머리 줄과 이력 줄은 add_fit으로 담는다. 버튼 글과 라벨 폭이 언어·글꼴에 따라 바뀌어도 손으로 고칠 길이가 없다.
  3. 가로 stack의 저장소 판은 { .weight = 1, .minimum = 200, .maximum = 300 }이다. 창이 넓어지면 300에서 멈춘다.
  4. 상한이 남긴 폭은 아직 걸리지 않은 유연 항목(detail, 비율 3)이 갖는다. detail 안의 두 판은 하한 120·160을 지킨다.
  5. 양식은 grid_element라서 grid가 원하는 높이를 답한다.

결과는 test가 잠근다: 창 폭 1600에서 저장소 판이 300, 700에서 200이다. 같은 화면의 tree에는 중복 id도 미배치 element도 없다. 유연 항목이 하한·상한을 지키며 나누는 걸음은 stack 실험장에서 직접 돌려 볼 수 있다.

도구 막대: 맞춤 항목·유연 간격·겹친 배지

  • 가로 stack에 cross_alignment = center를 주면 맞춤 항목이 원하는 높이로 줄 가운데에 선다.
  • add_flexible_gap()이 제목과 단추 무리 사이를 벌린다. 바깥에 남는 자리를 두는 것은 main_alignment, 항목 사이를 벌리는 것은 gap이다. 그래서 stack_main_alignment에는 space_between이 없다.
  • 배지는 layer_element에 단추 다음으로 담아 위에 그려지고 먼저 눌린다. margin = { 0.0f, -8.0f, -8.0f, 0.0f }는 edge_insets의 위치 순서 (left, top, right, bottom)로 읽혀 위로 8, 오른쪽으로 8 바깥이다. layer는 자르지 않으므로 바깥으로 나간 배지도 그려진다.

같은 크기 타일 줄바꿈 (wrap)

항목 크기는 항목마다가 아니라 컨테이너에 한 번 적는다. 그래서 줄 수가 폭에서 나오는 산수가 되고, wrap_height_for(config, 폭, 개수)가 tree를 짓기 전에 높이를 답한다. arrange도 같은 wrap_columns_for로 열을 세므로 둘이 어긋나지 않는다. 폭 인자는 wrap이 실제로 받을 논리 폭이어야 한다 — 예제는 페이지 여백을 뺀다. 칩을 세로로 흘리려면 wrap을 scroll_view_element의 내용으로 두고 같은 높이를 내용 높이로 넘긴다.

가로로 흐르는 띠 (strip)

가장 완전한 예는 휴대폰 데모의 별 열이다. 핸들(handle), 한계 계산(frame), strip 조립 순서로 읽는다.

  • content_width는 담는 쪽이 알려 준다. 측정 단계가 없기 때문이다.
  • scroll을 주면 넘칠 때 띠가 가로 흘림의 임자가 된다. 그러면 터치 끌기·휠·초점 되살리기가 이 메시지로 띠를 흘린다. 없으면 아무도 흘리지 않는다.
  • arrange는 화면에 쓸 값만 다듬는다. 앱 상태는 앱이 다듬는다. 예제는 frame에서 한계(content − viewport)를 적고 handle에서 std::clamp한다. 같은 식이 clamp_scroll이다.

데스크톱 데모의 단추 띠는 내용이 가로 stack이다. 내용 폭을 단추 폭과 간격의 합으로 센다.

만들기: 폼과 겹치기

칸이 행·열로 맞아야 하면 grid, 한 자리에 둘 이상이 서면 layer다. panel은 바탕을, group은 접힘을, root는 창 전체를 맡는다.

폼: 라벨 열은 맞춤, 입력 열은 유연

  1. 열은 { fit(), flexible() }이다. 라벨 열이 가장 긴 라벨 폭이 되고, 입력 열이 나머지를 갖는다.
  2. 행은 { fit(28), fixed(author_height), fit(28) }이다. 맞춤 행의 하한 28이 입력 칸이 서는 높이를 지킨다. 작성자 줄은 검증 글이 서면 48로 늘린다.
  3. 라벨은 vertical = center로 칸 가운데에 원하는 높이로 선다. 입력은 기본 stretch라 칸을 채운다.
  4. 작성자 칸은 편집형 콤보다. grid는 칸이 무엇이든 같은 규칙으로 놓는다.
  5. 담는 순서가 곧 Tab 순서다. 행 순서대로 담는다.

grid는 열 폭을 먼저, 행 높이를 나중에 정한다. 맞춤 행의 높이는 자식이 자기 칸 폭에서 원하는 높이라, 여러 줄 글이 열 폭에서 접힌 높이가 된다. 맞춤 줄은 그 줄 하나에만 놓인 자식만 잰다 — 두 열에 걸친 자식은 맞춤 열을 넓히지 않고 줄들이 정한 자리를 받는다. 선언보다 뒤의 칸에 놓은 자식이 있으면 모자란 줄은 맞춤 줄이다. 결과는 test가 잠근다: 고정 폭 가짜 측정기(UTF-8 바이트 하나 = 글꼴 크기의 절반)로 가장 긴 라벨 "마지막 커밋"(16바이트)의 열이 96, 첫 행이 28이다.

겹치기: 본문 위의 판, 화면 전체 오버레이

처음 배치와 앱 상태다. apply_dock_command 세 번으로 분할 둘과 떠 있는 패널 하나를 만든다.

element를 짓는다. change는 명령을 그대로 앱 메시지로 싸고, content는 고른 패널의 내용을 짓는다. handle은 한 줄이다.

  • dock-2 — 분할, 좌우 (root 자리)
    • dock-4 — 분할, 위아래

패널 닫기, 떠 있는 패널 앞으로·옮기기

dock_operation에는 닫기가 없고, 빈 그룹·한쪽만 남은 분할을 치우는 정리 함수는 공개되지 않았다. 떼어 띄우기(detach)가 원래 자리를 치운 뒤 그 패널만 든 떠 있는 그룹을 맨 뒤에 붙이므로, 그 그룹을 지우면 닫기가 된다. raise·reposition은 dock_element가 내지 않는 명령이라 앱이 자기 단추나 제목 줄에 잇는다.

위 닫기 함수를 src/ui/dock_layout.cpp와 함께 짓고 처음 배치에 돌려 보았다. close_dock_panel(layout, u8"inspector")는 참이고, 한쪽만 남은 분할 dock-2가 사라져 dock-4가 root가 되며, 결과는 valid_dock_layout을 통과한다. raise·reposition의 target은 떠 있는 그룹의 맨 위 node key다 — 떠 있는 자리에 분할이 생겼으면 그 분할의 key다.

넘기는 페이지 (pager)

  • offset은 페이지 단위다. 1.25면 둘째 장에서 다음 장으로 1/4 넘긴 자리다. 끄는 동안은 offset이 움직이고, 손을 떼면 정착한 값이 온다. apply_pager_command 하나가 네 갈래(끌기·걸음·정착·고르기)를 모두 적용한다.
  • 정착은 round(지금 + clamp(속도 × 0.18초, −1, 1))이다. 빠르게 튕기면 0.2만 넘겨도 다음 장이고, 아무리 빨라도 한 장까지다. 정착은 곧바로 서고, 부드러운 애니메이션은 앱이 붙인다.
  • count는 앱이 지은 장 수와 같아야 한다. 예제는 3을 handle과 장을 짓는 곳에 따로 적는다. element는 자기 자식 수로 다듬지만 앱 상태는 count로 다듬어진다.
  • 이전·다음 단추는 앱이 pager_command { .operation = step, .delta = ±1 }을 같은 메시지 길로 보낸다. 장 표시 점은 라이브러리에 없다 — 앱이 offset으로 그린다.

배치 요소의 코드에는 플랫폼 분기가 없다. 배치 결과는 어디서나 같고, 차이는 입력 장치와 검증 범위에서 난다.

몸짓·장치배치 요소에서
손가락으로 가로 쓸기strip·pager가 흐른다(scroll·change가 있을 때). 손가락이 움직인 축의 창만 흐른다. 400ms 안에 축 방향으로 12 논리 픽셀을 넘겨야 흘리기가 된다
손을 뗌pager는 정착(settle) 한 번, strip은 관성으로 이어 흐르다 끝에서 멈춘다
나눔 손잡이를 누름 (터치)누르는 즉시 끌기다. 감싼 창의 스크롤 후보가 아니다 — 사이드바·dock 손잡이도 같다
마우스로 끌기pager·strip은 마우스 끌기로 흐르지 않는다. 흘리는 pan 판정은 터치에만 있다. 마우스는 휠·키보드·앱의 단추로 넘긴다
hover손잡이는 hover·누름 동안만 강조 선을 긋는다. 터치 화면에서 쉬는 손잡이가 보이려면 resting_divider를 켠다
커서손잡이는 좌우·위아래 크기 조절 커서를 단다. 포인터가 없는 터치 화면에서는 뜻이 없다
  • dock·pager는 Windows에서만 돌려 보았다. 두 요소의 소스는 모든 플랫폼의 공용 core에 들지만, 예제 luil_selected_nodes는 Windows 실행 파일이고 test도 Windows 전용 묶음에만 있다. Android·macOS·iOS에서 돌려 본 기록은 없다.
  • 창 폭 등급은 host가 논리 폭으로 매긴다. Android의 창 크기는 시스템 막대·컷아웃을 뺀 안전 영역이다. 휴대폰 데모는 Windows에서도 세워 창 폭으로 두 꼴을 본다.
  • 시스템이 상태 표시줄을 그리는 플랫폼에서는 caption_element가 자리를 차지하지 않는다. 휴대폰 데모는 current_ui_platform().window_caption으로 caption을 넣을지 고른다.
  • dock에서 떼어 낸 패널은 같은 표면 안에 떠서 dock 자리로 잘린다. 놓은 자리의 화면 좌표(drag_release::screen)는 그것을 모르는 플랫폼에서 비어 있다.
  • 접근성 다리: Windows(UIA)와 macOS(AX)는 역할을 플랫폼 이름으로 옮긴다. Android 쪽에는 access_role을 옮기는 코드가 이 저장소에 없어 보조 기술 동작을 코드에서 확인할 수 없다.
  • 배율: 끌기 변화량은 물리 이동 ÷ 배율이라 배율 1·1.25·2에서 같은 논리 값이다. strip의 최대치도 논리 픽셀이라 배율과 무관하다.

함정

오류 없이 조용히 틀리는 자리들이다. "코드에서 확인한 동작"은 test가 잠그지 않은 것을 소스로 따라간 결론이다.

  1. 자르지 않는 그릇은 넘친 자식을 그리고 누른다. stack·wrap·grid·layer·panel·group·sidebar에서 넘친 단추는 옆 판 위에서 눌린다. 잘라야 하면 strip이나 세로 스크롤 창에 담는다.
  2. 유연 하한의 부족분은 다른 유연 항목의 몫에서 나온다. 하한들의 합이 남은 자리를 넘을 때만 stack·grid가 넘친다. 고정 길이는 다시 흥정하지 않는다. (설계 문서의 불변식 한 줄은 아직 "재분배하지 않고 넘친다"는 옛 규칙을 적고 있다. 코드와 test가 정본이다.)
  3. 주축 정렬은 유연 항목이 모두 상한에 서도 뜻을 갖는다. 헤더 주석은 "유연 항목이 하나라도 있으면 정렬이 뜻이 없다"고 쓰지만, 코드는 모두 상한에 섰을 때 남는 자리를 main_alignment대로 둔다.
  4. stack_item { .weight = 0 }은 길이 0의 고정 항목이다. 구조체로 담으면 다듬지 않는다. 0 이하를 1로 고치는 것은 add_flexible뿐이다. 그리고 fit은 weight·length를 이긴다.
  5. 맞춤 자리에 넣은 panel·wrap·strip·group·sidebar·pager·dock은 길이 0이다. 원하는 크기에 답하는 배치 요소는 stack·grid·layer뿐이다. 길이를 직접 주거나 height_for·width_for·wrap_height_for를 쓴다.
  6. 맞춤으로 담은 grid의 높이는 열을 "제한 없는 폭"으로 잰 값이다. grid의 원하는 크기는 받은 폭을 버리고 유연 열까지 맞춤처럼 잰다. 폭에 따라 줄이 접히는 내용을 유연 열에 두고 add_fit하면 잡힌 높이가 모자랄 수 있다 (코드에서 확인한 동작). 한 줄 입력만 든 폼은 영향이 없다.
  7. grid의 맞춤 열은 자식에게 무한대 폭을 묻는다. 여러 줄로 접히는 긴 글을 맞춤 열에 두면 그 열이 한 줄 폭만큼 넓어진다. grid_track {}는 맞춤 줄이고, grid에는 상한 필드가 없다.
  8. root_element를 make_arranged_tree에 넣으면 자식이 배치되지 않는다. root는 자기 bounds만 정한다. 빠뜨린 배치는 unarranged()가 잡는다.
  9. stack·wrap·root·panel·strip에 nullptr를 넘기지 않는다. 이 다섯은 null을 거르지 않고, tree 색인과 그리기가 자식을 역참조한다. grid·layer·pager는 거른다. group·sidebar의 내용 인자와 dock의 content는 nullptr여도 된다.
  10. panel의 둥근 모서리는 내용을 자르지 않는다. 가장자리까지 칠하는 내용은 모서리 밖을 덮는다. 테두리는 내용 뒤에 그어 남는다.
  11. 그룹은 slot 높이를 무시한다. bounds 높이가 height_for(config)라 stack 칸 길이를 다르게 주면 칸과 어긋난다. content_height를 빠뜨리면 내용 칸이 0이다. 그룹은 여백을 두지 않으므로 내용 stack의 padding으로 준다.
  12. 토글만 준 그룹은 보조 기술로 접고 펼 수 없다. Expand·Collapse는 set_collapsed만 탄다.
  13. 같은 owner의 그룹·사이드바 둘, 빈 id ui_element_id {}의 반복은 id가 겹친다. 첫 것이 이겨 hover·초점·보조 기술이 엉뚱한 쪽에 간다. duplicate_ids()로 확인한다.
  14. dock 탭 id에는 owner가 없다. dock 둘이나 dock과 다른 탭 막대가 같은 패널 key를 쓰면 탭 id가 겹친다.
  15. 잘못된 dock_layout은 아무것도 그리지 않는다. 오류도 내지 않는다. 손으로 고친 layout은 valid_dock_layout으로 확인한다.
  16. layout.root.key는 가장자리 놓기 뒤에 바뀐다. 처음 배치 뒤 root key는 dock-2다. "root"를 박아 두지 않는다.
  17. dock 분할은 최소 판을 표시에서만 지킨다. 상태의 ratio는 0.05~0.95로만 묶인다. 손잡이를 최소 판 너머로 끈 뒤 되돌리면 비율이 표시 범위로 돌아올 때까지 손잡이가 움직이지 않는다 (코드에서 확인한 동작).
  18. dock 분할 손잡이에는 끝 알림이 없다. resize 명령마다 ratio가 바뀐다. "놓을 때 한 번 저장"하는 길이 dock에는 없으니 저장 시점은 앱이 정한다.
  19. 떠 있는 dock 패널은 자리 밖으로 나가지 않지만 상태는 나간 채 남는다. 표시만 dock 자리 안으로 다듬는다. 떼어 낸 자리는 언제나 360×240이다.
  20. strip은 화면만 다듬는다. 앱이 다듬지 않으면 끝을 넘은 값이 상태에 쌓인다. frame과 handle에서 같은 clamp_scroll을 쓴다.
  21. 앱 정책을 둔 앱은 strip의 휠과 초점 되살리기를 직접 잇는다. 기본 on_wheel·on_focus_moved는 빈 목록이다. 몸통에서 route_wheel·route_reveal을 부른다. pager처럼 step이 있는 창의 휠은 정책보다 먼저 받는다.
  22. strip 안에 걸쳐 둔 손잡이는 바깥 절반이 hit되지 않는다. 걸치기는 부모가 자르지 않을 때만 선다. 자르는 그릇 안에서는 판 사이의 한 칸으로 담는다.
  23. 사이드바 손잡이의 바깥 절반은 뒤에 담은 형제가 가져갈 수 있다. hit test는 뒤의 형제부터 본다. 내용 판이 그 자리에서 누를 수 있는 것을 가지면 그것이 이긴다 (코드에서 확인한 동작).
  24. 사이드바는 접혀도 받은 내용을 버리지 않는다. 접힌 폭이 0보다 크면 내용을 접힌 폭(기본 48)에 배치한다. 접힌 동안은 내용 대신 nullptr를 넘긴다. toggle_tooltip이 비면 토글은 접근 이름도 역할도 없다.
  25. split_handle_element는 resize 없이는 아무것도 아니다. 끌기·커서·Tab 자리·키가 모두 없다. finish는 손잡이가 사라졌거나 가려진 뒤의 뗌에는 오지 않으니 저장을 그것에만 걸면 한 번을 놓칠 수 있다.
  26. pager의 장은 전부 tree에 있고 전부 Tab 순서에 든다. 초점이 옆 장으로 가도 넘어가지 않는다 — pager는 되살리기에 답하지 않는다 (코드에서 확인한 동작). 막으려면 지금 장이 아닌 장 안의 초점 받는 요소마다 set_enabled(false)를 준다. 자리 판정은 그 요소 자신의 상태만 보고 조상을 보지 않는다.
  27. pager의 count는 앱이 맞춘다. 지은 장 수와 다르면 상태와 화면이 어긋난다. pager의 키는 pager 자신에 초점이 있을 때만이다 — 장 안의 단추에 초점이 있으면 ←/→는 pager로 가지 않는다.
  28. wrap에 크기가 다른 자식을 넣어도 모두 같은 칸을 받는다. wrap_height_for에 준 폭이 실제 slot 폭과 다르면 마지막 줄이 넘친다.
  29. visible(false)는 자리를 비우지 않는다. 자리까지 빼려면 그 frame에서 담지 않는다.
  30. edge_insets의 위치 초기화는 (left, top, right, bottom)이다. CSS의 (top, right, bottom, left)와 다르다. 헷갈리면 .left = 지정 초기화나 symmetric을 쓴다.
  31. 창 폭 등급은 delegate의 넓은 훅에서만 온다. 기본 make_metrics_message는 세 값짜리 훅으로 넘겨 등급을 버린다. classify_window_width는 +∞를 expanded로 본다 (헤더 주석은 "유한하지 않으면 compact"라 쓰지만 코드와 test는 숫자가 아닌 값과 −∞만 compact다).
  32. factory는 어느 thread에서 불릴지 모른다. 포인터·키는 input thread, 보조 기술은 UI thread다. 앱 상태를 참조로 잡지 않는다. 생성자에서 불리는 dock의 content만 logic thread다.

자주 묻는 질문

사이드바가 접혔는지는 누가 들고 있나?

앱이다. sidebar_config::collapsed로 받아 그리고 toggle만 낸다.

전환 중의 지금 폭은 width에 따로 싣는다. collapsed는 목표, width는 지금이다 (사이드바).

나눔 손잡이로 바꾼 폭은 어디에 저장되나?

손잡이는 길이를 담지 않는다. 앱이 resize(delta)를 더하고 finish()가 올 때 저장한다.

뗄 때 한 번, 키는 걸음마다 한 번 온다. 손잡이가 사라졌거나 가려진 뒤의 뗌에는 오지 않는다 (좌우로 나눈 두 판).

오른쪽 판의 폭을 손잡이로 바꾸는데 반대로 움직인다.

grows = toward_start로 둔다.

요소가 부호를 맞춰 "+ = 그 판이 넓어짐"이 된다. 사이드바는 side에 따라 스스로 고른다.

손잡이를 키보드로 옮기면 몇 픽셀인가? Home/End는?

화살표 8, Page 64 논리 픽셀이다. Home/End는 답하지 않고 앱으로 흐른다.

손잡이는 자기 범위를 몰라 "끝"에 답할 값이 없다. 키 한 번이 곧 한 번의 바꾸기라 finish()가 바로 뒤따른다.

폼의 라벨 열을 가장 긴 라벨에 맞추려면?

grid_config::columns = { grid_track::fit(), grid_track::flexible() }.

라벨 열이 그 열 하나에만 놓인 라벨들의 원하는 폭 중 가장 큰 것이 된다. 언어가 바뀌어도 고칠 폭이 없다. arrange 뒤에는 column_widths()로 읽을 수 있다 (폼).

그림 위 오른쪽 위 모서리에 배지를 띄우려면?

layer_element에 그림, 배지 순서로 담고 배지에 { .horizontal = end, .vertical = start }를 준다.

바깥으로 빼려면 음수 margin을 준다 — { 0.0f, -8.0f, -8.0f, 0.0f }는 (left, top, right, bottom) 순서라 위·오른쪽으로 8 나간다 (도구 막대).

접힌 그룹의 내용은 눌리지 않나?

접히면 내용이 tree에 아예 없다.

그리지도, 누르지도, 보조 기술이 읽지도 않는다. 그룹 높이는 height_for(config)로 stack 칸에 쓴다 (접이식 섹션).

가로로 넘치는 단추 줄을 손가락으로 쓸어 흘리려면?

strip_element에 content_width와 scroll을 준다.

넘칠 때만 가로 흘림의 임자가 된다. 흘린 양은 앱이 들고 clamp_scroll로 다듬는다 (가로로 흐르는 띠).

strip 위에서 마우스 휠이 안 먹는다.

앱 정책이 있으면 on_wheel이 휠을 받는데 기본은 빈 목록이다.

몸통에서 route_wheel(tree, event, scroll_delta)를 부른다. 세로 휠은 축을 묻지 않아 가로 띠도 흘린다. 정책이 없으면 controller가 바로 표 없는 길을 탄다.

pager의 offset 단위는? 1.5는 무엇인가?

페이지다. 1.5는 둘째 장에서 셋째 장으로 반쯤 넘긴 자리다.

장 i의 자리는 x + (i − offset) × 폭이다. 모든 장이 배치되고 pager가 자른다.

손을 떼면 어느 장에 서나?

round(지금 + clamp(속도 × 0.18초, −1, 1))이다.

빠르게 튕기면 0.2만 넘겨도 다음 장이고, 아무리 빨라도 한 장까지다. 정착은 곧바로 서고 애니메이션은 앱이 붙인다.

pager를 마우스로 끌어 넘길 수 있나?

없다. 터치 끌기·휠(한 눈금에 한 장)·키보드·앱의 단추로 넘긴다.

pager는 끌기 대상을 두지 않고, 흘리는 pan 판정은 터치에만 있다.

dock 배치를 저장했다가 되살리려면?

dock_layout은 값이라 앱이 그대로 직렬화한다. 직렬화 함수는 라이브러리에 없다.

되살린 값은 valid_dock_layout으로 확인한다. 잘못이면 dock이 아무것도 짓지 않는다.

dock 패널을 닫는 명령이 있나?

없다. detach 뒤 생긴 떠 있는 그룹을 지우면 정리까지 공개 API로 된다.

패널 닫기의 close_dock_panel이 그 꼴이다.

dock 탭을 창 밖으로 끌어 새 OS 창을 띄우려면?

detach 명령의 release(화면 좌표·outside)를 읽어 앱이 보조 창을 연다.

기본 helper는 같은 표면에 띄운다 — OS 창을 만들지 않는다. 다중 창 경로는 창과 셸 통합에 있다.

dock의 판 내용은 언제 지어지나?

dock_element 생성자에서, 그룹마다 고른 패널 하나만, logic thread에서다.

고르지 않은 탭의 내용은 tree에 없다. 편집 중인 초안은 factory 밖 앱 상태에 둔다.

dock 분할 비율을 끌기가 끝났을 때 저장하려면?

그런 메시지가 없다. 분할 손잡이에는 끝 알림이 달리지 않아 resize 명령만 온다.

저장 시점은 앱이 정한다 (예: 종료 처리).

좁은 창은 한 판, 넓은 창은 두 판으로 하려면?

window_metrics::width_class != compact로 가른다 (경계 600).

다른 경계는 classify_window_width(폭 ÷ 배율, { .medium = …, .expanded = … })로 다시 매긴다 (등급 경계 바꾸기).

root_element와 stack 중 무엇을 뿌리로 쓰나?

가지를 따로 배치해 겹치지 않게 쌓는다면 root, 그릇 하나가 전부 배치하면 stack이다.

root는 가지마다 arrange해 담고 ui_tree 생성자로 감싼다. stack 뿌리는 make_arranged_tree 한 줄이다.

숨긴 자식이 자리를 차지한다. 빼려면?

visible(false)는 그리기와 hit만 끈다. 그 frame에서 담지 않는다.

같은 크기 칩을 여러 줄로 놓고 높이를 미리 알려면?

wrap_height_for(config, 폭, 개수)다.

arrange와 같은 열 계산이라 담는 칸 길이에 그대로 쓴다 (줄바꿈의 실습에서 돌려 볼 수 있다).

stack 칸이 모자랄 때 하한을 준 항목은 넘치나?

다른 유연 항목의 몫을 먼저 줄인다. 하한들의 합이 자리를 넘을 때만 넘친다.

폭 300에 { weight 1, minimum 160 }과 { weight 1 }이면 160/140이다. 걸음은 비율 분배에 있다.
