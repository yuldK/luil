움직임은 앱이 든 값이고, 그 값은 시각만의 함수다. 라이브러리에는 시계가 없다. "이 시각에 다시 물어라"만 답한다. 시간은 logic thread와 UI thread의 두 시계가 흘린다.

이 문서를 읽으면

  1. 움직임 값이 element가 아니라 앱 상태인 이유를 설명한다.
  2. "시각만의 함수"가 frame 건너뛰기와 늦은 timer에 강한 이유를 안다.
  3. 감쇠 조화 진동자의 닫힌 해와 response·ζ·허용치의 뜻을 말할 수 있다.
  4. spring_to와 spring_release의 차이, 끝이 한 번만 오는 이유를 안다.
  5. 화면 전환에서 두 시계가 나누는 일과 덮개가 입력을 막는 기간을 예측한다.

움직임의 세 질문

UI가 움직이면 세 가지를 풀어야 한다. 값이 시간에 따라 어떤 곡선을 그리는가. 그 시간을 누가 흘려 화면을 다시 그리게 하는가. 사람이 움직임을 원하지 않으면 어떻게 멈추는가.

① 움직임 값은 앱 상태다

"element는 전환의 소유자가 아니다." 앱이 값을 들고 지금 값을 물어 element config에 넣는다. 접힘·선택·스크롤 값이 앱 상태인 것과 같은 규칙이다. 사이드바의 collapsed는 목표, width는 지금 이 순간의 폭이고, 중간 폭은 전환하는 앱만 안다.

② 시각만의 함수다

시각 하나를 넣으면 값이 정해지고 그 사이 상태가 없다. 어느 frame에 물어도 같고, frame을 건너뛰어도 어긋나지 않으며, test가 시각을 손으로 정할 수 있다. Win32는 16ms 뒤 예고에 여유 15ms를 더해 31ms마다 그리지만, 늦게 깬 frame도 그 시각의 값을 그린다.

③ 시간은 두 시계가 흘린다

"라이브러리는 시계도 frame 루프도 갖지 않으므로 '이만큼 뒤에 다시 물어라'만 답한다." 배치를 바꾸는 움직임은 logic thread가 next_tick으로 깨어 tree를 다시 짓는다. 그림만 바뀌는 움직임은 UI thread가 next_update로 같은 tree를 다시 그린다.

길이 곡선과 연타의 멈칫

가장 단순한 움직임은 길이를 정한 곡선이다. 기본 140ms, 2차식 ease_in_out. 그런데 도는 중에 목표를 바꾸면 값은 이어지지만 속도는 이어지지 않는다.

transition은 { from, to, started, duration } 네 칸짜리 값이다. 길이가 0이면 언제 물어도 to다. 곡선이 2차식인 까닭을 주석이 적었다. "3차 이상이 더 부드럽지만 눈으로 갈리지 않고, 식이 짧아야 test가 손으로 검산할 수 있다."

transition_to는 도는 중이면 지금 값에서 새로 출발한다. 끝값으로 튀지는 않는다. 하지만 ease_in_out의 시작 기울기가 0이라서, 움직이던 값이 멈칫했다가 다시 출발한다. 사이드바 접힘을 연타하면 이것이 보였다. 스프링 설계의 출발점이 이 문제다.

  1. 앞 절반은 2t², 뒤 절반은 그 거울이다. t = 0에서 기울기가 0이다.
  2. 경과를 정수 밀리초로 잘라 길이로 나눈다. 스프링과 화면 전환 진행은 자르지 않는다는 점이 다르다.
  3. 새 전환의 from은 지금 값이다. 속도를 담을 칸은 없다.

spring_to smooth
사이드바 폭(44 ↔ 200)을 두 방식으로 움직인다. 세 번 연타를 눌러 보라. 길이 곡선은 목표가 바뀔 때마다 기울기 0에서 다시 출발해 그래프에 모서리가 생긴다. 스프링은 속도를 이어받아 매끄럽다. 그래프는 앞날까지 미리 그려져 있다 — 시각만의 함수이므로 아직 오지 않은 시각도 물을 수 있다. 그래프 위를 가리키면 그 시각의 값과 속도가 나온다.

스프링: 손잡이 둘과 허용치 하나

스프링의 성질은 "얼마나 빠르게"(response)와 "얼마나 튕기게"(damping_fraction), 그리고 끝 허용치 하나뿐이다. 값 자체는 다섯 칸짜리 평범한 값이라 앱이 들고 다닌다.

y″ + 2ζω·y′ + ω²·y = 0  ·  y = 값 − to  ·  ω = 2π / response  ·  ζ = damping_fraction

위 그래프는 값, 아래 그래프는 끝 판정의 척도 s = √(y² + (y′/ω)²)를 로그 눈금으로 그린 것이다. 값 |y|는 ζ < 1이면 목표를 지나며 0이 되지만, 그 순간은 끝이 아니다. 속도가 크기 때문이다. s는 줄기만 하므로 허용치 선을 한 번만 건넌다. 주황 점선이 spring_rest_time(16ms 격자 위의 첫 끝)이다.
  1. 감쇠가 없을 때 한 번 진동하는 시간이다. 지속 시간이 아니다 — smooth(350ms)도 100px을 옮기면 약 0.67초 돈다. 0 이하면 전환이 없다.
  2. 1이면 넘치지 않고 가장 빨리 선다(임계 감쇠). 작을수록 목표를 넘었다 돌아온다. 폭처럼 배치에 닿는 값은 1 이상이어야 이웃이 따라 흔들리지 않는다.
  3. 기본 0.01은 논리 픽셀에 맞췄다. 불투명도·배율처럼 0~1 값은 0.001쯤으로 낮춘다. 화면 전환은 알아서 낮춘다(화면 전환).
  4. SwiftUI의 response·dampingFraction 어휘를 빌렸다. (질량, 강성, 감쇠) 셋은 서로 영향을 줘 시간 감각을 잡기 어려워 변환 함수 spring_from_physics로만 연다.
  5. from, to, 시작 시각, config, 출발 속도. 단계 적분의 상태가 없으니 이것으로 충분하다. 속도는 값의 단위/초, 값이 커지는 쪽이 양수다.

닫힌 해, 그리고 끝은 한 번만 온다

미분방정식을 frame마다 한 걸음씩 적분하지 않는다. 시각 t를 넣으면 값과 속도가 바로 나오는 해를 쓴다. 단계 적분은 상태가 있어서 frame을 건너뛰면 값이 달라지기 때문이다.

  1. 인자는 시작부터 흐른 초(double, 밀리초로 자르지 않음) 하나뿐이다. ω는 response에서, 출발 조건은 y0 = from − to와 v0 = velocity에서 온다.
  2. |ζ − 1| < 1e-6이면 y = e^(−ωt)·(y0 + (v0 + ω·y0)·t)다. 띠를 둔 까닭: 두 쪽 식이 나눗셈에서 불안정해지는 띠이고, 띠 안의 오차는 띠의 폭과 같은 비율이다.
  3. 감쇠하는 진동이다. ω_d = ω·√(1 − ζ²)로 돌며 e^(−ζωt)로 줄어든다. ζ 0.5의 첫 마루는 이동 거리의 약 16.3%다.
  4. 두 지수의 합이다. 느린 뿌리를 −ω / (ζ + √(ζ²−1))로 구한다. ζ − √(ζ²−1)을 그대로 빼면 큰 ζ에서 두 수가 같아져 0으로 뭉개진다.
  5. 끝은 hypot(y, y′/ω) ≤ 허용치다. 에너지 E = ½(y′² + ω²y²)는 dE/dt = −2ζω·y′² ≤ 0이라 줄기만 하고, 척도의 제곱은 E에 비례한다. 그래서 한 번 끝난 스프링은 다시 움직이지 않는다.

이 페이지의 이식본이 계산했다. 이식본은 컴파일한 spring.h와 무작위 6,000건에서 같은 값을 냈다(float 정밀도 안). 시험은 smooth 660~690ms, snappy 600~620ms, bouncy 1500~1540ms를 요구한다.



왜 두 허용치(값·속도)가 아닌가

값과 속도에 허용치를 따로 두면 "상자 모서리"에서 끝났다가 다시 나가는 일이 생긴다. 이동 거리에 비례하는 허용치는 같은 값에서 속도만 주는 놓기(from == to)에서 0이 된다. 한 척도 s는 둘 다 피한다. 속도 허용치는 따로 없고 ω·허용치로 따라온다.

재목표와 놓기

도는 중에 목표만 바꾸는 것(spring_to)과 손을 뗀 값·속도에서 새로 출발하는 것(spring_release)은 다른 함수다. 이어받은 속도에 더하는지 덮는지 헷갈리지 않게 하려는 것이다.

시간은 누가 흘리나: 두 시계

라이브러리가 시간에 대해 아는 것은 기본 길이 140ms, 다시 물어볼 간격 16ms, 움직임 줄이기면 길이를 0으로 접는 함수 하나뿐이다. 실제로 깨어나는 것은 앱의 두 시계다.

logic thread의 시계 — 앱 상태의 시간. app_host::logic_loop가 frame을 게시한 뒤 next_tick()을 묻는다. 예고 시각이 되면 메시지가 없어도 tick(now)를 부르고 frame을 다시 게시한다. "답이 없으면 시간 경로는 완전히 잠잔다."

UI thread의 시계 — 그림의 시간. 그릴 때 draw_context::now를 채우고, 그린 뒤 보이는 element들의 next_update를 모아 가장 이른 시각에 timer 하나를 건다(그리기와 렌더러). 헤더가 둘을 한 줄로 가른다. "그쪽은 그림만 다시 그리고 이쪽은 logic 상태가 실제로 바뀐다."

logic thread가 깨어 tree를 짓는다 UI thread가 그린다 덮개가 포인터를 막는 동안
위는 사이드바 폭 스프링(200 → 44, smooth), 아래는 화면 전환이다. 사이드바 폭은 배치를 바꾸므로 logic thread가 16ms마다 깨어 tree를 다시 짓는다. 화면 전환은 앱이 시작과 끝에만 깬다. 도는 동안은 UI thread가 같은 tree를 now만 바꿔 다시 그린다. 막대 위를 가리키면 그 사건의 시각이 나온다.
  1. 시간이 지나야 바뀌는 것(토스트 만료, 사이드바 스프링, 페이지 전환)의 예고 가운데 가장 이른 것을 답한다. 모두 nullopt면 logic thread가 잠든다.
  2. 스프링 예고는 "지금"이 아니라 마지막으로 지은 frame의 시각(frame_time_)에서 센다. 지금 시각에서 세면 그 사이에 끝난 스프링이 "도는 중" 표시를 남긴 채 잠든다. 페이지 전환은 끝 시각 하나만 싣는다.
  3. 끝 시각에 깨어난 tick이 prior를 놓는다. 다음 frame은 prior 없는 tree라서 덮개가 걷히고 포인터가 풀린다.

화면 전환: 떠나는 화면은 tree 밖에 있다

앱은 떠나는 화면을 따로 지어 배치한 tree(prior)로 한 번 넘긴다. 전환 요소는 시각만으로 두 화면을 겹쳐 그리고, prior가 있는 동안 칠하지 않는 덮개로 포인터를 막는다.

이전 화면을 같은 tree에 넣으면 id가 겹치고 두 화면이 함께 눌리고 읽힌다. hit test, 놓을 자리, 초점 테, UIA 좌표가 모두 배치한 bounds()를 읽기 때문이다. 그래서 prior는 shared_ptr<const ui_tree>로 따로 든다. 요소가 설 자리와 같은 크기·같은 배율로 배치하고, hover·초점이 없는 빈 snapshot으로 그린다. 접근 tree에는 새 화면만 선다.

시각0ms
"상세로"를 누르고 도는 중에 화면을 눌러 보라. 덮개(주황 빗금)가 막는다. 진행이 1이 되어도 덮개는 남아 있다가, 앱이 끝 시각에 깨어 prior를 놓은 다음 tree에서 사라진다. 시각 막대를 끌면 아무 시각이나 물을 수 있다. 10배 느리게 보기는 시계만 늦출 뿐 식은 그대로다.
  1. 스프링 곡선을 "진행 0→1 스프링"으로 바꿔 쓴다. 허용치는 앱 값과 0.001 중 작은 쪽이다. 기본 0.01이면 마지막 1%가 한 번에 붙는다 — 1280픽셀 밀기에서 13픽셀이다.
  2. 길이 0 이하이거나 쓸 수 없는 스프링이면 "시작한 적도 없이 끝난" 곡선이다.
  3. 움직임 줄이기이거나 곡선이 움직이지 않으면 prior를 버린다. 그러면 덮개도 서지 않는다. "언제 물어도 끝인 전환이 입력을 막는" 일이 없다.
  4. 길이 곡선은 started + duration, 스프링은 spring_rest_time이다. 앱은 이 시각 하나를 next_tick에 싣는다. 앱이 frame마다 깨는 길은 "16ms마다 tree를 다시 짓는" 비용 때문에, 요소가 끝에 메시지를 내는 길은 "그리기에서 메시지를 낼 길이 없어서" 거절했다.
  1. prior가 있을 때만 생성자에서 붙인다. 시각과 무관하게, 앱이 prior 없는 tree를 낼 때까지 포인터를 막는다. hit_test를 재정의하지 않고 자식으로 둔 까닭은 끌어 놓기(drop_hit_test)가 virtual이 아니고 자식부터 걷기 때문이다.
  2. 움직임 줄이기이거나 prior 크기가 요소와 0.5 물리 픽셀 넘게 다르면 진행을 묻지도 않고 새 화면만 그린다. 아니면 draw_context::now로 진행을 구한다.
  3. 이전 root를 요소 자리로 옮겨 interaction_snapshot {}으로 그린다. 떠나는 화면에는 hover·누름·caret·초점 테·tooltip이 없다.
  4. 도는 중이면 16ms 뒤를 예고한다. UI thread는 같은 tree를 다시 그린다. 그림의 시간은 이렇게 흐른다.

움직임 줄이기

OS 접근성 설정 하나가 UI thread(draw_context·update_context)와 logic thread(window_metrics)로 함께 간다. 새 움직임은 "움직임 없이 끝값"이 된다. 다른 효과로 바꾸지는 않는다.

문제. 설정이 UI thread 안에서만 쓰였다. logic thread의 앱에는 닿는 길이 없어서 앱이 든 전환(사이드바 폭)은 설정을 지킬 방법이 없었다. Android는 값을 읽지도 않아 회전 표시가 계속 돌았다.

규칙. 값의 주인은 시스템이다. 같은 값이 두 thread로 가되, logic thread에는 메시지로 늦게 닿아 바뀐 직후 한두 frame은 어긋날 수 있다. "어느 쪽도 틀린 그림은 아니다." 배율(느리게·빠르게)은 싣지 않는다 — 앱이 정할 것은 줄일지 여부이고, Windows에는 배율이 없다. 앱은 새 전환을 시작할 때 motion_duration을 거친다.

플랫폼읽는 값다시 읽는 때
WindowsSPI_GETCLIENTAREAANIMATION이 FALSE면 참WM_SETTINGCHANGE 등. 값이 달라졌을 때만 metrics를 다시 보낸다
AndroidSettings.Global의 animator_duration_scale ≤ 0시작, 설정 변경, RESUME, GAINED_FOCUS (Java 코드 0줄 방침이라 변경 관찰자는 없다)
macOSaccessibilityDisplayShouldReduceMotion알림 구독
iOSUIAccessibilityIsReduceMotionEnabled()알림 구독
대상움직임 줄이기면
앱이 든 transition새 전환의 길이가 0 → 언제 물어도 끝값, 예고 없음
앱이 든 springspring_to·spring_release가 spring_at_rest(target) — 값은 목표, 속도 0, 놓은 속도 무시
새 화면 전환start_page_transition이 prior를 버림 → 덮개도 전환도 없음
도는 중인 화면 전환요소가 진행을 묻기 전에 새 화면만 그리고 예고하지 않는다. 데모 앱은 metrics에서 전환을 놓는다
도는 중인 스프링데모 앱이 spring_at_rest(target)으로 붙인다
회전 표시·배지·탭 막대의 도는 표시돌지 않는 글리프나 고정 각도의 호로 서고, 예고도 없다
바뀌지 않는 것토스트 흐려짐, caret 깜빡임, 움직이는 이미지 재생 — "흐려짐은 움직임이 아니라는 견해도 있어 따로 정한다"
다른 효과로 대체?하지 않는다. "옅어짐으로 바꾸지 않는다. motion_duration이 모든 전환을 0으로 두는 규칙과 같다."

이 문서의 실험 셋(연타, 끌어 놓기, 화면 전환)에 "움직임 줄이기" 칸이 있다. 켜고 다시 해 보라.

요약

  1. 움직임 값(transition·spring·page_transition)은 앱 상태다. element는 그 값과 draw_context::now로 그릴 때마다 계산할 뿐, 전환을 소유하지 않는다.
  2. 모든 움직임은 시각만의 함수다. frame을 건너뛰거나 timer가 늦어도 값은 맞고, 덜 촘촘할 뿐이다.
  3. transition_to는 값만 잇고 속도를 잇지 못해 연타에서 멈칫한다. spring은 감쇠 조화 진동자의 닫힌 해이고, spring_to가 값과 속도를 함께 잇는다. 놓은 속도는 spring_release로만 넣는다.
  4. response는 지속 시간이 아니라 감쇠 없는 한 주기다. 끝은 √(y² + (y′/ω)²) ≤ 허용치로 정하고, 이 척도가 줄기만 해서 끝은 한 번만 온다.
  5. 라이브러리에는 시계가 없다. logic thread는 next_tick·tick으로 앱 상태의 시간을, UI thread는 next_update와 draw_context::now로 그림의 시간을 흘린다. 화면 전환은 tree를 두 번만 짓는다.
  6. 움직임 줄이기는 새 움직임을 "움직임 없이 끝값"으로 만든다: 길이 0, spring_at_rest, prior 버림. 다른 효과로 바꾸지 않는다.

자주 묻는 질문

값 하나(접힘 폭, 불투명도)를 부드럽게 바꾸려면?

앱 상태에 transition을 두고 목표가 바뀔 때 transition_to로 새로 출발시킨다. frame을 지을 때 transition_value(값, now)를 element config에 넣는다.

길이를 주지 않으면 transition_duration(140ms)이고 곡선은 ease_in_out이다. element는 전환 중인지 모른다 (움직임의 세 질문). 도는 동안 frame을 다시 짓도록 next_tick에 transition_next_update를 싣는다 (두 시계).

연타하면 움직임이 멈칫한다.

transition_to는 값만 잇고 속도는 잇지 않는다. 도는 중에 목표가 자주 바뀌는 값은 spring과 spring_to로 바꾼다.

ease_in_out은 시작 기울기가 0이라 새 전환마다 멈췄다 출발한다. spring_to는 그 시각의 값과 속도를 함께 이어받고, 같은 목표로 매 frame 불러도 궤적이 같다. 데스크톱 데모의 사이드바 접힘이 spring_to를 쓴다 (길이 곡선과 연타의 멈칫, 재목표와 놓기).

움직이는 동안에만 frame을 다시 짓게 하려면?

driver의 next_tick이 다음 시각을 답하고, 다 끝나면 nullopt를 답한다. 답이 없으면 logic thread의 시간 경로가 잠잔다.

transition_next_update·spring_next_update는 도는 중이면 16ms 뒤, 끝나면 nullopt다. 화면 전환은 page_transition_end의 끝 시각 하나만 싣는다. 움직이는 것이 여럿이면 가장 이른 시각을 답한다. 데모는 "지금"이 아니라 마지막으로 지은 frame의 시각에서 센다 (두 시계, 시간이 흐르는 두 길).

배치는 그대로이고 그림만 움직이는 표시를 직접 만들려면?

element에서 next_update를 재정의해 다음 시각을 답하고, draw는 draw_context::now로 그린다. 앱이 tree를 다시 짓지 않아도 UI thread가 그 시각에 같은 tree를 다시 그린다.

spinner_element가 이 모양이다. 도는 동안 now + 16ms를 답하고, update_context::reduce_motion이 참이면 nullopt를 답하며 멈춘 그림을 그린다. 자식 몫은 tree가 모으므로 자기 것만 답한다 (두 시계, 언제 다시 그리나).

애니메이션이 처음 값에 멈춰 있거나 엉뚱하게 느리다.

움직임 값을 frame마다 새로 만들고 있지 않은지 본다. 목표가 바뀔 때 한 번 만들어 앱 상태로 든다.

transition_to는 부를 때마다 그 시각을 시작으로 새로 출발한다. frame을 지을 때마다 부르면 매번 기울기 0에서 다시 출발해 곡선보다 훨씬 느리게 다가간다 (코드에서 확인한 동작). spring_to는 같은 목표로 매 frame 불러도 궤적이 같지만, 돌려받은 값을 앱 상태에 다시 넣어야 한다. 움직이는 그림의 image_playback::started도 한 번 정해 드는 값이다 — 헤더가 "frame마다 now를 새로 넣으면 그림이 첫 장에 멈춘다"고 적는다.

OS의 '동작 줄이기'를 따르게 하려면?

delegate에서 make_metrics_message를 넓혀 window_metrics::reduce_motion을 앱 상태에 두고, 새 움직임을 시작할 때마다 넘긴다.

길이 곡선은 transition_to(…, motion_duration(길이, 값)), 스프링은 spring_to·spring_release의 마지막 인자, 화면 전환은 start_page_transition의 마지막 인자다. 참이면 셋 다 "움직임 없이 끝값"이 된다. 세 값짜리 make_window_metrics_message만 넓힌 delegate는 이 값을 받지 못한다. 네 플랫폼의 host가 OS 설정을 읽어 채운다 (움직임 줄이기, API: window_metrics::reduce_motion).

도는 중에 '동작 줄이기'가 켜지면?

앱이 이미 든 값은 남은 시간만큼 더 돈다. metrics 메시지에서 값이 거짓에서 참으로 바뀌면 앱이 끝값에 붙인다.

데모는 사이드바 스프링을 spring_at_rest(목표)로 바꾸고 화면 전환을 놓는다. 라이브러리 요소(spinner_element, 배지·탭 막대의 도는 표시, 안내 풍선의 나타남, page_transition_element)는 draw_context::reduce_motion을 직접 읽어 곧 멈춘다. 토스트의 흐려짐, caret 깜빡임, 움직이는 이미지의 재생은 이 값을 읽지 않는다 (코드에서 확인한 동작, 움직임 줄이기).

끌다 놓은 손가락의 속도를 이어받아 멈추게 하려면?

놓는 메시지에서 spring_release(놓은 값, 속도, 목표, now, config, reduce_motion)로 새 스프링을 만든다. 이전 스프링의 속도는 보지 않는다.

pointer_drag_target::on_release가 주는 drag_velocity는 초당 물리 픽셀이라 논리 픽셀 값에는 scale로 나눠 넣는다. 값이 줄어드는 쪽이 손가락 방향이면 부호를 뒤집는다. 도는 중에 다시 잡으면 spring_value로 지금 값을 읽어 거기서부터 끌고, 스프링은 spring_at_rest로 거둔다 — 모바일 데모의 시트가 이렇게 한다 (재목표와 놓기).

스프링의 빠르기와 튕김, 끝 허용치를 정하려면?

프리셋 spring_smooth·spring_snappy·spring_bouncy를 쓰거나 spring_config의 response·damping_fraction·rest_threshold를 정한다. 질량·강성·감쇠로 생각하면 spring_from_physics가 바꿔 준다.

response는 지속 시간이 아니라 감쇠가 없을 때의 한 주기다. damping_fraction이 1이면 넘치지 않고 작을수록 튕긴다. 허용치 기본 0.01은 논리 픽셀 값에 맞춘 것이다. 불투명도·배율처럼 0~1인 값은 0.001쯤으로 낮춘다 — 기본값이면 끝 무렵 1% 안쪽이 한 번에 붙는다 (스프링, 닫힌 해).

스프링이 언제 끝날지 미리 알려면?

spring_rest_time이 시작부터 16ms 격자 위에서 처음 끝나는 시각을 답한다. 지금 끝났는지는 spring_finished(값, now)다.

상한(기본 10초) 안에 끝나지 않으면 started에 상한을 더한 시각이다. 끝 판정의 척도는 줄기만 하므로 한 번 끝난 스프링은 다시 움직이지 않는다. 화면 전환의 page_transition_end가 스프링 곡선에 이 함수를 쓴다 (닫힌 해).

화면(페이지) 전환 애니메이션은?

본문을 늘 page_transition_element로 감싸고, 페이지를 바꾸는 메시지에서 떠나는 화면을 따로 지어 start_page_transition에 넘긴다.

떠나는 화면은 요소가 설 자리와 같은 크기·같은 배율로 배치한 std::shared_ptr<const ui_tree>다. 데모는 지난 frame의 본문 자리를 기억해 두었다가 make_arranged_tree로 짓는다. next_tick에 page_transition_end를 싣고, tick에서 page_transition_finished가 참이면 전환을 비운다. started는 앱이 적는 시각이라, 들어오는 화면을 짓는 데 오래 걸리면 첫 그림이 이미 중간이다 — 모바일 데모는 그 화면을 지은 뒤 시작 시각을 다시 적는다 (화면 전환).

옅어짐·확대·세로 밀기, 뒤로 갈 때의 반대 방향은?

page_transition_style의 effect(slide·fade·zoom), axis, direction, curve로 고른다.

뒤로 가는 이동은 page_transition_direction::backward로 시작한다. 모바일 데모는 앱 바의 뒤로 단추와 시스템 뒤로 가기에서 backward 밀기를, 넓은 화면의 오른쪽 판에서는 옅어짐을 쓴다. 곡선은 page_transition_timing(기본 250ms와 easing 함수)이나 page_transition_spring이다. 스프링 곡선은 허용치가 0.001을 넘지 않게 알아서 줄인다 (화면 전환).

전환이 끝났는데도 새 화면이 클릭을 받지 않는다.

덮개는 앱이 prior를 놓을 때까지 남는다. next_tick에 page_transition_end를 실었는지, tick에서 끝난 전환을 비우는지 본다.

요소는 prior가 있는 동안 시각과 무관하게 칠하지 않는 덮개로 누름·hover·끌어 놓기를 막는다. hit_test는 시각을 받지 않아 요소가 끝을 스스로 알 수 없다. 키 입력은 막지 않는다 (화면 전환).

전환 도중에 창 크기나 배율이 바뀌면?

요소는 새 화면만 그리고 다음 frame을 청하지 않는다. 덮개는 남으므로 앱이 metrics 메시지에서 전환을 놓는다.

이전 root의 크기가 요소와 0.5 물리 픽셀 넘게 다르면 옛 크기 그림을 남기지 않으려고 이전 화면을 그리지 않는다. 덮개는 prior가 있는 한 서 있어, 놓지 않으면 끝 시각까지 포인터가 막힌다. 두 데모는 크기·배율(모바일은 폭 등급도)이 바뀌거나 움직임 줄이기가 켜지면 전환을 비운다 (화면 전환).

사례로 확인하기

입력과 상태를 하나 정해 두고, luil이 그때 무엇을 하는지 코드에서 따라간 결과다. 펼치면 결과와 까닭이 나온다.

luil의 spring은 값을 어떻게 구하나?

감쇠 조화 진동자의 닫힌 해를 시각으로 바로 계산한다

상태가 없는 닫힌 해라서 어느 시각에 물어도 같은 값이다. 단계 적분은 "상태가 있어 frame을 건너뛰면 값이 달라지고 계약이 깨진다"며 거절했다. test는 거꾸로 0.1ms RK4 적분을 기준 삼아 닫힌 해를 대조한다.

spring_smooth(response 350ms)로 사이드바 폭을 100px 옮기면 언제 끝나나?

약 670ms

response는 감쇠 없는 한 주기이고, 끝은 허용치(0.01)가 정한다. 1ms씩 훑으면 674ms에 처음 끝난다. 그래서 "duration + bounce" 어휘는 "duration이 거짓 이름이 된다"며 거절했다. 140ms는 transition_duration, 250ms는 page_transition_duration이다.

사이드바가 접히는 도중에 다시 토글했다. spring_to가 만든 새 스프링의 출발 속도는?

그 순간 이전 스프링의 속도

spring_to는 값과 속도를 모두 이어받으며 속도 인자가 없다. 손을 뗀 속도를 넣는 길은 spring_release 하나이고, 이것은 이전 스프링을 무시한다. 옛 transition_to가 연타에서 멈칫한 원인이 속도를 잇지 못한 것이다.

기본 밀기 전환(250ms)이 도는 동안 앱(logic thread)은 tree를 몇 번 짓나?

시작과 끝, 두 번

도는 동안의 그림은 전환 요소의 next_update가 맡는다. UI thread가 같은 불변 tree를 draw_context::now만 바꿔 다시 그린다. 앱의 next_tick에는 끝 시각 하나만 실린다. 사이드바 폭 스프링은 폭이 배치를 바꾸므로 16ms마다 짓는다.

밀기 그림의 진행이 1이 되면 그 frame부터 새 화면의 단추를 마우스로 누를 수 있나?

아니다. 앱의 tick이 prior를 놓은 다음 tree부터 누를 수 있다

덮개는 prior가 있는 동안 시각과 무관하게 서 있다. hit_test는 시각을 받지 않아 요소가 끝을 스스로 알 수 없다. 앱이 끝 시각에 깨어 prior를 놓아야 풀린다. 키 입력과 UIA Invoke 같은 패턴은 처음부터 막히지 않는다.

움직임 줄이기를 켜면 화면 전환은 어떻게 되나?

전환 없이 새 화면이 바로 선다

start_page_transition이 prior를 버리고, 문서는 "옅어짐으로 바꾸지 않는다"고 못 박았다. 같은 설정에서 transition은 길이 0, 스프링은 spring_at_rest(target)이다. 배율(느리게·빠르게)은 싣지 않으므로 ②는 없다.
