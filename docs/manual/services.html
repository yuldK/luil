플랫폼 서비스와 네트워크

개념: thread를 가진 부품과 배출구 하나

망과 파일 감시의 부품은 자기 thread에서 일하고 결과를 deliver 함수 하나로 내보낸다. 요청마다 callback을 받지 않는다. 앱은 그 자리에서 값을 logic thread로 옮기고, 앱 상태는 logic thread의 handle에서만 바꾼다.

HTTP 요청 하나가 지나가는 길

logic threadhandle이 요청을 짓고 send(request, error)를 부른다. 0이 아닌 표(http_ticket)를 앱 상태에 적는다.
OSWinHTTP·HttpURLConnection·NSURLSession이 선을 탄다. Android는 요청마다 떼어 낸 worker가 JNI 호출로 몬다.
client thread완료를 받아 몸을 값으로 푼다. JSON은 수십 ms, 그림은 초 단위까지 걸린다. 그래서 OS callback에서도 logic thread에서도 하지 않는다. 전체 마감과 되풀이 회차의 시계도 이 thread가 돈다.
client threaddeliver(response)가 불린다. 앱이 할 일은 post_app_message로 값을 옮기는 것 하나다.
app inbox1024칸 큐다. 차 있으면 새 메시지를 조용히 버린다 (reject_newest).
logic threadhandle이 response.ticket으로 흐름을 가르고 상태를 바꾼 뒤 표를 잊는다. 다음 frame이 새 값으로 지어진다.

배출구가 하나뿐인 것은 판단이다. 요청마다 callback을 받으면 앱 상태를 남의 thread에서 만지는 코드가 생긴다. http_response·http_body의 무거운 슬롯은 참조 공유이고 app_message도 공유 소유의 불변 상자라, 큰 몸도 thread를 건너는 값 복사가 싸다.

표(ticket)와 "정확히 하나"

요청을 받아들였다는 표시는 0이 아닌 표다. 받아들인 요청의 답은 정확히 하나 온다. 0이면 손잡이가 서기 전의 거절이라 error에 이유가 있고 답은 오지 않는다. 가르는 선은 "손잡이가 섰는가" 하나다. 그래서 앱의 상태 기계는 "표를 받았으면 답을 기다린다" 한 줄이면 된다.

HTTP 몸은 이미 값으로 풀려 온다

답의 body는 client thread에서 decode_http_body가 푼 값이다. 갈래(http_body_kind)를 정하는 차례는 넷이다.

  1. 바이트가 비었으면 empty다. Content-Type이 무엇이라 적혔든 그렇다 (출처 absent).
  2. 요청의 parse.assume_kind가 있으면 그 갈래다 (assumed).
  3. Content-Type이 없거나, 읽을 수 없거나, application/octet-stream이면 앞 바이트에서 그림 서명 다섯만 본다. 그림이 아니면 bytes다 (sniffed).
  4. 아니면 Content-Type이 말한 대로다 (declared): json → image(svg는 bytes) → html → text → 그 밖은 bytes.

갈래는 서버가 한 말이다. 푸는 데 실패해도 갈래는 낮아지지 않고 이유가 parse_error에 적힌다. 깨진 JSON도 kind == json이고 json 슬롯은 비어 있다. 아래 실습에서 Content-Type과 몸을 바꿔 가며 갈래를 본다.

종료: stop()은 언제, 무엇을 남기나

app_host::shutdown()은 UI thread에서 이 차례로 간다. 부품의 자리는 0단계와 3단계다.

UI threadlogic_driver::cancel() — 오래 걸리는 일을 일찍 접게 알린다. HTTP의 cancel_all() 자리다.
UI thread종료 메시지(make_close_message)를 app inbox에 넣는다. 차 있으면 마감까지 다시 넣어 본다.
logic thread종료 메시지를 처리하고 종료 저장을 낸다. UI thread는 그 확인을 기다린다.
UI threadlogic_driver::stop_workers() — 모든 부품의 stop() 자리다. deliver가 쥔 host보다 먼저 멈춘다.
UI threadapp inbox를 닫고 logic thread를 join한다.
UI threadinput thread를 join한다.
부품stop()이 하는 일마지막 답
http_client새 요청 거절 → 되풀이표를 비우고 pump를 멈춤(이 뒤로 deliver 없음) → 날아가는 요청을 접고 stop_budget까지 기다림 → 세션을 닫음. 예산을 넘기면 문맥과 세션을 일부러 남긴다세 백엔드 모두 배달을 먼저 끄고 남은 요청을 stopped로 접는다. 그래서 stopped 답이 앱에 닿는다고 기대하지 않는다 (test도 "0개도 옳다"고 적는다)
smb_client받기를 닫고, 진행 중인 요청을 끊고, 배달 thread를 거둔다아직 배달하지 않은 답은 버린다
file_watcher새 add 거절 → thread join(이 뒤로 deliver 없음) → OS 감시를 풀고 예산 안에서 버퍼를 돌려받음내지 않은 변경은 버린다
websocket_client연결을 끊고 reader·writer를 join한다. 돌아온 뒤에는 deliver가 없다돌아오기 전에 reader가 closed(오류 stopped, 코드 1006)를 낼 수 있다
  • 소멸자도 모두 stop()을 부른다. 그래도 소멸자에 맡기지 않는다. deliver가 쥔 host·this보다 먼저 멈춰야 해서 stop_workers()에서 부른다.
  • cancel()과 stop_workers()는 UI thread에서 불린다. logic thread가 소유한 client는 원자적 손잡이로만 본다 — 데모의 live_client_가 그 꼴이다.
  • 앱이 살아 있는 동안 client를 멈출 때(화면을 닫거나 다시 붙을 때)도 같다. stop() 뒤에는 남은 표의 답이 오지 않는다고 보고 앱이 그 표를 직접 잊는다.

종료 단계 전체와 시간 예산은 스레드 모델의 종료 절차에 있다.

app inbox는 차면 조용히 버린다


버려진 답은 다시 오지 않는다app inbox는 1024칸이고 넘치면 새 메시지를 버린다(reject_newest). post_app_message는 버린 것을 알리지 않는다. post_app_message_ticketed는 버렸으면 0을 돌려준다. 파일 감시의 deliver만 bool을 돌려주어, 거짓이면 감시자가 그 묶음을 다음 변경과 합쳐 다시 낸다. HTTP·SMB·WebSocket의 deliver는 void라 inbox가 버린 답은 그것으로 끝이다. 표를 기다리던 화면이 영원히 "보내는 중"에 남는다 — 대책은 답을 잃지 않기.

유실된 수는 app_inbox_statistics()의 rejected가 센다. 넘칠 때의 정책은 스레드 경계 메시징에 있다.

만들기: HTTP 요청과 답

client 하나를 logic이 시작할 때 세운다. deliver는 답을 logic thread로 옮기기만 하고, 보낸 쪽은 받은 표를 상태에 적었다가 답이 오면 그 표로 흐름을 가른다.

client 세우기

데모의 셸(logic_driver)은 host 포인터를 원자적 손잡이로 든다. deliver는 client의 thread에서 불리고, host 포인터는 UI thread가 bind_host로 준다.

  1. 데모는 프로세스 안에 HTTP 서버를 세워 오프라인에서 돈다. luil::testing::loopback_http_server는 tests/의 시험 도구이지 라이브러리 API가 아니다.
  2. User-Agent를 정한다. use_system_proxy = false는 되돌이 주소라서다. 실제 앱은 기본값(참)을 둔다.
  3. client thread에서 불린다. 하는 일은 답을 앱 메시지에 담아 post_app_message로 넘기는 것 하나다.
  4. 실패하면 nullptr이고 이유가 client_error_에 적힌다. UI thread가 종료 때 볼 원자적 손잡이(live_client_)도 여기서 채운다.
  • client는 앱 하나에 하나면 넉넉하다. 연결은 host별로 안에서 다시 쓰인다.
  • Android에서는 host가 JavaVM을 적기 전에 create를 부르면 실패한다. host가 선 뒤(logic의 start)에 세운다.

GET으로 JSON 받기 — 보내기

  1. 세우기가 실패했으면 보내지 않고 그 이유를 화면에 넘긴다.
  2. http_request는 값이다. 주소와 동사를 넣고, POST면 몸과 Content-Type을 싣는다.
  3. 요청마다 몸을 푸는 규칙(parse)을 준다. 밖에서 오는 그림에는 디코드 상한을 건다.
  4. send가 돌려준 표를 상태에 적는다. 0이면 거절이고 error에 이유가 있다 — 그때는 답이 오지 않는다.

받기 — 셸의 handle

네트워크 메시지는 client를 든 셸이 먼저 받는다. 답이 온 흐름은 표를 잊는다. 잊지 않으면 취소 단추가 끝난 표를 겨누고, cancel은 모르는 표에 아무 일도 하지 않는다.

페이지의 상태와 갈래별 처리

페이지는 표가 유효한 동안을 "오는 중"으로 본다. 맥박(되풀이) 흐름은 표를 따로 든다.

  1. 되풀이의 표는 회차마다 바뀌지 않는다. 그 표면 회차 번호(sequence)와 상태를 적고, last에서 표를 잊는다.
  2. 모르는 표는 지나간 흐름의 늦은 답이다. 새 요청이 이미 그 자리를 가져갔으므로 화면을 뒤집게 두지 않는다.
  3. 답은 불변 값이라 통째로 들어도 싸다. 미리 보기 줄은 답이 왔을 때 한 번 짓는다 — frame마다 dump(2)를 부르지 않는다.
  4. json 슬롯이 비었으면 풀리지 않은 것이다. 이유는 parse_error에 있다. 갈래는 그래도 json이다.
  5. 글은 as_text()로 읽는다. 그림은 image.valid()로 성패를 가르고, 값이 서면 재생 시계를 건다.
  6. html은 바이트와 charset만 남긴다. bytes는 실패가 아니라 "우리가 풀지 않는 몸"이다.

가장 작은 꼴은 test에 있다.

  • 404도 답이다. error.empty()가 참이고 ok()가 거짓이며 몸은 평소대로 풀린다. 데모의 /missing은 application/problem+json 404라 json으로 풀린다.
  • 한 번짜리 답은 sequence == 0, last == true다.
  • json 슬롯은 std::shared_ptr<const nlohmann::json>이다. 공개 헤더는 json_fwd.hpp만 들이므로 값을 읽는 파일이 <nlohmann/json.hpp>를 include한다.

POST로 보내기

  • 글을 몸 바이트로 옮기는 도우미는 http_text_body다. dump()한 JSON 글을 그대로 넣는 자리다.
  • 몸이 있으면 content_type이 Content-Type이 된다. 비어 있으면 headers에 적은 Content-Type을 존중하고, 둘 다 없을 때만 application/octet-stream이다.
  • 몸이 있는 요청은 재지정을 따라가지 않는다. 307이 와도 3xx가 답으로 온다. 앱이 Location을 보고 다시 보낸다.
  • GET·HEAD에 몸을 싣지 않는다. Android·Apple은 send가 그 자리에서 거절하고(표 0), Windows는 그대로 보낸다.

만들기: HTTP로 그림 받기

요청에 디코드 상한을 걸고, 답의 body.image를 image_element에 그대로 싣는다. 디코딩은 이미 client thread에서 끝나 있다.

밖에서 오는 4000×3000 사진 하나가 48 MB이고, 움직이는 그림이면 장 수가 곱해진다. 그래서 상한은 거의 언제나 채운다. 데모는 보낼 때 건다.

  • 움직이는 gif도 파일에서 읽은 것과 같은 값(ui_animated_image)이라 재생 시계 하나로 돈다. 그림 쪽 규칙은 이미지·영상·웹·잉크에 있다.
  • 갈래가 image인데 디코딩이 실패해도 갈래는 image이고 이유는 parse_error다. 잘린 그림을 받아들이는 설정이면 그림과 parse_error가 함께 선다. 그래서 데모는 body.image.valid()로 가른다.
  • 섬네일이면 parse.image.animated = false로 첫 장만 푼다. 한 장이 필요한 자리는 still_image()다.
  • svg는 bytes로 온다. 앱이 decode_svg_bytes로 연다 (LUIL_ENABLE_SVG를 켠 구성).
  • 받는 몸 전체의 상한은 max_body_bytes(기본 64 MiB)다. 디코드 상한과 따로다.

만들기: HTTP 취소와 되풀이 요청

취소는 표 하나를 겨눈다. 답은 그래도 하나 온다. 주기적인 조회는 start_heartbeat 하나로 걸고, 멈추는 것도 같은 cancel이다.

취소 단추

단추는 겨눌 본문 흐름이 있을 때만 연다. in_flight()로 열면 맥박만 도는 동안에도 열려 누르는 것이 맥박을 접는 일이 된다.

답(cancelled)은 그래도 오고, 셸의 handle이 표를 잊는다. test가 "정확히 한 번"을 잠근다.

  • 손잡이를 꾸미는 사이 취소가 지나갔으면 선을 건드리지 않고 접는다. 취소된 POST가 뒤늦게 서버에 닿지 않는다 (WinHTTP 백엔드 코드).
  • cancel_all()은 날아가 있는 것 전부와 되풀이표를 접는다. 종료 0단계(logic_driver::cancel)의 자리다. 맥박이 도는 중에 느린 요청 하나를 접는 자리에는 지나치다.

되풀이 요청 (맥박)

  • 요청은 한 번짜리와 같은 http_request이고, 시간표(http_heartbeat)만 더한다. immediate가 참이면 첫 회차가 곧바로 나간다. max_rounds 0은 cancel·stop까지다.
  • 다음 회차는 답을 배달한 뒤에 잰다. 회차가 겹치지 않는다.
  • 전송 오류와 4xx·5xx로는 멈추지 않는다. 네트워크가 돌아오는 것을 보는 것이 되풀이 요청이 있는 이유다. 멈추는 것은 cancel·max_rounds·stop과 영원히 실패할 오류뿐이다 — invalid_url·unsupported_scheme·invalid_header, 그리고 invalid_method. 헤더 주석은 앞의 셋만 들지만 코드(failure_is_permanent)는 넷을 본다.
  • 쉬는 중에 취소하면 날아가는 회차가 없으니 마지막 답을 지어 낸다. 그 sequence는 지금까지 낸 회차 수라 앞 회차와 같은 번호다 (WinHTTP 백엔드 코드에서 읽은 것이고, test는 회차 없이 취소한 0만 본다). 중복은 sequence가 아니라 last로 가른다.

"몇 번 틀리면 물러선다"는 앱 정책이라 손잡이가 없다. sequence와 error를 세어 cancel하고 더 긴 interval로 다시 건다. 저장소에 그 예제가 없어 묶어 썼다.

start_beat가 표 0을 받으면(주소가 틀렸거나 상한에 걸렸다) on_beat는 아무 답도 받지 않는다. 그 이유는 start_heartbeat의 error에 있다.

만들기: HTTP 답을 잃지 않기

app inbox가 차서 답이 버려지면 그 표의 답은 다시 오지 않는다. post_app_message_ticketed의 0을 보고 잃은 표를 따로 적어 둔다.

HTTP의 deliver는 void다. 파일 감시처럼 "받지 못했다"를 돌려줄 길이 없다. 그 표를 기다리던 화면이 "보내는 중"에 멈추지 않게 하려면 게시가 실패한 것을 앱이 알아채야 한다. 저장소에 예제가 없어 묶어 썼다.

  • post_app_message_ticketed는 받았으면 0보다 큰 수를, 버렸으면 0을 돌려준다. post_app_message는 같은 일을 하고 알리지 않는다.
  • lost_tickets와 host는 client보다 오래 살아야 한다. stop_workers()에서 client를 먼저 멈추면 그 뒤로 deliver가 불리지 않는다.
  • 잃은 것은 답 하나다. 되풀이 흐름이면 다음 회차는 그대로 온다. 한 번짜리면 그 표로는 더 오지 않으니 앱이 표를 잊고 실패로 보인다.
  • 버려진 수만 알면 될 때는 app_inbox_statistics()의 rejected를 본다.

만들기: WebSocket 주고받기

client 하나가 연결 하나다. create가 reader·writer thread를 띄우고, 사건은 reader thread의 deliver로 온다. 다시 붙는 것은 새 client다.

저장소에는 WebSocket을 쓰는 예제 앱이 없다. 주고받기의 규칙은 test가 원문으로 보인다. 아래 test는 바깥 echo 서버(LUIL_WS_PORT)가 있을 때만 도는 묶음([.live])이다.

  1. create가 돌아온 순간은 아직 열리지 않았을 수 있다. opened나 closed 가운데 먼저 오는 것을 기다린다.
  2. 글은 send_text, 바이트는 send_binary다. 빈 메시지도 메시지다. 큐에 넣고 곧 돌아오며, 거짓이면 넣지 못한 것이다.
  3. 조각난 메시지는 다시 이어 한 사건으로 온다. data는 공유 불변 바이트라 앱 메시지로 옮겨도 싸다.
  4. sequence는 client마다 1부터 하나씩 는다.
  5. close(1000, …) 뒤로 보내기는 거짓이다. 상대가 답하면 closed가 코드 1000과 빈 오류로 온다.
  6. stop()은 멱등이다. 돌아온 뒤로 deliver가 없다.

앱 상태와 handle

앱 상태와 메시지 갈래까지 갖춘 꼴은 저장소에 없어 묶어 썼다. 다시 붙을 때마다 세대 번호를 올려, 지난 연결의 늦은 사건이 지금 화면을 덮지 않게 한다.

  • 보내기가 거짓인 경우. 아직 열리지 않았다, 닫는 중이다, 보낼 큐가 찼다(기본 64개·8 MiB), 메시지가 max_message_bytes보다 크다, send_text의 글이 올바른 UTF-8이 아니다. 숨은 무한 큐가 없다.
  • close는 이유 123바이트 이하, 코드 1000–1014(1004·1005·1006 제외)·3000–4999만 받는다.
  • URL·설정 오류는 create가 실패한다. 연결·TLS·upgrade 오류는 closed 사건으로 온다. closed는 연결에 실패해도 client마다 정확히 한 번 온다.
  • URL은 소문자 ws://·wss://로 시작하고 ASCII(32–126)만 쓴다. 한글 경로는 escape해서 넣는다. 자격 증명(@)·공백·#은 받지 않는다.
  • 끊겨도 저절로 다시 붙지 않는다. 다시 붙는 것은 새 client다 — 위 connect가 그 자리다.
  • stop()이 돌아오기 전에 closed(오류 stopped, 코드 1006)가 올 수 있다. deliver가 쥔 host는 stop()이 끝날 때까지 살아 있어야 한다.
  • Android는 Java 전송부(WebSocketTransport)를 APK에 실어야 한다. 없으면 모든 조작이 "Include the luil Java transport in the APK." 오류다. minify를 켠 앱은 luil-websocket.pro 규칙도 싣는다.

만들기: SMB 공유 둘러보기

계약은 http_client와 같은 모양이다. 받은 요청마다 표 하나와 답 하나가 있고, 답은 client의 배달 thread에서 차례로 온다. 같은 서버·공유·계정의 연결은 잠시 쉬게 두었다 다시 쓴다.


Android와 iOS, 그리고 LUIL_ENABLE_SMB=ON일 때만 선다기본은 꺼져 있다. Windows·macOS와 끈 구성에서는 create가 nullptr이고 supported()가 거짓이다. 헤더 주석과 "지원 안 함" 오류 글은 "Android 전용"이라 적지만, 빌드 규칙은 iOS에서도 libsmb2로 세우고 모바일 데모도 iOS에서 같은 client를 세운다. Windows에서 공유를 읽으려면 운영체제의 SMB(UNC 경로)를 쓴다.

client 세우기

모바일 데모는 delegate가 host가 선 뒤(on_started) client를 세워 logic에 메시지로 넘긴다. SMB를 세우지 않은 구성이면 create가 nullptr이라 넘기지 않는다.

페이지는 client 포인터를 함수 묶음으로 감싸 쥔다. 서버 없이 상태를 시험하는 test가 같은 길로 가짜 함수를 넣는다.

상태와 보내기

보낸 요청의 표와 경로를 쥐어 늦은 답을 거른다. 보내기 전에 앞 요청을 취소하고 표를 바꿔 쥔다.

받기

  1. 표가 다르면 지나간 요청의 답이다. 맞으면 표를 잊는다.
  2. 걸린 시간과 쓴 연결(connection)은 진단이다. 실패면 error.message에 libsmb2의 글이 그대로 있다. 암호는 들어 있지 않다.
  3. discover의 답은 servers다. 빈 목록도 성공이다.
  4. 서버가 준 것은 다 온다. 디스크이고 관리용이 아니며 $로 끝나지 않는 공유만 보이는 것은 앱의 거르기다.
  5. 항목은 서버가 준 차례로 온다. 폴더 먼저·이름순 정렬은 앱이 한다.
  6. 큰 파일은 구간으로 나눠 읽는다. 받은 길이가 요청보다 짧으면 파일 끝이다.

쉬는 연결 닫기와 멈추기

앱이 뒤로 가면 close_idle을 부르는 메시지를 낸다. 돌아왔을 때 망이 바뀌었어도 끊긴 연결을 다시 쓰지 않게 하려는 것이다. 멈추는 것은 logic의 stop_workers다.

  • Android 17부터 같은 망의 NAS에 붙으려면 먼저 로컬 네트워크 권한(app_permission::local_network)을 받는다. 없으면 연결이 시간 상한까지 기다리다 실패한다. iOS에는 묻는 API가 없어 첫 접속에 시스템이 묻는다.
  • read 하나의 길이는 1 이상 max_read_bytes(16 MiB) 이하다. 동시 요청은 max_in_flight(4)까지이고, 넘기면 줄 세우지 않고 표 0으로 거절한다.
  • 쓰기(만들기·지우기·이름 바꾸기)는 없다. 인증은 NTLM만이고 SMB 2.02–3.1.1이다.
  • NAS의 주소를 모르면 discover가 같은 망에서 찾는다. smb_server_found::server()가 smb_location::server에 넣을 꼴을 짓는다.

만들기: 파일 감시

감시자 하나가 thread 하나를 갖고 여러 경로를 본다. 변경은 잠시 모여 묶음으로 오고, deliver는 받았는지를 bool로 답한다. 거짓이면 감시자가 그 묶음을 다음 변경과 합쳐 다시 낸다.

세우고 걸기

  1. 감시할 폴더를 앱이 만든다. Android 데모는 앱 내부 저장소(internalDataPath) 아래를 쓴다. luil은 그 경로를 내주는 공개 접근자를 두지 않는다.
  2. 감시 thread에서 불린다. post_app_message_ticketed가 0이 아니면 inbox가 받은 것이다. 이 답이 거짓이면 묶음은 버려지지 않는다.
  3. create로 thread를 세우고 add로 경로를 건다. 표가 0이면 걸지 못한 것이고 error에 이유가 있다. 멈추는 함수는 원자적 손잡이 대신 감시자 포인터를 잡은 함수로 넘긴다.
  4. 표와 멈추는 함수를 메시지로 logic에 넘긴다. 감시자 자체는 delegate가 host보다 오래 쥔다.

add 먼저, 읽기는 그다음감시는 처음 목록을 주지 않는다. 앱이 add를 먼저 하고 그다음 폴더를 읽는다. 거꾸로 하면 그 사이의 변경을 놓친다. 다른 thread에서 add를 부르면 감시 thread가 감시를 걸 때까지 기다린다 — 돌아온 뒤의 변경은 놓치지 않는다.

페이지의 상태와 받기

다른 표의 묶음은 거른다. 끝 묶음(end가 none이 아닌 것) 뒤로 그 표에는 묶음이 없으니 표를 잊는다. 멈추는 것은 stop_workers의 files_.stop()이다 (SMB 조각의 stop_workers).

파일을 원자적으로 바꾸기

읽는 쪽은 언제나 옛 파일 전체나 새 파일 전체를 본다. 같은 폴더의 임시 파일에 다 쓰고 디스크까지 내린 뒤 이름을 바꾸기 때문이다. 데모는 창 배치를 저장할 때 쓴다. 폴더는 앱이 먼저 만든다.

그 저장은 종료 메시지를 처리하는 logic thread에서 일어난다 (종료 2단계).

  • 폴더를 만들지 않는다. 없으면 failed다.
  • 임시 파일 이름은 네 플랫폼 모두 <경로>.<pid>.tmp다. 그래서 같은 프로세스의 두 thread가 같은 파일을 동시에 바꾸면 임시 파일이 겹친다. 한 파일의 저장은 한 thread로 모은다.
  • POSIX 쪽(Android·macOS·iOS)은 임시 파일을 0600으로 만들고 그 파일이 결과가 되므로, 바꾼 파일의 권한이 0600이 된다.
  • 위 두 항목은 코드에서 읽은 것이다. test는 내용·남는 임시 파일·없는 폴더만 본다.

브라우저로 주소 열기

라이브러리는 링크를 열지 않는다. 링크 메시지를 받은 앱이 open_url을 부른다.

허용 판정(url_scheme_allowed)의 규칙은 test가 표로 잠근다. 기본 목록은 http·https·mailto다.

  • 자기 scheme을 열려면 open_url(url, { .schemes = { u8"myapp" } })처럼 목록을 넘긴다. 넘긴 목록은 기본 목록을 대신한다. 빈 목록은 아무것도 열지 않는다.
  • 공백으로 시작·끝나거나 제어 문자가 섞인 주소는 거짓이다. OS가 그것들을 걸러 읽으면 막은 scheme이 되살아나기 때문이다. 도메인(피싱)은 보지 않는다.
  • ok는 "넘겼다"까지다. Windows는 브라우저가 열었는지 모른다. Android 10+는 앞에 없는 앱의 Activity를 OS가 조용히 막아도 ok다. iOS는 메인 큐에 비동기로 넘기고 늘 ok다 — 헤더 주석의 "열 앱이 없으면 not_found"는 iOS에서 오지 않는다.
  • 사용자가 링크를 누른 그 순간처럼 앱이 앞에 있을 때 부른다. Android는 앞에 보이지 않는 앱이 띄우는 Activity를 막는다.

둘째 실행의 인자를 첫째로 넘기기

파일을 더블 클릭해 앱을 또 띄우면, 둘째가 인자를 첫째에 넘기고 끝나는 꼴이다. single_instance를 이름 하나로 세우면 첫째인지 알 수 있다. 데모의 둘째 쪽은 --send-to-first가 있을 때만 보내고 끝낸다. 실행 파일 경로(argv[0])는 빼고 보낸다.

첫째 쪽은 window_environment::instance를 단다. instance는 창보다 오래 산다.

받는 훅은 UI thread의 창 프로시저 안에서 불린다. 보낸 쪽이 답을 기다리므로 게시만 하고, 표가 0이 아닌지를 답한다.

  • 훅을 만들지 않으면 둘째는 늘 failed다. on_instance_arguments의 기본 구현은 거짓을 답한다. 창은 그래도 앞으로 선다.
  • macOS도 받는다. luil::macos::application_environment::instance를 달고, 앱 delegate가 win32::window_delegate를 구현했으면 macOS host가 그 on_instance_arguments를 메인 thread에서 부른다. 설계 문서 머리는 "Win32 전용"이라 적지만, 같은 문서의 macOS 절과 코드는 macOS도 받는다. 훅의 선언 자리가 Win32 헤더일 뿐이다.
  • Android·iOS에서는 둘째가 생기지 않는다. primary()는 늘 참이고 status()·send_to_primary는 unsupported다. 앱을 다시 여는 요청은 Intent 쪽으로 온다.
  • send_to_primary는 부른 thread를 시한(기본 3 s)까지 막는다. 시한이 지난 보내기도 첫째가 나중에 받을 수 있어, 다시 보내면 받는 쪽이 중복을 견뎌야 한다. not_found는 시한 안에 첫째의 주 창이 서지 않았거나 이 객체가 첫째라는 뜻이다.
  • 인자는 명령 줄과 같이 믿을 수 없는 입력이다. 같은 데스크톱의 어느 프로세스든 보낼 수 있고 받는 쪽은 보낸 프로세스를 모른다. 관리자 권한으로 도는 첫째가 낮은 권한 둘째의 인자를 받으려면 instance_from_lower_integrity를 켠다 — 끄면 그 둘째는 접근 거부 failed다.

파일 관리자에서 보이기 · 외부 프로그램 띄우기

  • reveal_in_file_manager는 파일 관리자를 열고 그 파일을 고른 채로 둔다. 없는 경로는 not_found다. Windows는 부르는 thread에서 COM을 연다. Android·iOS는 unsupported다 (헤더 주석에는 Android만 적혀 있다).
  • launch_program: Windows는 인자를 Windows 명령 줄 규칙으로 따옴표 처리해 CreateProcessW로 띄우고 프로그램은 PATH에서 찾는다. macOS는 posix_spawnp에 argv를 그대로 넘기고 show_window는 쓰지 않으며, 신호로 끝나면 exit_code가 비어 있다. Android·iOS는 unsupported다.
  • launch_options::wait를 켜면 끝날 때까지 기다려 exit_code를 싣는다. Windows는 시한 없이 기다리므로 logic thread에서 켜지 않는다.

만들기: 파일 목록 클립보드

OS 파일 관리자와 파일을 복사·잘라내기·붙여넣기로 주고받는다. 클립보드는 UI thread의 것이라 앱은 요청을 값으로 내고, 답과 바뀜은 delegate 훅이 지은 앱 메시지로 받는다.

요청은 액션이다

단추가 클립보드 요청을 그대로 돌려준다. logic thread가 정한 순간에 넣을 때는 app_host::post_clipboard_request를 부른다. 잘라 온 것을 옮긴 뒤 비울 때는 읽은 번호(expected_sequence)를 싣는다.

  • 경로는 UTF-8 절대 경로다. 하나라도 절대 경로가 아니면 아무것도 넣지 않는다.
  • 빈 목록은 클립보드를 비운다. 잘라 둔 항목을 붙여 넣어 옮긴 뒤 같은 항목이 다시 붙지 않게 하는 자리다.
  • 파일을 옮기거나 지우지 않는다. 잘라내기는 받는 쪽에 "옮겨 달라"는 뜻만 싣는다. 옮기는 것은 앱이다.

답과 바뀜은 delegate 훅이 짓는다

  1. 임자(owned)만 보지 않는다. 같은 앱이 글을 복사하거나 클립보드를 비워도 임자는 이 앱이다. owned && has_files일 때만 "우리 것"이다.
  2. 잘라 넣은 뒤 처음 온 번호를 적어 두고, 그 번호의 파일 목록일 때만 표시를 남긴다.
  3. supported가 거짓이면 이 플랫폼에 파일 클립보드가 없다. 목록이 비면 붙일 파일이 없다. 읽기를 청하면 답은 늘 온다.
  4. 잘라 온 목록이면 읽은 번호를 든다. 옮긴 뒤 그 번호로 비우면, 그 사이 사용자가 다른 것을 복사했을 때는 지우지 않는다.
  • Android·iOS는 넣기를 무시하고, 읽기 답의 supported가 거짓이다.
  • 헤더 주석(make_clipboard_changed_message)은 "지금은 Win32만 알린다"고 적지만 macOS·iOS host도 바뀜 알림을 부른다. 바뀜 메시지가 Windows에서만 온다고 짜지 않는다.
  • file_clipboard_content::sequence와 clipboard_change::sequence는 클립보드가 바뀔 때마다 느는 번호다. 지원하지 않는 플랫폼은 0이다.

보안과 한계

라이브러리가 막아 주는 것과 앱에 남는 것이다. 인증서 검증을 끄는 손잡이는 어디에도 없다. 밖에서 오는 값에는 모두 상한이 있다.

TLS와 평문

  • Windows HTTP는 TLS 1.2·1.3만 켠다 (1.3을 걸 수 없는 OS면 1.2만). Android HTTP는 플랫폼 기본값과 인증서 검증을 그대로 쓴다 — 버전을 묶지 않아 Android 9 이하는 1.0·1.1도 받을 수 있다. Apple HTTP는 ephemeral 세션이고 ATS가 평문을 막으면 secure_failure다.
  • Windows WebSocket 세션은 TLS 버전 옵션을 따로 걸지 않는다. Android WebSocket은 기본 SSL 소켓에 호스트 이름 검사를 켠다.
  • TLS가 서지 않은 이유(인증서 만료·이름 불일치·믿지 못할 CA…)는 secure_failure의 message에 붙는다.
  • Android의 network security config가 그 host로 평문을 막으면 HTTP는 선을 건드리기 전에 secure_failure로 답한다. WebSocket도 같은 정책을 본다.

재지정

  • 기본은 따라가기(follow), 최대 10회다.
  • https→http는 따라가지 않는다. Android·Apple 코드는 그 3xx를 답으로 돌려준다. Windows는 WinHTTP의 정책 플래그(WINHTTP_OPTION_REDIRECT_POLICY_DISALLOW_HTTPS_TO_HTTP)에 맡긴다. 그때 Windows가 3xx를 답으로 주는지 오류로 주는지는 확인하지 못했다 — 저장소의 test는 되돌이 http만 쓴다. 헤더의 secure_failure 주석은 이 걸음을 그 갈래에 넣지만, 같은 헤더의 재지정 주석과 Android·Apple 코드는 3xx를 답으로 준다.
  • 다른 출처로 옮길 때 앱이 붙인 헤더를 지운다. 남는 것은 Accept·Accept-Language·Cache-Control·Range·If-Range·If-None-Match·If-Modified-Since·Depth뿐이다. 지울 이름이 아니라 남길 이름을 정해서, 인증 헤더가 다른 도메인으로 새지 않는다.
  • 몸이 있는 요청은 따라가지 않는다. 따라간 303은 GET(HEAD는 그대로)이 되고, 301·302의 POST도 GET이 된다. 확장 메서드는 동사를 바꾸지 않으며 303을 따라가지 않는다.

주입과 크기

헤더 이름은 token이어야 하고, 이름·값에 CR·LF·NUL이 있으면 요청 전체가 invalid_header다. Windows는 헤더 글이 올바른 UTF-8이 아니어도 거절한다. URL에 CR·LF·NUL이 있으면 invalid_url이다.

charset과 냄새 맡기

  • charset이 없거나 utf-8·utf8·us-ascii·ascii면 UTF-8로 읽는다. 옛 HTTP의 latin-1 기본값을 따르지 않는다. 깨진 바이트는 U+FFFD로 바꿔 담고 parse_error에 적는다.
  • 그 밖의 charset은 transcode 갈고리가 옮긴다. 갈고리가 모르는 이름이면 바이트를 그대로 두고 이유만 적는다. 갈고리가 돌려준 글도 다시 UTF-8 검사를 한다.
  • iso-8859-1·latin1은 세 백엔드 모두 windows-1252로 읽는다. 변환이 실패할 때의 결과는 플랫폼마다 다르다 (플랫폼 차이).
  • 바이트로 갈래를 짐작하는 것은 Content-Type이 없거나 읽을 수 없거나 application/octet-stream일 때뿐이고, 그때도 그림 서명 다섯만 본다. json·text·ico는 맡지 않는다. 서버가 구체적인 형식을 말했으면 뒤집지 않는다 — png 바이트에 text/plain이면 글이다.

proxy

  • use_system_proxy가 참이면 시스템 설정을 따른다. 거짓이면 Windows는 세션을 proxy 없이 열고 요청 손잡이마다 직접 연결을 다시 못박는다. 세션만 그렇게 열면 요청마다 proxy 해석이 뜨고, 그것이 묶이는 중에 손잡이를 닫으면 프로세스가 죽을 수 있다는 것이 설계 문서의 기록이다 (PAC·WPAD 환경은 확인하지 않았다고 적혀 있다).
  • Android는 거짓일 때 proxy 없이, Apple은 빈 proxy 사전으로 나간다.
  • WebSocket에는 proxy 손잡이가 없다. Windows는 늘 시스템 proxy를 타고, Android는 proxy 없이 직접 소켓을 연다.
  • WebSocket은 URL 자격 증명·재지정·사용자 지정 헤더·서브프로토콜·압축 확장을 하지 않는다.

SMB · 비밀 저장소 · 주소 · 둘째 인스턴스

  • SMB는 NTLM만이고 SMB 2.02–3.1.1을 협상한다. Kerberos·SMB1은 없다. 서명은 서버가 요구할 때 따른다. 암호는 오류 글·logcat에 남기지 않고 넘긴 사본과 연결 장부의 열쇠를 지우지만, 모든 사본을 지운다고 보장하지는 않는다.
  • 비밀 값은 이 기기·이 사용자에게만 열린다. Windows는 같은 사용자의 다른 프로세스가 읽을 수 있다. Android 키는 Keystore 밖으로 나오지 않는다. Apple은 기본 접근 목록이라, 다시 서명한 실행 파일은 OS가 허락을 묻는다.
  • open_url은 허용 목록 밖을 열지 않는다. scheme을 RFC 3986대로 읽고, 공백으로 시작·끝나거나 C0·DEL·C1 제어 문자가 섞이면 거짓이다. 도메인은 보지 않는다 — 표시 글과 실제 주소를 함께 보이는 것은 앱의 일이다.
  • 둘째 인스턴스의 인자는 같은 데스크톱의 어느 프로세스든 보낼 수 있다. 라이브러리는 모양만 검사한다. macOS는 소켓을 사용자 전용 임시 폴더에 두고 보낸 사용자를 다시 확인한다.

함정

오류 없이 조용히 틀리는 자리들이다. 주석·설계 문서와 코드가 다른 곳은 코드를 따랐다.

  1. inbox가 차면 답이 조용히 사라진다. app inbox는 1024칸이고 넘치면 새 것을 버린다. post_app_message는 알리지 않는다. HTTP·SMB·WebSocket의 deliver는 void라 그 답은 다시 오지 않고, 표를 기다리던 화면이 영원히 "보내는 중"에 남는다. 파일 감시의 bool deliver만 거짓을 답하면 다시 낸다 — 그래서 감시에서는 post_app_message_ticketed(...) != 0을 그대로 답해야 하고, 참을 답하고 값을 잃으면 감시자는 모른다. HTTP의 대책은 답을 잃지 않기.
  2. stop() 뒤에는 "표마다 답 하나"가 깨진다. HTTP 세 백엔드는 배달을 먼저 끄고 pump를 join한 뒤 남은 요청을 stopped로 접으므로, stopped 답이 화면을 정리해 줄 것이라 기대하지 않는다 (test도 "0개도 옳다"고 적는다). SMB와 감시도 내지 않은 답·묶음을 버린다. 예외는 WebSocket이다 — stop()이 돌아오기 전에 closed(오류 stopped, 코드 1006)가 올 수 있으니 deliver가 쥔 host가 stop()이 끝날 때까지 살아 있어야 한다.
  3. deliver 안에서 stop을 부르지 않는다. 자기 thread를 join하게 된다. debug 빌드는 assert로 잡는다.
  4. deliver가 잡은 것보다 먼저 멈춘다. 소멸자에 맡기지 말고 stop_workers()에서 stop()한다. 그 함수는 UI thread에서 불리므로 logic이 소유한 client는 원자적 손잡이로 본다.
  5. 늦은 답은 표로 거르고, 답이 온 흐름은 표를 잊는다. 취소한 흐름·바뀐 화면의 답은 늦게 온다. 표를 잊지 않으면 취소 단추가 끝난 표를 겨누고 cancel은 아무 일도 하지 않는다.
  6. 주석이 말하는 것보다 플랫폼이 많다. luil은 Windows·Android·macOS·iOS 넷을 세운다. 여러 헤더 주석이 Windows·Android(또는 Windows·Android·macOS)만 든다 — file_watcher.h(iOS kqueue 빠짐), secret_store.h(iOS는 macOS 구현), smb_client.h("Android 전용"이지만 iOS도 선다), platform_services.h의 unsupported 목록, 클립보드 바뀜 훅("Win32만 알린다"지만 macOS·iOS도 알린다). 플랫폼 분기는 플랫폼 차이의 표를 따른다.
  7. 되풀이 요청을 멈추는 영구 오류에 invalid_method도 든다. 헤더 주석은 invalid_url·unsupported_scheme·invalid_header 셋만 들지만 failure_is_permanent는 넷을 본다. 이름이 틀린 확장 메서드는 대개 start_heartbeat가 먼저 표 0으로 거절하고, 회차의 답으로 invalid_method가 오면 그 흐름은 그 답에서 last로 끝난다 — 다시 시도되지 않는다.
  8. 몸 있는 GET·HEAD는 플랫폼마다 다르다. Windows는 그대로 보내고, Android·Apple은 send가 표 0으로 거절한다. 같은 코드가 한쪽에서만 답을 받는다.
  9. Android의 charset과 압축은 주석과 다르다. 기본 변환은 utf-16만이 아니라 JVM CharsetDecoder로 그 밖의 이름도 옮기고, 엄격해서 실패하면 빈 글과 이유가 온다(Windows는 바꿔 넣는다). 압축은 플랫폼이 몰래 푸는 것이 아니라 luil이 gzip·deflate를 모두 푼다. 같은 몸이 플랫폼마다 다른 글이 될 수 있다.
  10. https→http 재지정은 플랫폼마다 다른 답이 될 수 있다. Android·Apple은 3xx를 답으로 준다. Windows는 WinHTTP 정책 플래그에 맡겨, 그 답이 3xx인지 secure_failure 같은 오류인지 코드로 확인할 수 없다. 헤더의 secure_failure 주석은 이 걸음을 오류로 적는다. 앱은 둘 다 견딘다.
  11. iOS의 open_url은 늘 ok다. 메인 큐에 비동기로 넘기고 바로 답한다. 헤더 주석의 "열 앱이 없으면 not_found"는 오지 않는다. 다른 플랫폼의 ok도 "넘겼다"까지다.
  12. macOS도 둘째 실행의 인자를 받는다. 설계 문서 머리는 "Win32 전용"이라 적지만, macos::application_environment::instance를 달면 macOS host가 delegate의 win32::window_delegate::on_instance_arguments를 부른다. 데스크톱 둘이면 받는 코드도 둘에 맞춘다.
  13. SMB는 iOS에서도 선다. 헤더와 오류 글은 "Android 전용"이라 적지만 LUIL_ENABLE_SMB=ON이면 iOS도 libsmb2로 세운다. 권한과 찾기의 동작은 둘이 다르다 (iOS는 권한을 묻는 API가 없다).
  14. Android 비밀 키의 별칭은 luil-secret:<hex(service)>다. 설계 문서의 luil-secret:<service>가 아니다. Windows 자격 증명 이름도 luil-v2:<hex(service)>-<hex(name)>라 OS 도구로 찾을 때는 16진 이름을 찾는다.
  15. 비밀 저장소의 이름 규칙이 플랫폼마다 다르다. NUL이 든 이름은 Windows가 받고 macOS가 거절한다. 그리고 모두 동기라 UI thread에서 부르지 않는다.
  16. receive_timeout은 전체 시한이 아니다. 조각 사이의 상한이다. "얼마 안에 끝난다"는 total_timeout뿐이고 그것도 바닥이지 천장이 아니다.
  17. 4xx·5xx는 오류가 아니다. error.empty()가 참이다. 성공은 ok()로 묻는다.
  18. parse_error가 있어도 값이 있을 수 있고, 갈래는 낮아지지 않는다. 깨진 JSON도 kind == json이고 json이 비어 있다. 깨진 UTF-8 글은 U+FFFD가 든 채 text가 선다. 슬롯마다 따로 묻는다.
  19. 서버가 말한 형식이 이긴다. png 바이트에 text/plain이면 글이다. 서버가 틀린 것을 알면 parse.assume_kind를 준다. html은 풀지 않고(html_as_text를 켜도 parsed()는 거짓), svg는 bytes다.
  20. 쉬는 되풀이를 취소한 마지막 답은 앞 회차와 같은 sequence를 단다. 지어 낸 답의 sequence가 지금까지의 회차 수라서다. WinHTTP 백엔드 코드에서 읽은 것이고 Android·Apple의 같은 자리는 읽지 않았다. 회차가 있었던 뒤의 취소를 보는 test는 없다. 중복은 sequence가 아니라 last로 가른다.
  21. method_name의 표준 동사 검사는 대소문자를 가린다. u8"get"은 거절되지 않고 확장 메서드로 받아 소문자 그대로 선에 실린다. test는 propfind가 그대로 실리는 것과 GET·DELETE·CONNECT의 거절만 보고, 소문자 get은 코드에서 읽은 것이다.
  22. Android에서 create를 너무 일찍 부르지 않는다. host가 JavaVM을 적기 전이면 실패한다.
  23. WebSocket URL은 소문자 scheme과 ASCII다. WSS://나 한글 경로는 create가 거절한다. 그리고 opened 전의 보내기는 거짓이다.
  24. WebSocket의 끝맺음이 플랫폼마다 다르다. macOS·iOS의 로컬 Close는 상대를 기다리지 않고 곧 끝난다. Windows는 상한을 넘는 메시지를 받으면 1009 Close를 보내지 않고 끊는다. Android는 Java 전송부를 APK에 싣지 않으면 모든 조작이 실패한다.
  25. 감시는 처음 목록을 주지 않고, modified는 쓰기 완료가 아니다. add 먼저, 읽기는 그다음이다. 읽다 해석에 실패하면 이전 값을 지키고 다음 묶음을 기다린다. 폴더를 통째로 옮기면 그 아래 항목마다 알리지 않을 수 있다.
  26. replace_file_atomically는 폴더를 만들지 않고, 같은 프로세스 안에서 같은 파일을 동시에 바꾸면 겹친다. 임시 이름이 <경로>.<pid>.tmp라서다. POSIX에서는 결과 파일의 권한이 0600이 된다. 뒤의 둘은 코드에서 읽은 것이고 test가 보지 않는다.
  27. on_instance_arguments를 만들지 않으면 둘째는 늘 failed다. 기본 구현이 거짓을 답한다. send_to_primary는 부른 thread를 시한까지 막고, 시한이 지난 보내기도 나중에 닿을 수 있어 다시 보내면 중복이 생긴다.
  28. SMB의 cancel은 이미 끝난 요청에 닿지 않는다. 배달을 기다리던 답은 본래 결과로 온다. 그리고 stop의 "한 번만" 표지가 원자 값이 아니라 두 thread가 동시에 부르는 경우를 막지 않는다. 둘 다 코드에서 읽은 것이고 test가 없다.
  29. SMB 공유 목록을 거르는 것은 앱이다. C$·ADMIN$·IPC$와 프린터도 온다. iOS의 찾기가 빈 목록으로 끝나도 "서버 없음"이라 단정하지 않는다 — 권한 창이 떠 있는 동안 시작한 찾기는 빈 목록(성공)으로 끝난다.

자주 묻는 질문

HTTP 답은 어느 thread로 오나? 요청마다 callback을 줄 수 있나?

client가 소유한 thread에서 deliver가 불린다. 요청마다 callback은 없다.

logic thread도 UI thread도 아니다. 그 자리에서 post_app_message로 logic thread에 옮기고, handle에서 response.ticket으로 어느 요청의 답인지 가른다 (개념).

send가 0을 돌려준다.

손잡이가 서기 전의 거절이다. 답은 오지 않고 error에 이유가 있다.

URL·scheme·헤더·메서드 규칙 위반, 동시 상한(max_in_flight 32)이나 배달 대기 상한(max_pending_responses 128) 초과, 멈춘 client다. 몸을 실은 GET·HEAD도 Android·Apple에서는 여기서 거절된다 — Windows는 그대로 보내므로 한 플랫폼에서만 시험하면 놓친다.

취소하면 답이 안 오나?

온다. cancelled를 실은 답 하나다.

취소가 답을 지우면 "아직 오는 중"과 "접었다"를 앱이 따로 들어야 한다. 모르는 표·끝난 표의 cancel은 아무 일도 하지 않는다. test가 "정확히 한 번"을 잠근다 (취소).

stop()을 부르면 남은 요청에 stopped 답이 오나?

기대하지 않는다. WebSocket의 closed만 예외다.

HTTP 세 백엔드는 배달을 끄고 pump를 join한 뒤에 남은 요청을 stopped로 접으므로 그 답은 앱에 닿지 않는다. test도 "0개도 옳다"고 적는다. SMB와 파일 감시도 배달하지 않은 답·묶음을 버린다. WebSocket은 stop()이 돌아오기 전에 closed(오류 stopped, 코드 1006)를 낼 수 있다. 화면을 다시 쓰는 중에 client를 멈췄다면 앱이 표를 직접 잊는다.

답이 몰려 app inbox가 차면?

새 메시지가 조용히 버려진다. 파일 감시만 다시 낸다.

app inbox는 1024칸 reject_newest다. HTTP·SMB·WebSocket의 deliver는 void라 버려진 답은 다시 오지 않는다. 감시의 deliver는 post_app_message_ticketed(...) != 0을 답하면 거절된 묶음을 다음 변경과 합쳐 다시 낸다. HTTP는 같은 함수의 0을 보고 잃은 표를 적어 둔다 (답을 잃지 않기). 버려진 수는 app_inbox_statistics()가 센다.

404·500은 어떻게 오나?

오류가 아니라 답이다. error.empty()가 참이고 ok()가 거짓이다.

몸은 평소대로 풀린다. application/problem+json 오류 몸은 json으로 온다. 성공은 언제나 ok()로 묻는다.

JSON인데 text/plain으로 온다.

요청의 parse.assume_kind = http_body_kind::json을 준다.

라이브러리는 서버가 구체적인 형식을 말하면 바이트를 보고 뒤집지 않는다. 서버가 틀린 것을 아는 쪽은 앱이고, 그 문이 assume_kind다. 빈 몸은 그래도 empty다.

euc-kr이나 deflate로 압축된 응답이 플랫폼마다 같게 풀리나?

세 백엔드 모두 CP949 계열 표로 옮기지만, 옮기지 못할 때의 답이 다르다. Android는 주석과 달리 charset과 압축을 모두 직접 다룬다.

euc-kr은 Windows가 코드 페이지 949로, Android가 JVM CharsetDecoder(windows-949)로, Apple이 CoreFoundation 표로 옮긴다. 헤더 주석은 "Android 기본 변환은 utf-16만"이라 적지만 코드는 그렇다. 옮길 수 없는 바이트를 만나면 Windows는 바꿔 넣고 이유를 적고, Android·Apple은 엄격해서 빈 글과 이유를 준다. 압축은 Android에서도 luil이 gzip·deflate를 모두 푼다 (설계 문서의 "deflate는 풀지 않는다"는 코드와 다르다). 다른 규칙이 필요하면 http_client_config::transcode를 준다.

큰 그림이 메모리를 터뜨리지 않게 하려면?

parse.image.decode에 상한을 준다. 섬네일이면 parse.image.animated = false.

4000×3000 사진 하나가 48 MB이고 움직이는 그림은 장 수가 곱해진다. 받는 몸 자체를 줄이려면 max_body_bytes를 낮춘다 (그림 받기).

https에서 http로 재지정되면? POST가 307을 받으면?

둘 다 따라가지 않는다. 다만 https→http의 답 모양은 플랫폼마다 다를 수 있다.

Android·Apple은 그 3xx를 답으로 준다. Windows는 WinHTTP의 정책 플래그에 맡겨서, 3xx가 답으로 오는지 오류로 오는지 확인하지 못했다. 헤더의 secure_failure 주석은 이 걸음을 그 오류로 적는다. 몸이 있는 요청(POST·307)은 정책과 무관하게 따라가지 않고 3xx가 답으로 온다 — 앱이 Location을 보고 다시 보낸다.

인증 헤더가 다른 도메인으로 새지 않나? 인증서 검증을 끌 수 있나?

다른 출처로 재지정되면 여덟 이름 밖의 앱 헤더를 지운다. 검증을 끄는 손잡이는 없다.

남는 것은 Accept·Accept-Language·Cache-Control·Range·If-Range·If-None-Match·If-Modified-Since·Depth다. Windows HTTP는 TLS 1.2·1.3만 쓴다 (보안과 한계).

주기적으로 상태를 물으려면? 오류가 나면 멈추나?

start_heartbeat 하나다. 전송 오류와 4xx·5xx로는 멈추지 않는다.

답을 받은 뒤 interval을 쉬므로 회차가 겹치지 않는다. 멈추는 것은 cancel·max_rounds·stop과 영원히 실패할 오류다 — 헤더 주석은 invalid_url·unsupported_scheme·invalid_header를 들지만 코드는 invalid_method도 영구 오류로 본다. "몇 번 틀리면 물러선다"는 앱이 센다 (되풀이 요청).

WebSocket이 끊기면 저절로 다시 붙나? send_text가 거짓이다.

다시 붙지 않는다. 새 client를 세운다. 보내기가 거짓이면 넣지 못한 것이다.

아직 열리지 않았거나(opened 전), 닫는 중이거나, 큐(64개·8 MiB)가 찼거나, 메시지가 상한보다 크거나, 올바른 UTF-8이 아닐 때다. 숨은 무한 큐는 없다 (WebSocket).

SMB는 어느 플랫폼에서 쓰나? Windows에서는?

Android와 iOS에서, LUIL_ENABLE_SMB=ON으로 빌드했을 때만 선다.

헤더 주석과 오류 글은 "Android 전용"이라 적지만 빌드 규칙은 iOS에서도 libsmb2로 세운다. Windows·macOS에서는 create가 nullptr이다. Windows는 운영체제의 SMB(UNC 경로)로 읽는다.

감시를 걸면 지금 있는 파일 목록도 오나? rescan이 참이면?

오지 않는다. add 뒤에 앱이 읽는다. rescan은 넘쳤다는 뜻이다.

거꾸로(읽고 나서 add) 하면 그 사이의 변경을 놓친다. rescan이 참이면 changes는 일부이거나 비었으니 그 범위를 다시 훑는다.

비밀은 어디에 어떤 이름으로 저장되나? 얼마나 크게?

값은 2560바이트까지다. OS 쪽 이름은 service·name의 16진이다.

Windows는 자격 증명 관리자의 luil-v2:<hex(service)>-<hex(name)>이다. Android는 Keystore 키 별칭 luil-secret:<hex(service)>와 앱 내부 파일 luil-secrets/<hex(service)>-<hex(name)>이다 — 설계 문서의 luil-secret:<service>가 아니다. macOS·iOS는 Keychain 일반 암호(서비스·계정)다. 앱을 지웠다 다시 깐 Android에서는 키가 없어 not_found가 온다.

open_url이 ok인데 아무것도 열리지 않았다.

ok는 "넘겼다"까지다. iOS는 늘 ok다.

Windows는 브라우저가 실제로 열었는지 모른다. Android 10+는 앞에 보이지 않는 앱의 Activity를 OS가 조용히 막아도 ok다. iOS는 메인 큐에 비동기로 넘기고 곧 ok를 답하므로, 헤더 주석의 "열 앱이 없으면 not_found"를 iOS에서 기대하지 않는다. 사용자가 링크를 누른 그 순간에 부른다.

둘째 실행의 인자를 받으려면? macOS에서도 되나?

된다. Windows는 window_environment::instance, macOS는 macos::application_environment::instance를 달고 on_instance_arguments를 만든다.

macOS host는 delegate가 win32::window_delegate를 구현했으면 그 훅을 메인 thread에서 부른다. 설계 문서 머리는 "Win32 전용"이라 적지만 코드는 macOS도 받는다. 훅은 게시만 하고 post_app_message_ticketed(...) != 0을 답한다. Android·iOS는 둘째가 생기지 않는다 (send_to_primary는 unsupported).

헤더 주석에는 Windows·Android만 있는데 macOS·iOS에서는?

luil은 네 플랫폼을 세운다. 주석보다 개요의 표와 플랫폼 차이를 따른다.

파일 감시(iOS는 kqueue), 비밀 저장소(iOS는 macOS 구현), SMB(iOS도 선다), 클립보드 바뀜 알림(macOS·iOS도 알린다), unsupported 목록(blocking_io_canceller는 Windows만 된다)이 주석보다 넓다. iOS 기기에서 돌려 본 결과는 이 문서에 없다.

앱을 닫을 때 무엇을 하나?

logic_driver::cancel()에서 cancel_all(), stop_workers()에서 모든 부품의 stop().

둘 다 UI thread에서 불리므로 logic이 소유한 client는 원자적 손잡이로 본다. 종료 저장은 그 사이(종료 메시지를 처리하는 logic thread)에서 replace_file_atomically로 한다 (종료).
