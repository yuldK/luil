불변 UI tree

화면은 고치는 것이 아니라 다시 짓는 것이다. 게시한 tree는 아무도 고치지 않으므로 세 스레드가 잠금 없이 함께 읽고, element는 주소가 아니라 값인 id로 frame을 건넌다.

이 문서를 읽으면

  1. 불변 tree가 잠금 없는 공유와 단순한 갱신을 동시에 주는 이유를 설명한다.
  2. element의 정체성이 주소가 아니라 ui_element_id(kind, owner)인 이유를 안다.
  3. tree가 생성 때 한 번 짓는 색인과 그 쓰임을 말할 수 있다.
  4. hit test와 Tab 순서가 그리기 순서에서 나오는 규칙을 손으로 따라갈 수 있다.

게시하면 고치지 않는다

element는 짓는 동안만 바뀔 수 있다. tree로 게시되는 순간부터는 읽기 전용이다.

게시된 tree 하나를 세 곳이 동시에 읽는다. UI thread는 그리고, input thread는 hit test하며, Win32의 caption 비클라이언트 판정은 UI thread에서 동기로 같은 게시본을 조회한다. 아무도 쓰지 않으니 tree를 위한 잠금이 필요 없다. 잠금이 필요한 곳은 게시본을 건네는 slot 하나뿐이다.

"값을 바꾸고 싶다"는 다음 frame에서 다른 값으로 element를 다시 만드는 것으로 이룬다. 그래서 ui_element는 복사도 이동도 막혀 있고, setter는 게시 전에만 쓴다. 옛 tree는 shared_ptr<const ui_tree>라서, 아직 그것을 그리는 스레드가 있으면 그 스레드가 놓을 때까지 산다.


부분 갱신 경로가 없다상태가 바뀌면 기존 element를 고치지 않고 새 tree를 게시한다. "이 라벨만 고친다"는 길이 없으니 화면의 구조와 앱 상태가 섞이지 않는다. 화면은 언제나 make_frame(상태)의 결과다.

element의 정체성은 id다

frame마다 객체가 새로 생기므로 주소로는 "같은 버튼"을 알아볼 수 없다. 그래서 값인 id를 쓴다.

  1. kind는 "무슨 종류인가"(버튼, 목록 행…), owner는 "그 종류 중 어느 것인가"를 가르는 앱 정의 문자열(항목 키, 행 번호…)이다. hover·눌림·초점은 모두 이 값으로 비교된다.
  2. 0부터 end_of_library_kinds 앞까지는 라이브러리 kind, 1024부터는 앱 kind다. 라이브러리는 앱 kind의 뜻을 모른다.
  3. 처음 예약 대역은 64였다. 라이브러리 kind가 그것을 넘어 앱의 첫 kind들과 같은 수가 되면서, kind로 찾는 코드가 서로를 집을 수 있었다. 대역을 1024로 넓히고 static_assert로 다시는 겹치지 못하게 했다.
  4. 앱은 application_element_kind(index) = 1024 + index로 상수를 만든다. luil 개요 문서의 hello가 kind_label, kind_button을 이렇게 정했다.

id의 유일성 범위는 tree 하나다. popup이나 보조 창처럼 다른 표면의 tree는 같은 id를 다시 써도 된다. 상호작용 상태는 표면 id와 함께 게시되므로 섞이지 않는다.

실험: 새 객체, 같은 id

작은 할 일 앱의 tree를 매 frame 새로 짓는다. 객체 번호는 매번 바뀌지만, 포인터를 올린 행의 hover는 id로 이어진다.

행 위에 포인터를 올리고 창 크기 바꾸기나 같은 상태로 다시 짓기를 눌러 보라. 오른쪽 객체 번호(#…)가 모두 바뀌어도 hover가 그대로인 것은 hover가 row:b 같은 id로 저장되어 있어서다. 버그를 켜면 tree의 진단이 그것을 드러낸다.

element가 하는 일

배치하고, 그리고, 맞는지 답하고, 다음에 언제 달라지는지 예고한다. 모두 const이거나 게시 전에만 불린다.

  1. 부모가 준 slot(물리 픽셀) 안에서 자기 bounds와 자식 배치를 확정한다. 게시 전, logic thread의 make_frame 안에서 불린다(배치).
  2. 내용이 원하는 크기다. 배치는 여전히 부모가 정하고, 맞춤 열처럼 묻는 컨테이너만 부르는 선택적 질문이다. config만 보고 답한다.
  3. 자신과 자식을 그린다. hover·눌림은 element가 갖지 않고 interaction_snapshot으로 받아 자기 id와 비교한다. 그래서 같은 tree를 다른 상호작용으로 다시 그릴 수 있다.
  4. 좌표를 포함하는 가장 안쪽의 상호작용 대상을 돌려준다. 기본 구현은 자식을 역순으로 찾는다(4.6).
  5. 시간이 흘러야 그림이 바뀌는 element(spinner, caret, 토스트의 흐려짐)만 재정의한다. 기본값 nullopt는 "시간이 흘러도 그대로"다. 플랫폼은 tree 전체의 가장 이른 시각에 timer 하나만 건다.

tree가 생성 때 한 번 짓는 색인

tree는 불변이므로 질문의 답을 미리 계산해 둘 수 있다. 생성자가 pre-order로 한 번 훑으며 색인을 짓는다.

  1. 색인을 짓고, 초점을 가두는 element와 기본 버튼을 한 번 찾는다. 가둠 밖의 기본 버튼은 이 자리에서 걸러 둔다. 매 frame 묻는 질문을 매번 계산하지 않는다.
  2. pre-order(부모 먼저, 자식은 담은 순서) 목록과 kind별 id 목록이다. 키보드 탐색이 ids_of_kind로 쓴다.
  3. 해시 맵에 넣으며, 같은 id가 이미 있으면 뒤의 것을 중복 목록에 남긴다. find는 포인터 이동·tooltip이 매 frame 부르는 길이라 문자열 선형 비교 대신 해시다.
  4. 보이는데 arrange가 한 번도 불리지 않았으면 진단 목록에 남긴다. 숨긴 element는 배치하지 않아도 된다.
  5. 보조 기술(스크린 리더)이 읽는 접근 tree의 부모·형제 자리를 적어 둔다. 형제마다 root에서 부모를 다시 찾으면 긴 목록의 순회가 형제 수의 제곱이 되므로 O(1) 색인으로 둔다(플랫폼과 host).
  6. 자식에게 내려갈 때 "가장 안쪽 스크롤 창"과 "여기까지 모두 보이는가"를 넘긴다. 숨긴 가지의 애니메이션은 창을 깨우지 않는다.

hit test: 위에 그린 것부터

뒤에 담은 자식이 위에 그려진다. 그래서 자식을 뒤에서부터 묻고, 처음 맞은 것이 답이다.

  1. 보이지 않으면 자식까지 볼 것 없이 놓친다.
  2. 스크롤 창처럼 자식을 자르는 컨테이너는, 좌표가 자기 bounds 밖이면 잘려 보이지 않는 자식이 눌리지 않게 안을 보지 않는다.
  3. 마지막 자식부터 묻는다. 스크롤로 자식이 부모 slot 밖에 걸칠 수 있어, 자르지 않는 부모는 자기 bounds로 탐색을 막지 않는다.
  4. 자식이 모두 놓쳤고 좌표가 내 안이면, 상호작용 대상이거나 hit_opaque일 때 내가 답이다. hit_opaque는 modal 배경·메뉴·토스트처럼 위에 뜬 판의 빈자리 클릭이 아래로 새지 않게 흡수한다.
해 볼 것: popup의 빈 아래쪽, 목록 아래로 잘려 나간 다섯째 행, popup과 겹친 행 위에 포인터를 대 보라. 체크를 하나씩 끄면 답이 어떻게 바뀌는지 오른쪽 경로가 보여 준다.

그리기 순서가 곧 Tab 순서

따로 매기는 번호가 없다. 보이는 tree를 pre-order로 훑은 순서가 Tab이 도는 순서다.

  1. modal dialog처럼 초점을 가두는 element가 있으면 그 안만 훑는다. 밖의 자리는 목록에 없다.
  2. 색인은 보이지 않는 자식도 담으므로 여기서는 tree를 직접 걷는다.
  3. 탭 막대·라디오 묶음처럼 항목이 줄선 것(focus group)은 Tab에서 한 자리다. 그 안은 화살표가 돈다. 중첩된 묶음도 같은 규칙으로 접힌다.
  4. 초점을 받을 수 있으면 넣고 자식으로 내려간다. 화면에 보이는 순서가 곧 도는 순서다.

왜 번호를 따로 두지 않나배치와 순서가 두 곳에 살면 반드시 어긋난다. 순서를 바꾸고 싶으면 order_focus()로 조정하고, 순회에서 빼려면 tab_stop을 끈다. 4.6의 실험에서 Tab 순서 보이기와 목록을 focus group으로를 켜 보라. 키 라우팅과 초점 규칙 전체는 입력과 초점 문서에서 다룬다.

조용한 오동작을 드러내는 진단

어떤 버그는 아무 오류도 내지 않고 화면에서 무언가를 조용히 사라지게 한다. tree는 그런 버그를 값으로 드러낸다.

duplicate_ids()

find·hover·초점이 전부 id로 상태를 잇는다. 같은 id가 둘이면 find는 늘 첫 것을 돌려주고, hover는 두 element에 함께 켜진다. 오류는 나지 않는다.

tree는 색인을 지으며 뒤쪽 중복을 모아 둔다. 비어 있어야 정상이고, 앱의 테스트가 이것을 확인한다.

unarranged()

배치 사슬은 어디서든 끊길 수 있다. 끊긴 element는 bounds가 0이라 그려지지도 맞지도 않고 화면에서 조용히 사라진다.

보이는데 arrange가 불리지 않은 element를 모아 둔다. 넘치지 않는 탭 막대의 넘침 버튼처럼 일부러 숨긴 것은 세지 않는다.

위 테스트는 쓰는 법을 보이려고 지은 예시다. build_settings_screen은 저장소에 없는 이름이다.

tree가 위에 얹는 것, tree 안의 tree

초점 테와 끌기 표시, tooltip은 element가 아니라 tree가 맨 위에 그린다.

  1. root부터 자식까지 그린다.
  2. 키보드로 옮긴 초점에만 그린다. 한곳에서 얹으므로 모든 element의 초점 테가 같은 모양이다.
  3. 끄는 중일 때만 ghost와 놓을 자리 강조를 얹는다. 조상의 잘림을 반영한 visible_bounds()라 강조가 잘린 영역을 넘지 않는다.
  4. tooltip은 무엇보다 위에 있어야 하므로 마지막이다.

독립 tree를 그리는 element가 둘 있다. 커스텀 tooltip 내용과 화면 전환의 떠나는 화면이다. 둘 다 앱이 따로 지은 shared_ptr<const ui_tree>이고 element가 빈 snapshot으로 그리기만 한다. 그 안의 id는 주 tree의 색인·hit test·초점·접근 tree에 들어가지 않으므로, 같은 id가 두 tree에 있어도 겹치지 않는다. 화면 전환은 애니메이션 문서에서 다시 본다.

요약

  1. tree는 frame마다 새로 짓고, 게시한 뒤에는 아무도 고치지 않는다. 그래서 UI·input·caption 판정이 잠금 없이 함께 읽는다.
  2. element의 정체성은 주소가 아니라 ui_element_id(kind, owner)다. hover·눌림·초점은 이 값으로 frame을 건넌다.
  3. kind는 라이브러리 대역(0~1023)과 앱 대역(1024~)으로 나뉘고, 둘이 겹치면 static_assert가 막는다.
  4. tree는 생성 때 pre-order로 한 번 훑으며 id·kind·접근 tree 색인과 진단을 짓는다. 같은 id는 첫 등록이 이긴다.
  5. hit test는 자식을 역순으로 묻고, 자르는 컨테이너 밖은 보지 않으며, hit_opaque는 빈자리 클릭을 흡수한다.
  6. Tab 순서는 그리기 순서(pre-order)이고, focus group은 한 자리로 접히며, 가둠이 있으면 그 안만 돈다.

자주 묻는 질문

버튼 글자 하나만 바꾸려면?

고칠 길이 없다. 상태를 바꾸면 make_frame이 새 글을 가진 element로 tree 전체를 다시 짓는다.

게시된 element는 읽기 전용으로 공유되고 setter는 게시 전에만 쓴다. 그래서 화면은 언제나 make_frame(상태)의 결과다. hello의 라벨이 그렇게 바뀐다 (게시하면 고치지 않는다, hello 읽기 ②).

매 frame tree 전체를 다시 지으면 느리지 않나?

tree에 담는 element가 많을수록 짓는 값이 커진다. 그래서 긴 목록은 보이는 행만 tree에 넣는다.

생성자는 색인을 지으려고 element를 한 번씩 모두 훑는다. 10만 행 목록도 virtual_list_element는 창에 걸치는 행 위주로만 tree에 세운다. 바뀌지 않은 popup·보조 창의 tree는 다시 짓지 않고 그대로 실어도 된다 (아주 큰 목록, 가상 목록).

id의 kind와 owner에는 무엇을 넣나?

kind는 application_element_kind(index)로 만든 앱 상수(1024 + index)이고, owner는 같은 kind 여럿을 가르는 앱의 문자열이다.

목록 행이라면 행 번호보다 항목의 키가 낫다. 초점은 id로 다음 frame에 이어지므로, 번호를 쓰면 앞에 행이 끼어들 때 초점이 다른 항목으로 옮겨 간다 (코드에서 확인한 동작). hover는 새 tree를 받을 때 마지막 포인터 자리로 다시 판정한다 (element의 정체성은 id다).

같은 id를 popup이나 보조 창의 tree에서 다시 써도 되나?

된다. id의 유일성 범위는 tree 하나다.

상호작용 상태는 표면 id와 함께 게시되므로 표면끼리 섞이지 않는다. tooltip 내용과 화면 전환의 떠나는 화면처럼 element가 그리는 독립 tree의 id도 주 tree의 색인·hit test·초점에 들지 않는다. 같은 tree 안에서 겹치면 duplicate_ids()에 나타난다 (element의 정체성은 id다, tree 안의 tree).

element가 화면에서 사라졌다. 그려지지도 눌리지도 않는다.

먼저 unarranged()를 본다. 담기만 하고 arrange를 빠뜨린 element는 bounds가 0이라 조용히 사라진다.

그 밖에는 숨긴 조상(set_visible(false))이 있는지, 자르는 조상의 영역 밖에 있는지 본다. 화면 시험에서 duplicate_ids()와 unarranged()가 비었는지 확인하면 두 조용한 오동작이 함께 잡힌다 (조용한 오동작을 드러내는 진단, arrange 계약).

set_visible(false)와 set_enabled(false)는 무엇이 다른가?

숨긴 element는 색인(find)에는 남지만 그리기·hit test·Tab 순서·접근 tree·next_update에서 빠진다. 비활성 element는 그려지고 hit test에도 걸리지만 액션이 실행되지 않는다.

숨긴 조상 아래 가지도 통째로 같고, 숨긴 element는 배치하지 않아도 unarranged()에 세지 않는다. 비활성 element가 hit test에 걸리는 것은 tooltip을 보이기 위해서이고, 실행을 막는 것은 interaction controller다. 비활성 element는 초점을 받지 못해 Tab 순서에서도 빠진다 (hit test, 그리기 순서가 곧 Tab 순서).

초점을 가진 element를 다음 frame에서 빼거나 숨기면?

새 tree를 받는 순간 초점이 거둬진다. 비활성이 되거나 modal 가둠 밖에 남아도 같다.

다시 보이거나 활성이 되어도 초점은 저절로 돌아오지 않는다 (test가 잠근다). 이렇게 거둬진 초점에는 focus_leave_action이 불리지 않는다. 그 element를 뺀 tree를 지은 것이 앱이라 이미 알기 때문이다 (그리기 순서가 곧 Tab 순서, 초점의 규칙).

Tab 순서를 바꾸거나 어떤 element를 빼려면?

빼려면 그 element에 set_tab_stop(false)를 준다. 순서를 바꾸려면 정책의 order_focus를 재정의한다. element마다 번호를 매기는 자리는 없다.

ui_trigger::left_click 액션이 있는 element는 기본으로 Tab 자리다. 액션 없이 초점만 받게 하려면 set_tab_stop(true)를 준다. 탭 막대·라디오처럼 한 자리로 묶고 그 안은 화살표로 돌게 하려면 set_focus_group이다. order_focus는 Tab을 누를 때만 불린다 (그리기 순서가 곧 Tab 순서, 초점의 규칙).

위에 띄운 판의 빈 곳을 누르면 아래 버튼이 눌린다.

판에 set_hit_opaque(true)를 준다. 상호작용이 없어도 자기 bounds 안의 hit를 흡수한다.

hit test는 상호작용 대상이 아닌 element를 지나쳐 그 아래를 본다. modal 배경·메뉴·토스트가 이 값을 쓴다. 키보드까지 가두려면 set_focus_trap(true)를 함께 쓴다. 포인터는 hit_opaque가, 키보드는 가둠이 각자 맡는다 (hit test, 직접 짓는 modal).

스크롤로 잘려 보이지 않는 행이 눌린다.

그 컨테이너가 자식을 자르는지(set_clip_children(true)) 본다. 자르는 컨테이너만 자기 영역 밖의 좌표에서 안을 보지 않는다.

자르지 않는 부모는 스크롤로 자식이 slot 밖에 걸칠 수 있어 자기 bounds로 탐색을 막지 않는다. 라이브러리의 strip_element와 scroll_view_element(scroll_area_element가 안에 쓴다)는 스스로 자른다 (코드에서 확인한 동작). 직접 만든 흘리는 컨테이너는 이 값을 켠다. 자르기는 그리기와 hit test에 함께 걸린다 (hit test).

화면 tree를 단위 시험하려면?

창 없이 ui_tree를 직접 지어 묻는다. find·hit_test·focus_order·duplicate_ids·unarranged가 모두 값으로 답한다.

배치는 element마다 arrange를 부르거나, root가 자식까지 배치하면 make_arranged_tree로 배치와 생성을 묶는다. 라이브러리의 시험(tests/ui_element_tests.cpp)이 같은 방식이다 (조용한 오동작을 드러내는 진단, 창 없이 도는 core).

바뀌지 않은 popup이나 보조 창의 tree도 frame마다 새로 지어야 하나?

아니다. 지난 frame의 shared_ptr<const ui_tree>를 그대로 다시 실어도 된다.

Win32 host는 표면마다 지금 그리는 tree와 새로 실린 tree의 주소를 견주어, 같으면 그 표면을 다시 그리지 않는다. 게시된 tree는 불변이라 주소가 같으면 그림도 같다. 이 대조 규칙은 Win32 test가 잠근다. hover 같은 상호작용이나 테마·글꼴이 바뀌면 tree가 같아도 모든 표면을 다시 그린다 (코드에서 확인한 동작) (언제 다시 그리나).

직접 그리는 element를 만들려면?

ui_element를 상속해 arrange와 draw를 구현한다. arrange에서는 받은 slot으로 set_bounds를 부른다.

생성자는 ui_element_id를 받고, 앱 상태는 생성할 때 값으로 받는다. 자식은 protected add_child로 담고 draw_children으로 그린다. hover는 받은 interaction_snapshot의 id를 자기 id()와 견주어 그린다. 색은 context.palette에서 고르고 (커스텀 그리기에서 역할 쓰기), 보조 기술에는 accessibility()를 재정의해 답한다 (직접 그린 요소의 역할·값·범위, element가 하는 일).

사례로 확인하기

입력과 상태를 하나 정해 두고, luil이 그때 무엇을 하는지 코드에서 따라간 결과다. 펼치면 결과와 까닭이 나온다.

창 크기가 바뀌어 새 frame이 게시되었다. 포인터 아래의 행이 hover 표시를 잃지 않는 이유는?

hover가 ui_element_id 값으로 저장되어, 새 tree의 같은 id를 가진 행과 다시 맞춰지기 때문에

element는 매 frame 새 객체다(복사·이동도 막혀 있다). hover·초점은 input thread의 snapshot에 id 값으로 들어 있고, 새 tree를 받으면 마지막 포인터 좌표로 hover를 다시 판정한다.

root의 자식이 [목록 패널, 저장 버튼, popup] 순서로 담겼다. 세 곳이 모두 겹친 점을 누르면 무엇이 먼저 검사되는가?

popup — 마지막에 담겨 가장 위에 그려지므로

뒤에 담은 자식이 위에 그려지므로 hit test는 자식을 역순으로 묻는다. 자식이 모두 놓쳤을 때만 부모 자신을 검사한다.

두 행에 실수로 같은 id를 주었다. 무슨 일이 일어나는가?

오류 없이 find는 늘 첫 행을 돌려주고, 뒤의 것은 duplicate_ids()에 남는다

중복은 조용한 오동작이다. 첫 등록이 색인을 차지하고, hover는 같은 id를 가진 두 행에 함께 켜진다. tree는 중복을 진단 목록으로 드러내고, 앱 테스트가 그것이 비었는지 확인한다.

Tab 순서는 어떻게 정해지나?

보이는 tree의 pre-order이고, focus group은 한 자리로 접힌다

focus_order()는 보이는 tree를 pre-order로 훑어 초점을 받을 수 있는 id를 모은다. 묶음은 대표 자리 하나로 접히고, 가둠이 있으면 그 안에서 시작한다.
