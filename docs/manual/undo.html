앱 수준 실행 취소

되돌리기의 한 걸음은 앱이 정의한 메시지 두 개의 쌍이다. stack은 메시지를 열어 보지도, 앱 상태를 건드리지도 않는다. 그래서 되돌림도 앱의 handle 길을 탄다.

이 문서를 읽으면

  1. 칸 기록과 앱 stack이 맡는 범위를 가를 수 있다.
  2. 걸음을 메시지 쌍으로 표현한 이유와 거절한 두 길을 말한다.
  3. 합치기의 조건과 "절대 값 메시지"가 필요한 이유를 설명한다.
  4. 묶음·저장 지점·용량의 규칙을 시나리오로 예측한다.
  5. Ctrl+Z가 칸과 앱 가운데 어디로 가는지 판단한다.

두 개의 되돌리기

luil에는 텍스트 칸 하나의 글을 시점마다 복사해 두는 기록이 이미 있었다. 하지만 항목 삭제, 체크, 순서 바꿈처럼 칸 밖에서 바뀌는 앱 상태는 되돌릴 길이 없었다.

설계 문서가 꼽은 문제는 넷이다.

  1. 되돌리기가 칸 하나의 글 스냅숏뿐이다. 데모 변경 작업대의 체크, 스테이지, 버리기는 되돌릴 수 없다.
  2. 앱마다 같은 규칙을 다시 짠다. 되돌릴 정보를 어떻게 들지, 끌기 같은 연속 동작을 한 걸음으로 합칠지, 용량을 어떻게 막을지, 저장 시점을 어떻게 기억할지, 메뉴 글과 켜짐을 어떻게 맞출지.
  3. 키가 어디로 가는지 앱이 알아야 한다. 초점이 텍스트 칸이면 칸이 Ctrl+Z를 먼저 먹는다.
  4. 명령표의 실행 취소·다시 실행 두 항목의 id와 단축키를 앱마다 다시 적는다.

문서의 첫 문장이 방향을 정한다. "Qt의 QUndoStack이 하는 일 가운데 불변 상태와 메시지 구조에 맞는 것만 가져온다."

한 걸음은 메시지 쌍이다

걸음에는 실행 코드가 들어 있지 않다. 앱이 정의한 메시지 두 개, 곧 되돌림 메시지와 다시 실행 메시지가 들어 있다. 여기에 메뉴에 보일 이름, 병합 키, 무게가 붙는다.

  1. 1000걸음, 32MiB. 바이트 상한은 칸 기록과 같은 값이다. 걸음 수를 칸(100)보다 크게 잡은 것은 문서 단위로 더 깊이 되돌리기 때문이다.
  2. 이름은 앱의 말이다("항목 삭제"). 두 메시지는 모두 비어 있지 않아야 쌓인다. 주석이 "절대 값" 원칙의 이유를 합치기와 묶어 적는다.
  3. 키가 비어 있지 않고 바로 앞 걸음의 키와 같으면 합친다. 무게는 걸음이 쥔 바이트의 어림이다. stack은 메시지 안을 볼 수 없어 앱이 알린다.
  4. 걸음 수와 무게 합. 둘 다 0이면 제한이 없다.
  5. stack이 메시지를 건네는 앱의 함수다. 보통 앱의 handle이다. 그래서 되돌림이 앱의 보통 메시지 길을 탄다.
걸음의 표현판정까닭
app_message 쌍채택stack이 값이라 복사와 시험이 싸고, 앱 상태를 가리키는 참조를 쥐지 않는다. 되돌림이 앱 handle의 길을 타므로 로직이 두 벌이 되지 않는다. 대가: 되돌림마다 메시지 타입을 앱이 정의하고, 역 메시지가 맞는지 라이브러리가 검증하지 못한다
std::function do/undo 쌍 (QUndoCommand식)거절람다가 앱 상태의 참조를 쥔다. 문서를 닫거나 컨테이너가 다시 잡히면 허공을 가리킨다. 걸음을 시험이나 기록으로 들여다볼 수도 없다
상태 스냅숏 전용 stack거절걸음마다 상태 전체를 쥔다(칸 기록이 32MiB 상한을 둔 까닭). 일부만 바꾸는 걸음에 맞지 않는다. 메시지 쌍 위에서 앱이 restore { before }/{ after }로 쓸 수 있으므로 따로 만들지 않는다

약속 ① 메시지는 절대 값이다

연속 동작을 합치면 앞 걸음의 되돌림과 뒤 걸음의 다시 실행만 남는다. 메시지가 "다음 값으로 토글"이 아니라 "이 값으로 정함"을 담아야 중간 걸음이 없어도 맞다.

약속 ② 처음 실행과 다시 실행이 한 길이다

사용자 동작은 걸음을 쌓은 뒤, 다시 실행 메시지와 같은 것을 적용한다. 재생 중에는 stack이 쌓지 않으므로 기록하는 handle에 그대로 흘려도 걸음이 두 번 쌓이지 않는다.

약속 ③ 역 메시지는 앱의 test가 잠근다

라이브러리는 되돌림이 맞는지 검증할 수 없다. 데모는 "동작, 되돌림, 처음 상태"를 test로 잠근다.

push의 네 갈래

막힘, 묶음에 담기, 합치기, 새 걸음. 합치기는 시계가 아니라 앱이 붙인 병합 키로 한다.

  1. 재생 중이거나 두 메시지 가운데 하나라도 비었으면 거짓이다. 아무것도 바뀌지 않는다.
  2. 묶음이 열렸으면 메시지를 묶음 목록 끝에 붙이고 무게를 더한다. 키와 이름은 무시하고 합치지 않는다.
  3. 무장되어 있고, 새 키가 비어 있지 않고, 되돌릴 걸음이 있고, 맨 위 걸음의 키가 같고, 저장 지점에 서 있지 않을 때. 저장 지점에서 합치면 저장한 상태로 돌아갈 수 없다.
  4. 앞 걸음의 되돌림은 그대로, 다시 실행과 이름은 뒤 걸음의 것으로 바꾼다. 무게는 합이 아니라 큰 쪽이다. 그 뒤의 trim()이 "병합 뒤 용량 제한"을 지키는 줄이다(10.7).
  5. 새 걸음으로 쌓고(redo를 자르고 상한을 맞춘다), 키가 있으면 무장한다. 그래서 다음 같은 키 push부터 합쳐진다.

무장을 켜는 것은 묶음 밖에서 키 있는 걸음을 새 걸음으로 쌓은 push뿐이다. 끄는 것은 undo, redo, begin, set_clean, clear, break_merge, 키 없는 push, 묶음 확정이다.

시간 창은 없다. stack이 순수 값이라 test가 시각 없이 돌아야 하고, 사용자가 천천히 두 번 한 일과 빠르게 두 번 한 일을 시간이 가르면 체감이 우연에 달린다. 한 번의 끌기가 끝나면 앱이 break_merge()를 부른다. 데모는 표가 낸 resize_column_end 메시지에서 부른다.

먼저 옮기고, 재생 표시 아래에서 넘긴다

undo와 redo는 대칭이다. 막힘 조건 넷을 본 뒤 걸음을 반대쪽으로 옮기고, 그다음에야 재생 표시를 세우고 메시지를 넘긴다.

  1. 재생 중, 묶음 열림, apply가 빔, 걸음이 없음. 하나라도 걸리면 거짓이고 아무것도 바뀌지 않는다. 빈 stack에서 Ctrl+Z가 맞아도 여기서 조용히 끝난다.
  2. 걸음을 redo 쪽으로 옮기고 무게를 빼고 합치기를 끊는다. apply 안에서 질의하면 이미 옮긴 자리가 보인다.
  3. 재생 표시를 세운 채 되돌림 메시지를 쌓은 반대 차례로 넘긴다. 그래서 apply가 기록하는 handle을 다시 타도 그 안의 push는 거짓이 된다. 메시지 목록을 돌려주는 길은 앱이 재생하는 동안 stack이 그 사실을 몰라 이 재진입을 막을 수 없어서 거절했다.
  4. 되돌릴 쪽으로 돌아온 걸음 때문에 상한을 넘을 수 있어서 redo만 trim()을 부른다. undo는 되돌릴 쪽을 줄이기만 한다.
  5. 다시 실행 메시지는 쌓은 차례로 넘긴다. apply가 예외를 던져도 replay_guard가 재생 표시를 푼다. 위치는 옮긴 채로 남는다.

묶음과 저장 지점

저장 지점은 어느 걸음에 붙은 표시가 아니다. "되돌릴 수 있는 걸음 수"라는 숫자다. 그래서 커서가 그 수에 오면 "저장됨"이고, 그 수로 돌아갈 길이 끊기면 사라진다.

  1. 중첩은 깊이 숫자 하나로 센다. 가장 바깥 begin만 이름을 적고, begin은 언제나 합치기를 끊는다. 한 동작이 다른 동작의 helper를 부르는 앱을 위해 중첩을 허용했다.
  2. 가장 바깥 end만 확정한다. 빈 묶음은 걸음을 만들지 않고 redo도 그대로 둔다.
  3. 열린 묶음에 메시지가 없고, 저장 지점이 있고, 그 수가 되돌릴 걸음 수와 같을 때다. 첫 조건: 열린 묶음의 메시지는 앱이 이미 적용했으므로 상태가 저장한 것과 다르다.
무게
설계 문서의 규칙을 따라 이어 붙인 열다섯 걸음이다. 8번에서 커서가 저장 지점에 오자 "저장됨"이 된다. 10번에서 새 걸음이 redo 쪽을 자를 때 그쪽에 있던 저장 지점도 함께 사라진다. 그 뒤로는 set_clean이나 clear 전까지 어떤 되돌리기로도 "저장됨"에 돌아가지 못한다.

용량, 그리고 커지는 합친 걸음

상한은 걸음 수와 무게의 합이고, 되돌릴 쪽만 센다. 넘치면 가장 오래된 걸음부터 버리되 가장 새 걸음 하나는 남긴다. "한 번은 되돌린다."

  1. 모두 버리는 clear()를 빼면 redo 가지를 자르는 유일한 자리다. 새 걸음과 묶음 확정 때 불린다.
  2. 저장 지점이 잘려 나갈 redo 쪽에 있었으면 지운다. 같은 걸음 수라도 상태가 다르기 때문이다.
  3. 걸음이 하나보다 많은 동안만 버린다. 상한 0은 != 0 검사로 제한 없음이 된다. 상한보다 무거운 걸음 하나도 홀로 남는다.
  4. 맨 아래 걸음을 버리면 "되돌릴 수 있는 걸음 수"가 하나 준다. 0이었으면 갈 곳이 없어 사라진다.

합친 걸음은 걸음 수를 늘리지 않지만 무게는 커질 수 있다. 합치기 갈래가 무게를 바꾼 뒤 그 자리에서 trim()을 부르는 까닭이다. 이것을 빠뜨렸던 버그를 고칠 때 아래 회귀 test가 함께 들어왔다. 고치기 전 코드는 이 저장소에 남아 있지 않다.

  1. 상한은 무게 100. old(40) 뒤에 저장 지점을 찍을지, 합칠 걸음의 무게가 90인지 150인지로 네 경우를 돌린다. 합치면 무게가 max(40, 90)=90으로 커져 합이 130이 된다.
  2. 그 자리에서 old가 버려져 걸음은 하나, bytes()는 합친 무게다. 되돌림은 여전히 첫 drag의 것(3)이다.
  3. old 뒤에 찍었으면 1에서 0으로 내려가 되돌린 빈 자리와 맞는다. 찍지 않았으면 처음 자리 0이 버려지며 사라진다. 다시 실행하면 어느 쪽이든 저장됨이 아니다.
무게
회귀 test의 네 조합을 그대로 돈다. 무게 150이면 old를 버려도 상한 100을 넘지만, 하나 남은 가장 새 걸음이라 남는다.

명령표와 키 경로

실행 취소·다시 실행 두 명령은 make_undo_commands가 짓는다. 키 판정에 쓰는 표는 정적이고, 메뉴에 그리는 표는 stack 상태를 따른다.

판정용 표는 정적이다. 단축키 판정은 input thread의 정책이 하는데, stack은 logic thread의 것이라 정책이 stack 상태를 읽을 수 없다. 게다가 match_command는 꺼진 명령을 건너뛴다. 그래서 판정용 표는 두 명령을 늘 켠다. 빈 stack에서 Ctrl+Z가 맞으면 앱 handler가 부른 undo가 거짓을 받고 끝난다.

보이는 표는 logic thread가 stack 상태로 짓는다. "실행 취소: 체크" 같은 문장은 앱이 잇는다. 할 일이 없으면 끄는 까닭도 데모 test에 있다. 켜 둔 채 빈 동작을 내면 보조 기술의 Invoke가 오류로 끝난다. macOS에서 주 수정자는 Command라 실행 취소의 단축키 글은 ⌘Z, 다시 실행은 ⌘Y다. 다시 실행의 ⇧⌘Z(extra_shortcuts)도 실행되지만, 메뉴 줄과 툴팁은 effective_shortcuts의 첫 조합만 보인다.

메뉴·팔레트의 클릭키 경로를 타지 않으므로 초점과 상관없이 앱 stack의 것
  1. 앱 쪽의 모양이다. 걸음을 쌓은 뒤 다시 실행과 같은 메시지를 handle에 흘린다. "처음 실행과 다시 실행이 한 길"이라는 약속이다.
  2. 사용자 메시지 workbench_resize_intent는 델타를 싣는다. 끌기는 본래 "이만큼 더"다.
  3. 걸음은 절대 폭 둘(width, next)을 담는다. 같은 열의 조절은 키 resize:열로 합쳐져도 "처음 폭 / 마지막 폭"이 남아 맞다. 바뀌는 것이 없으면 걸음을 만들지 않는다.
  4. 열 경계를 놓으면 break_merge()를 부른다. 그래서 끌기 하나가 걸음 하나다.


데모에서 확인한 것 둘

데스크톱 데모의 메뉴 막대 "편집 > 실행 취소"는 make_undo_commands를 쓰지 않고 직접 짓는다. 고르면 "마지막 메뉴 명령" 글만 바뀌고 작업대 stack에는 닿지 않는다. 작업대를 되돌리는 길은 키, 팔레트, 단추다. 또 작업대의 주석 두 곳(workbench_page.h 253행, workbench_page.cpp 1097행)은 읽기 전용 칸이 키를 삼키던 수정 전 상황을 아직 적고 있다.

요약

  1. 칸 기록(text_edit_state)은 칸 하나의 글을, 앱 stack(undo_stack)은 칸 밖의 앱 상태를 되돌린다. 둘은 따로 가고, 키는 칸이 먼저다.
  2. 한 걸음은 앱 메시지 쌍이다. stack은 메시지를 열지 않고 apply에 넘길 뿐이라 되돌림도 앱의 handle 길을 탄다.
  3. 같은 키의 연속 push는 앞 걸음의 되돌림과 뒤 걸음의 다시 실행만 남기고 합친다. 그래서 메시지는 "이 값으로 정함"이어야 한다. 시계는 없고, 끌기의 끝은 앱이 break_merge()로 알린다.
  4. undo·redo는 위치를 먼저 옮기고 재생 표시 아래에서 메시지를 넘긴다. 재생 중의 push는 거짓이라 기록하는 handle을 그대로 넘겨도 안전하다.
  5. 저장 지점은 "되돌릴 수 있는 걸음 수"다. 그 자리가 redo 쪽에 있다가 새 걸음이 쌓이면 사라진다. 맨 아래 걸음이 버려질 때는 한 칸 내려가고, 0이었으면 사라진다.
  6. 상한은 걸음 수와 무게 합(기본 1000걸음·32MiB)이고 되돌릴 쪽만 센다. 합친 걸음이 무거워지면 그 자리에서 오래된 걸음을 버린다.

자주 묻는 질문

실행 취소를 앱에 붙이려면?

앱 상태에 undo_stack을 하나 두고, 사용자 동작마다 되돌림·다시 실행 메시지 쌍을 undo_step으로 push한 뒤 다시 실행 메시지를 handle에 흘린다.

되돌리기는 undo(apply), 다시 실행은 redo(apply)이고 apply는 앱의 handle을 부르는 람다다. 데모 작업대의 commit_step이 "쌓고, 같은 메시지로 적용"하는 모양이다. stack은 logic thread 전용이고 스레드 안전하지 않다 (한 걸음은 메시지 쌍이다, 명령표와 키 경로, API: undo_stack).

되돌림 때문에 상태를 바꾸는 코드를 두 벌 짜야 하나?

아니다. 되돌림·다시 실행 메시지도 앱의 보통 메시지라 같은 handle이 처리한다.

재생하는 동안 stack은 push에 거짓을 돌려준다. 그래서 걸음을 쌓는 handle을 그대로 apply로 넘겨도 걸음이 두 번 쌓이거나 redo가 지워지지 않는다. 대가는 역 메시지가 맞는지 라이브러리가 검증하지 못한다는 것이다. "동작 → 되돌림 → 처음 상태"를 앱의 test로 잠근다 (먼저 옮기고, 재생 표시 아래에서 넘긴다).

되돌림 메시지에 "토글"을 넣어도 되나?

넣지 않는다. 메시지는 "다음 값으로 토글"이 아니라 "이 값으로 정함"처럼 절대 값을 담는다.

같은 병합 키의 걸음이 합쳐지면 앞 걸음의 되돌림과 뒤 걸음의 다시 실행만 남는다. 토글·델타 메시지는 중간 걸음이 빠지면 틀린 값으로 돌아갈 수 있다. 데모의 열 폭 조절은 입력이 델타여도 걸음에는 처음 폭과 다음 폭을 담는다. 색 편집기의 마지막 칸을 켜면 어긋나는 모습을 볼 수 있다.

텍스트 칸의 실행 취소와 앱의 실행 취소는 어떻게 나뉘나?

따로 간다. 편집할 수 있는 텍스트 칸에 초점이 있으면 Ctrl+Z·Ctrl+Y는 칸의 기록(text_edit_state)이 받고, 그 밖이면 앱 정책의 on_key가 받는다.

칸의 기록이 비어도 키는 앱으로 넘어가지 않는다. 읽기 전용 칸은 키를 삼키지 않고 넘긴다. 메뉴·팔레트의 클릭은 키 경로를 타지 않으므로 초점과 상관없이 앱 stack의 것이다 (두 개의 되돌리기, 명령표와 키 경로, 텍스트 입력의 두 실행 취소).

Ctrl+Z·Ctrl+Y를 앱의 stack에 연결하려면?

입력 정책의 on_key에서 make_undo_commands({})가 지은 표로 match_command를 부르고, 맞은 명령 id를 앱 메시지로 낸다. logic thread는 id가 undo_command_id·redo_command_id인지 보고 undo·redo를 부른다.

판정용 표는 정적이다. 정책은 input thread에서 돌아 logic thread의 stack을 읽을 수 없고, match_command는 꺼진 명령을 건너뛰기 때문이다. 그래서 빈 stack에서도 Ctrl+Z가 맞고, 앱의 undo가 거짓을 받고 끝난다. 다시 실행은 Ctrl+Y와 Ctrl+Shift+Z 둘이다. macOS(와 iOS의 하드웨어 키보드)에서는 key_chord::control이 Command로 읽힌다 (명령표와 키 경로, 명령표에서 항목 짓기).

메뉴에 "실행 취소: 항목 삭제"처럼 보이고, 할 일이 없으면 끄려면?

logic thread가 frame을 지을 때 make_undo_commands에 stack 상태를 넣어 보이는 표를 짓는다. 켜짐은 can_undo()·can_redo(), 글은 앱이 undo_label()·redo_label()을 이어 짓는다.

글을 비우면 라이브러리 기본 문구("실행 취소"·"다시 실행")다. 걸음 이름을 잇는 문장은 앱 몫이다. 메뉴 항목은 menu_item_from, 단추 tooltip은 command_tooltip이 짓고 둘 다 첫 단축키만 보인다. 그래서 macOS의 다시 실행은 ⌘Y로 보이고 ⇧⌘Z는 판정에서만 맞는다 (코드에서 확인한 동작). 할 일이 없을 때 끄는 까닭은 데모 작업대의 주석이 적는다 — 켜 둔 채 빈 동작을 내면 보조 기술의 Invoke가 오류로 끝난다 (명령표와 키 경로).

끌기처럼 이어지는 동작을 한 걸음으로 합치려면?

같은 대상을 바꾸는 걸음에 같은 merge_key를 주고, 한 번의 끌기가 끝나면 break_merge()를 부른다.

키가 비어 있지 않고 바로 앞에 쌓은 걸음의 키와 같으면 합친다. 시간 창은 없다. 천천히 두 번 끌어도 그 사이에 break_merge나 다른 걸음이 없으면 한 걸음이다. 저장 지점에 서 있을 때는 합치지 않는다. 합친 걸음의 무게는 합이 아니라 큰 쪽이다 (push의 네 갈래).

여러 변경을 한 걸음으로 묶으려면?

begin(이름)과 end() 사이에서 push한다. 범위로 묶으려면 undo_macro를 쓴다 — 소멸할 때 end()를 부른다.

중첩해도 되고 가장 바깥 end에서 한 걸음으로 확정하며 이름도 바깥 begin의 것이다. 되돌림은 쌓은 반대 차례로, 다시 실행은 쌓은 차례로 넘긴다. 묶음이 열린 동안 undo·redo는 거짓이고, 빈 묶음은 걸음을 만들지 않는다 (묶음과 저장 지점).

문서의 "수정됨" 표시는?

저장할 때 set_clean()을 부르고, frame을 지을 때 clean()을 읽는다.

저장 지점은 "되돌릴 수 있는 걸음 수"라서 되돌리거나 다시 실행해 그 자리로 오면 다시 참이다. 그 자리가 redo 쪽에 있을 때 새 걸음이 쌓이거나, 상한으로 걸음이 버려지며 그 자리가 걸음 밖으로 나가면 set_clean이나 clear를 부를 때까지 거짓이다 (묶음과 저장 지점).

기록이 메모리를 너무 쓰지 않게 하려면?

생성자나 set_limits에 undo_stack_limits의 steps·bytes를 주고, 걸음마다 weight에 쥔 바이트의 어림을 적는다.

기본은 1000걸음·32MiB이고 0은 제한 없음이다. weight가 0이면 걸음 수만 센다. stack은 메시지 안을 볼 수 없어 무게는 앱이 알린다. 넘치면 가장 오래된 걸음부터 버리되 가장 새 걸음 하나는 상한보다 무거워도 남긴다. redo 쪽은 세지 않는다 (용량, 그리고 커지는 합친 걸음).

파일을 다시 열거나 밖에서 상태가 바뀌면 기록은?

clear()로 모두 버린다. 걸음의 메시지가 가리킬 대상이 사라졌기 때문이다.

열린 묶음도 버리고, 빈 자리가 저장 지점이 된다. 데모 작업대는 커밋한 행이 저장소로 넘어가면 기록을 비운다. 재생 중에 부른 clear는 아무 일도 하지 않는다.

문서나 페이지마다 따로 되돌리려면?

stack을 문서(페이지) 상태마다 하나씩 두고, 단축키·메뉴 명령이 오면 앱이 지금 문서의 stack을 고른다.

stack은 앱 상태 안의 값이다. 데스크톱 데모는 작업대 페이지가 stack을 들고, 셸은 지금 페이지가 작업대일 때만 실행 취소 명령을 그 페이지로 넘긴다. 모바일 데모의 목록 페이지도 자기 stack을 따로 든다.

되돌리는 중에 apply가 예외를 던지면?

예외는 그대로 나가지만 stack은 잠기지 않는다. 걸음은 이미 반대쪽으로 옮겨져 있다.

위치를 먼저 옮긴 뒤 재생 표시를 세우고, 그 표시는 범위 객체(replay_guard)라 예외에도 풀린다. 그래서 다음 push·undo가 정상으로 돈다. 앞서 넘긴 메시지는 되돌아가지 않으므로 메시지가 여럿인 걸음에서는 앱 상태가 중간에 멈출 수 있다 (코드에서 확인한 동작, 먼저 옮기고, 재생 표시 아래에서 넘긴다).

사례로 확인하기

입력과 상태를 하나 정해 두고, luil이 그때 무엇을 하는지 코드에서 따라간 결과다. 펼치면 결과와 까닭이 나온다.

같은 키로 걸음 셋을 쌓는다. 되돌림/다시 실행 값과 무게는 (1→2, 10), (2→3, 30), (3→4, 20)이다. undo_count(), bytes(), 되돌릴 때 적용되는 값, 다시 실행할 때 적용되는 값은?

1 / 30 / {1} / {4}

무장된 같은 키의 연속 push는 맨 위 걸음에 합쳐진다. 첫 걸음의 되돌림과 마지막 걸음의 다시 실행만 남고, 무게는 합(60)이 아니라 큰 쪽(30)이다.

begin("바깥") → push(1→2) → begin("안쪽") → push(3→4) → end() → push(5→6) → end(). 안쪽 end() 직후의 undo_count(), 확정된 걸음의 이름, 되돌림 차례, 다시 실행 차례는?

0 / "바깥" / {5, 3, 1} / {2, 4, 6}

확정은 가장 바깥 end에서만 일어나고 이름도 바깥 begin의 것이다. 걸음 안에서 되돌림은 쌓은 반대 차례, 다시 실행은 쌓은 차례다.

push a → push b → set_clean() → undo → push c → undo → undo. 마지막의 clean()과, "저장됨"으로 돌아가는 방법은?

거짓 — set_clean()이나 clear()를 다시 불러야 한다

저장 지점 2가 redo 쪽에 있는 채로 새 걸음 c가 쌓여, discard_redo가 저장 지점을 지웠다. 걸음 수가 다시 같아져도 상태가 다르므로 저장 지점이 아니다.

되돌리는 도중, apply 안에서 앱이 push, undo, clear를 부르면?

push·undo는 거짓, clear는 아무 일도 하지 않는다

위치를 먼저 옮기고 replay_guard가 재생 표시를 세운 뒤 apply를 부른다. 질의는 옮긴 자리를 보고, 바꾸는 호출은 모두 막힌다. 그래서 기록하는 handle을 apply로 넘겨도 걸음이 두 번 쌓이거나 redo가 지워지지 않는다.

상한 { steps: 0, bytes: 100 }에서 old(1→2, 무게 40, 키 없음) → drag(3→4, 40, 키 drag) → drag end(5→6, 90, 키 drag)를 쌓았다. undo_count(), bytes(), 되돌릴 때 적용되는 값은?

1 / 90 / {3}

합치면 무게가 max(40, 90)=90으로 커져 합계가 130이 된다. 합치기 갈래의 trim()이 그 자리에서 old를 버린다. 되돌림은 첫 drag의 것(3)이 남는다.

편집할 수 있는 텍스트 칸에 초점이 있고 칸의 기록은 비었다. Ctrl+Z를 누르면?

칸이 받고 끝난다. 앱 stack으로 넘어가지 않는다

키는 칸이 먼저이고, 칸 기록이 비어도 넘어가지 않는다. 읽기 전용 칸만 이 키를 앱에 넘긴다. 판정용 표는 정적이라 꺼지지 않는다.
