창과 셸 통합

luil에서 창과 셸 기능은 함수 호출이 아니라 frame에 싣는 상태다. 앱이 매 frame 지금 바라는 것(보조 창, 주 창 숨김, 트레이 아이콘, 전역 단축키, 작업 표시줄 진행률)을 ui_frame에 실으면, UI thread가 지난 값과 견주어 바뀐 것만 OS에 옮긴다. OS에서 오는 사건은 delegate 훅이나 frame에 실린 함수가 앱 메시지로 바꿔 돌려준다.

이 문서를 읽으면

  1. 주 창과 보조 창을 띄우고, 창 배치를 저장했다가 다음 실행에서 되돌린다.
  2. caption에 앱 단추와 검색 칸을 두고, 끌기·창 버튼·client 판정이 어디서 오는지 안다.
  3. 작업 표시줄·점프 목록·트레이·전역 단축키를 frame 상태로 싣고 셸의 보고를 받는다.
  4. 파일 끌어 놓기, 둘째 인스턴스, 닫힘과 수명 주기를 어느 thread의 어떤 훅이 맡는지 안다.

무엇을 어디에 싣나

창과 셸 기능은 세 자리 가운데 하나에 산다. 창을 만들 때 한 번 주는 설정, 매 frame 싣는 요청, OS가 부르는 훅이다.

window_config

  • 창을 만들 때 한 번 읽는다. 실행 중에 바꿀 길이 없다.
  • 주 창 caption(판정용 버튼·치수·OS 제목), 초기 크기·자리, 저장 배치.
  • 파일 끌기 받기, 앱 식별(AUMID), 창 아이콘, 렌더러.
  • macOS는 macos::application_config가 같은 자리다.

ui_frame

  • logic thread가 매 frame 짓는다. 실으면 서고 빼면 사라진다.
  • 보조 창·popup·도킹 표면, 주 창 숨김·전체 화면·배치 요청·초점.
  • 작업 표시줄·점프 목록·트레이·전역 단축키, 주 창 닫힘 훅.
  • 마지막 frame의 값이 이긴다. 바뀐 것만 OS에 간다.

window_delegate

  • OS 사건마다 UI thread가 부른다. 기본 구현은 아무 일도 하지 않는다.
  • 크기·배율, 배치 보고, 셸 보고(작업 표시줄·트레이·단축키·점프 목록).
  • 받는 element가 없는 파일 드롭, 둘째 인스턴스의 인자.
  • app_delegate를 넓힌 것이라 모바일 host에도 그대로 넘긴다.

하지 못하는 플랫폼은 받기만 한다. 같은 frame을 네 플랫폼에 실어도 된다. 트레이가 없는 Android는 ui_frame::tray를 받고 아무 일도 하지 않는다. 그래서 앱은 플랫폼마다 frame을 다르게 짓지 않는다. 능력 플래그(ui_platform_capabilities)는 설정 화면에 그 항목을 둘지 고를 때 쓴다. host가 어떻게 서고 깨어나는지, 기능 28개의 플랫폼 매트릭스는 플랫폼과 host에 있다. 아래 표는 이 문서가 다루는 기능만 추렸다.

개념: 창은 frame 요청이다

앱은 창을 열고 닫는 함수를 부르지 않는다. 지금 있어야 할 창과 셸의 상태를 frame에 싣고, UI thread가 그것을 OS와 맞춘다.

  • 실으면 서고 빼면 사라진다. 보조 창, popup, 도킹 표면, 트레이 아이콘, 전역 단축키가 모두 같은 규칙이다. UI thread는 frame의 id 목록을 살아 있는 창과 맞춘다 — 새 id는 만들고, 남은 id에는 최신 tree·caption·함수를 적용하고, 사라진 id는 파괴한다.
  • id 이름 공간은 하나다. 주 창은 빈 id이고 ui_window::id·ui_popup::id·ui_docked_surface::id가 같은 이름 공간을 쓴다. popup의 anchor와 초점 요청의 surface가 이 id를 가리킨다.
  • 만들 때 한 번만 쓰는 값이 있다. 보조 창의 x·y·width·height·screen_anchor·initial_placement·independent는 생성 때만 읽는다. 그 뒤 자리는 사용자의 것이다.
  • 번호가 바뀔 때만 새 요청이다. 실행 중 배치 요청은 window_placement_revision이, 초점·활성화 요청은 focus_request::id가 바뀐 frame에서만 이행한다. 같은 값을 매 frame 실어도 한 번이다.
  • 그림은 몸통으로 견준다. 트레이·오버레이 그림은 ui_image::backing() 포인터로 같은지 가른다. 처음 한 번 지은 ui_image를 계속 싣는다.
  • 함수는 견주지 않는다. tray_icon::activate·메뉴의 select·global_hotkey::pressed는 사건이 올 때 그 순간 게시된 frame에서 읽는다.

메뉴로 창을 되살리는 한 번의 길

사용자트레이 아이콘을 오른쪽 클릭하고 메뉴에서 "창 보이기"를 고른다.
UI thread라이브러리가 게시된 frame의 tray에서 메뉴를 읽어 시스템 메뉴로 띄우고, 고른 키로 그 메뉴의 select(key)를 부른다.
UI thread돌려받은 input_action이 앱 메시지면 app inbox에 넣는다. ui_command면 그 자리에서 실행한다.
logic thread앱의 handle이 숨김 표시를 끄고, 새 번호의 활성화 요청을 준비한다.
logic thread다음 make_frame()이 main_hidden = false와 focus를 싣는다.
UI thread주 창 숨김을 풀고, 바뀐 번호를 보고 창을 앞으로 세운다. 앱이 앞 창이 아니면 OS가 막고 작업 표시줄 단추만 깜빡일 수 있다.

OS 사건이 앱에 닿는 두 길

  1. delegate 훅 → app inbox. UI thread가 훅을 부르고, 받은 app_message가 비어 있지 않으면 inbox에 넣는다. 빈 메시지는 게시하지 않는다. 훅이 던진 예외는 삼키고 디버그 출력에 적는다. 크기·배치·셸 보고가 이 길이다.
  2. frame의 함수 → input_action. 트레이·단축키·닫힘 훅은 input_action을 돌려준다. 앱 메시지면 inbox로, ui_command면 UI thread에서 곧바로 실행, app_ui_command면 execute_app_ui_command로 간다.

값을 돌려주는 훅이 둘 있다. on_file_dropped는 true를 돌려주면 나머지 경로를 보지 않고, on_instance_arguments는 true면 보낸 쪽이 "받았다"를 받는다. 둘은 메시지를 돌려주지 않으므로 앱이 post_app_message로 스스로 게시한다. thread와 inbox의 일반 규칙은 스레드 모델과 스레드 경계 메시징에 있다.


끝내기는 logic thread를 거치지 않는다트레이 메뉴의 "끝내기"가 input_action { ui_command::application_exit }를 돌려주면 UI thread가 곧바로 종료 절차를 시작한다. 그 절차는 여느 종료와 같이 make_close_message의 종료 신호를 게시하고 shutdown_completed를 기다린다 — 저장은 거기서 한다.

caption: 그림과 판정이 한 tree를 본다

caption은 앱이 tree에 담는 caption_element다. 그것을 놓는 자리(arrange에 준 slot)가 곧 끌기 띠다. Win32 host는 OS가 비클라이언트를 물을 때(WM_NCHITTEST) 게시된 tree에서 그리기 순서로 첫 caption을 찾아 그 자리로 판정한다. 그래서 caption을 창 아래에 두거나 일부만 덮어도 판정이 따라온다. 판정이 쓰는 값은 셋에서 온다.

만들기: 창 하나와 여러 창

주 창은 진입점이 띄우고, 보조 창은 frame에 싣는다. 배치는 보고를 받아 적어 두었다가 다음 실행의 시작 설정으로 돌려준다.

주 창 띄우기 (Windows 진입점)

  1. DPI 인지를 창보다 먼저 켠다. com_sta_scope는 파일 대화 상자·텍스트 입력(TSF)·OS 끌어 놓기·접근성·작업 표시줄·점프 목록이 요구한다. 빠뜨리면 셸 기능이 오류 없이 빠진다.
  2. 창의 겉모습이다. 길이는 논리 96 DPI px이고, 만든 뒤 그 모니터의 배율로 다시 잡는다. caption은 판정·창 스타일·OS 제목에 쓰이며 창을 만들 때 한 번 읽힌다.
  3. 명령 줄의 --position=x,y를 initial_position에 넣는다. 이 값은 물리 픽셀·가상 화면 좌표라 왼쪽·위 모니터에서는 음수다. 크기와 단위가 다르다.
  4. logic driver와 UI thread 훅(delegate)을 꽂는다. 입력 정책(policy)은 없으면 비워 둔다.
  5. 메시지 루프가 끝날 때까지 돌고, 반환값이 프로세스 종료 코드다.

첫 frame: 맨 위 막대와 내용

  1. 창 크기는 delegate가 보낸 메시지로 안다. 값은 물리 픽셀이고 scale은 물리/논리다. 첫 metrics는 첫 make_frame()보다 먼저 처리되므로 기본값은 안전망이다.
  2. 데스크톱은 caption_element, caption이 없는 플랫폼은 app_bar_element다. 어느 쪽인지는 current_ui_platform().window_caption이 말하고, 높이는 height_for가 미리 알려 준다.
  3. 맨 위 막대 아래가 내용의 자리다. caption의 slot이 곧 끌기 띠이므로 내용이 그 위를 덮지 않게 둔다.
  4. tree를 frame에 담아 돌려준다. 보조 창·popup·셸 요청도 이 frame에 함께 실린다.

caption 설정을 짓는 함수 하나를 창 설정과 tree 양쪽에 쓴다(hello의 진입점은 같은 값을 손으로 적었다). 크기 메시지는 delegate가 UI thread에서 짓고, logic thread의 handle이 받아 다음 frame을 새 크기로 배치한다.

보조 창

  1. 열려 있으면 싣는다. 다음 frame에서 빼면 창이 사라진다. id는 popup·도킹 표면과 같은 이름 공간이다.
  2. caption과 초기 자리·크기다. x·y는 주 창 client 기준 논리 픽셀이고 만들 때 한 번만 읽는다. width·height가 0 이하면 창을 만들지 않는다. 최소 크기는 살아 있는 정책이다.
  3. 창마다 그 client (0,0)에서 시작하는 분리 tree다. 크기·배율이 바뀌면 metrics가 메시지를 낸다.
  4. caption의 닫기·Alt+F4는 이 동작만 낸다. 창을 없애는 것은 앱이 목록에서 빼는 것이다. 비워 두면 닫기가 아무 일도 하지 않는다.
  5. 기본은 주 창이 소유하는 창이다(주 창 위에 뜨고 함께 숨는다). independent면 작업 표시줄에 따로 서고 따로 최소화된다. 만들 때 정하므로 바꾸려면 id를 빼고 다시 싣는다. 독립 창만 자기 taskbar 요청을 읽는다.

metrics가 오기 전, 창이 만들어지는 바로 그 frame에서는 요청 크기에 배율을 곱해 배치한다. caption의 창 버튼은 비클라이언트 경로가 이 창에 직접 실행하므로 tree의 caption은 그리기와 tooltip만 맡는다.

버튼 집합을 줄이면 그 창 스타일(WS_MINIMIZEBOX·WS_MAXIMIZEBOX)도 빠진다. 그래서 닫기만 둔 도구 창은 caption 더블클릭·Win+↑·시스템 메뉴로도 최대화되지 않는다. 크기 조절 테두리와 시스템 메뉴는 버튼 집합과 상관없이 남는다. 보조 창은 frame마다 ui_window::caption을 다시 싣고, 판정·스타일·OS 제목이 그 값을 따라온다.


tooltip이 곧 접근 이름이다위 둘째 caption(make_taskbar_window_caption)은 close_tooltip만 준다. 창 버튼의 tooltip은 보조 기술이 읽는 유일한 이름이라, 이 창의 최소화·최대화 단추는 이름도 역할도 없는 요소로 읽힌다. 버튼마다 tooltip을 준다.

배치 저장과 복원

라이브러리는 배치를 알리고 요청을 적용할 뿐이다. 어디에 어떻게 적을지는 앱이 정한다. 주 창의 보고(make_window_placement_message)는 첫 표시 직후(저장값이 없어도), 끌기 끝, 끌기 밖의 이동·크기·최대화, 전체 화면 전환, 종료 직전에 온다. 보조 창의 보고는 그 창의 placement 함수다. 받은 값을 그대로 저장했다가 다음 실행의 initial_placement에 넣는다.

  • window_placement의 x·y는 작업 영역 좌표, 크기는 물리 픽셀이다. fullscreen이 참이면 나머지는 "전체 화면을 풀면 돌아갈 자리"다.
  • initial_placement는 첫 표시·첫 frame 전에 적용되고 initial_position·초기 크기보다 앞선다. 크기가 양수가 아니거나, 어느 모니터에도 걸치지 않거나, 그 모니터에서 잰 최소 크기보다 작으면 통째로 무시하고 기본 배치로 연다.
  • 실행 중에 옮기려면 window_placement_request를 싣고 window_placement_revision을 올린다. 번호가 그대로면 다시 적용하지 않는다. 저장 자리가 화면 밖이면 크기만 적용하고, 주 창이 숨었거나 아직 보이지 않으면 미룬다.

저장소의 예제는 아직 옛 길(아래)을 쓴다. 새 앱이 쓸 길을 손으로 묶었다. 저장 형식은 앱이 정하므로 load_saved·save_layout 두 선언으로만 두었다. 주 창 tree와 패널의 tree·metrics는 위 조리법과 같아 뺐다 — 이대로면 두 창이 빈 tree로 선다.

종료 저장은 종료 신호(make_close_message가 지은 메시지)를 처리할 때 한다. 종료 직전의 배치 보고가 같은 inbox에 먼저 게시되므로 그때 든 값이 닫히던 순간의 배치다. 데모도 같은 자리에서 저장한다.


데모의 옛 길데모는 저장 배치의 x·y를 initial_position에 넣고 크기·최대화를 첫 frame의 배치 요청으로 다시 맞춘다. initial_placement가 생기기 전의 길이다. initial_position은 화면 좌표이고 보고의 x·y는 작업 영역 좌표라, 작업 표시줄이 위나 왼쪽에 있는 모니터에서는 그 두께만큼 어긋난다. 주석의 "크기는 논리 픽셀"은 initial_width의 이야기다 — 배치 값 자체는 물리 픽셀이다.

전체 화면

두 길이 있다. 명령 ui_command::window_toggle_fullscreen은 지금 상태를 뒤집는다. frame 상태 ui_frame::fullscreen은 앱이 정한 값을 매 게시마다 맞춘다. 값을 싣는 앱은 배치 보고의 fullscreen을 되비추지 않는다 — 되비추면 늦은 보고와 새 frame이 서로를 뒤집는다. 비워 두면 명령과 배치 요청이 정하고, 최소화된 동안은 전환을 미룬다.

Windows의 전체 화면은 지금 모니터를 덮는 테두리 없는 창이고 주 창 전용이다. 그동안 비클라이언트가 없어 어디를 눌러도 client다(아래 판정 지도). 크기 조절과 최대화 스타일을 빼서 Alt+Space의 "크기 조정"과 Win+↑도 막고, 최소화와 시스템 메뉴는 남겨 Alt+Tab·Alt+F4가 산다. 데모는 전체 화면이면 caption 줄을 아예 접는다.

탭을 떼어 화면 한 점에 새 창 세우기

받는 대상 없이 창 밖에 놓은 탭은 탭 막대의 unclaimed_drop이 놓은 화면 점과 함께 알린다. 앱은 그 점에 window_screen_anchor로 새 독립 창을 세운다. 닻은 "새 창 client의 논리 점 (client_x, client_y)이 화면의 물리 점 screen에 오게" 놓는다. 배율은 그 화면 점이 있는 모니터의 것이고, 그 뒤 작업 영역 안으로 밀려 점이 어긋날 수 있다. 탭 막대 쪽은 탭 문서에 있다.


잡은 지점은 출발 창의 물리 픽셀이다탭 막대는 grab_offset_x를 누른 점(물리 픽셀, 창 좌표)에서 탭의 왼쪽(tree 좌표, 역시 물리 픽셀)을 빼 채운다. 닻의 client_x는 논리 점이므로 출발 창의 배율로 나눠 더한다. 라이브러리의 dock도 떼어 낸 자리를 그렇게 나눠 잰다. 위 데모는 나누지 않고 더하므로 100% 배율에서만 잡은 자리가 정확히 맞는다.

보조 창에 붙인 popup

anchor가 popup의 자리·소유자·배율을 정한다. 자리(x·y)는 앵커 창 client 기준 논리 픽셀이고, 앵커 창이 없는 frame에서는 popup을 만들지 않는다. dismiss의 빈 동작은 "이 계기에는 닫지 않는다"이다. 닫힘 계기와 메뉴는 드롭다운·콤보·팝업과 메뉴와 메뉴 막대에 있다.

도킹 표면 (작업 표시줄 곁의 작은 판)

caption도 작업 표시줄 단추도 없고, 늘 위에 뜨며, 눌러도 활성화되지 않는 판이다. 자리는 "어느 모니터의 어느 가장자리에서 얼마"로 말하고 물리 사각형은 UI thread가 푼다. 길이·거리는 그 모니터 배율의 논리 픽셀이다. 키보드가 필요하면 focus_request의 activate로 잠깐 청한다. Windows에서 "늘 위의 작은 판"이 필요하면 이것이 그 자리다 — 주 창의 ui_frame::topmost는 Windows가 읽지 않는다.

만들기: 캡션과 앱 바

caption은 앱이 tree에 담는 element다. 창 버튼 왼쪽에 앱 단추를 두고, 그 위에 누를 수 있는 칸을 겹치고, 자리도 앱이 정한다. caption이 없는 플랫폼의 맨 위는 앱 바다.

caption에 앱 단추 두기

  • 앱 단추는 창 버튼 바로 왼쪽에 목록 차례대로 왼쪽에서 오른쪽으로 서고, 폭은 창 버튼과 같다. 제목은 그 앞에서 잘린다.
  • action이 없으면 단추를 만들지 않는다. tooltip이 보조 기술이 읽는 유일한 이름이다.
  • 앱 단추는 Tab의 자리다(창 버튼은 아니다). 앱 단추가 창 버튼보다 먼저 담겨, 보조 기술이 형제를 읽는 차례가 화면의 차례와 같다.
  • 앱 단추는 스스로 client 표시(set_caption_client(true))를 단다. 끌기 띠 위에 있어도 누르면 창이 끌려가지 않고 단추가 눌린다. 비활성 단추 위도 끌기 자리가 아니다.
  • 누르면 단추의 action이 낸 input_action이 여느 단추처럼 input thread에서 나간다. 창 버튼(최소화·최대화·닫기)은 다르다 — 비클라이언트 판정을 지나 UI thread가 창 명령으로 실행한다.

데모는 이 함수를 창 설정과 frame 양쪽에서 부른다. macOS에서 시스템 제목 막대를 쓰는 창이면 같은 앱 단추가 제목 막대 오른쪽 끝의 부속 view로 옮겨 선다 — 글리프·tooltip·켬 상태가 같다. 아래는 macOS 도구 창 예제의 "늘 위 고정" 단추다. 단추가 바꾼 pinned_를 frame이 topmost로 싣는다.

caption 위에 누를 수 있는 칸 겹치기

끌기 띠 위의 element에 set_caption_client(true)가 달려 있으면 그 보이는 자리는 끌기가 아니라 client다. caption 다음에 담아 위에 겹치면 된다. 라이브러리의 명령 팔레트 입구(make_command_palette_entry)는 이 표시를 스스로 단다. 숨은 조상 아래의 칸은 자리를 내지 않고, 자르는 조상(clip_children) 아래에서는 잘린 만큼만 client다. 비활성이어도 client다.

caption의 자리: 아래에 두기, 전체 화면에서 접기

  • caption을 놓은 자리가 곧 끌기 띠다. 창 아래에 두면 띠·창 버튼·시스템 메뉴 칸이 모두 그리로 간다. 아래 가장자리 몇 픽셀은 여전히 크기 조절이다 — 가장자리 판정이 띠보다 먼저다.
  • 숨긴 caption(set_visible(false))에는 띠가 없다. 어느 자리도 끌기가 아니다.
  • tree에 caption이 아예 없으면 Windows는 맨 위 띠(높이 36 논리 픽셀)를 기본으로 판정한다. 그리지 않은 자리가 끌리고 오른쪽 끝에 보이지 않는 창 버튼이 선다. caption을 그리지 않을 화면이면 caption을 담고 숨긴다. macOS borderless 창은 반대로, caption이 없으면 끌 자리가 없다.

세 경우를 아래 판정 지도에서 바꿔 가며 볼 수 있다.

모바일: caption 대신 앱 바

어느 쪽을 쓸지는 current_ui_platform().window_caption으로 고른다. 창 caption이 없는 플랫폼(Android·iOS, 그리고 시스템 제목 막대를 쓰는 macOS)에서 caption은 스스로 숨고 높이가 0이다. 보이는 경로에 남으면 보조 기술이 화면에 없는 창 단추를 읽기 때문이다. 같은 코드를 데스크톱 창으로 띄우면 caption 아래에 앱 바가 선다.

  • 앱 바는 제목, 왼쪽의 navigation 단추(뒤로·메뉴), 오른쪽 끝부터 쌓는 actions로 짓는다. 단추의 label이 접근 이름이자 tooltip이고, action이 비면 누를 수 없다.
  • 치수는 터치용이다: 높이 64, 단추 48, 아이콘 24, 제목 22 (모바일 1 = 1dp). 색은 caption 팔레트를 쓴다.
  • caption과 앱 바는 둘 다 보조 기술에 title_bar 역할이고 이름은 제목이다.

window_metrics의 width·height는 앱이 배치할 자리(Android·iOS는 안전 영역)다. scrim이나 시트 바탕처럼 안전 영역 밖까지 칠할 것은 window_surface(metrics)를 배치 문맥의 surface로 넘긴다. root를 (0,0)에 둘 때 표면 전체를 tree 좌표로 준 값이다. Windows·macOS는 outside가 0이라 자리와 표면이 같다.

macOS 테두리 없는 도구 창

borderless면 macOS에서도 window_caption이 참이 되어 앱이 caption 전체를 그리고, host가 같은 계산으로 판정한다. 다만 창 버튼 집합·치수는 tree의 caption 설정에서 읽고, 시스템 메뉴 칸과 크기 조절 가장자리는 판정에 없다(가장자리는 시스템이 한다). Windows에는 같은 이름의 설정이 없다 — Windows 주 창은 늘 시스템 caption을 떼고 앱이 그린다. topmost·all_spaces·activation·corner_radius는 macOS 설정에만 있다.

on_window_moving은 caption을 잡고 끄는 걸음마다 창이 갈 바깥 사각형을 받아 고친다. 곧 돌아와야 하고 메시지를 게시하지 않는다(배치는 끌기 끝에 한 번 알린다). 지금은 macOS host가 테두리 없는 주 창에서만 부른다. Windows는 부르지 않는다.

만들기: 작업 표시줄·점프 목록·트레이·전역 단축키

넷 다 앱 상태다. 매 frame 지금 바라는 값을 싣고, 셸에 닿았는지는 보고 훅이 따로 알린다. 못 거는 것이 정상 경로다.

작업 표시줄 진행률과 오버레이

  • 진행률은 state(none·indeterminate·normal·error·paused)와 0..1의 value다. 값은 1000단계로 셸에 가고, 범위 밖은 잘린다. 그보다 작은 변화는 셸을 부르지 않는다.
  • 주 창의 요청은 ui_frame::taskbar, 독립 창은 ui_window::taskbar다. 소유된 창은 단추가 없어 읽지 않는다. 주 창이 숨은 동안 주 창 요청은 쥐기만 했다가 다시 보일 때 건다.
  • 오버레이의 description은 보조 기술이 읽는 글이다. 진행 막대에는 읽는 글이 없으므로 같은 정보를 창 안에도 둔다.

오버레이 그림은 처음 켤 때 한 번 짓는다. 셸 쪽은 그림을 몸통 포인터로 견주므로, frame마다 새로 지으면 매번 새 그림으로 읽혀 셸을 다시 부른다.

보고는 단추마다 온다. surface가 빈 것이 주 창, 아니면 그 독립 창의 id다. 상태는 off·waiting(탐색기가 단추를 아직 만들지 않았다)·applied·unavailable·failed다. 셸에는 읽는 길이 없어 applied는 "호출이 오류 없이 끝났다"는 뜻이다.

점프 목록

작업 하나는 "이 실행 파일을 이 인자로 새로 띄운다"이다. 인자의 따옴표는 라이브러리가 붙인다. 앱이 이미 떠 있으면 새 프로세스는 둘째 인스턴스이므로 첫째에 인자를 넘기고 끝낸다. 위 작업 둘이 --send-to-first를 싣는 까닭이다.

  • taskbar_request::jump_list가 비어 있으면(std::nullopt) 셸의 목록을 만지지 않는다 — 앞 실행이 지은 목록도 그대로다. 작업이 든 목록은 달라졌을 때만 다시 짓고, 빈 목록을 실으면 지운다.
  • Windows의 점프 목록은 사용자 프로필에 남아 앱이 끝나도, 지워도 남는다. 라이브러리는 스스로 지우지 않는다.
  • 점프 목록은 앱마다 하나라 주 창의 것만 읽는다. 독립 창의 taskbar.jump_list는 읽지 않는다.
  • 작업 표시줄과 점프 목록은 COM STA가 있어야 선다. 없으면 보고가 unavailable이다.

트레이 아이콘과 메뉴

  • ui_frame::tray에 실으면 서고 빼면 사라진다. 주 창이 숨은 동안에도 선다.
  • 그림이 비면 창 아이콘(window_config::icon_resource, 없으면 시스템 기본)이다. 알림 영역은 앱의 밝기 모드가 아니라 작업 표시줄의 테마를 따르므로 light_icon·high_contrast_icon을 따로 줄 수 있다.
  • tooltip이 툴팁이자 접근 이름이다. 비면 창 제목, 그것도 비면 luil이다.
  • menu가 있으면 오른쪽 클릭에 라이브러리가 시스템 메뉴를 띄우고 고른 키를 select로 낸다. 그때 context 사건은 오지 않는다. 메뉴는 OS가 그려 앱 테마를 따르지 않는다.
  • 그 밖의 사건(왼쪽 클릭·두 번 클릭·키보드)은 activate로 온다. 비어 있으면 버린다.

"창 보이기"는 숨김을 풀고 새 번호의 활성화 요청을 싣는다. 라이브러리는 트레이 사건에서 창을 앞으로 세우지 않는다. 숨기기는 보고가 shown일 때만 하고, 아이콘이 내려가면(waiting·failed·off) 숨은 창을 되살린다 — 아이콘 없이 숨은 창은 되살릴 길이 없다. 탐색기가 다시 뜨면 라이브러리가 아이콘을 다시 더한다. 셸이 frame에 싣는 자리는 아래와 같다.

닫으면 트레이로 숨기기

라이브러리는 "닫으면 트레이로"를 정책으로 주지 않는다. 저장소에도 예제가 없어 손으로 묶었다. 앱이 ui_frame::close에서 숨김 메시지를 내고 main_hidden을 싣는다. close가 있으면 caption의 닫기·Alt+F4·작업 표시줄의 닫기가 그 동작만 내고 아무것도 닫지 않는다. 그래서 정말 끝내는 길은 트레이 메뉴의 "끝내기"가 내는 ui_command::application_exit 하나다 — 이 명령은 닫힘 훅을 비켜 간다. 아이콘이 서지 않은 동안에는 훅을 비워 닫기가 평소처럼 앱을 끝내게 둔다. 예제의 intent·함수 이름(hide_intent, tray_report_intent, make_caption …)은 앱이 지은 것이다.

전역 단축키

  • 조합은 앱 안 단축키와 같은 key_chord다 — Ctrl·Shift·Alt와 키 하나. Windows 키 조합은 그 칸이 없어 걸 수 없다.
  • 앱이 뒤에 있거나 창이 최소화·숨김이어도 받는다. 한 번 눌러 한 번이고, 누르고 있어도 반복하지 않으며 뗌은 오지 않는다.
  • 걸린 조합은 앱이 앞에 있어도 앱 안 키 이벤트로 오지 않는다. 같은 조합의 앱 안 단축키(app_command)는 그동안 죽는다.
  • 목록의 견주는 값은 id와 chord다. pressed는 눌림이 올 때 그 순간의 frame에서 읽는다.

눌림에서 창을 앞으로 세우는 것도 앱의 몫이다(트레이와 같다). 걸기 결과는 항목마다 make_hotkey_message로 온다. 라이브러리는 OS를 부르기 전에 거른다 — 빈·겹친 id는 invalid_id, 옮길 수 없는 키는 invalid_key, OS 예약 조합과 F12는 reserved, Ctrl·Alt 없이 건 글자·이동·편집 키는 needs_modifier, 같은 목록 앞 항목과 같은 조합은 conflict다. 남은 것만 OS에 묻고, 다른 프로그램이 쥔 조합도 conflict로 온다. conflict·failed는 frame마다 다시 걸지 않고 주 창이 활성화될 때 한 번 다시 건다.


설정 뒤에 둔다전역 단축키는 시스템 전체에서 키를 가져가는 기능이라, 헤더는 사용자가 켜는 설정 뒤에 두기를 권한다. 키 잡기 칸에 초점이 있는 동안 라이브러리는 건 단축키를 모두 풀었다가(알리지 않는다) 끝나면 다시 건다 — 사용자가 같은 조합을 새로 고를 수 있게.

만들기: 파일 끌어 놓기

창 설정 하나로 받기를 켜고, 자리가 뜻을 갖는 드롭은 element의 drop_target이, 나머지 파일은 delegate의 물러섬이 받는다.

accept_file_drop을 켜면 주 창·보조 창·도킹 표면이 OS 끌어 놓기를 등록한다(popup은 아니다). COM STA가 없으면 이 기능이 오류 없이 꺼진다. macOS는 macos::application_config::accept_file_drop이 같은 자리다.

자리에 놓인 파일: drop_target

  • accepts는 끄는 동안 input thread와 UI thread 양쪽에서 불린다. 형식만 보는 가벼운 판정이어야 한다. 받는 자리의 강조는 interaction snapshot이 그린다.
  • on_drop은 놓는 순간 UI thread에서 불리고, 앱 메시지 목록을 돌려준다. 메시지에는 꺼낸 값(경로·글)을 담는다.
  • "밖에서 온 끌기인가"는 payload.files.empty()가 아니라 payload.external()로 가린다. 경로 없이 형식만 실린 OS 끌기도 있다.

받는 자리가 없는 파일: on_file_dropped

받는 element가 없는 자리에 놓인 파일은 경로 순서대로 이 훅으로 물러선다. true를 돌려주면 나머지 경로를 보지 않는다. 메시지를 돌려주는 훅이 아니라 앱이 post_app_message로 스스로 게시한다. 경로는 셸이 준 그대로다(절대 경로라는 보장이 없다). 형식만 실린 끌기와, modal·메뉴·토스트처럼 불투명한 표면이 가린 자리에 놓인 끌기는 물러서지 않는다. 훅이 던진 예외는 진단 없이 삼킨다.

경로 없는 끌기: 브라우저의 그림, 주소

디스크에 없는 가상 파일(FileGroupDescriptorW)이나 주소만 실린 끌기는 ui_action_context::native_drop_data(Windows는 IDataObject*)에서 꺼낸다. drop_data.h의 도우미 drop_virtual_files·drop_data_bytes·drop_data_text가 흔한 셋을 덮는다. 원시 객체는 on_drop 호출 동안만 유효하므로 그 안에서 꺼내 메시지에 값으로 담는다. 한 번에 읽는 상한은 64 MiB(default_drop_data_limit)이고, 넘으면 잘린 값 대신 빈 값이다. macOS의 원시 객체는 NSPasteboard*이고, 도우미가 흔한 Windows 형식 이름을 같은 뜻의 형식으로 옮겨 읽는다(가상 파일은 이름만).

만들기: 둘째 인스턴스

같은 이름의 single_instance를 먼저 쥔 프로세스가 첫째다. 둘째는 인자를 첫째에 넘기고 창 없이 끝나고, 첫째는 주 창 프로시저 안에서 받는다.

둘째의 길: 넘기고 끝낸다

  • send_to_primary는 보낸 그대로를 넘긴다. argv[0]은 앱이 넣어야 들어가고, 작업 폴더는 늘 함께 간다.
  • 옵션의 timeout(기본 3000 ms)은 첫째의 창을 기다리는 시간과 답을 기다리는 시간의 합이다. activate(기본 참)면 보이는 첫째의 주 창을 앞으로 세운다 — 숨은 주 창을 보이게 하지는 않는다.
  • 시한 안에 첫째의 주 창이 서지 않았거나 이 프로세스가 첫째면 not_found, 첫째의 앱이 받지 않았거나 시한이 지났으면 failed다. 시한이 지난 보내기도 첫째가 나중에 받을 수 있으므로, 받는 쪽은 같은 인자가 두 번 와도 견딘다.

첫째의 길: 받을 준비와 받기

  • environment.instance를 달아야 주 창에 받는 표식이 선다. 객체는 창보다 오래 살아야 한다 — wWinMain의 지역에 두면 된다. 비었거나, 둘째거나, delegate가 없으면 받지 않고 보낸 쪽은 not_found를 받는다.
  • on_instance_arguments는 보낸 프로세스가 답을 기다리는 동안 UI thread의 주 창 프로시저 안에서 불린다. 막지 않는다. post_app_message_ticketed로 게시하고 표가 0이 아닌지만 답한다. 앞으로 세우기는 라이브러리가 콜백 뒤에 한다.
  • 인자는 명령 줄처럼 믿을 수 없는 입력이다. 받는 쪽이 검사한다. 알림 클릭으로 뜬 둘째의 표식이 섞일 수 있어 데모는 notification_launch로 거른다.
  • 관리자 권한으로 뜬 첫째는 낮은 권한 프로세스(탐색기에서 연 파일)의 인자를 기본으로 받지 않는다. 그때 보낸 쪽은 failed다. 받으려면 instance_from_lower_integrity를 켠다 — 낮은 권한 프로세스가 높은 권한 앱에 입력을 먹이는 길이 열리므로 위험을 알고 켠다.

Windows는 같은 사용자 세션 안에서 이름 있는 뮤텍스로 첫째를 가르고 창 메시지로 보낸다. macOS는 사용자 임시 폴더의 잠금 파일과 Unix 소켓이다. Android는 OS가 앱마다 프로세스 하나를 두어 늘 첫째이고 보내기는 unsupported다. iOS도 늘 첫째다. 둘째 객체는 첫째가 끝나도 둘째로 남는다 — 다시 겨루려면 놓고 새로 만든다.

만들기: 닫힘과 수명 주기

주 창의 닫기는 기본으로 앱을 끝낸다. 닫힘 훅을 달면 앱이 정하고, 끝내는 길은 명령 하나로 남는다. 모바일은 앞뒤 전환과 뒤로 가기를 더 받는다.

끝낼 때 Windows host는 둘째 인스턴스 표식·트레이 아이콘·전역 단축키를 먼저 거두고, 마지막 배치를 보고한 뒤 종료를 시작한다. 종료는 cancel()을 알리고, 종료 신호(make_close_message가 지은 메시지)를 inbox에 넣고, shutdown_completed()가 참이 되기를 기다린다. 게시와 기다림이 함께 3초 예산이다. 그래서 종료 저장은 종료 신호를 처리하는 handle에서 제출하고, 그 뒤 shutdown_completed를 참으로 둔다. 두 함수는 UI thread에서도 불리므로 thread-safe여야 한다(예제들이 std::atomic<bool>을 쓰는 까닭이다).

logic thread가 비동기 작업을 기다렸다가 끝낼 때는 app_host::post_ui_command로 application_exit(훅을 거치지 않는다)나 window_close(훅을 다시 거친다)를 낸다. 주 창을 숨긴 채 독립 창만 남은 앱이 마지막 창을 닫을 때 application_exit를 내지 않으면, 보이는 창 없이 프로세스가 남는다.

앞뒤 전환: make_lifecycle_message

모바일 OS는 뒤로 간 앱을 종료 알림 없이 거둘 수 있다. background가 저장할 마지막 기회일 수 있으므로 종료 신호만 믿지 않는다. 같은 이름의 훅이 플랫폼마다 뜻이 다르다.

macOS앱이 앞에 서거나 다른 앱에 자리를 내줄 때마다 foreground·background를 낸다. 창 사이를 오가는 것은 수명 주기가 아니다

헤더 주석과 다른 점app_delegate.h는 이 훅의 뜻을 Android의 onStart·onStop으로 적고 "Win32는 부르지 않는다"고만 한다. macOS host는 데스크톱인데도 앱 활성 전환마다 부른다 — 사용자가 다른 앱을 잠깐 눌러도 background가 온다. 데스크톱에서 이 훅으로 무거운 정리를 하면 macOS에서만 잦게 돈다.

뒤로 가기 (Android)

안쪽 화면일 때만 ui_frame::back을 싣고 맨 앞 화면이면 비워 플랫폼의 기본 동작(Activity 끝내기)을 받는다. popup이 떠 있으면 host가 popup을 먼저 닫고 이 함수는 부르지 않는다. Windows·macOS·iOS host는 이 칸을 읽지 않는다 — 데스크톱에서는 앱 바의 뒤로 단추가 같은 일을 한다.
