배치

부모가 자리를 정하고, 자식은 그 안에 선다. 측정 단계 없이 한 방향으로 흐르는 배치는 logic thread가 tree를 지을 때 끝난다.

이 문서를 읽으면

  1. 논리 픽셀·물리 픽셀·scale의 관계로 slot을 손으로 계산할 수 있다.
  2. arrange 계약과, luil이 측정 단계를 두지 않은 이유를 말할 수 있다.
  3. stack이 고정·유연·맞춤 길이와 하한·상한을 나누는 걸음을 따라갈 수 있다.
  4. 컨테이너를 "자르지 않음"과 "자르고 흘림"으로 나눠 고를 수 있다.
  5. 가상 목록이 10만 행을 수십 개의 element로 보여 주는 방법을 설명한다.

배치는 tree를 지을 때 끝난다

그리기 직전에 계산하지 않는다. 창 크기가 바뀌면 옛 tree를 다시 배치하지 않고 새 크기로 새 tree를 짓는다.

  1. UI 창 크기나 DPI가 바뀌면 delegate가 make_window_metrics_message(width, height, scale)로 앱 메시지를 만든다. 폭·높이는 물리 픽셀, scale은 물리 ÷ 논리다.
  2. logic handle()이 크기를 상태에 저장하고, 바뀐 것이 있으니 make_frame()이 불린다.
  3. logic 앱이 make_frame() 안에서 tree를 새로 짓고 arrange()를 부른다. 배치는 여기서 끝난다.
  4. logic host가 tree, 표면 tree 목록, frame 순서로 게시한다(스레드 모델).
  5. UI·input 배치가 끝난 불변 tree를 그리고, hit test한다.

결과는 값이다배치의 결과는 element마다 확정된 bounds()다. 게시된 뒤에는 바뀌지 않으므로 그리기와 hit test가 같은 사각형을 본다. 그리기와 입력이 서로 다른 배치를 보는 일이 구조적으로 없다.

두 가지 픽셀

설정은 논리 픽셀로 적고, slot과 bounds는 물리 픽셀이다. 둘 사이를 scale이 잇는다.

논리 픽셀은 96 DPI 기준의 길이다(Android에서는 dp). 앱이 적는 여백 24, 간격 12, 버튼 높이 30이 모두 논리 값이다. 물리 픽셀은 화면의 실제 픽셀이다. 150% 모니터에서는 scale이 1.5라 논리 24가 물리 36이 된다.

  • 논리로 남는 것 — 모든 config, preferred_size()의 답, scroll offset, scroll 치수
  • 물리인 것 — slot, bounds(), viewport(), hit test 좌표
  • 반올림은 없다 — stack의 배치 코드에는 round·floor·ceil이 없어 139.5 같은 소수가 그대로 나온다.
모니터 배율

arrange 계약: 부모가 slot을 준다

자식은 받은 slot으로 자기 bounds를 확정하고, 다시 자기 자식에게 slot을 내려 준다. 전면적인 측정 단계는 없다.

  1. 부모가 준 자리(물리), 물리 ÷ 논리 배율, 그리고 가장 가까운 세로 스크롤 창이 흘러간 양(논리)이다. scroll_offset은 sticky 머리행이 창의 윗변을 되짚을 때 쓴다.
  2. 그릴 수 있는 표면 전체, 글 폭 측정기, 스타일 치수, 앱 스타일이다. 모두 포인터만 들고 배치가 끝나면 잊는다. 측정기를 넣을 수 있어 test가 고정 폭 가짜를 쓴다.
  3. 맞춤 항목에게 원하는 크기를 물을 때의 문맥이다. 배치 결과(bounds)를 읽지 않고 config만으로 답하게 한다.
  4. 자식 문맥을 손으로 지으면 뒤의 값을 빠뜨리기 쉽고, 빠뜨려도 그 자리에서는 아무 일도 없다. 몇 계층 아래의 sticky 머리행이 조용히 어긋날 뿐이다. 그래서 자리만 새로 주는 함수 하나로 모았다. 문맥에 새 값이 생겨도 모든 부모가 저절로 잇는다.

새 컨테이너가 따르는 순서

  1. 자기 bounds를 context.slot으로 정한다.
  2. 논리 길이에 유효한 scale(scale > 0 ? scale : 1)을 곱한다.
  3. 자식마다 물리 slot을 계산한다.
  4. context.for_child(slot)으로 자식을 배치한다.
  5. 스크롤 창의 viewport·최대치 같은 결과를 남긴다.

측정 단계를 두지 않는 이유

길이는 담을 때 정한다. element가 자기 크기를 알릴 필요가 없고, 배치가 담는 쪽 코드에 그대로 드러난다. 내용 크기가 꼭 필요한 맞춤 자리만 preferred_size()로 묻는다. 고정·유연 길이만 쓰는 tree는 아무에게도 묻지 않는다.

stack 읽기

105줄 안에 맞춤 측정, 고정 합, 유연 분배, 주축 정렬, 교차축 정렬이 차례로 들어 있다.

  1. 계약의 첫걸음이다. 빈 stack은 자기 bounds만 잡고 끝난다.
  2. padding에 scale을 곱해 안쪽 영역을 구한다. padding이 slot보다 커서 음수가 되어도 다듬지 않는다. 주축은 쌓는 방향, 교차축은 그와 직각이다.
  3. 맞춤(fit) 항목에게만 원하는 크기를 묻는다. 가로 stack은 폭 제한 없이, 세로 stack은 교차 폭에서 묻는다. 여러 줄 글이 그 폭에서 접히기 때문이다.
  4. 간격은 항목 수 − 1번 들어가고, gap도 항목으로 센다. 고정·맞춤 길이를 더해 빼고 남은 자리를 구한다. 음수면 0이다.
  5. 하한·상한도 물리로 바꿔 distribute_flexible에 넘긴다(비율 분배). 하한에 걸린 항목의 부족분은 다른 유연 항목의 몫에서 나온다.
  6. 유연 항목이 남는 자리를 다 가져가므로 정렬은 유연 항목이 없거나 모두 상한에 섰을 때만 뜻이 있다. free는 음수로 내려가지 않아, 넘칠 때 가운데 정렬이 여백 밖으로 새지 않는다.
  7. 교차 길이를 주면 그 길이, 아니면 남는 폭을 다 채운다. stretch는 지정한 교차 길이를 늘리지 않는다. 그때는 start와 같다.
  8. slot을 만들어 for_child로 배치하고 offset을 늘린다. gap 항목은 자식이 없어 offset만 늘린다.

하한·상한을 지키는 비율 분배

CSS flexbox의 "유연 길이 풀기"와 같은 절차다. 한 걸음마다 어긴 항목을 세우고, 남은 자리를 나머지가 다시 나눈다.

  1. 하한에 걸린 항목의 부족분은 다른 유연 항목의 몫에서 나오고, 하한들의 합이 자리를 넘을 때만 넘친다. 하한이 상한보다 크면 하한이 이긴다. stack과 grid가 같이 쓴다.
  2. 세운(frozen) 항목이 쓴 자리와 아직 서지 않은 항목의 비율 합을 센다. 열린 비율이 없으면 끝이다.
  3. 몫 = 남은 자리 × 비율 / 열린 비율 합. 상한을 먼저, 하한을 나중에 적용해 하한이 이긴다. 어긴 양(excess)과 그 합(violation)을 센다.
  4. 어긴 양의 합이 늘리는 쪽(양수)이면 하한에 걸린 것만, 줄이는 쪽(음수)이면 상한에 걸린 것만 세운다. 한쪽을 세우면 다른 쪽의 몫이 바뀌기 때문이다. 세운 것이 없으면 끝이다.
  5. 한 걸음에 적어도 하나를 세우므로 걸음 수는 항목 수 + 1을 넘지 않는다. stack 실험장 아래 표가 이 걸음을 그대로 보여 준다.

규칙이 바뀐 이야기예전에는 하한이 다른 항목의 몫을 줄이지 않아, 한 항목이 하한에 걸리면 늘 넘쳤다. 데모의 변경 작업대가 좁은 창에서 잘린 원인이었다. 지금 규칙으로 바꾸면서 test가 "폭 300에서 [w1 min 160, w1] → 160/140"을 잠근다. 설계 문서의 불변식 목록 한 줄은 아직 옛 규칙을 적고 있어, 코드와 test를 정본으로 본다.

이름 붙은 필드가 막은 버그

항목의 길이를 이름 없는 float 세 개로 받던 시절, 가로 stack의 버튼들이 60px 넘게 줄 밖으로 삐져나가도 아무도 알아채지 못했다.

  1. 세 번째 인자였던 cross_length가 세로 stack의 습관인 (높이, 폭) 순서로 가로 stack에 적혀 있었다. { .length = 96.0f, .cross_length = 30.0f }처럼 이름을 쓰게 하면 그 실수는 애초에 쓸 수 없다. luil 개요 문서의 hello 버튼도 이 꼴로 담는다.
  2. 한 구조체 안에서 "없음"을 말하는 법이 둘(0과 std::optional)이 되면 안 된다.
  3. weight > 0이면 유연 항목이고 length는 쓰지 않는다. 교차 길이가 0이면 남는 폭을 다 채운다.
  4. 고정 항목은 length가 이미 하한이자 상한이다. 배치가 그것을 다시 흥정하면 "길이는 담을 때 정한다"가 거짓이 된다.
  5. 주축 길이를 자식의 원하는 크기로 잰다. 답하지 않는 자식은 0이다.

컨테이너 지도: 자르는가, 흘리는가

컨테이너마다 맡은 일은 하나다. 고를 때의 첫 질문은 "넘친 것을 자르고 흘려야 하는가"다.

  1. viewport는 받은 slot(물리)이다.
  2. 넘치는 만큼만 흘릴 수 있다. 앱이 tree를 짓기 전에 쓰는 공개 함수 clamp_scroll과 같은 식이라 막대와 내용이 어긋나지 않는다. 식이 두 벌이 되면 반드시 어긋난다.
  3. 내용은 offset × scale만큼 위로 올린 자리에 통째로 배치된다. 내용이 받은 slot으로 보이는 범위를 알 수 있어 가상화가 여기서 가능해진다.
  4. 다른 컨테이너는 모두 for_child로 잇는다. 세로 스크롤 창만 scroll_offset을 자기 값으로 바꾸고 surface를 비운다. 아래의 sticky 머리행이 가장 가까운 스크롤 창의 값을 봐야 하기 때문이다.

"십만 줄짜리 화면이 element 십만 개가 되지 않게 하는 것이 이 컴포넌트가 하는 일의 전부다." 창에 걸치는 행과 그 위아래 몇 줄만 짓는다.

초록 테가 보이는 창이다. 테 밖에 흐리게 걸린 행은 overscan으로 지었지만 안쪽 scroll_view가 잘라서 그리지도 누르지도 않는다. 커서 행에 9000을 넣고 처음에 두면, 창 밖 커서 행 하나가 따로 서는 것이 숫자에 보인다.
  1. slot이 정해져야 창 높이를 알고, 창 높이를 알아야 어디까지 걸치는지 답할 수 있다.
  2. tree가 아직 게시되지 않았으므로 arrange에서 행 element를 만드는 것이 허용된다. 행은 높이가 있는 첫 배치에서 한 번만 짓는다. 두 번 지으면 같은 자리표가 둘 서고, 높이 0 배치를 계기로 삼으면 빈 목록이 굳는다.
  3. 격자 모드는 지금 폭에서 열 수를 세고, 막대가 서면 막대 폭을 빼고 한 번 더 센다. 열이 줄면 더 넘칠 뿐이라 한 번이면 된다.
  4. offset을 다듬고 창에 걸치는 반열린 구간 [begin, end)를 구한 뒤 위아래로 overscan만큼 넓힌다. 반열린 구간이라 창 높이가 행 높이의 배수여도 한 줄을 덤으로 짓지 않는다.
  5. 창 구간의 행, 구간 밖이면 커서 행, 창 밖에서 고른 행(최대 64개)을 모델 차례로 짓는다. 그리고 안쪽 scroll_area를 한 번 배치한다. 내용의 arrange가 한 frame에 두 번 불리면 같은 행이 둘 선다.

아직 재지 않은 것은 재지 않았다고 쓴다가변 높이를 지원하려고 보이는 범위는 앞에서부터 더해 찾는다(O(n)). 누적 높이 캐시는 "100만 줄 frame 하나가 Release에서 1ms를 넘으면 넣는다"는 기준과 함께 계측 뒤로 미뤘고, 설계 문서의 계측 표는 아직 "측정 전"이다. 잰 것은 공유 모델의 효과다. 10만 항목을 frame마다 값으로 넘기면 약 2.1ms, shared_items로 공유하면 약 0.1ms였다.

요약

  1. 배치는 logic thread가 make_frame()에서 tree를 지을 때 끝난다. 결과인 bounds는 게시 뒤 바뀌지 않는다.
  2. config는 논리 픽셀, slot과 bounds는 물리 픽셀이다. scale이 둘을 잇고, 배치 코드에는 반올림이 없다.
  3. 부모가 slot을 정하고 자식이 bounds를 확정한다. 측정 단계는 없고, 맞춤 자리만 preferred_size()로 묻는다.
  4. stack은 고정·간격을 빼고 남은 자리를 유연 항목에 나눈다. 하한·상한은 CSS flexbox식 걸음으로 풀고, 넘쳐도 자르지 않는다.
  5. stack·wrap·grid·layer는 자르지 않고, strip·scroll_view는 자르고 흘린다. scroll_view만 자식 문맥의 scroll_offset을 새로 짓는다.
  6. 가상 목록은 배치 시점에 창의 반열린 구간과 overscan, 커서 행, 고른 행(최대 64)만 짓는다.

자주 묻는 질문

자식을 내용 크기에 맞추려면?

add_fit(child)로 담는다 (stack_item::fit). 그 자리만 자식에게 preferred_size를 묻는다.

가로 stack은 폭 제한 없이 원하는 폭을, 세로 stack은 자기 교차 폭에서 원하는 높이를 묻는다. 그래서 여러 줄 글은 그 폭에서 접힌 높이가 된다. 답하는 것은 글이 든 element(label·글자 버튼·체크·글리프·배지 등)와 stack·grid·layer다. 아이콘 버튼(button_element)처럼 답하지 않는 자식은 0이 된다. 교차축 정렬이 stretch가 아니고 cross_length가 0이면 교차 길이도 원하는 크기다 (stack 읽기, 도구 막대).

남는 공간을 나눠 가지려면?

add_flexible(child, weight)로 담는다. 고정·맞춤 길이와 간격을 뺀 나머지를 비율대로 나눈다.

하한·상한은 add(child, { .weight = 1, .minimum = 200, .maximum = 300 })처럼 stack_item으로 준다. 하한에 걸린 항목의 부족분은 다른 유연 항목의 몫에서 나오고, 하한들의 합이 남은 자리를 넘을 때만 넘친다. 상한에 걸린 항목이 남긴 자리는 아직 걸리지 않은 유연 항목이 나눈다. 하한이 상한보다 크면 하한이 이긴다. 0 이하 비율을 1로 고치는 것은 add_flexible뿐이고, 구조체로 담으면 다듬지 않는다 (비율 분배, stack 실험장).

논리 픽셀과 물리 픽셀은?

config에 적는 길이는 논리 픽셀(96 DPI 기준, Android의 dp)이고, slot·bounds()·hit test 좌표는 물리 픽셀이다. 배율 scale은 물리 ÷ 논리다.

150% 모니터에서 scale은 1.5라 여백 24가 물리 36이 된다. 창 크기 메시지의 폭·높이는 물리 픽셀이라 그대로 뿌리의 slot으로 쓰고(make_arranged_tree(root, { 0, 0, width, height }, scale)), 배율은 각 컨테이너가 곱한다. preferred_size()의 답과 scroll offset은 논리 픽셀로 남는다 (두 가지 픽셀).

오른쪽 끝에 붙이거나 가운데에 두려면?

항목 사이를 벌리는 것은 add_flexible_gap(), 남는 자리를 앞이나 뒤에 두는 것은 main_alignment다.

유연 항목이 하나라도 있으면 남는 자리를 그것이 다 가져가므로, main_alignment는 유연 항목이 없거나 모두 상한에 섰을 때만 뜻이 있다. "제목은 왼쪽, 단추는 오른쪽"은 둘 사이에 add_flexible_gap()을 둔다. space_between은 없다. 교차축은 cross_alignment다. 자식 하나를 두 축 모두 가운데에 세우려면 layer_element에 담고 layer_item의 horizontal·vertical을 layout_alignment::center로 준다. 길이(width·height)를 주지 않으면 원하는 크기에 서고, 답하지 않는 자식은 칸을 채운다 (도구 막대, 겹치기).

stack에 다 들어가지 않으면? 넘친 것을 자르거나 흘리려면?

stack·wrap·grid·layer는 자르지 않는다. 넘친 자식도 그대로 그려지고 눌린다. 자르고 흘리려면 세로는 scroll_area_element, 가로는 strip_element에 담는다.

넘친 stack에서 유연 항목은 0을 받고, 고정 항목은 slot 밖으로 나간다. 자르는 컨테이너는 bounds 밖의 자식을 그리지도 누르지도 않는다. 흘러간 양(scroll_offset)은 앱 상태다 (컨테이너 지도, 흘리는 영역).

흘리는 창의 내용 높이는 누가 알려 주나?

담는 쪽(앱)이다. 측정 단계가 없어서 scroll_area_config::content_height에 직접 적는다.

내용이 stack이면 그 stack의 preferred_size(고정·맞춤 길이와 간격·여백의 합)로 읽고, 폭은 막대 칸(scroll_area_bar_width)을 뺀 값을 준다. 칩 묶음은 wrap_height_for, 접이식 섹션은 group_element::height_for로 센다. 폭에 따라 줄 수가 바뀌는 내용은 담는 element가 자기 arrange에서 set_content_height를 부른 뒤 영역을 배치한다 (위치는 앱이, 배치에서 재는 높이).

창 크기를 바꿔도 배치가 그대로다.

delegate가 크기 메시지를 만드는지 본다. make_window_metrics_message의 기본 구현은 빈 메시지를 돌려주고, 빈 메시지는 게시되지 않는다.

앱은 그 메시지를 handle에서 상태에 저장하고, make_frame()에서 그 크기로 tree를 새로 짓는다. host는 메시지를 처리한 뒤 make_frame()을 부르므로 따로 다시 그리라고 할 일이 없다. 게시된 tree를 다시 배치하는 길은 없다. hello 예제가 이 꼴이다 (배치는 tree를 지을 때 끝난다, hello 읽기 ②).

창 폭에 따라 한 판·두 판을 바꾸려면?

window_metrics::width_class로 고른다. 이 값을 받으려면 delegate의 make_metrics_message(const window_metrics&)를 재정의한다.

host가 논리 폭(물리 폭 ÷ 배율)을 기본 경계 600·840으로 나눠 compact·medium·expanded를 싣는다. 세 값짜리 make_window_metrics_message만 재정의하면 등급은 버려진다. 다른 경계를 쓰려면 앱이 논리 폭으로 classify_window_width를 다시 부른다. 기기 방향이 아니라 창 폭으로 고르므로 화면 분할·접는 기기·태블릿이 한 규칙이다 (창 폭 등급).

여러 줄 글은 폭에 따라 높이가 바뀌는데 어떻게 담나?

세로 stack에 add_fit으로 담는다. stack이 자기 교차 폭에서 높이를 묻고, 줄을 바꾸는 label(label_config::wrap)은 그 폭에서 접은 줄 수만큼의 높이를 답한다.

tree를 짓기 전에 높이가 필요하면 label_element::measure_wrap이 그리기·배치와 같은 규칙으로 잰다. 한 줄 label의 높이는 label_element::height_for다. 같은 규칙으로 글을 직접 재고 그리는 길은 measure_text_block·draw_text_block이다 (stack 읽기, label).

배치가 좌표를 정수 픽셀로 맞추나?

맞추지 않는다. 배치 코드에는 반올림이 없어 150%에서 139.5 같은 좌표가 그대로 bounds가 된다.

stack·grid·wrap·layer·scroll_view·strip의 arrange에 round·floor·ceil이 없다 (stack 밖은 코드에서 확인한 동작). 맞춤 크기를 답하는 label과 글자 버튼은 잰 글 폭을 올림해 논리 픽셀로 답한다. 잰 폭에 꼭 맞춘 자리에서 부동소수 잔차로 말줄임이 서지 않게 하려는 것이다 (두 가지 픽셀).

배치 요소를 직접 만들려면?

ui_element를 상속해 arrange와 draw를 구현한다. arrange는 set_bounds(context.slot)으로 시작하고, 자식은 context.for_child(slot)으로 배치한다.

자식은 생성자에서 add_child로 들이고, 그리기는 draw_children에 맡긴다. 논리 길이에는 유효한 배율(context.scale, 0 이하면 1)을 곱한다. 맞춤 자리에 담길 것이면 preferred_size도 답한다. 문맥을 손으로 지으면 측정기·스타일 같은 뒤의 값을 빠뜨려 몇 계층 아래가 조용히 어긋난다. 데모의 style_scope(examples/demo/tabs_page.cpp)가 자식 하나를 담는 작은 예다 (arrange 계약).

담았는데 화면에 보이지 않고 눌리지도 않는다.

배치(arrange)를 빠뜨렸을 수 있다. 배치되지 않은 element는 bounds가 0이라 그려지지도 맞지도 않는다.

ui_tree::unarranged()가 그런 보이는 element의 id를 모은다. test에서 duplicate_ids()와 함께 비었는지 확인하고, dump_tree의 첫 줄에도 미배치 수가 나온다. 뿌리 하나가 전부 배치하는 tree는 make_arranged_tree로 감싸면 빠뜨릴 자리가 없다. root_element처럼 가지를 각자 배치해 담는 조립에서 잘 생긴다 (진단).

폭에 따라 열 수가 바뀌는 타일 목록은?

grid_element에는 그 규칙이 없어 열 수는 앱이 고른다. 항목이 많으면 virtual_list_element의 격자 모드가 minimum_column_width로 폭에서 열을 센다.

grid는 config의 columns 길이만큼 열을 두므로, 데모 갤러리는 폭을 보고 2열·3열을 고른다. 가상 목록의 격자에서는 모든 칸이 row_height 높이다. 열 수가 바뀌어도 같은 항목을 보이려면 virtual_list_grid_offset_keeping으로 스크롤 값을 다시 정한다 (카드 격자, 목록 설정).

노치·상태 표시줄 밑까지 바탕을 칠하려면?

앱이 받는 크기는 안전 영역이다. window_surface(metrics)를 배치 문맥의 surface(make_arranged_tree의 넷째 인자)로 넘기면 scrim과 시트 바탕이 화면 끝까지 칠해진다.

window_metrics::outside가 앱 자리에서 표면 끝까지의 거리(물리 픽셀)다. Android는 시스템 막대·컷아웃 몫이고 Windows는 0이다. iOS host도 상태 표시줄·홈 표시줄·키보드 몫을 빼고 알린다 (코드에서 확인한 동작). 누르기는 여전히 자리 안에서만 받는다. 이 값을 쓰는 것은 modal_host_element·sheet_host_element처럼 화면 끝까지 칠해야 하는 것뿐이다 (arrange 계약).

사례로 확인하기

입력과 상태를 하나 정해 두고, luil이 그때 무엇을 하는지 코드에서 따라간 결과다. 펼치면 결과와 까닭이 나온다.

세로 stack(spacing 8, 좌우 padding 10)에 길이 30짜리 고정 항목 둘을 담고 slot {0, 0, 200, 200}, scale 2로 배치했다. 둘째 항목의 y는?

76

길이·간격은 논리라 stack이 scale을 곱한다. 첫째 높이 30 × 2 = 60, 간격 8 × 2 = 16이므로 둘째 y = 60 + 16 = 76이다. 좌우 padding 10은 각각 20이 되어 x = 20, 폭 = 160이다.

폭 300인 가로 stack에 { weight 1, minimum 160 }과 { weight 1 }을 담았다. 두 폭은?

160 / 140

처음 몫 150이 하한 160에 걸려 첫째가 160에 선다. 남은 140은 둘째가 갖는다. 하한의 부족분은 다른 유연 항목에서 나오고, 하한들의 합이 자리를 넘을 때만 넘친다.

행 높이 20, 항목 5개, 창 높이 40, scroll_offset 40, overscan 0이다. 실현되는 구간은?

[2, 4)

창은 [40, 80)이다. 1번 행 [20, 40)은 윗변에 닿기만 하고, 4번 행 [80, 100)은 아랫변에서 시작한다. 둘 다 걸치지 않으므로 [2, 4)다. overscan 1이면 [1, 5)가 된다.

기본 정렬(stretch)인 세로 stack에 버튼을 { .length = 30, .cross_length = 120 }으로 담았다. 버튼은 어디에 서는가?

폭 120으로 안쪽 영역의 왼쪽 끝에 선다

stretch는 교차 길이를 지정하지 않은 항목을 채우는 기본 동작이고, 지정한 cross_length를 강제로 늘리지 않는다. offset 계산에서 stretch는 start와 같다.
