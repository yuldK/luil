luil 개요

Skia로 직접 그리고, 화면을 frame마다 새로 짓고, 앱 상태는 스레드 하나가 쥔다. 이 세 가지 결정이 luil의 나머지를 거의 다 설명한다.

luil은 무엇인가

창을 열고, 그 안의 모든 것을 직접 그리고, 입력을 받아 앱 상태를 바꾸는 C++20 애플리케이션 프레임워크다.

저장소의 README는 luil을 이렇게 소개한다.

luil은 Windows용 C++20 애플리케이션 프레임워크다. Skia로 UI를 그리고, 불변 element tree와 메시지 전달로 앱 상태·입력·렌더링을 연결한다. CPU·Direct3D 렌더링, 여러 창과 팝업, 텍스트 입력, 접근성, 이미지, 비동기 HTTP와 WebView2 웹 콘텐츠를 제공한다.README.md

처음에는 Windows용으로 시작했고, 지금은 같은 앱 코드가 Windows·Android·macOS·iOS 네 플랫폼에서 돈다. 버튼·목록·표·텍스트 칸 같은 컨트롤을 OS에서 빌려 쓰지 않고, 모두 Skia로 직접 그린다. 그래서 플랫폼마다 다른 것은 창을 여는 일, 입력을 받는 일, 그린 픽셀을 화면에 내는 일, 그리고 OS 기능(클립보드·알림·접근성)을 잇는 일로 좁혀진다.

클릭 한 번이 지나가는 길

luil의 가장 작은 예제 hello를 눌러 보자. 숫자 하나가 바뀌기까지 세 스레드를 건넌다.

hello luilframe 1
버튼을 누른 횟수: 0
속도
왼쪽 창의 하나 더를 눌러 보라. 버튼이 눌린 모양은 input thread가 바로 그리게 하지만, 숫자는 logic thread가 새 tree를 게시한 뒤에야 바뀐다. 점의 움직임은 보이도록 늦춘 것이다. 실제로는 한 frame 안팎에 끝난다.

이 실험에서 읽어 낼 것은 셋이다.

  • 버튼의 액션은 상태를 바꾸지 않는다. input thread에서 실행된 액션은 increment_intent라는 메시지를 만들어 logic thread로 보낼 뿐이다.
  • 상태를 바꾸는 곳은 한 곳뿐이다. logic thread의 handle()이 clicks_를 1 늘린다.
  • 화면은 고치지 않고 새로 짓는다. make_frame()이 라벨과 버튼을 새로 만들어 통째로 게시하면 UI thread가 그것을 그린다.

세 가지 큰 결정

luil의 구조는 세 결정에서 나온다. 각각이 무엇을 얻고 무엇을 치르는지가 이 설명서 전체의 줄기다.

결정 1

모든 것을 Skia로 직접 그린다

얻는 것 — 네 플랫폼에서 같은 모양, custom caption·배경 효과 같은 자유, OS 위젯 툴킷에 기대지 않는 코드.

치르는 것 — OS 컨트롤이 공짜로 주던 것을 직접 이어야 한다. 접근성(UIA·VoiceOver), 텍스트 입력과 IME, 클립보드가 그렇다. luil은 이것들을 플랫폼마다 다리로 잇는다(입력과 초점 · 텍스트 처리 · 플랫폼과 host).

결정 2

화면은 frame마다 새로 짓는 불변 tree다

얻는 것 — 게시한 tree를 아무도 고치지 않으므로 세 스레드가 잠금 없이 함께 읽는다. 부분 갱신 경로가 없어 화면 구조와 앱 상태가 섞이지 않는다.

치르는 것 — 매 frame 다시 짓는 비용. 그래서 긴 목록은 보이는 행만 tree에 넣고(가상화, 배치), element는 주소가 아닌 값인 id로 frame을 넘어 이어진다(불변 UI tree).

결정 3

앱 상태는 logic thread 하나가 쥔다

얻는 것 — 앱 상태에 경쟁 조건이 없다. 앱 코드가 오래 걸려도 창과 입력은 멎지 않는다. 메시지만 넣으면 창 없이도 테스트할 수 있다(시험과 빌드).

치르는 것 — 모든 동작이 메시지를 거친다. 상태에서 나오는 화면 변화는 다음 frame에 보인다(스레드 모델 · 스레드 경계 메시징).


한 줄로 줄이면입력 → element 액션 → 앱 메시지 → logic의 상태 변경 → 새 frame과 불변 tree 게시 → UI의 그리기. 데이터는 이 한 방향으로만 흐른다.

상태가 어디 살고, 화면을 어떻게 바꾸는지로 나란히 놓으면 luil의 자리가 보인다.

luil은 Elm·React 계열의 단방향 데이터 흐름을 따르지만 두 곳에서 갈린다. 첫째, 새 tree를 이전 tree와 비교(diff)하지 않는다. 게시본을 통째로 바꾸고, 표면 전체를 다시 그린다. 둘째, hover·눌림·초점 같은 상호작용 상태는 앱 상태가 아니다. input thread가 따로 쥐고 값(interaction_snapshot)으로 게시하며, element는 그 안의 id를 자기 id와 비교할 뿐이다. 그래서 클릭 한 번이 지나가는 길 실험에서 눌린 모양은 logic을 거치지 않고 먼저 보였다.

앱과 라이브러리의 경계

앱은 세 조각을 꽂는다. 셋 모두 상태를 직접 바꾸지 않고 메시지만 만든다.

앱이 구현하는 것도는 스레드책임
luil::logic_driverlogic앱 상태를 소유한다. 메시지를 처리하고(handle), 불변 tree를 담은 frame을 만든다(make_frame). 시간 갱신과 종료 처리도 여기다.
luil::interaction_policyinput앱 element 종류와 텍스트 대상을 잇고, 휠·키·편집 요청을 해석한다. 텍스트 입력이 없는 hello는 꽂지 않는다(nullptr).
luil::win32::window_delegateUI창 크기·DPI 변화, 파일 드롭 같은 UI thread의 사건을 앱 메시지로 바꾼다.

hello 읽기 ① 조립하는 main

Windows 진입점은 창의 겉모습을 정하고 앱의 조각을 꽂은 뒤, 메시지 루프에 들어간다.

  1. 모니터마다 배율이 다를 수 있다(100%·150%·200%). 창을 만들기 전에 모니터별 DPI 인지를 켜야 OS가 그림을 늘려 흐리게 만들지 않고, luil이 물리 픽셀로 또렷하게 그린다. 이 배율이 뒤에서 scale로 내려온다.
  2. Windows의 텍스트 서비스(TSF, IME 조합 입력)와 파일 대화 상자는 COM STA를 요구한다. com_sta_scope는 RAII로 이 함수가 끝날 때 정리된다.
  3. luil 창은 OS 제목 표시줄 대신 직접 그리는 custom caption을 쓴다. 여기 적는 길이(800×500)는 96 DPI 기준의 논리 픽셀이다. 150% 모니터라면 실제로는 1200×750 물리 픽셀이 된다.
  4. 앱 쪽 절반인 hello_driver(logic)와 hello_delegate(UI)를 환경에 넣는다. 텍스트 입력·휠·단축키가 없으니 interaction_policy는 비워 둔다. 라이브러리는 이 객체들의 수명을 빌려 쓸 뿐 소유하지 않는다.
  5. run_application_window는 창을 만들고 logic·input 스레드를 세운 뒤, 호출한 이 스레드에서 메시지 루프를 돈다. 창이 닫히고 종료 절차가 끝나면 돌아오며, 반환값이 프로세스 종료 코드다.

hello 읽기 ② 상태와 화면

앱의 전부는 두 함수다. 메시지로 상태를 바꾸는 handle, 상태로 화면을 짓는 make_frame.

  1. 메시지는 앱이 정의한 평범한 구조체(close_intent, metrics_intent, increment_intent)다. 라이브러리는 이 타입을 모른 채 불투명 상자 app_message에 담아 나르고, 앱은 get<T>()로 꺼낸다. 타입이 다르면 nullptr라 순서대로 물으면 된다(스레드 경계 메시징).
  2. 창을 닫으면 라이브러리가 make_close_message()가 준 메시지를 inbox에 넣는다. 앱은 여기서 종료 저장을 제출하고, closed_를 세워 "처리했다"고 답한다. 이 값은 UI thread도 읽으므로 std::atomic이다(스레드 모델).
  3. delegate가 보내 온 창 크기·배율을 쓴다. 설정 길이(24px 여백, 14px 글자)는 논리 픽셀이고, arrange에 넘기는 slot은 물리 픽셀이다. scale이 둘을 잇는다(배치).
  4. root를 창 전체에 배치하고, 그 위에 caption(데스크톱) 또는 앱 바(모바일)를 얹는다. 어느 쪽인지는 current_ui_platform()이 알려 주므로 같은 코드가 네 플랫폼에서 돈다.
  5. 세로 stack_element가 자식의 자리를 나눠 준다. 라벨의 글은 clicks_에서 나온다. 상태가 바뀌면 이 함수가 다시 불려 새 글을 가진 새 라벨이 생긴다.
  6. 버튼의 왼쪽 클릭에 make_message_action(increment_intent {})를 단다. 클릭되면 input thread에서 이 액션이 실행되어 메시지 하나를 돌려준다. 앱 상태를 건드리는 캡처가 없으니, 여러 스레드가 이 tree를 동시에 읽어도 안전하다.
  7. 내용을 caption 아래 자리에 배치하고, root를 ui_tree로 감싸 shared_ptr<const …>로 게시한다. const가 곧 계약이다. 게시한 뒤에는 아무도 고치지 않는다.

빌드하고 실행하기

의존성의 버전과 체크섬은 저장소에 고정되어 있고, CMake configure는 네트워크를 쓰지 않는다.

Windows 11 x64, Visual Studio 2022 또는 2026(MSVC 19.40 이상), Windows SDK 10.0.22621.0 이상, CMake 4.2 이상과 PowerShell이 필요하다. 저장소 루트에서 실행한다.

Apple Silicon, macOS 11 이상. Xcode와 Ninja가 필요하다.

Android arm64. Android Studio(SDK·JBR), NDK r27d, Ninja가 필요하다. core test는 adb로 연결한 기기에서 돌고, 예제는 Gradle이 APK로 싼다.

iPhone·iPad(iOS 15 이상), 기기와 Apple Silicon 시뮬레이터.

내 프로젝트에 연결하기

소스 트리로 넣든 설치 패키지를 쓰든 링크하는 타깃은 luil::luil 하나다. C++20과 UTF-8 컴파일 요건은 타깃이 전파한다. 공개 헤더는 모두 luil/로 시작하고, #include <luil/luil.h>가 공개 API 전체다.


실행 파일에 필요한 것앱과 Skia의 CRT 설정이 같아야 하고, 실행 파일에는 Codicons 글꼴과 제3자 고지를 담은 리소스 스크립트가 들어가야 한다. luil_generate_third_party_notices와 luil_configure_resource_script로 만든다(시험과 빌드).

요약

  1. luil은 Skia로 모든 것을 직접 그리는 C++20 애플리케이션 프레임워크다. 같은 앱 코드가 Windows·Android·macOS·iOS에서 돈다.
  2. 세 결정 — 직접 그리기, frame마다 새로 짓는 불변 tree, logic thread 하나가 쥐는 상태 — 이 구조를 정한다.
  3. 데이터는 한 방향으로 흐른다. 입력은 메시지가 되어 logic에 닿고, logic은 불변 frame을 게시하며, UI가 그것을 그린다.
  4. hover·눌림·초점은 앱 상태가 아니다. input thread가 snapshot으로 따로 게시하므로 logic을 기다리지 않고 보인다.
  5. 앱은 세 조각을 꽂는다. logic_driver(logic), interaction_policy(input), window_delegate(UI).
  6. 구현의 절반은 플랫폼을 모르는 core, 나머지 절반은 OS를 잇는 네 host다.

자주 묻는 질문

luil로 앱을 만들려면 무엇을 구현하나?

logic_driver 하나는 꼭 구현한다. 순수 가상 함수는 handle·make_frame·make_close_message·shutdown_completed 넷이다.

입력 정책(interaction_policy)과 창 사건을 메시지로 바꾸는 delegate는 필요할 때 더한다. 다만 delegate가 없으면 창 크기 메시지도 오지 않는다. 진입점은 이것들을 환경(window_environment 등)에 꽂고 플랫폼의 실행 함수(Windows는 run_application_window)를 부르는 몇 줄이다 (앱과 라이브러리의 경계, 첫 앱 ① 파일과 꽂는 자리).

interaction_policy를 꼭 꽂아야 하나? 없으면 무엇이 빠지나?

꽂지 않아도 된다(nullptr). 빠지는 것은 정책의 훅이 하던 일이다. 텍스트 칸의 입력·편집, 컨텍스트 메뉴의 키보드 탐색, 앱이 받는 키(on_key), 키보드로 옮긴 초점을 흘리는 창 안으로 들이기(on_focus_moved)가 대표적이다.

Tab 이동, 초점 둔 컨트롤의 Space·Enter, 기본 버튼, modal의 Esc처럼 라이브러리가 직접 하는 키 처리는 정책 없이 돈다. 휠도 정책이 없으면 공통 라우팅(route_wheel)으로 포인터 아래의 흘리는 창에 간다. 거꾸로 정책을 두면 휠은 on_wheel로만 가고, 기본 구현은 아무것도 하지 않는다. interaction_controller의 헤더 주석은 정책이 없으면 휠 라우팅도 꺼진다고 적었지만 코드는 이와 같다 (코드에서 확인한 동작) (키 라우팅, 정책에서 휠과 되살리기 잇기).

luil의 버튼·목록은 OS 컨트롤인가?

아니다. 모든 컨트롤을 Skia로 직접 그린다. 그래서 네 플랫폼에서 모양이 같다.

OS 컨트롤이 공짜로 주던 것, 곧 보조 기술(UIA·VoiceOver), IME 조합 입력, 클립보드는 플랫폼마다 다리로 잇는다. 플랫폼마다 다른 일은 창을 열고, 입력을 받고, 그린 픽셀을 화면에 내고, OS 기능을 잇는 것으로 좁혀진다 (luil은 무엇인가, 세 가지 큰 결정).

같은 코드로 네 플랫폼을 돌리려면 무엇을 갈라야 하나?

진입점 몇 줄뿐이다. hello의 앱 쪽 절반(hello_app)은 네 플랫폼이 같은 파일이다.

화면 모양이 갈리는 자리는 current_ui_platform()으로 묻는다. hello는 window_caption이 참이면 caption을, 아니면 앱 바를 얹는다. frame에 실은 요청(화면 방향·트레이·전역 단축키 등)을 하지 못하는 플랫폼은 받고 무시하고, 무엇을 하는지는 ui_platform::capabilities가 말한다. 렌더러는 네 플랫폼 모두 GPU를 먼저 세우고 실패하면 CPU로 물러선다 (같은 앱, 네 진입점, 플랫폼 매트릭스).

앱 상태에는 무엇을 넣고 무엇을 넣지 않나?

hover·눌림·초점·tooltip·끌기 표시는 넣지 않는다. input thread가 interaction_snapshot으로 따로 쥐고 게시한다.

앱 상태에 두는 것은 앱이 정하는 값이다. 입력 중인 글, 고른 행과 펼침, 스크롤 위치, 열린 popup과 보조 창이 그렇다. 라이브러리의 컨트롤은 그런 값을 바꾸고 싶을 때 메시지를 낼 뿐이다 (익숙한 프레임워크와 견주기, 열림은 앱이, 자리와 수명은 규약이).

앱 상태는 어디에 두나?

logic_driver를 구현한 객체의 멤버로 둔다. logic thread만 만진다.

hello의 clicks_와 metrics_가 그것이다. 다른 스레드에서 바꾸고 싶은 것은 메시지로 보낸다. 종료 절차 중 UI thread에서도 불리는 shutdown_completed가 읽는 값만은 std::atomic으로 지킨다 (hello 읽기 ② 상태와 화면, 왜 스레드를 셋으로 나누나).

메뉴·드롭다운·보조 창은 어떻게 띄우나?

앱 상태에 "열렸다"를 적고 make_frame이 frame에 싣는다. 실으면 서고 빼면 사라진다.

메뉴·드롭다운은 ui_frame::popups, 보조 창은 ui_frame::windows에 싣고, 각각 자기 tree를 갖는다. 닫으라는 계기(popup 밖 누름·Esc, 보조 창의 닫기 단추)는 메시지로 오고, 빼는 것은 앱이다. modal 대화(modal_host_element)는 frame이 아니라 tree 안에 담는 overlay다. tooltip만은 앱 상태 없이 element의 set_tooltip으로 끝난다 (열림은 앱이, 자리와 수명은 규약이, 창 하나와 여러 창, 직접 짓는 modal).

가만히 있을 때도 계속 다시 그리나?

아니다. 새 frame이나 상호작용 상태가 게시될 때, 크기·DPI·테마가 바뀔 때, element가 예고한 시각에만 그린다.

예고(next_update)가 없으면 timer도 걸지 않는다. logic thread도 메시지와 예고한 tick이 없으면 잠들어, 250ms마다 종료 신호만 확인한다 (언제 다시 그리나, 시간이 흐르는 두 길).

길이는 어떤 단위로 적나? DPI가 바뀌면?

설정에 적는 길이는 논리 픽셀(96 DPI 기준)이고, arrange에 넘기는 slot은 물리 픽셀이다. 배율(scale)이 둘을 잇는다.

150% 모니터라면 800×500 논리 픽셀 창이 1200×750 물리 픽셀이 된다. 크기와 배율은 delegate가 메시지로 보내고, 모니터를 옮겨 배율이 바뀌면 다시 온다. make_frame이 그 값으로 다시 배치한다 (hello 읽기 ① 조립하는 main, 두 가지 픽셀).

내 CMake 프로젝트에는 무엇을 링크하고 무엇을 include하나?

링크하는 타깃은 luil::luil 하나다. luil/luil.h 하나를 include하면 공개 API 전체가 들어온다.

C++20과 UTF-8 컴파일 요건은 타깃이 전파한다. 빌드 시간을 아끼려면 필요한 헤더만 골라 include해도 되고, 경로는 늘 luil/로 시작한다. umbrella header가 공개 헤더를 빠뜨리지 않았는지는 test(luil_umbrella_header)가 본다 (빌드하고 실행하기, 내 프로젝트에 붙이는 두 길).

라이선스는? 실행 파일에 무엇을 넣어야 하나?

luil 자체는 MIT 라이선스다. Codicons와 의존성에는 각 원본의 라이선스가 적용된다.

Windows 실행 파일에는 Codicons 글꼴과 luil·제3자 고지를 담은 리소스가 들어가야 한다. luil_generate_third_party_notices와 luil_configure_resource_script로 만든다. 다른 플랫폼에서 무엇을 앱이 싣는지는 자산과 글꼴에 있다 (빌드하고 실행하기).

사례로 확인하기

입력과 상태를 하나 정해 두고, luil이 그때 무엇을 하는지 코드에서 따라간 결과다. 펼치면 결과와 까닭이 나온다.

hello에서 "하나 더"를 누르면 clicks_를 실제로 늘리는 코드는 어느 스레드에서 실행되는가?

logic thread — handle()이 메시지를 받아 바꾼다

액션은 input thread에서 실행되지만 상태를 바꾸지 않고 increment_intent 메시지를 돌려줄 뿐이다. 상태를 바꾸는 곳은 logic thread의 handle() 하나다.

상태가 바뀌면 luil은 화면을 어떻게 갱신하나?

새 tree를 통째로 지어 게시하고, 이전 tree와 비교하지 않는다

게시된 element는 수정하지 않는다. make_frame()이 새 tree를 지어 latest_slot에 게시하고, 부분 갱신 경로는 없다. 지금은 표면 전체를 다시 그린다.

"클릭 한 번이 지나가는 길" 실험에서 버튼의 눌린 모양이 숫자보다 먼저 보이는 까닭은?

눌림은 input thread가 게시하는 interaction snapshot이고, 앱 상태를 거치지 않기 때문에

hover·press·focus는 input thread의 interaction_snapshot에 값으로 들어 있다. element는 그 안의 id와 자기 id를 비교해 그린다. 그래서 logic을 기다리지 않는다.

iOS 진입점에서 driver와 delegate를 static으로 만든 이유는?

run_application이 UIApplicationMain을 불러 돌아오지 않으므로, 프로세스가 끝날 때까지 살아야 해서

다른 플랫폼은 종료 절차가 끝나면 진입 함수가 돌아오지만, iOS의 UIApplicationMain은 돌아오지 않는다. 지역 변수의 수명에 기대면 안 되므로 정적 수명을 준다.

이 문서가 다루는 헤더

이 문서의 내용이 기대는 공개 헤더다. 기호를 누르면 API 찾아보기에서 주석과 선언 원문을 본다.

include/luil/luil.h최상위 기호 0

라이브러리 공개 API 전체를 한 번에 들이는 umbrella header다. 빌드 시간을 아끼려면 필요한 header만 골라 include해도 된다 — 어느 쪽이든 경로는 항상 `luil/` 접두로 시작한다.

include/luil/version.h최상위 기호 1

판번 매크로(LUIL_VERSION_MAJOR 등)다. 근원은 CMake의 project VERSION 하나이고 configure가 생성한다. 소비자는 매크로로 `#if` 분기를 하고, 런타임 표시는 아래 함수를 쓴다.

flibrary_version
