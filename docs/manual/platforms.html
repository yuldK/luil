플랫폼과 host

플랫폼을 모르는 luil_core 위에 플랫폼마다 얇은 host가 선다. host가 하는 일은 다섯 가지로 정해져 있다. 그래서 hello_app.cpp 한 파일이 Windows·Android·macOS·iOS의 네 진입점에서 그대로 돈다.

  1. luil_core와 luil의 경계와 그것을 지키는 장치를 설명한다.
  2. host가 꼭 구현할 다섯 가지를 플랫폼별 기술로 말할 수 있다.

  4. 접근성 어휘가 UIA·NSAccessibility·UIAccessibility 낱말이 되는 자리와, Android에 접근성이 없는 이유를 안다.
  5. OS 프레임워크를 모르는 "순수 층"을 따로 두는 무늬의 이점을 말한다.

두 층: luil_core와 luil

정적 라이브러리를 둘로 나눈다. 플랫폼을 모르는 core, 그리고 그 위에 플랫폼마다 하나씩 서는 조립. 소비자는 어느 플랫폼에서나 luil::luil 하나만 링크한다.

  4. core 위의 계층(win32/, android/, macos/, ios/, net/) include도 막는다.

깨우기는 내용을 싣지 않고 신호만 나른다. 내용은 core의 큐와 slot이 나른다. 그래서 신호 하나를 잃어도 명령은 큐에 남아 다음 신호에 실행된다. 빈 갈래는 그 기능이 꺼졌다는 뜻이다. Android에서 capture가 비어 있으니 app_host가 화면 남기기 실행 함수를 만들지 않고, input pump도 그 요청을 내지 않는다.
  1. logic·input thread에서 불리므로 구현은 thread-safe해야 한다. 공개 API는 Win32의 타입을 드러내지 않는다.
  2. 창 메시지 큐 포화처럼 전달에 실패하면 거짓을 돌려준다. 그러면 slot이 다음 게시에서 다시 신호한다. 한 번의 실패가 영구적인 미갱신으로 굳지 않는다.
  3. 창 명령, 앱 UI 명령, 클립보드, 화면 남기기는 큐가 내용을 나른다. 키 보고(key_report)만 내용이 표와 참거짓 하나라 신호가 직접 나른다.
  4. UI thread 전용 진입점이다. 입력 inbox는 drop_oldest라 밀리면 오래된 것부터 버린다(스레드 경계 메시징).
  5. 깨어난 UI thread가 큐를 통째로 꺼내 실행한다. 이 넷을 실행하는 것이 host의 네 번째 일이다.
  1. Android host의 루프는 ALooper_pollOnce 하나로 Activity 수명 주기(MAIN), 입력(INPUT), luil의 깨우기(USER)를 함께 기다린다. 시간 제한 poll_timeout()이 곧 타이머다.
  2. 수명 주기와 입력은 GameActivity glue가 준 처리기에 넘긴다.
  3. USER 출처면 eventfd를 비우고, 쌓인 명령을 실행하고, 다시 그려야 한다고 표시한다.
  4. 다른 thread가 eventfd에 쓰면 looper가 깬다. 주석이 말하듯 Win32의 PostMessageW에 해당한다.
  5. snapshot, 창 명령, 앱 UI 명령, 클립보드가 모두 같은 eventfd 쓰기다. 화면 남기기와 키 보고 갈래는 채우지 않는다 — Android에서는 그 기능이 꺼져 있다.

만드는 법은 플랫폼, 정책은 core

렌더러는 플랫폼이 생성 함수만 넘기고, 실패하면 CPU로 물러서는 정책은 core의 renderer_host가 한 곳에서 정한다. 글꼴과 즉시 종료는 등록 함수가 아니라 링크로 묶는다.

  1. 플랫폼이 넘기는 것은 GPU·CPU 렌더러를 만드는 함수 둘과 오류 글에 쓸 GPU 이름뿐이다. GPU 함수가 비어 있으면 GPU가 없는 플랫폼이다.
  2. 앱이 쓰는 값은 gpu 하나다. 플랫폼별 값(vulkan, metal)을 두어 다른 플랫폼에서 고르면 오류가 나게 하는 길은 거절했다. 결과를 알리는 renderer_backend에만 그 이름들이 있다.
  3. automatic은 GPU를 먼저 세우고, 만들거나 크기를 바꾸거나 그리다 실패하면 CPU로 바꾼다. 한 번 물러선 표면은 GPU를 다시 시도하지 않는다(그리기와 렌더러). Android는 더 넓다 — 한 번 물러선 Activity는 창이 다시 생겨도 CPU다.
  1. 글꼴 registry의 cache·자물쇠·설정·대체 규칙은 플랫폼을 가리지 않는다. 플랫폼마다 다른 것은 네 함수뿐이라 interface 하나로 받는다.
  2. 시스템 글꼴 관리자, 부를 때마다 새로 만드는 관리자, 기본 UI 글꼴 가족, 사용자 UI 언어. Windows는 DirectWrite와 Segoe UI, Android는 FreeType과 sans-serif, Apple은 CoreText와 시스템 글꼴이다.
  3. 플랫폼 계층이 이 함수를 하나 정의한다. 등록 순서가 없으므로 창 없는 test와 input thread의 글자 폭 측정이 어느 시작 순서에서든 같은 자원을 본다. core test는 빈 글꼴 관리자와 abort()를 정의한 stub을 링크한다.


필요 없는 interface는 만들지 않았다

이식 계획은 경계를 둘로 나눴다. core가 의존하는 경계(글꼴, 자산, 렌더러, host API)는 Windows로 먼저 세웠다. 플랫폼 안쪽에서만 쓰는 경계(텍스트 입력, 클립보드 실행, 커서)는 모양만 적어 두고 쓰는 단계에서 만들었다. 이유: "Win32 구현 하나만 보고 세운 인터페이스는 두 번째 구현에서 대개 다시 고치게 되기 때문이다." 계획에 있던 system_appearance·asset_reader interface는 끝내 만들지 않았다.

접근성: 어휘가 플랫폼 낱말이 되는 자리

element는 플랫폼 중립 어휘(access_role 37값, access_command 9값)로 자기를 설명한다. 플랫폼마다 번역 표 하나가 그것을 UI Automation, NSAccessibility, UIAccessibility로 옮긴다. Android에는 번역 코드가 없다.

역할은 "platform 어휘가 아니라 이 저장소의 element가 실제로 하는 일의 목록"이다. 번역은 플랫폼마다 한 곳이다: Windows는 control_type_for, macOS는 ax_role_of, iOS는 traits_of와 container_type_of. iOS의 trait에는 역할과 상관없는 공통 규칙이 덧붙는다: 바꿀 수 있는 범위면 Adjustable, 선택되었거나 켜졌으면 Selected, 비활성이면 NotEnabled.

provider는 포인터가 아니라 id를 쥔다. tree는 frame마다 통째로 새로 지어지고, 그것을 넘어 남는 정체성은 id뿐이다. 그래서 질의가 올 때마다 지금 tree에서 다시 찾는다. 신원은 세 플랫폼에서 같은 꼴(kind:owner)이다.

보조 기술의 호출 안에서는 앱을 부르지 않는다. 눌러서 하는 명령은 access_click_event로 input thread에 보내 마우스 클릭과 같은 자리, 같은 순서로 나가게 한다. 상태 변화는 그 뒤 발행본 대조가 알린다. "앱이 동작을 처리하기 전에 상태가 바뀌었다고 보고하지 않기 위한 순서다."

보조 기술로 할 수 있는 일은 사람이 할 수 있는 일의 부분집합이다. 보이지 않는 것, modal 가둠 뒤의 것, 이미 그 상태인 누름은 거절한다. 판정은 사람이 쓰는 hit_test로 상자 안의 아홉 자리를 훑어서 한다.

  1. 접근 색인은 tree를 만들 때 한 번 짓는다(불변 UI tree). 구조 역할(none)은 형제 줄에 서지 않고, 그 자리는 자식들이 잇는다.
  2. 부모가 없으면 최상위 줄, 있으면 부모의 자식 줄이다.
  3. 자리 번호 ±1이 곧 다음·이전 형제다. 색인이 없으면 UIA 클라이언트가 NextSibling을 되풀이할 때 형제마다 root에서 부모를 찾아 형제 수의 제곱이 된다. 줄에는 id의 임자만 서므로, 같은 id가 둘이어도 "다음"이 제자리로 돌아와 열거가 끝나지 않는 일이 없다.
  1. VoiceOver의 AXPress가 오면, 상태를 든 요소는 그 상태의 명령이 된다: 켬끔이면 toggle, 선택이면 select, 펼침이면 expand·collapse. 범위가 있거나 누를 역할이 아니면 할 수 없음이다. 나머지는 invoke다.
  2. 범위가 있을 때만 step만큼 값을 바꾸는 요청이 된다.
  3. 메뉴를 보이라는 것은 펼침, 물리기(Esc)는 펼친 것을 접기다.

순수 층이라는 무늬

이 번역은 AppKit을 include하지 않는 accessibility_mapping.cpp에 있다. 그래서 AppKit도 화면 읽기도 없이 core test로 돌고, iOS 다리가 같은 파일을 그대로 쓴다. 같은 무늬가 저장소에 되풀이된다: Win32 포인터 번역은 "창도 시계도 모르므로 test가 결정적이다", Android 입력 번역은 "GameActivity의 구조체를 모르게 둔다", macOS 키 변환도 "AppKit을 모르게 둔다". OS 프레임워크를 모르는 계산을 떼어 내면 플랫폼 없이 시험할 수 있고, 다른 플랫폼이 그대로 가져다 쓸 수 있다.

오해하기 쉬운 점

아니다"luil::win32는 Windows 전용이다"

macOS host 헤더가 win32_window.h를 include하고, 동영상 헤더 luil/win32/media_player.h는 macOS에서 AVFoundation으로 구현된다. hello도 네 플랫폼에서 이 이름공간의 별칭을 쓴다. 이름은 역사적이다.

반만 맞다"iOS는 macOS 이식을 고친 것이다"

host 본체, 접근성 다리, 웹뷰, 파일 감시는 따로 썼다. AppKit을 모르는 macOS 파일 25개는 그대로 컴파일하고, IME 연결은 Android의 ime_session을 가져다 쓴다. 두 플랫폼의 순수 층을 조합해 섰다.

아니다"UI thread는 늘 메인 thread다"

Android만 다르다. luil의 UI thread는 glue가 띄운 android_main thread다. 창 장식·햅틱·방향·권한처럼 View를 만지는 일은 Java 메인 thread로 넘긴다.

아니다"LUIL_ENABLE_WEBVIEW를 끄면 웹뷰가 모두 빠진다"

이것은 WebView2(Windows) 옵션이다. Windows가 아니면 아예 꺼 둔다. macOS·iOS의 WKWebView 파일은 늘 컴파일된다.

아니다"GPU가 회복되면 다시 GPU로 그린다"

automatic에서 물러선 표면은 GPU를 다시 시도하지 않는다. Android는 Activity 단위로, 창이 다시 생겨도 CPU다.

아니다"접근 tree는 창이 뜨면 바로 있다"

그린 적이 없는 창에는 tree가 없다. macOS는 가려진 창을 그리지 않아 보조 기술이 옛 계층을 읽은 적이 있다. 그리기를 건너뛸 때도 바뀐 tree를 다리에 건네도록 고쳤다.

주석이 코드보다 늦은 곳

ui_platform.h는 clipboard_image_copy를 "Win32만 참", desktop을 "(Windows)"라 적는다. accessibility.h는 "platform 번역은 win32 계층의 표 하나"라 적는다. 지금은 macOS·iOS도 참이고 번역 표도 셋이다. 주석을 인용할 때 코드와 맞춰 봐야 하는 자리다.

요약

  1. 정적 라이브러리를 플랫폼을 모르는 luil_core와 플랫폼별 luil로 나눈다. core가 플랫폼 헤더를 들이지 않았는지는 include 줄을 읽는 시험이 Windows에서 지킨다.
  2. host의 일은 다섯 가지다: UI thread와 이벤트 루프, 깨우기(PostMessageW·eventfd·CFRunLoopPerformBlock), 입력 변환, take_* 명령 실행, 링크로 묶는 자원.
  3. 깨우기는 신호만 나르고 내용은 core의 큐와 slot이 나른다. 빈 갈래는 그 기능이 꺼졌다는 뜻이다.
  4. 렌더러는 생성 함수만 플랫폼의 것이고 물러섬 정책은 core 한 곳이다. 글꼴과 즉시 종료는 등록 순서가 없도록 링크로 묶는다.
  5. 같은 hello_app.cpp가 네 진입점에서 돈다. Android의 UI thread는 메인 thread가 아니고, iOS의 진입점은 돌아오지 않는다.
  6. 접근성 어휘는 플랫폼을 모르고, 번역 표는 플랫폼마다 한 곳이다. Android에는 "Java 0줄" 방침 때문에 접근성 계층이 없다. OS를 모르는 번역 층은 core test로 돌고 다른 플랫폼이 그대로 쓴다.

자주 묻는 질문

플랫폼마다 다른 코드는 어디에 두나?

진입 파일 하나에 둔다. 앱 상태·메시지·frame을 짓는 driver, delegate, 입력 정책은 네 플랫폼이 같은 파일을 쓴다.

hello는 플랫폼마다 진입 파일(main.cpp·android_main.cpp·macos_main.cpp·ios_main.cpp)이 config를 채워 그 플랫폼의 run_application(Windows는 run_application_window)을 부르고, 플랫폼별 빌드가 자기 진입 파일을 고른다. OS API가 다른 몇 곳(실행 파일 경로, 지역 시각)은 데모가 _WIN32·__APPLE__로 가른다 (같은 hello, 네 진입점, 다른 플랫폼에서 짓기).

지금 어느 플랫폼에서 도는지 앱이 알려면?

current_ui_platform()을 부른다. 어느 thread에서 불러도 된다. 다만 OS 이름을 담은 칸은 없고 형태와 능력만 있다.

form_factor(desktop·mobile), window_caption, command_key_shortcuts(⌘ 표기), capabilities(화면 방향·시스템 막대·볼륨 키·햅틱·작업 표시줄·OS 알림·그림 복사·트레이·전역 단축키)다. host가 시작할 때 정하고 Windows는 실행 중에도 고쳐 적으므로(원격 세션의 둥근 모서리, 알림 가능 여부) frame을 지을 때 읽는다 (플랫폼 매트릭스, API: current_ui_platform).

데스크톱의 caption과 모바일의 앱 바는 어떻게 가르나?

current_ui_platform().window_caption이 참일 때만 앱이 그리는 caption(caption_element)이 선다. 거짓일 때 맨 위에 무엇을 둘지는 앱이 고른다 — hello는 app_bar_element를 둔다.

Windows는 참, Android·iOS는 거짓이고, macOS는 테두리 없는 창일 때만 참이다(기본은 시스템 제목 막대). 거짓인 플랫폼에서 caption_element는 높이가 0이고 보이지 않아, 잊고 넣어도 모바일 화면에 창 단추가 서지 않는다. hello는 거짓이면 늘 앱 바를 두므로 기본 macOS 창에서는 시스템 제목 막대 아래에 앱 바가 선다. 데스크톱 데모는 앱 바를 두지 않는다 (코드에서 확인한 동작,같은 hello, caption 만들기).

그 플랫폼이 못 하는 기능을 frame에 실으면?

받기만 하고 아무 일도 하지 않는다. 그래서 앱은 플랫폼마다 frame을 다르게 짓지 않는다.

능력 플래그(ui_platform_capabilities)는 그 기능의 설정 항목을 화면에 둘지 고를 때 쓴다. 답이 오는 요청은 "지원 안 함"으로 답한다. Android의 파일 대화 상자는 UI를 열지 않고 file_dialog_status::unsupported를 돌려주고, 보조 창·도킹 표면은 무시하며 로그에 한 번 적는다 (코드에서 확인한 동작, 플랫폼 매트릭스).

Android에서 빠진 기능은?

보조 기술 다리(element를 TalkBack 같은 보조 기술에 알리는 계층), 웹뷰, 파일 대화 상자, 동영상 재생기, 보조 창·도킹 표면, 화면 남기기가 없다.

접근성과 파일 대화 상자는 View를 상속한 Java 클래스가 있어야 해서 "luil이 드는 Java 소스는 0줄" 방침과 부딪힌다. 웹뷰는 Android host에 구현이 없어 webview_element가 자리 글만 그린다. 기능마다의 상태는 매트릭스의 "없음" 칸에 근거 줄과 함께 있다 (코드에서 확인한 동작, 플랫폼 매트릭스, 접근성, 접근성의 플랫폼 차이).

렌더러를 CPU로 고정해 띄우려면?

플랫폼 config의 renderer를 renderer_mode::cpu로 둔다. 다시 빌드하지 않고 바꾸려면 진입점에서 Android는 apply_debug_properties, iOS는 apply_debug_arguments를 불러 둔다(hello가 그렇게 한다). 그러면 시스템 속성 debug.luil.renderer나 --renderer= 인자로 고른다.

칸은 Windows가 win32::window_config::renderer, Android·macOS·iOS가 각자의 application_config::renderer다. 데스크톱 데모는 --renderer= 인자를 parse_renderer_mode로 읽어 넣는다. 받는 글은 auto·cpu·gpu·direct3d다 (만드는 법은 플랫폼, 정책은 core, 다른 플랫폼에서 짓기).

GPU가 실패하면 앱이 죽나?

기본 automatic이면 죽지 않는다. GPU 렌더러를 만들거나 크기를 바꾸거나 그리다 실패하면 그 표면은 CPU로 물러선다.

한 번 물러선 표면은 GPU를 다시 시도하지 않는다 (코드에서 확인한 동작). Android는 Activity 단위라 창이 다시 생겨도 CPU다. gpu를 고르면 물러서지 않고 실패를 돌려주고, 그 뒤는 플랫폼마다 다르다 — Android는 Activity를 끝내고 iOS는 그리지 않는다. 물러섬 정책은 플랫폼이 아니라 core의 renderer_host 한 곳에 있다 (만드는 법은 플랫폼, 정책은 core, 렌더러 물러섬).

macOS·iOS 코드에서 luil::win32:: 이름을 써도 되나?

빌드는 된다. luil::win32::logic_driver·app_host·ui_frame은 luil::의 같은 형식을 가리키는 별칭이다. 새 코드는 luil/app/app_host.h와 luil:: 이름을 쓰라고 헤더가 적는다.

별칭은 옛 이름을 한 판 동안 남긴 다리다. win32::window_delegate는 별칭이 아니라 Windows의 delegate 형식인데, Android·iOS host에 넘기면 그 가운데 플랫폼 중립 부분(app_delegate)만 불린다. macOS host는 그 형식을 구현했으면 그 훅도 부른다 (코드에서 확인한 동작, 같은 hello, 오해하기 쉬운 점).

웹뷰는 어느 플랫폼에서 되나?

Windows(WebView2), macOS·iOS(WKWebView)다. Android에는 없다.

LUIL_ENABLE_WEBVIEW는 Windows의 WebView2 옵션이다. 끄면 SDK를 찾지도 링크하지도 않고, 웹뷰를 실은 frame에는 자리 글만 남는다. macOS·iOS의 WKWebView 파일은 이 옵션과 상관없이 늘 컴파일된다 (오해하기 쉬운 점, 웹뷰 만들기).

HTTP 요청은 어떤 네트워크 스택을 쓰나?

OS의 것이다. Windows는 WinHTTP, Android는 JNI로 부르는 HttpURLConnection, macOS·iOS는 NSURLSession이다.

프록시·인증서·TLS를 OS가 맡으므로 앱이 인증서 저장소를 따로 다루지 않는다. libcurl과 TLS 라이브러리를 들이는 길은 의존이 무겁고 인증서 저장소를 따로 다뤄야 해서 거절했다 (고른 길과 이식의 순서, HTTP 요청).

앱이 뒤로 갈 때 저장하려면?

delegate의 make_lifecycle_message가 app_lifecycle::background를 받을 때 저장 메시지를 낸다. 모바일 OS는 그 뒤 종료 알림 없이 프로세스를 거둘 수 있다.

Android(onStart·onStop), iOS(장면이 앞뒤로 갈 때), macOS(앱이 다른 앱에 자리를 내줄 때)가 부르고 Windows는 부르지 않는다 (코드에서 확인한 동작). Windows에서는 종료 신호가 저장을 맡는다. 플랫폼마다의 뜻은 닫힘과 수명 주기에 있다.

단축키 글을 macOS식(⌘·⇧)으로 보이려면?

따로 할 일이 없다. command_key_shortcuts가 참인 플랫폼(macOS·iOS)에서 shortcut_label이 ⌥⇧⌘ 기호로 쓰고, key_chord::control이 Command로 읽힌다.

명령표는 한 벌로 둔다. parse_shortcut은 두 꼴을 모두 읽어, 저장해 둔 단축키 글이 어느 플랫폼에서나 읽힌다 (플랫폼 매트릭스, 명령표에서 항목 짓기).

Windows 진입점에서 먼저 할 준비는?

창을 만들기 전에 win32::enable_per_monitor_dpi_awareness()를 부르고, win32::com_sta_scope를 하나 둔다. 다른 플랫폼의 진입점에는 이런 준비가 없다.

hello의 주석대로 COM STA는 TSF(텍스트 입력)·파일 대화 상자가 요구한다. hello는 텍스트 입력이 없어도 관례로 켠다 (같은 hello, 네 진입점, 첫 앱 ③ 진입점).

사례로 확인하기

입력과 상태를 하나 정해 두고, luil이 그때 무엇을 하는지 코드에서 따라간 결과다. 펼치면 결과와 까닭이 나온다.

Windows에서 src/ui의 파일 하나에 #include <windows.h>를 넣었다. Windows 빌드와 기존 시험은 모두 통과한다. 이 실수는 어디서 잡히나?

include 줄을 읽는 CTest 항목 luil_core_portability

Windows에서는 core가 Win32 헤더를 들여도 빌드되고 시험도 통과한다. 그래서 스크립트가 core 디렉터리의 include 줄을 직접 읽어 세 SDK의 헤더와 상위 계층 include를 찾아 실패시킨다.

platform_font_source()를 앱 시작 때 부르는 등록 함수로 바꾸면 무엇이 나빠지나?

시작 순서에 기대게 되어, 등록보다 먼저 registry를 부르는 test와 input thread가 빈 자원을 본다

링크 결합에는 등록 순서가 아예 없다. core test는 플랫폼 계층 대신 빈 글꼴 관리자와 abort()를 정의한 stub을 링크해, 어느 플랫폼에서나 같은 시험을 같은 수만큼 돌린다.

네 플랫폼의 진입점은 무엇을 공유하고 무엇이 다른가?

iOS의 run_application은 돌아오지 않으므로 driver와 delegate를 static으로 둔다

iOS는 UIApplicationMain을 불러 돌아오지 않는다. Android의 UI thread는 android_main thread이고, Activity가 끝나면 돌아온다. macOS는 창이 닫히고 종료가 끝나면 돌아온다.

UIA 클라이언트가 항목 1만 개인 목록의 자식을 NextSibling으로 훑는다. 접근 색인이 없어 걸음마다 root에서 부모를 찾는다면 비용은?

형제 수의 제곱

색인이 있으면 한 걸음이 해시 조회와 벡터 색인으로 끝난다. 색인은 같은 id가 둘일 때 "다음"이 제자리로 돌아와 열거가 끝나지 않는 문제도 막는다. 줄에는 id의 임자만 선다.

VoiceOver 번역(역할 표, 값, 실행 번역, 발행본 대조)을 AppKit 없는 accessibility_mapping.cpp에 따로 두어 얻은 것은?

AppKit 없이 core test로 돌고, iOS 다리가 같은 파일을 그대로 쓴다

UIKit 쪽 파일은 객체·trait·알림 게시만 맡는다. 같은 생각이 Win32 포인터 번역, Android 입력 번역, macOS 키 변환에도 되풀이된다.

luil의 access_role::button은 Android에서 무엇으로 번역되나?

번역되지 않는다. Android host에는 접근성 계층이 없다

AccessibilityNodeProvider를 쓰려면 View를 상속한 Java 클래스가 필요하다. 이것이 "Java 소스 0줄" 방침과 부딪혀 들이지 않았다. access_info를 고쳐도 Android에서는 아무도 읽지 않는다.
