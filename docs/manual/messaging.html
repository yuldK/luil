스레드 경계 메시징

사건은 순서대로, 상태는 최신 것만. channel과 latest_slot 두 장치가 세 스레드 사이의 모든 이야기를 나른다.

관련 소스
include/luil/messaging/, app_message.h
실습
channel·latest_slot 시뮬레이터, get<T> 판정기
먼저 읽기
스레드 모델, mutex·condition variable

이 문서를 읽으면

  1. 사건과 상태를 서로 다른 장치로 나르는 이유를 설명한다.
  2. channel의 post·receive·drain·close와 두 넘침 정책의 결과를 예측한다.
  3. latest_slot의 version, 신호 병합, 실패한 신호의 되돌림을 설명한다.
  4. app_message가 타입을 지운 채 메시지를 나르는 방법과 그 한계를 안다.

사건과 상태는 다르게 나른다

클릭은 하나도 잃으면 안 되고 순서가 중요하다. frame은 최신 것만 의미가 있다. 둘을 같은 장치로 나르면 어느 한쪽이 망가진다.

channel — 우편함

편지가 온 순서대로 쌓이고, 받는 사람이 하나씩 꺼낸다. 클릭·키·앱 메시지 같은 사건을 나른다.

  • 여러 생산자, 소비자 하나 (MPSC)
  • FIFO, 유한 용량
  • 넘치면 reject_newest 또는 drop_oldest

latest_slot — 전광판

새 글이 옛 글을 덮는다. 보는 사람은 언제 보든 가장 최신 글을 본다. frame·tree·interaction 같은 상태를 나른다.

  • 게시자·조회자 여럿 가능
  • 새 값이 이전 값을 대체, version은 1부터 증가
  • 소비자가 느리면 중간 version을 건너뛴다

frame을 FIFO로 나르면 UI가 잠깐 느려진 사이 낡은 frame이 줄줄이 쌓여, 메모리를 먹고 화면은 과거를 그린다. 반대로 클릭을 "최신 값 하나"로 나르면 빠르게 두 번 누른 클릭 중 하나가 사라진다. luil은 둘을 갈라 각자에 맞는 의미론을 준다.

channel 읽기 ① post

post는 절대 블로킹하지 않는다. 잠금은 짧게, 신호는 잠금 밖에서 낸다.

  1. 받아들인 항목만 접수 번호(sequence)를 얻고, 그 번호를 호출자에게 알려 준다. 소비자가 "이 번호까지 처리했다"를 알리면 생산자가 자기 메시지와 맞춰 볼 수 있다(스레드 모델 문서의 tree ticket이 이것을 쓴다).
  2. close 뒤의 게시는 channel_closed다. 번호도 쓰지 않는다.
  3. reject_newest면 새 항목을 거절하고 통계만 센다(channel_full). drop_oldest면 맨 앞을 버리고 받는다(posted_after_drop). 어느 쪽이든 post는 기다리지 않는다.
  4. 접수 번호와 시각을 붙여 envelope에 담는다. 시계는 주입할 수 있어 test가 고정 시계를 넣는다. 최대 깊이(peak_depth)도 센다.
  5. 잠금 안에서 "넣기 전에 비어 있었나"를 기록하고, 그랬을 때만 신호 함수를 꺼내 둔다. 이미 쌓여 있으면 소비자는 깨어 있거나 곧 깨므로 신호를 다시 낼 이유가 없다. 연속 게시는 깨우기 하나로 병합된다.
  6. condition variable을 깨우고, 잠금을 놓은 뒤에 신호 함수를 부른다. 신호 함수(예: PostMessageW)가 잠금을 쥔 채 불리면 다른 생산자가 그동안 막힌다.

해 볼 것: drop_oldest로 바꾸고 press → move ×6을 넣은 뒤 꺼내 보라. press가 버려지고, 소비자는 번호가 건너뛴 것을 본다. luil의 input pump는 이때 진행 중인 누름·끌기를 취소한다. reject_newest에서는 같은 순서가 마지막 move들을 거절한다.

넘칠 때, 무엇을 잃을 것인가

정책은 전달을 보장하지 않는다. 무엇을 잃을지 고를 뿐이고, 잃은 사실을 알아차리는 길을 함께 둔다.

input_inbox · drop_oldest · 4096

포인터 이동의 중간 좌표는 버려도 된다. 최신 좌표가 중요하다. 하지만 버려진 것 중에 누름·뗌·초점 상실이 섞일 수 있다.

그래서 소비자는 envelope.sequence가 건너뛴 것을 보면 cancel_dropped_gestures()로 진행 중인 누름과 끌기를 취소한다. 초점은 유지하고 다음 초점 이벤트가 갱신한다.

app_inbox · reject_newest · 1024

앱 메시지는 버리면 안 된다. 넘치면 새 것을 거절하고 channel_full을 돌려줘 게시한 쪽이 알게 한다.

input pump는 여유가 생길 때까지 짧게 재시도하고, 종료 신호는 종료 예산 안에서 재시도한다(스레드 모델). post_app_message는 반환값을 보지 않으므로 거절은 app_inbox_statistics()로 확인한다.

  1. 셋째 post는 맨 앞(1)을 버리고 받아들인다. 결과는 posted_after_drop이다.
  2. 접수는 3건, 버린 것은 1건이다. 유실은 조용하지 않고 숫자로 남는다.
  3. 첫 수신의 번호가 0이 아니라 1이다. 소비자는 번호 0이 사라졌다는 것을 이 구멍으로 안다. 접수된 항목에만 번호가 붙기 때문에 가능한 일이다.

channel 읽기 ② 소비자와 close

꺼내는 쪽은 한 스레드뿐이다. debug 빌드는 그 약속을 assert로 지킨다.

  1. 비어 있으면 닫혔는지에 따라 closed 또는 empty다. 닫힌 뒤에도 남은 항목은 끝까지 꺼낼 수 있다(drain 의미론).
  2. condition variable로 최대 wait_limit만 잔다. 스레드 모델 문서의 logic loop가 250ms나 다음 tick까지로 이 값을 준다. 시간이 다 되면 timed_out이다.
  3. 최대 max_count개를 꺼낸다. 상한이 한 번 깰 때 끝없이 소비하는 것을 막아 렌더링 기회를 보존한다. logic loop는 63을 준다.
  4. 이미 닫혔으면 아무 일도 없다. 닫고, 기다리는 소비자를 모두 깨우고, 신호를 낸다. noexcept 함수라 신호 함수가 계약을 어기고 던져도 삼킨다.
  5. debug 빌드는 첫 수신 스레드의 id를 기억하고, 다른 스레드가 꺼내면 assert한다. MPSC라는 계약을 실행 중에 확인하는 장치다. release 빌드에서는 비용이 없다.

latest_slot 읽기

값 하나, version 하나, 그리고 "아직 가져가지 않은 새 값이 있다"는 표시 하나. 125줄이 전부다.

  1. 최신 값 하나만 유지한다. 신호는 소비자가 가져가지 않은 새 값이 처음 생길 때만 부르고, 연속 게시는 깨우기 하나로 병합된다. 신호 함수는 전달에 성공했는지를 돌려준다.
  2. 닫혔으면 0을 돌려준다. version은 1부터 시작하므로 0은 "게시되지 않음"이다. 값을 덮어쓰고 version을 올린다.
  3. 아직 소비되지 않은 신호가 있으면(pending_) 신호를 다시 내지 않는다. UI가 깨어나기 전에 frame이 열 번 게시되어도 창 메시지는 하나다.
  4. 신호 함수가 실패를 알리면(창 메시지 큐가 가득 찬 경우 등) pending_을 되돌린다. 그래야 다음 게시가 다시 신호한다. 한 번의 일시적 실패가 영구적인 미갱신으로 굳지 않는다.
  5. 소비자는 자기가 본 version을 들고 와서, 그보다 새 값이 있을 때만 받는다. 받으면 pending_을 내려 다음 게시가 신호하게 한다. 중간 version은 자연히 건너뛴다.

latest_slot 실험

logic이 frame을 여러 번 게시하는 동안 UI가 한 번만 깨어나는 모습을 본다.

해 볼 것: publish ×5 뒤에 take_newer를 한 번. 신호는 1번, UI가 본 version은 마지막 하나다. 이번에는 신호 전달 성공을 끄고 publish, 다시 켜고 publish를 눌러 보라. 실패한 신호가 다음 게시의 신호를 막지 않는다.
  1. 신호 함수가 deliverable을 돌려준다. 처음에는 실패다.
  2. 첫 게시는 신호를 냈지만 실패했다. 이것이 "이미 신호했음"으로 남으면 다음 게시는 신호 없이 잠긴다.
  3. 전달이 가능해진 뒤의 게시가 신호를 낸다. 실패가 굳지 않았다.
  4. 성공한 신호부터는 병합된다. 소비자는 최신 값 3을 받는다.

타입을 지운 운반체 app_message

라이브러리는 앱의 메시지 타입을 모른다. 그래도 나를 수 있게, 값을 shared_ptr<const void>와 타입 정보 한 쌍으로 싼다.

  1. element 액션은 앱 타입을 이 상자에 담아 돌려주고, 라이브러리는 내용을 보지 않고 logic inbox로 보낸다. 앱은 경계에서 꺼낸다.
  2. 생성자가 make_shared<const T>로 값을 한 번 옮겨 담고 typeid(T)를 기억한다. 게시된 tree의 액션은 여러 스레드에서 실행될 수 있으므로 담은 값은 const다.
  3. 기본 생성은 빈 메시지다. 액션이 아무것도 내지 않는 경우를 값으로 표현한다.
  4. 저장된 타입과 묻는 타입이 정확히 같을 때만 포인터를 돌려준다. 상속 변환은 하지 않는다. 앱 경계에서 알려진 타입 하나로 꺼내는 용도이기 때문이다.
  5. 멤버는 공유 포인터 하나와 type_info 포인터 하나다. channel을 값으로 지나도 payload는 복사되지 않는다.

액션이 돌려주는 값은 11갈래 variant다. 프레임워크는 갈래를 보고 그 값을 처리할 스레드로 보낸다.

const가 지켜 주지 못하는 것payload가 const여도, 그 안에 외부 포인터나 mutable 캡처가 있으면 안전하지 않다. 게시된 액션은 공유되는 앱 상태를 직접 바꾸면 안 된다. 바꾸고 싶은 것은 메시지로 말한다.

lock-free가 아닌 이유

두 장치는 mutex로 내부 저장소를 지키는 평범한 자료구조다. 빠르기보다 맞기를 먼저 골랐다.

단순함이 주는 것

  • 잠금 구간이 짧고(넣기·꺼내기 한 번), 경합은 스레드 셋뿐이다.
  • 정책·통계·close·신호 병합 같은 의미론을 잠금 안에서 그대로 쓸 수 있다.
  • 헤더만으로 된 component라 다른 프로젝트에 복사해도 그대로 컴파일된다.

검증하는 법

  • header-only라 별도 실행 파일에서 AddressSanitizer로 전체 구현을 검사한다(Release 테스트, 시험과 빌드).
  • MSVC의 /RTC1과 ASan은 함께 쓰지 않는다.
  • 여러 생산자의 순서 보존, close와 경쟁하는 생산자, 스트레스 테스트가 있다.

신호 함수의 세 가지 약속짧아야 하고, 예외가 없어야 하고, 채널 API를 다시 부르면 안 된다. 조립 순서는 채널·slot 생성 → callback 설정 → 스레드 시작이다. 신호는 잠금 밖에서 불리지만, 신호 안에서 같은 채널에 넣으면 의미론이 꼬인다.

요약

  1. 사건은 channel(FIFO, 유한 용량, 소비자 하나)로, 상태는 latest_slot(최신 값 하나, version)으로 나른다.
  2. post는 블로킹하지 않는다. 넘치면 reject_newest는 새 것을 거절해 알리고, drop_oldest는 맨 앞을 버린다.
  3. 접수된 항목에만 번호가 붙으므로 소비자는 번호의 구멍으로 유실을 알아챈다. input은 그때 진행 중인 몸짓을 취소한다.
  4. 신호는 "비어 있다가 채워질 때"와 "새 값이 처음 생길 때"만 나간다. 연속 게시는 깨우기 하나로 병합되고, 실패한 신호는 되돌린다.
  5. app_message는 shared_ptr<const void>와 type_info로 타입을 지운다. get<T>는 정확히 같은 타입만 꺼낸다.
  6. input_action의 갈래가 실행할 스레드를 정한다. 앱 상태를 바꾸는 갈래는 app_message 하나다.

자주 묻는 질문

앱 메시지는 어떻게 정의하고 보내나?

평범한 구조체를 정의해 app_message에 담는다. 라이브러리는 그 타입을 모른 채 나른다.

"누르면 이 메시지 하나"인 액션은 make_message_action(intent)로 짓고, 액션이 돌려주는 목록의 값 하나는 make_app_action(intent)로 싼다. 직접 넣을 때는 app_host::post_app_message다. 받는 쪽은 handle에서 get<T>()로 꺼낸다 (타입을 지운 운반체 app_message, hello 읽기 ②).

handle에서 메시지 종류를 어떻게 가르나? 화면마다 나눠 받으려면?

get<T>()를 차례로 묻는다. 타입이 다르면 nullptr라 맞는 하나에서만 값이 나온다.

라이브러리에 분배기는 없다. 데모는 페이지마다 handle(const app_message&)가 받았는지를 bool로 돌려주고, driver가 페이지들에 차례로 물어 처음 받은 곳에서 멈춘다. 앱 쪽 관례다 (타입을 지운 운반체 app_message).

worker나 다른 스레드에서 메시지를 보내도 되나?

된다. post_app_message는 어느 스레드에서 불러도 되고 막히지 않는다.

app inbox는 생산자 여럿·소비자 하나(logic thread)인 channel이다. 넣기는 잠금 안에서 큐 끝에 붙이는 것뿐이라 기다리지 않는다. 낯선 스레드의 게시가 driver에 닿는 것을 test가 잠근다 (channel 읽기 ① post).

메시지가 버려질 수 있나? 받았는지 알려면?

버려질 수 있다. app inbox는 1024칸 reject_newest라 가득 차면 새 메시지를 거절하고, post_app_message는 그 사실을 알리지 않는다.

받았는지 알아야 하면 post_app_message_ticketed를 쓴다. 거절되면 0을 돌려준다. 지금까지 버려진 수는 app_inbox_statistics().rejected가 센다. element 액션이 낸 메시지는 input thread가 자리가 날 때까지 다시 넣고, 종료 메시지는 종료 예산 안에서 다시 넣는다 (넘칠 때, 무엇을 잃을 것인가).

메시지 순서는 지켜지나?

한 스레드가 넣은 메시지끼리는 넣은 순서대로 handle에 온다. 여러 스레드 사이의 순서는 정해져 있지 않다.

channel은 받아들인 순서대로 내주는 FIFO다. test도 생산자별 순서와 개수만 잠그고, 전역 순서는 계약이 아니라고 적는다. input thread의 액션, delegate의 메시지, worker의 게시가 모두 같은 app inbox에 줄을 선다. 액션 하나가 돌려준 여러 메시지는 목록 순서대로 들어간다. 예외가 하나 있다. inbox가 찼을 때 따로 보관했다가 logic이 다시 넣는 파일 대화 상자 결과는, 그 뒤에 UI thread가 넣은 메시지보다 늦게 올 수 있다 (코드에서 확인한 동작) (channel 읽기 ② 소비자와 close).

메시지에 큰 데이터(파일 내용·그림)를 실어도 되나?

된다. app_message는 값을 shared_ptr<const T>로 한 번 담으므로, 복사하거나 channel을 지나도 내용은 복사되지 않는다.

대신 get<T>()는 const T*를 돌려준다. handle에서 값을 옮겨 가질 수는 없고, 상태에 두려면 복사한다. 복사가 비싼 값은 http_response처럼 무거운 부분을 공유 포인터로 두면 복사가 싸다 (타입을 지운 운반체 app_message).

빈 메시지는 무엇이고, 어디서 걸러지나?

기본 생성한 app_message {}다. empty()가 참이고, "보낼 것이 없다"를 값으로 나타낸다.

element 액션과 delegate 훅이 돌려준 빈 메시지는 게시하지 않는다. 시작 메시지(initial_messages)의 빈 것도 건너뛴다. post_app_message는 거르지 않으므로, 직접 넣은 빈 메시지는 handle에 그대로 닿는다 (코드에서 확인한 동작) (타입을 지운 운반체 app_message).

창 최소화·클립보드 복사·파일 대화 상자도 app_message로 보내나?

아니다. 액션이 input_action의 다른 갈래(ui_command, clipboard_copy_request 등)를 돌려주면 프레임워크가 UI thread로 보낸다.

창의 모양·클립보드·화면 남기기는 앱 상태가 아니라서 logic을 거치지 않는다. 앱이 정한 UI thread 일은 app_ui_command로 돌려주면 delegate의 execute_app_ui_command가 받는다. 라이브러리가 여는 파일 대화 상자는 앱 상태라 요청을 frame의 ui_frame::file_dialog에 싣고, 결과는 메시지로 handle에 온다. 앱이 자기 UI handler에서 직접 여는 대화 상자라면 app_ui_command 길을 쓴다 (input_action, 파일 열기·여러 파일·저장·폴더).

logic thread나 worker에서 창을 닫거나 클립보드에 넣으려면?

app_host의 post_ui_command·post_clipboard_request를 부른다. 어느 스레드에서 불러도 된다.

기다리던 작업이 끝난 뒤 앱을 끝내려면 ui_command::application_exit(닫힘 훅을 거치지 않는다), 사용자가 닫기를 누른 것과 같게 하려면 ui_command::window_close다. 진동은 perform_haptic이다. 플랫폼이 그 길을 꽂지 않았으면 아무 일도 없다 (닫힘과 수명 주기).

액션 람다에서 앱 상태를 캡처해도 되나?

안 된다. 액션은 input thread(일부 경로는 UI thread)에서 실행되고, 앱 상태는 logic thread의 것이다.

필요한 값은 frame을 지을 때 intent에 값으로 담는다. make_message_action이 그렇게 캡처한다. 누른 자리나 수식 키가 필요하면 ui_action_context를 받는 lambda를 직접 쓴다. payload가 const여도 그 안의 외부 포인터나 mutable 캡처까지 지켜 주지는 않는다 (input_action).

버튼 하나로 메시지 둘을 보내려면?

액션은 std::vector<input_action>을 돌려주므로, lambda에서 여럿을 담아 돌려준다.

make_app_action으로 싼 메시지 둘을 담아도 되고, 메시지와 ui_command를 섞어도 된다. input thread는 목록 순서대로 각 갈래를 제 목적지로 보낸다 (코드에서 확인한 동작) (input_action).

get<T>()가 늘 nullptr다.

담을 때의 타입과 정확히 같은 타입으로 묻는지 본다. 비교는 typeid가 같은지뿐이라, 기반 클래스로 물어도 nullptr다.

생성자는 받은 값의 타입을 그대로 추론하므로 생각과 다른 타입이 담기기 쉽다. 문자열 리터럴을 담으면 std::u8string이 아니라 포인터 타입이 담긴다 (코드에서 확인한 동작). 빈 메시지도 늘 nullptr다. 담은 값과 묻는 타입의 조합은 판정기에서 바꿔 볼 수 있다.

messaging::channel을 내 일감 큐로 써도 되나?

생산자 여럿·소비자 하나일 때만 된다. 두 스레드가 꺼내면 debug 빌드가 assert한다.

공개된 header-only 부품이고, 네임스페이스는 luil이 아니라 messaging이다. post는 막히지 않고, 넘치면 고른 정책대로 새 것을 거절하거나 맨 앞을 버린다. 여러 worker가 한 큐에서 나눠 꺼내는 pool에는 맞지 않는다. logic thread는 app inbox와 next_tick에만 깨어나므로, 그런 큐를 logic에서 읽으려면 깨울 메시지를 따로 보낸다 (코드에서 확인한 동작) (channel 읽기 ② 소비자와 close, lock-free가 아닌 이유).

사례로 확인하기

입력과 상태를 하나 정해 두고, luil이 그때 무엇을 하는지 코드에서 따라간 결과다. 펼치면 결과와 까닭이 나온다.

용량 2인 drop_oldest 채널에 1, 2, 3을 차례로 post했다. 첫 try_receive가 받는 봉투는?

payload 2, sequence 1

셋째 post가 맨 앞(1, 번호 0)을 버린다. 남은 첫 봉투는 payload 2이고 번호는 1이다. 번호 0의 구멍이 유실을 알린다.

UI가 잠든 동안 logic이 frame을 다섯 번 게시했다. 신호 함수는 모두 성공했다. 신호는 몇 번 나가는가?

1번

첫 게시가 pending_을 세우고 신호한다. UI가 take_newer로 가져가기 전까지 나머지 게시는 신호하지 않는다.

latest_slot이 실패한 신호의 pending_을 되돌리는 이유는?

되돌리지 않으면 다음 게시들이 신호 없이 잠겨 화면이 영영 갱신되지 않을 수 있어서

실패가 "이미 신호했음"으로 남으면 소비자는 깨지 않고, 다음 게시도 병합되어 신호하지 않는다. 일시적인 실패 한 번이 영구적인 미갱신으로 굳는다.

app_message { derived_intent {} }에 get<base_intent>()를 부르면? (derived_intent는 base_intent를 상속한다)

nullptr를 돌려준다

get은 저장된 type_info와 묻는 타입을 정확히 비교한다. 계층 변환은 지원하지 않으므로 nullptr다.
