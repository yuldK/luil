그리기와 렌더러

두 불변 입력을 표면의 크기·DPI·테마와 합쳐 frame_state를 만들고, 하나뿐인 draw_frame이 Skia 캔버스에 그린다. 화면에 내는 길은 플랫폼마다 다르고, GPU가 실패하면 CPU로 물러선다.

이 문서를 읽으면

  1. frame_state가 모으는 것과 draw_frame의 층 순서를 말할 수 있다.
  2. renderer_host의 네 모드와 물러섬 상태 전이를 예측할 수 있다.
  3. "옛 렌더러를 먼저 놓는다"가 화면의 정확성인 이유를 설명한다.
  4. 시간에 따른 다시 그리기를 예고와 timer 하나로 묶는 식을 계산할 수 있다.
  5. 색을 역할로만 말하는 팔레트와 raster test의 의도를 안다.

그리는 함수는 하나, 내는 길은 여럿

모든 백엔드가 같은 draw_frame을 부른다. 다른 것은 Skia 표면을 어디에 만들고, 그린 것을 어떻게 화면에 내는가다.

UI thread는 logic이 게시한 ui_frame과 input의 interaction_snapshot을 받아, 표면의 물리 크기·DPI 배율·창 상태·테마·accent·고대비 색과 합친다. 그 결과가 frame_state, 곧 렌더러가 한 frame을 그리는 데 필요한 전부다. 화면 남기기(capture)도 스왑체인을 되읽지 않고 같은 frame_state를 raster 표면에 한 번 더 그린다. 그래서 화면과 캡처가 갈리지 않는다.

층 순서와 웹뷰 구멍

배경을 칠하고, tree를 그리고, tree가 초점 테·끌기 표시·tooltip을 얹고, 마지막에 웹뷰 자리를 알파 0으로 비운다. 비워야 그 아래 합성된 웹 페이지가 드러난다.

    층을 하나씩 꺼 보라. 구멍은 다 그린 뒤에 비운다 — 도중에 비우면 뒤에 그려지는 것이 그 자리를 도로 덮는다. 그 대가로 구멍 자리에 그린 것은 모두 지워지므로, tooltip처럼 웹뷰 위를 덮어야 하는 frame에서는 그 사각형을 아예 구멍 목록에서 뺀다. 판정은 "전부 아니면 전무"다.
    1. 원점을 옮기기 전에 표면 전체를 칠한다. 배경 효과(mica·acrylic)가 선 표면은 backdrop_background, 투명 표면은 투명이다.
    2. 원점만큼 옮긴 뒤 tree를 그리고 검사기를 얹는다. tree 안에서는 root와 자식, 초점 테, 끌기 표시, tooltip 순서다(불변 UI tree).
    3. Android처럼 표면이 하나인 플랫폼에서는 popup이 같은 캔버스 위의 층이다. 뒤의 것이 위다.
    4. 사각형마다 kClear로 칠해 알파 0으로 비운다. 알파 0이 합성에서 뜻을 가지려면 스왑체인이 premultiplied여야 하고, 아니면 비운 자리가 불투명한 검정이 된다.

    렌더러 물러섬: renderer_host

    플랫폼은 GPU·CPU 렌더러를 만드는 함수만 넘긴다. 무엇을 언제 바꿀지는 플랫폼을 모르는 정책 객체 하나가 정한다.

    renderer_mode동작
    automatic (기본)GPU를 먼저 세운다. 생성·크기 변경·그리기 중 하나라도 실패하면 CPU를 만들고, 옛 GPU 렌더러를 놓고, 같은 frame을 CPU로 다시 그린다. 그 표면은 다시 GPU를 시도하지 않는다.
    gpu이 플랫폼의 GPU 경로(Windows Direct3D, Android Vulkan, Apple Metal). 실패를 호출자에게 돌려준다.
    direct3dWindows의 GPU 경로. gpu와 같다. 앱이 플랫폼마다 다른 값을 쓰지 않도록 gpu를 나중에 더했다.
    cpuCPU 렌더러만 만든다.
    모드
    플랫폼
    고장 주입
    아직 없음used_fallback = falseframe 0
    해 볼 것: automatic + "1 frame 뒤 손실"로 만들고 두 번 그리기 — 둘째 frame에서 CPU 생성 → GPU 소멸 → CPU로 같은 frame을 그린다. 그 frame은 성공(true)이지만 error에는 GPU 실패 글이 남는다. gpu 모드로 같은 일을 하면 오류를 돌려줄 뿐 물러서지 않는다.

    물러섬 코드 읽기

    CPU를 먼저 만들고, 옛 렌더러를 놓고, 같은 frame을 다시 그린다. 이 순서 하나하나가 화면의 정확성이다.

    1. frame_state를 값으로 받아 backend와 used_fallback을 채운다. 손실 주입이 올 차례면 실제 렌더를 부르지 않고 실패로 친다. 실제 장치 손실 경로를 test와 기기에서 재현하려는 장치다.
    2. automatic이 아니거나 이미 CPU면 그대로 false다. 이미 CPU인데 실패했다면 더 물러설 곳이 없다.
    3. CPU로 바꾸는 데 성공하면 같은 state를 used_fallback=true로 다시 그린다. 사용자는 한 frame도 잃지 않는다. 다만 error에는 GPU 실패 글이 남아 있어 플랫폼이 기록한다.
    4. CPU를 만들지 못하면 GPU 렌더러를 그대로 둔 채 실패를 돌려준다. 만들 수 있는지 확인하기 전에 GPU를 놓으면 아무것도 없는 상태가 된다.
    5. Win32의 CPU 렌더러는 GDI로 그리는데, 창이 합성 대상으로 남아 있으면 그 픽셀은 visual tree 아래에 깔려 화면에 닿지 못한다. Direct3D 렌더러의 소멸자가 IDCompositionTarget을 놓아야 GDI가 드러난다. Android도 창이 생산자를 하나만 받아 같은 순서다. 대입 한 줄로도 같은 순서지만, 지우지 못하게 한 줄을 따로 세웠다.
    
    이 순서가 틀리면오류 하나 없이 화면이 마지막 frame에 얼어붙는다. Win32 설정이 생성 실패와 실행 중 손실을 따로 주입할 수 있게 둔 것도 그 경로를 재현하기 위해서다. Android는 물러서는 단위가 창이 아니라 Activity 전체다. 창이 홈·화면 끄기마다 다시 생기므로, 창 단위로 두면 손실 뒤에도 매번 GPU를 다시 시도하게 된다.

    Direct3D의 한 frame

    back buffer의 fence를 기다리고, 그리고, flush·submit, Present, Signal. GPU와 CPU가 같은 버퍼를 동시에 쓰지 않게 하는 순서다.

    1. 알파 0 배경에 채널별 커버리지가 섞이면 경계에 잘못된 색이 생긴다. 구멍 유무가 바뀔 때만 같은 back buffer를 다른 픽셀 배치로 다시 감싼다.
    2. 버퍼 두 장(DXGI_SWAP_EFFECT_FLIP_DISCARD) 중 이번 것의 fence를 기다린다. 대기에는 상한(10초, 500ms 조각)이 있다. 무기한 대기는 CPU 물러섬을 포함한 모든 복구 코드보다 앞에 선 관문이 되기 때문이다.
    3. UI 글꼴을 묻고(cache됨) 다른 백엔드와 같은 draw_frame을 부른 뒤 Skia가 쌓은 명령을 GPU로 보낸다.
    4. 수직 동기 1로 제시한다. 동영상처럼 최신 장이 중요한 frame은 기다리지 않는 제시를 쓰고 "아직 그리는 중"은 건너뛴다.
    5. 이 버퍼를 쓴 GPU 작업의 끝을 fence 값으로 남긴다. 다음에 같은 버퍼를 쓸 frame이 이 값을 기다린다.

    메모리는 모드가, 크기는 빌드가 정한다

    2026-09-29, RTX 4080에서 Release hello로 잰 값이다. Direct3D의 상주 메모리는 대부분 드라이버가 장치·큐·스왑체인에 잡는 몫이다.

    
    CPU 렌더러로 충분한 경우문서는 "CPU 렌더러는 FHD 이하에서 한 frame에 수 ms 안쪽이다. 4K에서 계속 움직이는 화면처럼 프레임 예산이 빠듯한 앱에만 Direct3D가 필요하다"고 적는다. 960×540 표면의 spinner 하나는 평균 렌더 0.68ms, 2880×1620은 3.44ms였다(Debug CPU 렌더러).

    언제 다시 그리나: 사건과 예고

    게시·크기·DPI·테마가 바뀌면 그린다. 시간이 흘러야 바뀌는 그림은 element가 예고한 시각을 모아 timer 하나로 깨운다. 예고가 없으면 timer도 없다.

    next_update의 답뜻예
    nullopt시간이 흘러도 그림이 그대로다버튼, 라벨, 목록
    미래 시각그 시각에 한 번 다시 그린다caret 깜빡임 530ms, tooltip 지연 500ms
    지금 이하계속 움직이는 중 — 짧은 주기로 다시 그린다(spinner는 16ms 미래를 예고한다)

    표면마다 예고를 골라 보라. 미래 예고에는 15ms 여유를 더하고(timer가 ms 단위로 잘려 와 "아직 아니다"를 피하려고), 지금 이하는 33ms로 잇는다. 그 tick까지 시각이 되는 표면이 함께 깨어난다. macOS·iOS의 연속 간격은 16ms다.
    1. timer는 밀리초 단위로 잘려 온다. 여유 없이 깨우면 element가 "아직 아니다"라며 같은 시각을 다시 예고해 timer가 한 번 더 돈다.
    2. 모든 표면의 예고 중 가장 이른 것을 찾는다. 아무도 예고하지 않았으면 걸 timer가 없다. 평소에는 사건이 있을 때만 그린다.
    3. 미래면 남은 시간 + 15ms, 지금 이하면 연속 주기(Win32 33ms)다. Win32 timer의 상한으로 자른다.
    4. 그 tick까지 시각이 되는 표면을 모두 깨운다. 가장 이른 것 하나만 깨우면 같은 tick의 다른 표면이 빠지고, 전부 깨우면 보조 창 하나의 spinner가 모든 창을 같은 주기로 다시 그리게 한다.

    색은 역할로만 말한다

    element는 구체 색을 받지 않는다. "기본 버튼", "고른 행"처럼 뜻을 고르면, 그리는 순간 팔레트가 그 뜻을 색으로 바꾼다. 테마를 바꾸면 화면 전체가 손대지 않고 따라온다.

    테마
    키 컬러
    파생 역할은 키 컬러 역할에 tone 알파를 바꿔 끼워 만든다(soft 0.25, selection 0.35, row selection 0.18, pressed 0.70). 채운 바탕 위 글자는 바탕의 상대 휘도가 0.179 이하면 흰색, 아니면 검정이다 — mint는 dark에서 검정, light에서 흰색이 된다. 고대비는 OS 시스템 색을 알파 없이 쓰고, 고른 행의 채움을 접어 왼쪽 표식만 남긴다(여기 값은 OS 색을 읽지 못할 때의 기본값).

    with_alpha는 알파를 곱하지 않고 바꿔 끼운다. ui_color는 0xAARRGGBB다. 그리기·DWM 창 테두리·웹뷰의 바닥색이 같은 frame_palette를 보므로, 어두운 화면에서 흰 웹뷰 판이 번쩍이지 않는다.

    그림을 테스트하는 법: raster test

    빠진 draw 호출, 잘못된 clip, 조기 return, 채움과 테두리의 혼동. 순수 geometry test가 잡지 못하는 결함을 창과 GPU 없이 잡는다.

    어떻게 그리나

    • 색 공간 없는 SkBitmap에 그린다 — 변환을 한 번 지나면 팔레트 값과 정확히 같지 않다.
    • 기본 배율 2 — 배율 1의 1px 선은 두 픽셀에 나뉘어 어떤 팔레트 색과도 같지 않다. 배율 2면 선 가운데에 완전히 덮인 픽셀이 생긴다.
    • 글꼴을 싣지 않고 시각을 손으로 준다 — OS 글꼴과 시계에서 자유롭다.

    무엇을 단언하나

    • 채움과 테두리는 가운데 픽셀로 가른다.
    • 같은 색끼리는 덮은 넓이를 센다(count_color).
    • clipping은 안과 밖을 함께 본다.
    • 전체 이미지 golden file은 쓰지 않는다 — 관련 없는 antialiasing·팔레트·글꼴 변경에도 깨진다.

    예를 들어 기본 버튼 test는 가운데 픽셀이 palette.accent이고 accent 픽셀이 상자 넓이의 절반을 넘는지, 초점 테의 획 중심이 몸 밖 2×배율 자리에 있고 몸 안쪽에는 accent가 없는지, focus_visible=false면 테 영역의 accent가 0인지 본다. [raster] 태그 test만 50개다. 렌더러 정책과 timer 계획도 가짜 렌더러와 순수 함수로 창 없이 test한다(시험과 빌드).

    요약

    1. UI thread는 frame·interaction·표면 상태를 frame_state로 모으고, 모든 백엔드가 같은 draw_frame을 부른다.
    2. 층 순서는 배경 → tree(→ 초점 테 → 끌기 → tooltip) → popup 층 → 테두리 → 웹뷰 구멍이다. 덮이는 frame은 구멍을 뺀다.
    3. renderer_host는 automatic에서 GPU 실패 시 CPU를 먼저 만들고, 옛 렌더러를 놓고, 같은 frame을 다시 그린다. 그 뒤로 그 표면은 GPU를 다시 시도하지 않는다.
    4. 메모리는 렌더러 모드가(161MB 대 7MB), 실행 파일 크기와 DLL은 빌드 옵션이 정한다.
    5. 다시 그리기는 사건 때만, 시간 그림은 예고를 모은 timer 하나로 한다. 미래 + 15ms, 지금 이하 33ms(Apple 16ms).
    6. 색은 역할로만 말하고, 파생 역할은 tone 알파로 만든다. 그림은 배율 2의 raster test로 픽셀까지 확인한다.

    자주 묻는 질문

    automatic 모드에서 둘째 frame을 그리다 GPU 장치를 잃었다. 그 뒤 일어나는 일의 순서는?

    CPU 생성 → GPU 소멸 → CPU로 같은 frame (성공, error에는 GPU 실패 글)

    test가 고정한 순서는 "gpu created, gpu rendered, cpu created, gpu destroyed, cpu rendered after fallback"이다. CPU를 만들 수 있는지 먼저 확인하고, 옛 렌더러를 놓은 뒤 같은 frame을 그린다.

    주 창이 500ms 뒤를, 보조 창이 "지금"을 예고했다. Win32 timer의 지연과 깨우는 표면은?

    33ms, 보조 창만

    가장 이른 예고가 지금 이하라 연속 주기 33ms다. 그 tick(지금 + 33ms)까지 시각이 되는 것은 보조 창뿐이다. 주 창이 +20ms였다면 둘 다 깨어났다.

    도중에 비우면 뒤에 그려지는 것이 그 자리를 도로 덮기 때문에

    대신 끝에 비우면 그 자리에 그린 것이 모두 지워진다. 그래서 무언가가 웹뷰 위를 덮어야 하는 frame에서는 그 사각형을 구멍 목록에서 아예 뺀다.

    기본 빌드를 cpu 모드로 돌리면 Private 메모리는 대략 얼마인가?

    약 7MB — CPU 전용 빌드와 같다

    메모리 차이는 렌더러 모드에서 나고 빌드 옵션에서 나지 않는다. 빌드 옵션이 줄이는 것은 실행 파일 크기(8.07 → 5.17MB)와 올라오는 DLL이다.
