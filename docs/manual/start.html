설치와 첫 앱

필요한 것은 플랫폼의 도구사슬, CMake 4.2.0 이상, 그리고 대상마다 하나인 Skia 패키지다. 내 프로젝트에는 luil 소스 트리를 add_subdirectory로 넣거나(네 플랫폼), Windows라면 설치 패키지를 find_package로 찾는다. 어느 쪽이든 luil::luil 하나를 링크하고, 앱은 hello처럼 상태를 쥔 driver 하나와 진입 함수 하나로 시작한다.

luil 개요

이 문서를 읽으면

  1. 플랫폼마다 설치할 것과 고정된 의존성의 판번을 안다.
  2. Skia 패키지를 받고 preset으로 저장소와 hello를 빌드한다.
  3. 내 CMake 프로젝트에 luil을 소스 트리나 설치 패키지로 붙이고, 실행 파일에 필요한 리소스를 싣는다.
  4. hello를 본떠 상태·메시지·driver·delegate·진입점을 갖춘 첫 앱을 쓴다.
  5. configure·링크·시작 단계의 오류를 메시지로 찾아 고친다.

준비물

플랫폼의 도구사슬과 CMake 4.2.0 이상이 있으면 된다. 의존성은 판번과 체크섬이 저장소에 고정되어 있고, configure는 아무것도 내려받지 않는다.

Skia 받기

Skia는 소스로 짓지 않는다. 대상마다 하나인 핀 파일이 패키지(헤더·정적 라이브러리·고지)를 고르고, 스크립트가 받아 SHA-256을 확인한 뒤 정해진 자리에 푼다.

  1. 대상마다 핀 파일과 설치 자리가 따로다. win-x64만 접미사 없는 옛 경로를 쓴다. 자리가 따로라 한 저장소에서 두 대상을 함께 지을 수 있다.
  2. 구성을 주지 않으면 Release만 받는다. Visual Studio 같은 다중 구성 generator는 CMAKE_CONFIGURATION_TYPES의 구성을 모두 검사하므로 Debug도 있어야 한다. 문서의 명령이 늘 -Configuration Debug,Release인 까닭이다.
  3. 핀의 target과 고른 대상이 다르면 받거나 지우기 전에 멈춘다.
  4. 받아 둔 zip이 -ArchiveDirectory에 있고 해시가 맞으면 네트워크를 쓰지 않는다. -Offline은 받으러 가지 않고 실패한다. 같은 패키지가 이미 설치되어 있으면 다시 풀지 않고, -Force로 다시 푼다. -Symbols는 win-x64의 심볼 자산이다.

소비자에게 clang은 필요 없다Windows 패키지의 Skia는 clang-cl로 지었고, luil과 앱은 그대로 MSVC로 짓는다. configure는 패키지 옆의 args.gn과 toolchain.json을 읽어 컴파일러, ABI(is_trivial_abi = false), CRT(Debug /MTd, 그 밖 /MT)를 확인할 뿐 컴파일러를 찾지도 부르지도 않는다.

직접 빌드한 Skia를 쓸 때

캐시 변수 셋으로 자리를 준다. LUIL_SKIA_ROOT는 헤더와 고지가 있는 루트, LUIL_SKIA_BUILD_DEBUG·LUIL_SKIA_BUILD_RELEASE는 구성별 라이브러리와 args.gn이 있는 디렉터리다. 검사는 패키지와 같다 — 요구 라이브러리 전부, luil이 요구하는 GN 인자, is_trivial_abi = false, 구성에 맞는 CRT, clang-cl로 컴파일했다는 기록. 조건 다섯은 docs/skia-build.md의 "직접 빌드한 Skia 사용"에 있다.

저장소 빌드

저장소 루트에서 preset으로 configure하고 짓는다. 내 프로젝트보다 먼저 hello가 뜨는지 본다 — 도구사슬의 문제와 내 프로젝트의 문제를 가르는 가장 빠른 길이다.

Visual Studio 2022라면 vs2026 자리에 vs2022를 쓴다(vs2022-examples, vs2022-examples-debug). 웹뷰를 쓰지 않으면 fetch_webview2.ps1을 건너뛰고 LUIL_ENABLE_WEBVIEW=OFF로 구성한다. GPU가 필요 없으면 LUIL_ENABLE_DIRECT3D=OFF다 — 웹뷰도 기본으로 꺼진다.

core test는 adb로 연결한 기기에서 돈다. 예제의 네이티브 절반은 luil의 CMake가 공유 라이브러리로 짓고, examples/android의 Gradle이 APK로 싼다. NDK 경로와 Ninja 위치는 사람마다 달라 저장소의 preset에 넣지 않았다. 자주 쓰면 Git에서 빠지는 CMakeUserPresets.json에 적는다.

예제는 앱 번들이다. 로그를 터미널에서 보려면 번들 안의 실행 파일 build/macos-arm64/Debug/luil_demo.app/Contents/MacOS/luil_demo를 바로 띄운다. 창이 앞에 서는 test가 있어 ctest는 로그인한 화면이 있는 기계에서 돈다.

기기는 ios-arm64 preset이다. 서명 신원(LUIL_IOS_CODE_SIGN_IDENTITY)과 provisioning profile(LUIL_IOS_PROVISIONING_PROFILE)을 주지 않으면 서명하지 않은 번들이라 기기에 설치되지 않는다. iOS에는 test preset이 없다.

preset이 정하는 것

  1. 명령 줄의 -A x64와 같다. luil의 configure는 generator 플랫폼이 x64인지 본다. preset 없이 내 프로젝트를 configure할 때도 -A x64를 준다.
  2. build/<preset 이름>이다. 예제 실행 파일의 자리(build\vs2026-examples\examples\Debug\luil_hello.exe)가 여기서 나온다.
  3. Windows preset은 Windows 호스트에서만 보인다. macOS·iOS preset은 macOS 호스트에서만 보인다.
  4. Windows SDK 판을 10.0.22621.0으로 준다(CMAKE_SYSTEM_VERSION). luil은 고른 SDK가 그보다 낮으면 멈춘다. 시험과 분석은 끈 채로 시작하고, 이것을 이어받는 preset이 하나씩 켠다.

내 프로젝트에 붙이는 두 길

링크하는 이름은 어느 길이든 luil::luil 하나다. 소스 트리 길은 네 플랫폼에서, 설치 패키지 길은 Windows에서만 된다.

소스 트리 — add_subdirectory

  • luil 저장소를 내 프로젝트 안(submodule이나 사본)에 둔다.
  • Skia·nlohmann은 그 luil 안의 third_party에 준비한다.
  • Windows 실행 파일은 부모 scope에 변수 셋을 정하고 .rc 조각을 짓는다.
  • Android·macOS·iOS도 이 길이다.

소스 트리로 넣기

설치 패키지 — find_package

  • luil을 한 번 지어 설치하고, 앱은 설치 자리를 CMAKE_PREFIX_PATH로 준다.
  • 설치본의 config가 빌드 트리와 같은 Skia 검사를 다시 한다.
  • 설치본이 고지·.rc 함수와 원본 파일을 함께 싣는다.
  • Windows만 — 다른 플랫폼은 설치 규칙을 끈다.

소스 트리로 넣기

luil 저장소를 내 프로젝트 안에 두고 add_subdirectory한다. Windows 실행 파일에는 luil이 찾는 리소스 조각을 더한다.

1. luil 안의 의존성을 준비한다

받는 스크립트는 자기가 든 저장소의 루트를 기준으로 푼다(fetch_skia.ps1:56). 그래서 Skia는 third_party/luil/third_party/skia-prep에 놓이고, 그것이 luil의 LUIL_SKIA_ROOT 기본값이다(CMakeLists.txt:127). 다른 자리에 두었다면 LUIL_SKIA_ROOT를 준다. 웹뷰를 쓰지 않으면 셋째 줄을 빼고 LUIL_ENABLE_WEBVIEW를 끈다.

2. CMakeLists.txt

  • CMake 4.2. luil의 CMakeLists.txt 첫 줄이 cmake_minimum_required(VERSION 4.2.0 FATAL_ERROR)다. 부모가 더 낮은 판을 적어도 4.2 아래의 CMake는 거기서 멈춘다.
  • 정적 CRT를 먼저 정한다. luil은 최상위 빌드일 때만 정적 CRT를 강제하고, 하위로 들어오면 앱의 설정을 그대로 따른다(CMakeLists.txt:5). luil의 대상이 만들어지는 add_subdirectory보다 앞이어야 그 대상들도 같은 CRT를 받는다. 이 줄은 test 소비자의 2행과 같다.
  • RC 언어. .rc 조각은 앱 대상의 소스로 컴파일된다. 부모 프로젝트가 RC를 쓸 수 있어야 한다(소비자 계약). test 소비자도 LANGUAGES CXX RC다.
  • WIN32. hello의 진입점은 wWinMain이고, 예제 대상도 add_executable(luil_hello WIN32 …)로 짓는다.
  1. 이 줄이 luil의 configure를 돌린다. 플랫폼·generator·Skia 검사가 여기서 일어나고, 실패하면 앱의 configure도 멈춘다.
  2. 고지·.rc 함수가 이 변수를 읽는데, luil 안에서 set()한 값은 부모 scope에 보이지 않는다(generate_notices.cmake:262). 빠뜨리면 경로 앞부분이 비어 라이선스 파일을 찾지 못하고 멈춘다.
  3. 제3자 고지 파일을 만들고, Codicons 글꼴·라이선스 둘·고지를 리소스 101~104로 싣는 .rc 조각을 짓는다. 앱의 아이콘·manifest·버전 리소스는 따로 더하고, ID 101~104는 비워 둔다.
  4. 조각을 실행 파일 소스에 넣는다. 빠뜨리면 빌드는 되고 실행할 때 시작 실패 상자가 뜬다(자산과 글꼴).
  5. 링크는 luil::luil이다. 플랫폼을 모르는 층 luil_core는 PUBLIC으로 따라오고, Skia·nlohmann·WebView2도 빌드 트리에서 함께 이어진다.

3. configure하고 짓는다

generator는 Visual Studio 17 2022나 Visual Studio 18 2026만, 플랫폼은 x64만 받는다. luil의 configure가 검사하므로 Windows에서 이 길로는 Ninja를 쓸 수 없다.

옵션을 정하는 자리

luil의 옵션과 카탈로그 경로는 캐시 변수다. configure 명령의 -D로 주거나 add_subdirectory 앞에서 정한다. luil의 option()은 같은 이름의 일반 변수를 따르므로(CMP0077 — luil 자신이 다른 플랫폼에서 설치·Direct3D·웹뷰를 이렇게 끈다) set(LUIL_ENABLE_WEBVIEW OFF)도 된다.

luil을 한 번 지어 설치하고, 앱은 그 자리를 CMAKE_PREFIX_PATH로 주어 find_package한다. 설치·이동·빌드·실행을 test가 잠근 길이다(소비자 통합 계약을 test로).

1. 설치한다

설치본이 읽는 변수

설치할 때의 Skia 경로는 같은 기계에서 쓸 때의 기본값일 뿐이다. 다른 기계에서는 LUIL_SKIA_ROOT만 주면 구성별 자리가 <root>/out/skia-ui-debug·-release로 따라온다. WebView2 SDK는 LUIL_WEBVIEW2_ROOT다. config는 설치한 라이브러리의 선택을 LUIL_ENABLE_DIRECT3D·LUIL_ENABLE_WEBVIEW·LUIL_ENABLE_SVG 같은 변수로 알린다.

첫 앱 ① 파일과 꽂는 자리

hello를 그대로 본뜬다. 앱 쪽 절반(상태·메시지·driver·delegate)은 두 파일이고 네 플랫폼이 같다. 진입 파일만 플랫폼마다 다르다. 설계의 뜻은 개요의 hello 읽기가 줄마다 설명하므로, 여기서는 내 앱에 무엇을 써야 하는지만 본다.

  1. 예제 실행 파일들이 함께 쓰는 조각 하나를 짓는다. 내 프로젝트의 고지·.rc 줄과 같은 일이다. 저장소 안이라 변수 셋이 이미 보인다.
  2. luil_add_source_filter는 저장소가 IDE 필터를 짜는 도구다. 앱은 파일을 그냥 나열하면 된다.
  3. .rc 조각과 세 파일로 짓는다. wWinMain이라 WIN32다.
  4. #include "hello/hello_app.h"가 풀리도록 examples 폴더를 준다.
  5. luil_options는 저장소의 경고 규율이다. 앱은 luil::luil만 링크한다.

꽂는 자리의 원문: logic_driver

  1. 모든 함수는 logic thread에서 불린다. cancel·make_close_message·shutdown_completed는 UI thread에서도 불려 스레드 안전해야 한다. 콜백이 던지면 logic thread가 삼키고 멈춘다(app_host::faulted()) — 오류는 메시지나 frame의 상태 값으로 나른다(스레드 모델).
  2. driver는 한 객체로 산다. 진입 함수는 그 주소를 빌려 쓸 뿐 소유하지 않는다.
  3. logic thread가 선 직후 한 번 불린다. 처음 상태를 읽는 일을 여기서 제출한다.
  4. handle과 make_frame은 순수 가상이다. 메시지 1건을 처리하고, 처리 뒤 게시할 frame을 불변 값으로 만든다.
  5. make_close_message와 shutdown_completed도 순수 가상이다. 창이 닫히면 라이브러리가 종료 메시지를 inbox에 넣고, shutdown_completed가 참이 되기를 기다린다(종료 절차와 시간 예산).
  6. stop_workers는 worker를 둔 앱이, next_tick·tick은 시간이 흘러야 바뀌는 상태(토스트 만료 등)를 가진 앱이 쓴다. hello는 쓰지 않는다.

첫 앱 ② 상태·메시지·driver·delegate

상태는 driver의 멤버이고, 상태를 바꾸는 길은 메시지 하나뿐이다. 앱 헤더 하나에 element 종류·메시지·두 클래스를 모두 선언한다.

  1. luil/luil.h 하나다. 이 헤더를 네 플랫폼의 진입 파일이 같이 들인다.
  2. 상태는 driver의 private 멤버다. hello의 상태는 창 크기(metrics_), 누른 횟수(clicks_), 종료를 처리했는지(closed_)다. closed_만 std::atomic이다 — UI thread도 읽는다.
  3. 앱 메시지는 기반 클래스 없는 평범한 구조체다. 버튼 누름, 창 크기, 종료가 하나씩이다. app_message가 타입을 지운 채 스레드를 건너 나르고, 받는 쪽이 get으로 꺼낸다(스레드 경계 메시징).
  4. 앱의 element 종류는 application_element_kind(index)로 앱 대역에서 정한다. 낮은 대역은 라이브러리 몫이다.
  5. 순수 가상 넷만 재정의한다. hello는 옛 이름 luil::win32::logic_driver와 luil::win32::ui_frame을 쓴다 — 같은 형식의 별칭이고, 새 코드는 luil::logic_driver·luil::ui_frame이다(③의 끝).
  6. 창 크기·배율을 메시지로 바꾸는 훅 하나만 재정의한다. 나머지 훅의 기본은 "아무 일도 하지 않음"이다.

handle과 make_frame, 종료, 크기 메시지

  1. 메시지 종류마다 한 갈래다. 상태를 바꾸는 곳은 여기뿐이고, 모르는 메시지는 그냥 지나간다. 기능을 더할 때는 intent 하나와 갈래 하나를 더한다.
  2. 저장할 것이 있으면 여기서 제출하고 closed_를 세운다.
  3. 크기 메시지가 오기 전에도 불린다. 크기 0을 그대로 쓰지 않고 기본값을 둔다. 길이는 논리 픽셀, 배치 좌표는 물리 픽셀이다(두 가지 픽셀).
  4. root를 ui_tree로 감싸 frame에 싣는다. 생략한 가운데(58–108행)의 tree 짓기는 개요의 hello 읽기 ②가 줄마다 읽는다.
  5. UI thread에서도 불리므로 closed_는 atomic이다. 참이 되지 않으면 창을 닫을 때마다 종료가 시간 예산(3초)을 다 쓰고 저장을 포기한다.
  6. UI thread에서 불린다. 받은 크기·배율을 메시지로 돌려줄 뿐 상태를 만지지 않는다. delegate를 꽂지 않으면 이 메시지가 아예 없다.

delegate가 받는 것

훅은 모두 UI thread에서 불리고, 기본은 "아무 일도 하지 않음"이다. 메시지를 돌려주는 훅에서 빈 메시지는 게시되지 않는다. 플랫폼을 가리지 않는 훅은 app_delegate에, 데스크톱 창만 갖는 훅은 그것을 넓힌 win32::window_delegate에 있다.

첫 앱 ③ 진입점과 그다음

진입 함수는 창을 설정하고 세 조각을 꽂은 뒤 메시지 루프에 들어간다. 텍스트 입력이 생기면 정책을 더 꽂는다.

  1. 앱 헤더(그 안의 luil/luil.h)와, wWinMain의 형식을 위한 <windows.h>다.
  2. DPI 인지와 COM STA를 켠다. COM이 실패해도 앱은 뜨지만 파일 대화 상자·TSF·OS 끌어 놓기가 조용히 꺼지고, 접근성은 이 STA를 전제로 한다. 까닭은 개요의 hello 읽기 ①에 있다.
  3. 길이는 논리 픽셀이다. caption의 값은 tree에 그리는 caption_element의 설정과 같아야 한다 — 하나는 창의 비클라이언트 판정에, 하나는 그리기에 쓰여 버튼 자리가 맞물린다(hello_app.cpp의 make_caption 주석).
  4. driver는 꼭 꽂는다 — 비면 host 없이 caption만 그린다. delegate가 비면 크기 메시지가 없다. 텍스트 입력이 없으니 정책은 비워 둔다. 셋 다 이 함수가 돌아올 때까지 살아 있어야 한다.
  5. 창이 닫히고 종료 절차가 끝나면 돌아온다. 반환값이 프로세스 종료 코드이고, 시작에 실패하면 메시지 상자를 띄운 뒤 1이다.

텍스트 입력이 생기면: 정책

텍스트 칸·휠·단축키가 생기면 interaction_policy를 구현해 environment.policy에 꽂는다. 정책은 input thread에서 불리고, 어떤 element 종류가 텍스트 칸인지(text_target_of)와 편집 요청을 앱 메시지로 바꾸는 일(make_text_edit_action)을 맡는다. widgets 예제의 정책이 텍스트 대상·편집·휠·초점 이동을 모두 보인다(입력과 초점).

옛 이름과 새 이름

hello가 쓰는 luil::win32::logic_driver·luil::win32::ui_frame은 새 형식 그 자체를 가리키는 별칭이라 고치지 않아도 빌드된다. 새 코드는 luil/app/app_host.h의 luil::logic_driver·luil::ui_frame을 쓴다 — examples/selected_nodes/main.cpp와 examples/tool_window/main.cpp가 그렇게 쓴 예제다. win32::window_delegate는 별칭이 아니라 Win32 delegate 그 자체이고, 모바일만 겨냥하면 luil::app_delegate를 넓힌다(examples/mobile_demo).

자산과 글꼴

Windows 실행 파일에는 luil이 찾는 리소스 넷이 들어 있어야 한다. 다른 플랫폼은 Codicons 글꼴이 라이브러리 안에 있다. 생성 헤더는 빌드가 만들고, 앱 글꼴·그림과 고지 화면은 앱의 몫이다.

Codicons 쓰기

설치본을 쓰는 test 소비자의 한 대목이다. 상수 헤더는 우산 헤더에 들지 않아 따로 들인다. glyph_config::typeface가 비어 있으면 내장 Codicons로 그리므로, 보통의 앱은 load_codicon_typeface를 부를 일이 없다.

앱 글꼴을 함께 배포할 때

저장소의 예제에는 앱 글꼴을 등록하는 코드가 없어 아래에 썼다. 글꼴 이름과 파일 이름은 예시다. 기본 UI 글꼴은 앱이 시작하기 전에 정한다 — 이미 만든 화면과 글꼴 객체는 저절로 바뀌지 않는다(luil/text/fonts.h).

글꼴 디렉터리는 앱이 정한다. 데모는 실행 파일의 디렉터리를 쓰고, macOS 번들 안에서는 Contents/Resources를 답한다.

함정

오류 없이 조용히 틀리거나, 문서만 보고는 놓치기 쉬운 자리들이다. 문서와 코드가 다른 곳은 코드를 따랐고 표시를 달았다.

  1. CRT는 앱이 정한다. 소스 트리로 넣으면 luil은 앱의 CRT 설정을 바꾸지 않는다. add_subdirectory보다 먼저 /MT·/MTd를 정하지 않으면 링크가 원인을 말하지 않는 /FAILIFMISMATCH로 멈춘다.
  2. 변수 셋은 부모 scope에 정한다. LUIL_SOURCE_DIRECTORY·LUIL_ASSET_DIRECTORY·LUIL_NLOHMANN_JSON_ROOT는 luil 안에서 정해져도 앱의 CMakeLists.txt에는 보이지 않는다. 고지·.rc 함수가 그 값을 읽는다.
  3. .rc 조각을 빠뜨려도 빌드는 된다. 실행하는 순간 시작 실패 상자가 뜨고 1로 끝난다. 리소스 ID 101~104는 luil의 몫이라 앱이 쓰지 않는다.
  4. Skia 스크립트의 기본은 Release 하나다. Visual Studio는 Debug도 검사하므로 -Configuration Debug,Release로 받는다.
  5. 소스 트리 길은 Visual Studio generator와 x64만 받는다. Ninja나 -A 없는 configure는 luil의 검사에서 멈춘다.
  6. luil_options를 따라 링크하지 않는다. 예제가 링크하는 것은 저장소의 경고 규율이다. 앱은 luil::luil 하나만 링크한다.
  7. 문서가 말하지 않는다find_package는 Windows만이다. README와 시작 가이드는 설치 패키지 길의 플랫폼을 적지 않는다. 코드는 다른 플랫폼에서 설치 규칙을 끈다(CMakeLists.txt:348).
  8. 문서와 다르다우산 헤더에 macOS·iOS 진입 헤더가 없다. luil/macos/macos_app.h·luil/ios/ios_app.h를 직접 include한다. 우산 헤더 검사 스크립트를 이 체크아웃에서 돌리면 두 헤더가 빠졌다고 멈춘다.
  9. Codicons 상수 헤더는 따로 들인다. luil/generated/codicons.h는 우산 헤더에 들지 않는다.
  10. 문서와 예제가 다르다hello는 옛 이름을 쓴다. 소비자 계약은 새 코드에 luil::logic_driver·luil::ui_frame을 쓰라고 하는데, 첫 앱의 본보기인 hello는 luil::win32:: 별칭을 쓴다. 별칭은 "한 판 동안" 남고, namespace luil::win32 { class logic_driver; } 같은 전방 선언은 이미 깨진다.
  11. make_close_message·shutdown_completed·cancel은 UI thread에서도 불린다. hello처럼 std::atomic으로 지킨다. shutdown_completed가 참이 되지 않으면 창을 닫을 때마다 종료가 3초 예산을 다 쓴다.
  12. driver 콜백에서 예외를 던지지 않는다. logic thread가 예외를 삼키고 멈춰 frame 게시와 메시지 처리가 함께 멎는다.
  13. 세 조각은 진입 함수보다 오래 산다. 라이브러리는 주소만 빌린다. iOS의 run_application은 돌아오지 않으므로 static으로 둔다.
  14. 첫 frame은 크기를 모른 채 불린다. 크기 메시지는 delegate가 만들고, delegate가 없으면 영영 오지 않는다. hello처럼 기본 크기를 둔다.
  15. 창 설정의 caption과 tree의 caption_element는 같은 값이어야 한다. 하나는 비클라이언트 판정에, 하나는 그리기에 쓰여 어긋나면 버튼 자리가 맞물리지 않는다.
  16. Skia 기능 다섯은 예제·시험 preset만 켠다. 라이브러리 preset(vs2026)으로 지어 설치하면 SVG·Lottie·AVIF가 unsupported_format으로 답한다. 설치할 luil을 지을 때 기능을 고른다.
  17. 소스 트리 소비자의 고지는 켠 기능만 고르지 않는다. 켠 기능 목록(LUIL_SKIA_FEATURES)이 부모 scope에 보이지 않아 Skia의 NOTICE.md 전체를 싣는다. 해가 되지는 않는다. 코드에서 읽은 것이고 test로 잠긴 동작은 아니다.
  18. macOS 번들 함수는 예제에만 있다. iOS의 luil_ios_sign_bundle·luil_ios_embed_smb는 luil의 CMake가 들이지만, luil_add_macos_bundle·luil_sign_macos_bundle은 예제 파일 안의 함수다.
  19. Apple 헤더의 매크로를 막는 정의는 앱에 전파되지 않는다. 앱의 .mm에서 check가 펼쳐지면 앱 대상에도 같은 정의를 건다.
  20. 문서와 다르다차트 선택 라이브러리는 이 판에 없다. 빌드 체계·소비자 계약 문서가 말하는 LUIL_BUILD_CHART·luil::luil_chart·luil/chart.h는 이 판의 CMake와 헤더에 없다. 문서 머리의 "선택 이식 범위" 안내가 그 까닭이다.
  21. 문서가 모자란다Skia 빌드 준비 문서의 대상 표는 셋이다. 스크립트는 ios-arm64·ios-arm64-simulator까지 다섯을 받는다.
  22. 문서와 다르다"실행 파일에 내장된 Codicons"는 Windows 이야기다. fonts.md와 fonts.h의 주석이 그렇게 말하지만, Android·macOS·iOS에서는 글꼴이 라이브러리 소스로 들어간다.

자주 묻는 질문

Skia를 소스에서 빌드해야 하나?

아니다. scripts/fetch_skia.ps1이 핀으로 고정한 패키지를 받는다.

Skia 소스도, external도, gn·ninja도 필요 없다. 직접 빌드한 Skia도 LUIL_SKIA_ROOT·LUIL_SKIA_BUILD_DEBUG·LUIL_SKIA_BUILD_RELEASE로 쓸 수 있지만 패키지와 같은 다섯 조건을 통과해야 한다(Skia 받기).

clang을 설치해야 하나?

Windows에서는 아니다. Skia는 이미 clang-cl로 지어져 있고, luil과 앱은 MSVC로 짓는다.

configure는 패키지가 적어 둔 toolchain.json을 읽을 뿐 컴파일러를 찾지도 부르지도 않는다. Android·macOS·iOS는 원래 NDK·Xcode의 clang으로 짓는다.

Debug와 Release 패키지를 둘 다 받아야 하나?

짓는 구성만큼 받는다. Visual Studio처럼 구성이 여럿인 generator는 둘 다 필요하다.

검사는 configure가 실제로 짓는 구성에만 걸린다. 다중 구성 generator는 CMAKE_CONFIGURATION_TYPES가 정하고, Debug는 /MTd 산출물을, 그 밖의 구성은 Release 산출물을 쓴다.

Windows에서 Ninja로 지을 수 있나?

소스 트리 길에서는 안 된다. luil이 configure에서 Visual Studio 2022·2026만 받는다.

설치 패키지의 config는 generator를 검사하지 않는다. 다만 test는 luil을 지은 generator를 그대로 쓰므로, 다른 generator로 소비하는 길은 확인된 것이 아니다.

vcpkg나 Conan 패키지가 있나?

저장소에는 없다. 소비 길은 소스 트리와 설치 패키지 둘이다.

둘 다 링크하는 이름은 luil::luil이다. 의존성 취득은 사람이 돌리는 스크립트가 맡고 configure는 네트워크를 쓰지 않는다.

앱을 동적 CRT(/MD)로 지을 수 있나?

안 된다. Skia 패키지가 정적 CRT(/MT·/MTd)라 앱과 luil이 같은 것을 써야 한다.

configure는 Skia 쪽의 CRT만 확인하고 앱의 설정은 보지 않는다. 어긋나면 링커가 /FAILIFMISMATCH로 멈춘다.

C++20과 /utf-8은 내가 켜야 하나?

아니다. luil::luil을 링크하면 따라온다.

luil_usage가 공개 헤더를 컴파일하는 데 필요한 두 가지만 전파한다 — 헤더에 한국어 주석과 u8 문자열이 있어서다. 경고 수준과 /WX는 전파하지 않는다.

웹뷰를 쓰지 않으면 무엇을 빼나?

LUIL_ENABLE_WEBVIEW=OFF로 구성하고 fetch_webview2.ps1을 건너뛴다.

SDK를 찾지도, 정적 로더를 링크하지도, 고지에 싣지도 않는다. 공개 API는 그대로이고 frame에 실은 웹뷰는 placeholder로 남는다. CPU 렌더러만 넣는 LUIL_ENABLE_DIRECT3D=OFF는 웹뷰도 기본으로 끈다.

macOS·iOS·Android에서도 find_package를 쓸 수 있나?

아니다. 설치 규칙은 Windows에만 있다.

다른 플랫폼에서는 LUIL_INSTALL을 일반 변수로 먼저 꺼서 옵션이 그 값을 따른다. 그 플랫폼에서는 소스 트리를 add_subdirectory한다.

설치본을 다른 경로나 다른 기계로 옮겨도 되나?

경로는 된다 — test가 공백이 든 경로로 옮겨 확인한다. 다른 기계에서는 Skia 자리를 다시 준다.

설치본에 적힌 Skia·WebView2 경로는 설치한 기계의 절대 경로다. LUIL_SKIA_ROOT만 주면 구성별 자리는 그 아래 out/skia-ui-debug·-release로 따라온다.

판번은 어떻게 확인하나?

컴파일 때는 LUIL_VERSION_MAJOR 같은 매크로, 실행 중에는 library_version()이다.

둘 다 project(luil VERSION 0.1.0) 하나에서 configure가 만든다. 설치본은 같은 주 판번을 호환으로 보므로 README처럼 find_package(luil 0.1 REQUIRED)로 찾는다.

앱 아이콘이나 내 리소스는 어디에 넣나?

별도의 .rc로 더하고, ID 101~104는 피한다.

luil의 조각은 Codicons·라이선스·고지만 담는다. 창 아이콘은 실행 파일 리소스의 ID를 window_config::icon_resource에 준다(0이면 시스템 기본).

창 크기를 바꿔도 화면이 그대로다.

delegate가 크기 메시지를 만들고 handle이 그것을 상태에 넣는지 본다.

delegate를 꽂지 않으면 크기 메시지가 아예 없다. hello는 make_window_metrics_message가 metrics_intent를 돌려주고, handle이 metrics_를 바꾸고, make_frame이 그 크기로 배치한다.

창을 닫으면 잠깐 멈췄다가 끝난다.

shutdown_completed가 참이 되는지 본다.

라이브러리는 종료 메시지를 넣은 뒤 그 값이 참이 되기를 시간 예산(3초) 안에서 기다린다. 종료 메시지를 처리할 때 저장을 제출하고 참으로 세운다(종료 절차와 시간 예산).

hello와 달리 luil::logic_driver를 상속해도 되나?

된다. 같은 형식이고, 새 코드는 그쪽을 쓰라는 것이 소비자 계약이다.

luil::win32::logic_driver는 luil::logic_driver를 가리키는 별칭이다. 새 이름으로 쓴 예제는 examples/selected_nodes/main.cpp와 examples/tool_window/main.cpp다.

Linux에서 쓸 수 있나?

아니다. configure가 첫 갈래에서 멈춘다.

받는 플랫폼은 Windows 11 x64, Android arm64, macOS arm64, iOS arm64 넷이고, 나머지는 원인을 적은 오류로 끝난다. Skia 패키지도 그 대상들만 있다.

네트워크가 막힌 환경에서 빌드하려면?

핀이 가리키는 아카이브를 캐시 디렉터리에 두고 -Offline으로 받는다.

기본 캐시는 third_party/skia-prep-archives이고 -ArchiveDirectory로 바꾼다. 캐시 파일에도 같은 해시 검사가 걸린다. fetch_webview2.ps1도 같은 두 스위치를 받는다. configure 자체는 네트워크를 쓰지 않는다.

새 Visual Studio에서 luil 소스가 경고 때문에 빌드되지 않는다.

LUIL_WARNINGS_AS_ERRORS=OFF로 구성한다.

luil은 자기 소스에 경고=오류를 건다. 핀으로 고정한 luil을 새 도구사슬이 경고할 때 앱이 소스를 고칠 수는 없으므로, 그때 끄라고 둔 옵션이다. 앱의 경고 정책에는 영향이 없다.
